# Аутентификация и авторизация Admin

Владелец определил границу Admin-only и восстановление действующей сессии после обновления (DEC-001, DEC-007). В I1 по утверждённому DEC-010 refresh хранится в `sessionStorage`, access — в памяти. Транспортные правила описаны DEC-017.

## Протокол сервера

| Действие | API | Результат |
|---|---|---|
| Вход | POST /auth/admin/login, form `username,password` | JSON `access_token,refresh_token,token_type,expires_in,scope`. Scope пустого запроса не определяет права приложения. |
| Восстановление | POST /auth/admin/refresh, JSON `{refresh_token}` | Сервер атомарно ротирует refresh, сохраняя абсолютное время окончания сессии. Используем только свежую пару. |
| Чтение прав | GET /admin/admins/permissions с Bearer | JSON `{permissions:[...]}`, актуальные разрешения текущего Admin. Отдельное `admin.view` не нужно. |
| Выход | POST /auth/admin/logout, JSON `{refresh_token}` | 200 с сообщением об отзыве этой refresh-сессии. Выданный access может действовать до `exp` при действующем аккаунте. |

По умолчанию access живёт до 5 минут, refresh-сессия — до 7 дней. Сроки настраиваются, приложение использует `expires_in`, не продлевает абсолютный срок. API проверяет тип токена и текущее состояние учётной записи. Из JWT можно извлечь ID `sub` для UI-подстановок, права загружаются с сервера. ## Состояния клиента

1. **Нет активной сессии.** Показать вход и сохранить безопасный внутренний маршрут. После успешного входа загрузить права и отдать доступный маршрут. Поля пароля очищать при выходе из формы.
2. **Восстановление.** При сохранённом refresh показать нейтральный экран восстановления. Запустить single-flight refresh, атомарно принять свежую пару и загрузить права. Устаревший ответ игнорировать по поколению сессии. Без доступного хранилища вывести понятное ограничение восстановления.
3. **Активная сессия.** Права определяют навигацию и действия совместно с состоянием сущности. Сервер проверяет каждый запрос. При self-role change перечитать текущие права. При снятии права убрать доступ к странице и очистить соответствующий кэш.
4. **Временная недоступность.** Сетевой сбой, 500 или 503 при восстановлении показывают возможность повтора и выхода. Если ответ успешного refresh потерян, повтор со старым токеном может дать подтверждённый 401. В этом случае нужен вход.
5. **Истечение/завершение.** После окончательного 401 refresh очистить сессию и предложить вход с объяснением. При logout сразу прекратить доступ, сменить поколение, очистить черновики, кэш и хранилище. Координировать отзыв с уже запущенной ротацией, отправить наиболее свежий известный refresh этого поколения; поздний ответ может использоваться для отзыва, но не для восстановления UI. Сетевой сбой не подтверждает серверный отзыв, пользователю сообщается статус локального выхода.

Для защищённого запроса 401 от проверки аутентификации допустим один refresh и один повтор в том же поколении. Для мутаций повтор допустим только при однозначном отказе аутентификации до выполнения обработчика и с тем же payload/ключом. Для неизвестного исхода PATCH использовать чтение, для create/comment — политику idempotency. При 403 от GET заявок I1 сразу снимает локальное `ticket.view`, закрывает данные и предлагает явную перепроверку прав. Несогласованные ответы чтения заявок и `/permissions` не запускают автоматическую цепочку повторов. Временный сбой перепроверки отличается от отказа в доступе.

## Хранение и транспорт

| Вариант | Результат |
|---|---|
| DEC-010, refresh в `sessionStorage`, access в памяти | Утверждено для I1. Восстанавливает текущую вкладку при reload. Refresh доступен JavaScript. Поведение конкурирующей копии вкладки проверяется отдельно. |
| Только память | Теряет сессию при обновлении, не выполняет DEC-007 с текущим API. |
| `localStorage` | Персистентнее и доступен JavaScript между вкладками. Ротация требует межвкладочной координации. В первом релизе не предлагается. |
| HttpOnly cookie | Текущий API возвращает refresh в JSON. Отдельная серверная архитектура вышла бы за рамки этапа. |

Хранилище изолирует обычные независимые вкладки, но браузер при дублировании или открытии через opener может скопировать первоначальное состояние. Две копии refresh конкурируют. 401 в проигравшей вкладке приводит к локальному входу, без автоматического общего logout. Внутренние рабочие вкладки заявок живут в одной странице и используют общую сессию.

В production планируется same-origin HTTPS и согласованный путь к API. В development рассматривается Vite proxy. Bearer отправляется только фиксированному API, без передачи через открытые редиректы. Refresh, пароли, PII и черновики исключаются из URL, диагностических сообщений и общего browser storage. В представлении использовать текстовый рендеринг пользовательского ввода, заголовки доставки и CSP проверить перед эксплуатацией. Только параметры публичной конфигурации разрешены в `VITE_*`.
