# Требования к frontend Simple Tickets

## 1. Общие положения

Frontend предназначен для работы Admin с системой Simple Tickets.

Актуальным источником истины для API является текущий OpenAPI backend-а.

Предыдущая версия React frontend используется только как образец:

- общей компоновки интерфейса;
- таблиц;
- форм;
- модальных окон;
- навигации;
- работы с permissions;
- переключения оформления;
- визуальных решений.

Старые endpoint-ы, статусы и поля предыдущего frontend не должны переноситься в новую версию без проверки по актуальному OpenAPI.

---

## 2. Оформление

Необходимо сохранить простой механизм переключения оформления.

На первом этапе поддерживаются **четыре варианта оформления**, аналогично предыдущей версии frontend.

Механизм темизации должен оставаться простым и не усложнять архитектуру приложения.

---

## 3. Основные разделы

Основная навигация Admin-интерфейса:

1. **Заявки**
2. **Клиенты**
3. **Пользователи**
4. **Admin**
5. **Отделы**
6. **Роли**

Раздел **«Заявки»** является главным рабочим разделом системы и должен находиться первым в навигации.

Отдельный Dashboard на первом этапе не требуется.

---

# 4. Работа с permissions

Frontend получает permissions текущего авторизованного Admin через:

```text
GET /admin/admins/permissions
```

Permissions загружаются после авторизации и хранятся в состоянии приложения.

Пример:

```javascript
[
  "ticket.view",
  "ticket.created",
  "ticket.accepted",
  "ticket.at_work"
]
```

Отсутствие элемента интерфейса не является механизмом безопасности. Backend в любом случае повторно проверяет permissions и бизнес-правила.

## 4.1. Константы permissions

Строковые permissions не следует разбрасывать по компонентам.

Рекомендуется единый набор констант:

```javascript
export const ADMIN_PERMISSIONS = {
  CLIENT_OPERATION: "client.operation",
  CLIENT_VIEW: "client.view",

  ADMIN_OPERATION: "admin.operation",
  ADMIN_VIEW: "admin.view",

  USER_OPERATION: "user.operation",
  USER_VIEW: "user.view",

  TICKET_OPERATION: "ticket.operation",
  TICKET_CREATED: "ticket.created",
  TICKET_VIEW: "ticket.view",
  TICKET_ACCEPTED: "ticket.accepted",
  TICKET_AT_WORK: "ticket.at_work",
  TICKET_AT_WORK_REMOTE: "ticket.at_work_remote",
  TICKET_AT_WORK_RETROSPECTIVE:
    "ticket.at_work_retrospective",
  TICKET_CANCELLED: "ticket.canceled",
  TICKET_EXECUTED: "ticket.executed",

  ROLE_ASSIGN: "role.assign",
  ROLE_USER_ASSIGN: "role_user.assign",
};
```

## 4.2. Helper-функции

Нужны простые функции:

```javascript
export function hasPermission(
  permissions,
  permission
) {
  return permissions.includes(permission);
}

export function hasAnyPermission(
  permissions,
  required
) {
  return required.some(permission =>
    permissions.includes(permission)
  );
}
```

`hasAllPermissions()` добавляется только если реально понадобится.

## 4.3. Скрытие разделов

Если Admin не имеет permission просмотра соответствующей сущности, раздел не показывается в навигации.

Примеры:

- `client.view` → Клиенты;
- `admin.view` → Admin;
- `user.view` → Пользователи;
- `ticket.view` → Заявки.

## 4.4. Скрытие операций

Если Admin не имеет permission на конкретную операцию, соответствующая кнопка **не отображается**.

Для создания заявки разрешение:

```text
ticket.created OR ticket.operation
```

## 4.5. Permission + состояние Ticket

Для workflow одной проверки permission недостаточно.

Кнопка показывается только если одновременно:

1. Admin имеет необходимое permission;
2. текущее состояние Ticket допускает действие.

Логику UI-доступности действий желательно централизовать:

```javascript
function getTicketActions(
  ticket,
  permissions
) {
  // возвращает набор доступных UI-действий
}
```

Frontend использует это только для отображения. Backend остаётся окончательным источником истины.

# 5. Клиенты

Раздел предназначен для работы с `Client`.

Необходимо поддержать:

- просмотр списка клиентов;
- создание клиента;
- просмотр карточки клиента;
- изменение контактных данных;
- enable;
- disable;
- удаление, если разрешено backend.

Из карточки клиента должен быть прямой доступ к:

- его User;
- его заявкам.

Переход к User клиента должен открывать список пользователей с уже выбранным соответствующим клиентом.

Переход к заявкам клиента должен открывать раздел заявок с фильтром по данному клиенту.

---

# 6. Пользователи

Отдельный раздел для работы с `User` обязателен.

Необходимо поддержать:

- список User;
- фильтр по Client;
- создание User;
- просмотр User;
- изменение данных;
- создание/привязку account;
- удаление account;
- изменение пароля;
- назначение ролей;
- снятие ролей;
- enable;
- disable;
- удаление, если разрешено backend.

Из карточки User должен быть удобный переход к его заявкам.

---

# 7. Admin

Раздел предназначен для работы с сотрудниками типа `Admin`.

Необходимо поддержать:

- список Admin;
- создание;
- просмотр;
- редактирование;
- account;
- изменение пароля;
- назначение ролей;
- снятие ролей;
- назначение отдела;
- снятие отдела;
- enable;
- disable;
- удаление, если разрешено backend.

---

# 8. Отделы

Необходимо поддержать:

- просмотр списка отделов;
- создание отдела;
- изменение названия;
- enable;
- disable;
- удаление.

Frontend не должен самостоятельно реализовывать бизнес-ограничения отключения или удаления отдела.

Например, наличие активных Admin или открытых Ticket проверяет backend.

Frontend только отображает полученную ошибку.

---

# 9. Роли

Необходимо поддержать отдельно:

- роли Admin;
- роли User.

Для каждой роли:

- список;
- создание;
- просмотр permissions;
- удаление, если разрешено backend.

При создании роли permissions выбираются из списка, предоставляемого API.

Admin permissions и User permissions не смешиваются.

---

# 10. Заявки

## 10.1. Общий принцип

Раздел **«Заявки»** является основным рабочим интерфейсом.

Он состоит из:

- списка заявок;
- поиска;
- фильтров;
- рабочих представлений списка;
- формы создания;
- карточки заявки;
- панели доступных действий;
- истории;
- комментариев.

Frontend не предоставляет прямое изменение статуса.

Пользователь выполняет **действие**, а статус является результатом операции backend.

Основной принцип:

> показывать не список возможных статусов, а список возможных действий.

---

## 10.2. Основные представления списка

Необходимо поддержать:

- **Все**
- **Открытые**
- **Закрытые**
- **Назначенные мне**
- **Рекомендовано удалённо**

### Все

Основной список всех доступных заявок.

### Открытые

```text
GET /admin/tickets/open
```

### Закрытые

```text
GET /admin/tickets/closed
```

### Назначенные мне

Используется:

```text
GET /admin/tickets/by-executor/{executor_id}
```

где `executor_id` — `employee_id` текущего Admin.

Это не отдельный модуль frontend. Используется тот же компонент списка заявок.

### Рекомендовано удалённо

Показываются заявки:

```text
remote_work_recommended == true
```

Пока этот список может формироваться на frontend после загрузки заявок.

Следует различать:

- `remote_work_recommended` — рекомендация выполнить заявку удалённо;
- `work_is_remote` — фактический способ выполнения конкретного периода работы.

---

## 10.3. Макет списка заявок

Пример:

```text
┌──────────────────────────────────────────────────────────────────────────────────────────────────┐
│ ЗАЯВКИ                                                                        [+ Новая заявка] │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Все | Открытые | Закрытые | Назначенные мне | Рекомендовано удалённо                          │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Поиск...                                                                                        │
│                                                                                                 │
│ Клиент [Все ▼]  Отдел [Все ▼]  Исполнитель [Все ▼]                                            │
│ User    [Все ▼]  Статус [Все ▼] Срочность [Все ▼]                                             │
├──────────────────────────────────────────────────────────────────────────────────────────────────┤
│ №   │ Клиент    │ Отдел   │ Текст заявки              │ План       │ Статус  │ Срочность │ Исполнитель │ Время │
│─────┼────────────┼────────────────────────────┼────────────┼─────────┼───────────┼─────────────┼───────│
│ 152 │ ООО Альфа │ Support │ Не работает доступ к корп… │ 02.10 14:00│ AT_WORK │ URGENT    │ Иванов И.И. │ 1:25  │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Кнопка `+ Новая заявка` показывается только при:

```text
ticket.created OR ticket.operation
```

Сам раздел заявок показывается при:

```text
ticket.view
```

---

## 10.4. Обязательные колонки списка заявок

В основной таблице обязательно должны присутствовать:

1. **Номер заявки**
2. **Клиент**
3. **Отдел**
4. **Текст заявки — первые 50 символов**
5. **Запланированное время**
6. **Статус**
7. **Срочность**
8. **Исполнитель**
9. **Уже затраченное время**

### Номер заявки

Используется:

```text
ticket_id
```

Номер должен быть хорошо виден.

### Клиент

Показывается человекочитаемое имя Client, а не `client_id`.

### Отдел

Показывается человекочитаемое имя Department, а не `department_id`. Если отдел не назначен, показывается `—`.

### Текст заявки

Показываются первые **50 символов** `text_of_ticket`.

Если текст длиннее 50 символов, добавляется многоточие.

Пример:

```javascript
const preview =
  ticket.text_of_ticket.length > 50
    ? ticket.text_of_ticket.slice(0, 50) + "…"
    : ticket.text_of_ticket;
```

Полный текст доступен в карточке заявки.

### Запланированное время

Используется:

```text
planned_at
```

Если время не задано:

```text
—
```

Если задано — отображается в локальном человекочитаемом формате.

### Статус

Показывается текущий workflow-status.

Позже планируется добавить непосредственно в `TicketResponse`:

```text
current_status
```

До этого frontend может получать текущий статус из последней записи `statuses`.

### Срочность

Используется:

```text
urgency
```

Например:

- `NORMAL`
- `URGENT`
- `MAINTENANCE`

Срочность может визуально выделяться, но текстовое значение должно оставаться видимым.

### Исполнитель

Показывается текущий активный исполнитель.

Если исполнителя нет:

```text
—
```

Позже планируется добавить в `TicketResponse`:

```text
current_executor_id
```

Пока для представления «Назначенные мне» используется специализированный endpoint `/by-executor/{executor_id}`.

### Уже затраченное время

Используется:

```text
time_spent
```

В таблице значение показывается в человекочитаемом формате:

- `0 мин`
- `25 мин`
- `1 ч 15 мин`
- `4 ч 32 мин`
- `2 д 3 ч`

Секунды пользователю не показываются.

---

## 10.5. Дополнительная информация в списке

Чтобы таблица не становилась слишком широкой, следующие поля не являются обязательными постоянными колонками:

- User;
- Contact User;
- дата создания;
- `remote_work_recommended`;
- `user_ticket_id`;
- `version`;
- полный `text_of_ticket`;
- `description`.

Они доступны:

- через фильтры;
- в карточке;
- через компактные визуальные признаки.

Например, рекомендацию удалённой работы можно показать маленькой иконкой в строке.

Строка таблицы должна открывать карточку заявки.

---

## 10.6. Поиск

Поиск пока выполняется полностью на frontend.

Минимальный поиск:

- ticket ID;
- `text_of_ticket`;
- `description`.

При наличии загруженных справочников также желательно искать по:

- Client;
- User;
- Contact User;
- текущему Admin-исполнителю.

Поиск должен работать совместно с активными фильтрами.

---

## 10.7. Фильтры

На первом этапе комбинированная фильтрация выполняется преимущественно на frontend.

Необходимо предусмотреть фильтры по:

- Client;
- User;
- Contact User;
- исполнителю;
- статусу;
- urgency;
- рекомендации удалённой работы;
- open/closed.

Существующие endpoint-ы могут использоваться там, где это удобно:

```text
GET /admin/tickets/by-client/{client_id}
GET /admin/tickets/by-user/{user_id}
GET /admin/tickets/by-contact-user/{contact_user_id}
GET /admin/tickets/by-department/{department_id}
GET /admin/tickets/by-executor/{executor_id}
```

Сложная серверная система комбинированной фильтрации пока не требуется.

# 11. Создание заявки

В UI должна быть одна операция:

**Новая заявка**

Не должно быть отдельных кнопок:

- «Создать Ticket»;
- «Создать TicketUser».

Используется:

```text
POST /admin/tickets/
```

Форма включает:

- Client;
- User — необязательно;
- Contact User;
- `text_of_ticket`;
- `description`;
- urgency;
- `planned_at`;
- `remote_work_recommended`;
- comment.

Если:

```text
user_id == 0
```

backend создаёт только `Ticket`.

Если:

```text
user_id > 0
```

backend автоматически создаёт:

- `TicketUser`;
- связанный `Ticket`.

Frontend не реализует эту бизнес-логику самостоятельно.

При выборе Client списки User и Contact User должны содержать пользователей выбранного Client.

---

# 12. Карточка заявки

Карточка заявки является главным рабочим экраном системы.

При открытии строки списка пользователь попадает в карточку Ticket.

Карточка должна позволять:

- быстро понять состояние заявки;
- увидеть, кто отвечает за неё;
- выполнить доступное действие;
- изменить разрешённые данные;
- посмотреть историю;
- добавить комментарий.

Следует избегать одной огромной формы со всеми полями.

---

## 12.2. Верхняя панель

Обязательно показываются:

- возврат к списку;
- ticket ID;
- `text_of_ticket` либо его короткая первая строка;
- текущий статус.

Статус должен визуально выделяться.

Цвет может быть вспомогательным признаком, но статус всегда подписывается текстом.

---

## 12.3. Основная информация

Показываются:

```text
Клиент
User
Contact User
Department
Исполнитель
Urgency
Дата создания
planned_at
time_spent
remote_work_recommended
```

Редактируемые поля получают компактное действие редактирования.

Например:

```text
Контакт:       Пётр Петров        [изменить]
Отдел:         Support            [изменить]
Срочность:     URGENT             [изменить]
План:          02.10 14:00        [изменить] [снять]
Удалённо:      рекомендовано      [изменить]
```

---

## 12.4. Client, User и Contact User как ссылки

Client должен быть кликабельным и вести в карточку Client.

User должен быть кликабельным и вести в карточку User.

Contact User — аналогично.

---

## 12.5. Текущий исполнитель

Текущий исполнитель должен быть хорошо заметен.

Если исполнителя нет:

```text
Исполнитель: —
```

Если workflow допускает назначение, рядом показывается соответствующее действие.

---

## 12.6. Текст заявки

`text_of_ticket` является неизменяемым после создания.

Поэтому блок отображается без кнопки редактирования.

---

## 12.7. Описание

`description` редактируется независимо.

Предпочтителен небольшой modal или inline-редактор.

---

# 13. Панель доступных действий

Это один из главных блоков карточки.

Он должен находиться достаточно высоко.

Показываются только действия, доступные:

- по permissions;
- по текущему workflow state;
- по дополнительным данным Ticket.

Недоступные workflow-кнопки лучше не показывать.

---

## 13.1. Примеры панели по статусам

Примеры являются ориентировочными и должны соответствовать актуальному backend workflow.

### CREATED

```text
[Принять]
[Отклонить]
[Отменить]
```

### ACCEPTED

```text
[Назначить исполнителя]
[Отложить]
[Отменить]
```

### DEFERRED

```text
[Принять]
[Назначить исполнителя]
[Отменить]
```


### ASSIGNED

```text
[Начать работу]
[Начать удалённую работу]
[Отложить]
[Отменить]
```

### AT_WORK

```text
[Приостановить]
[Завершить работу]
```

### PAUSED

```text
[Продолжить работу]
```

### READY_FOR_REVIEW

```text
[Выполнить]
```

Для terminal status workflow-панель может отсутствовать.

# 14. Workflow permissions

Основные соответствия:

```text
TICKET_ACCEPTED
    -> принятие заявки

TICKET_AT_WORK
    -> обычные операции работы

TICKET_AT_WORK_REMOTE
    -> специальная операция начала рекомендуемой удалённой работы

TICKET_AT_WORK_RETROSPECTIVE
    -> ретроспективная регистрация работы

TICKET_CANCELLED
    -> отмена и отклонение

TICKET_EXECUTED
    -> выполнение заявки

TICKET_CREATED OR TICKET_OPERATION
    -> создание заявки
```

Permission-aware UI нужен для удобства, но не заменяет backend-проверки.

```text
Комментарий: [                    ]
```

Список должен содержать доступных Admin.

# 17. Отклонение и отмена

```text
Отменить заявку

Причина:
```

# 21. Продолжение

Используется:

Форма:

# 22. Завершение текущей работы

Используется:

```text
PATCH /admin/tickets/{ticket_id}/finish-work
```

Frontend вызывает одну операцию и показывает Ticket, возвращённый backend.

Frontend не должен самостоятельно определять следующий статус.

# 23. Ретроспективная регистрация работы

Используется:

```text
PATCH /admin/tickets/{ticket_id}/complete-work-retroactively
```

Пользователь может указать:

- начало;
- окончание;

либо:

- продолжительность.

Дополнительно:

- `work_is_remote`;
- comment.

Пример UI:

```text
Зарегистрировать выполненную работу

Начало:       [ дата ] [ время ]
Окончание:    [ дата ] [ время ]

или

Продолжительность:
Часы:         [  ]
Минуты:       [  ]

☐ Работа выполнялась удалённо

Комментарий:
[                                  ]

[Отмена] [Зарегистрировать]
```

Backend принимает `duration` как integer в секундах.

Frontend преобразует введённые часы и минуты в секунды.

Пример:

```text
1 ч 30 мин -> 5400
```

# 27. История и комментарии

Нижняя часть карточки:

```text
[ История ] [ Комментарии ]
```

По умолчанию можно открывать историю.

---

## 27.1. История статусов

История показывается хронологически.

Пример:

```text
01.10.2026 09:15
CREATED
Иванов А.А.
Комментарий: ...

────────────────────────────

01.10.2026 09:20
ACCEPTED
Петров П.П.

────────────────────────────

01.10.2026 09:40
ASSIGNED
Исполнитель: Сидоров С.С.

────────────────────────────

01.10.2026 10:00
AT_WORK
Локально
```

Для work records дополнительно показываются:

- `actual_started_at`;
- `actual_finished_at`;
- duration;
- `work_is_remote`.

Технические ISO-duration значения пользователю показывать не нужно.

---

## 27.2. Комментарии

Комментарии показываются отдельно от status history.

Пример:

```text
Иванов А.А.
Проверил доступ пользователя...

--------------------------------

01.10.2026 10:15
Петров П.П.
VPN работает, проверяем ACL...
```

Добавление комментария:

```text

```

# 28. Связанный TicketUser

Если:

```text

```

в карточке можно показывать:

```text

```

Это вторичная информация.

Главным рабочим объектом Admin остаётся внутренний Ticket.

TicketUser не должен становиться вторым параллельным рабочим интерфейсом для Admin.

# 29. Затраченное время

`time_spent` отображается:

- в списке заявок;
- в карточке заявки.

Формат человекочитаемый.

Пример:

```text
4 ч 20 мин
```

Frontend не показывает пользователю количество секунд.

---

# 30. Обновление карточки после операции

После успешной операции frontend использует новый `TicketResponse`.

Не следует вручную менять:

- статус;
- executor;
- `is_closed`;
- `date_finished`;
- историю;
- затраченное время.

Схема:

```text
действие
    ↓
API
    ↓
новый TicketResponse
    ↓
обновление карточки
```

---

# 31. Ошибка операции

Если backend отклонил действие:

- dialog не закрывается как успешный;
- пользователю показывается причина;
- локальное состояние Ticket не считается изменённым.

Если ошибка связана с конкурентным изменением Ticket, frontend может повторно запросить актуальную карточку.

---

# 32. Клиентская валидация

Frontend выполняет только простую проверку:

- обязательные поля;
- положительные ID;
- формат даты;
- обязательный comment;
- корректность формы.

Бизнес-валидация остаётся на backend.

Особенно это касается:

- workflow transitions;
- permissions;
- disabled Client/User/Admin;
- ограничений удаления;
- optimistic concurrency;
- ограничений Department;
- ограничений Ticket.

---

# 33. Адаптивность

Основной интерфейс ориентирован на desktop.

При недостаточной ширине:

- двухколоночные информационные блоки переходят в одну колонку;
- панель действий допускает перенос кнопок;
- таблица не должна ломать страницу.

---

# 34. Планируемые дополнения API

Позже планируется добавить непосредственно в `TicketResponse`:

```text
current_status
current_executor_id
```

Это позволит frontend не вычислять текущий статус и исполнителя из истории.

Пока:

- текущий статус при необходимости определяется из последней записи `statuses`;
- для «Назначенные мне» используется `/admin/tickets/by-executor/{executor_id}`.

---

# 35. Основной принцип frontend

Frontend:

- отображает текущее состояние;
- показывает доступные действия;
- вызывает API;
- принимает новый state от backend.

Frontend не должен:

- самостоятельно менять статус;
- выбирать следующий статус;
- дублировать domain workflow;
- воспроизводить сложную backend-валидацию.

Основной рабочий сценарий:

```text
список заявок
    ↓
поиск / фильтр
    ↓
карточка заявки
    ↓
доступное действие
    ↓
обновлённая карточка
```

Ключевой принцип Ticket UI:

> **Не показывать пользователю выбор статуса. Показывать доступные бизнес-действия.**
