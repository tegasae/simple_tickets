# AGENTS.md

## 1. Цель проекта

Разработка новой версии frontend для системы Simple Tickets на основе существующего frontend v2 и действующего backend на FastAPI.

Рабочая ветка: `frontend_new

## 2. Структура проекта и ограничения

### Backend — `src/`

- Обязательно исследовать исходный код.
- Изучать архитектуру, API, модели данных, авторизацию и бизнес-логику.
- Категорически запрещено изменять, удалять, перемещать и форматировать файлы.
- Запрещено изменять backend для устранения проблем совместимости с frontend.
- Обнаруженные ошибки документировать и сообщать пользователю.

### Исходный frontend — `simple_tickets_frontend_v2/`

- Использовать в качестве основы для разработки.
- Исследовать архитектуру, компоненты, зависимости и взаимодействие с API.
- Разрешено копировать код в frontend v3.
- Запрещено изменять оригинальные файлы.

### Новый frontend — `simple_tickets_frontend_v3/`

- Единственный каталог, в котором разрешено создавать, изменять и удалять файлы.
- Вся разработка, тестирование и документация должны находиться в этом каталоге.

Изменение любых файлов за пределами frontend v3 запрещено без отдельного разрешения пользователя.

## 3. Режим архитектурного консилиума

Работа над проектом должна осуществляться в режиме консилиума.

Основной агент выполняет роль Lead Architect и привлекает отдельных субагентов.

### Lead Architect

- Организует обсуждение.
- Координирует работу специалистов.
- Анализирует предлагаемые решения.
- Выносит архитектурные решения на согласование с пользователем.

### Senior React Expert — обязательный участник

- Эксперт по React и современным frontend-технологиям.
- Исследует существующий frontend v2.
- Проектирует архитектуру frontend v3.
- Анализирует компоненты, маршрутизацию, управление состоянием и взаимодействие с API.
- Отвечает за качество frontend-кода.

### Senior FastAPI Expert — обязательный участник

- Эксперт по Python, FastAPI, Pydantic, OpenAPI и REST API.
- Исследует существующий backend.
- Определяет реальные контракты API.
- Проверяет форматы запросов и ответов.
- Анализирует авторизацию, права доступа и обработку ошибок.
- Проверяет совместимость предлагаемых frontend-решений с backend.
- Работает исключительно в режиме чтения.

### QA Engineer / Code Reviewer

- Проверяет качество и корректность решений.
- Анализирует риски и пограничные случаи.
- Определяет требования к тестированию.
- Контролирует соблюдение ограничений проекта.

При необходимости Lead Architect может привлекать дополнительных специалистов по UX/UI, информационной безопасности и другим направлениям.

## 4. Регламент консилиума

Перед принятием существенных технических решений:

1. Сформулировать обсуждаемый вопрос.
2. Получить независимые заключения React Expert и FastAPI Expert.
3. Организовать взаимное рецензирование заключений.
4. Выявить противоречия и альтернативные решения.
5. Получить заключение QA Engineer.
6. Сформулировать итоговое предложение Lead Architect.
7. Представить решение пользователю для согласования, если оно существенно влияет на архитектуру.

Специалисты должны критически оценивать предложения друг друга.

Запрещено скрывать разногласия и нерешённые вопросы.

Использовать реальные субагенты, если окружение поддерживает их запуск. Если субагенты недоступны, сообщить об этом пользователю. Не выдавать имитацию консилиума за работу независимых агентов.

## 5. Правила исследования backend

Исходный код backend является основным источником истины.

Необходимо исследовать:

- Маршруты и endpoints.
- HTTP-методы.
- Модели Pydantic.
- Форматы запросов и ответов.
- Обязательные и необязательные параметры.
- Авторизацию и аутентификацию.
- Роли и права доступа.
- Обработку ошибок.
- Бизнес-логику.
- Фильтрацию, сортировку и пагинацию, если они реализованы.

Запрещено придумывать отсутствующие endpoints, параметры и поля данных.

Все существенные выводы подтверждать ссылками на файлы, классы и функции backend.

Frontend должен адаптироваться к backend, а не наоборот.

## 6. Правила разработки frontend

- Максимально использовать подходящие решения из frontend v2.
- Не переписывать работающие компоненты без обоснованной необходимости.
- Не добавлять новые зависимости без обоснования.
- Разделять пользовательский интерфейс, бизнес-логику и слой взаимодействия с API.
- Обеспечивать корректную обработку ошибок.
- Соблюдать согласованную архитектуру.
- Не использовать реальные секреты и учётные данные в исходном коде.

## 7. Порядок работы

### Этап 1. Исследование

Исследовать backend и frontend v2 без изменения файлов.

### Этап 2. Проектирование

Подготовить контракт API, архитектуру frontend v3 и план реализации.

Получить согласование пользователя.

### Этап 3. Реализация

Перенести необходимые файлы frontend v2 в frontend v3.

Адаптировать код к действующему API.

### Этап 4. Тестирование

Проверить функциональность и совместимость с backend.

### Этап 5. Code Review

Провести независимое рецензирование результатов.

Проверить отсутствие изменений за пределами разрешённого каталога.
