# DevOps-консилиум для simple_tickets / test-deploy

Комплект содержит корневой AGENTS.md, `.codex/config.toml`, 10 standalone custom agents и запросы для этапов. Председатель — основной агент Codex. Lead DevOps — независимый архитектурный советник. Максимум 6 дочерних потоков одновременно; модель наследуется от сеанса. Конфигурация не выдаёт дополнительных прав и не гарантирует поддержку TOML в конкретной версии Cloud.

## Строгое ограничение ветки

Единственная разрешённая ветка репозитория simple_tickets — test-deploy: только её исходники, история, коммиты и артефакты. Запрещены чтение, поиск, сравнение, получение (fetch), checkout, merge, cherry-pick, создание и изменение других веток, включая через GitHub API, веб-интерфейс и CI. Исключений нет. При отсутствии нужных файлов в test-deploy сообщи BLOCKED; не ищи их в других ветках. Все образы и релизы должны происходить из подтверждённого SHA test-deploy. Если Codex Cloud не может передать результат без создания иной ветки, используйте diff и примените его непосредственно в test-deploy.

## Установка

1. В локальном checkout репозитория выполните `git status --short`, убедитесь в отсутствии незакоммиченных изменений, затем `git switch test-deploy` (ветка должна существовать). Если ветка отсутствует, остановитесь; не создавайте её из другой ветки.
2. Распакуйте архив во временный каталог. Перенесите AGENTS.md, `.codex/` и `docs/devops-council/` в корень репозитория. Если файлы существуют, объедините вручную; не перезаписывайте старый AGENTS.md или config.toml. Не смешивайте два определения одинакового TOML ключа/таблицы. README из архива переносить не надо.
3. Проверьте `git diff` и `git status`, добавьте только согласованные новые/изменённые файлы. Сделайте коммит в `test-deploy` и push этой ветки. Не меняйте другие ветки.
4. В Codex Cloud выберите репозиторий, окружение и именно `test-deploy`. Запустите новый сеанс/задачу, вставив содержимое `docs/devops-council/FIRST_PROMPT.md`. Попросите подтвердить обнаружение custom roles и факт реального spawn. При отсутствии ролей используйте описанный в AGENTS.md fallback; не считайте имитацию консилиумом.
5. После первого заключения используйте `docs/devops-council/PHASE_PROMPTS.md`. Отдельно согласуйте реализацию, read-only аудит и deployment.

## Cloud

Начните с ограниченного интернет-доступа, только нужные registry/package hosts по результатам исследования. Не вводите SSH ключи в чат или обычные переменные среды. Cloud secrets предназначены для setup, а не для передачи в agent phase. Проверка Docker CLI не равна проверке доступности daemon. Не запускайте deployment в setup или maintenance скриптах. Не открывайте сервер в интернет исключительно ради агента.

Предпочтительный путь: отдельный build/test в CI, ручной запуск deploy конкретного релиза на согласованном runner с доступом к серверу. Если `workflow_dispatch` требует другую ветку, не используйте его. Выберите CI, работающий только из test-deploy, либо ручной скрипт. Проверяйте происхождение релиза из test-deploy. GitHub environment secrets и runner настраивает владелец. Если прямой SSH или CI недоступен, получите точные команды от Codex и выполните вручную.
