# Интеграция клиентов между 1С и Simple Tickets через промежуточный сервис

## 1. Цель

Необходимо организовать обмен клиентами между 1С и Simple Tickets таким образом, чтобы:

- не хранить идентификаторы 1С в Simple Tickets;
- не вносить в Simple Tickets специальную логику интеграции;
- не изменять доменную модель Simple Tickets;
- не добавлять в Simple Tickets отдельные поля, таблицы или признаки синхронизации;
- не реализовывать специальную авторизацию для 1С;
- сохранить возможность в будущем организовать обратный обмен клиентами из Simple Tickets в 1С.

Для этого вводится отдельный промежуточный сервис интеграции — **Integration Service / Bridge Service**.

---

## 2. Общая идея

Каждая система продолжает использовать только собственные идентификаторы клиентов.

### В 1С

Используется собственный уникальный номер клиента:

```text
one_c_id
```

### В Simple Tickets

Используется собственный:

```text
client_id
```

### В промежуточном сервисе

Хранится соответствие между двумя системами:

```text
one_c_id
simple_tickets_id
```

Именно промежуточный сервис знает, что клиент с номером `000347` в 1С соответствует клиенту `125` в Simple Tickets.

Simple Tickets ничего не знает о номере клиента в 1С.

---

## 3. Общая схема

```text
        полный список клиентов раз в день

1С  ------------------------------------> Integration Service
                                                |
                                                |
                                                | обычный API
                                                | с авторизацией
                                                v
                                         Simple Tickets
```

Направление обмена на первом этапе:

```text
1С -> Integration Service -> Simple Tickets
```

Обратное направление пока не требуется, но архитектура должна его допускать.

---

## 4. Таблица клиентов промежуточного сервиса

Пример структуры:

```text
id
one_c_id
simple_tickets_id

name
phone
email
address
...

source_hash
confirmed_hash

last_sync_at
last_error
last_seen_run
active_in_1c

created_at
updated_at
```

### `id`

Внутренний идентификатор записи самого Integration Service.

### `one_c_id`

Уникальный идентификатор клиента в 1С.

Может быть `NULL` в будущем для клиентов, которые появились сначала в Simple Tickets.

Должен быть уникальным, если указан.

### `simple_tickets_id`

Идентификатор клиента в Simple Tickets.

Может быть `NULL`, пока клиент ещё не создан в Simple Tickets.

Должен быть уникальным, если указан.

### Данные клиента

Например:

```text
name
phone
email
address
```

Состав этих полей определяется контрактом интеграции.

На первом этапе источником истины для таких данных является 1С.

---

## 5. Источник истины

Для клиентов, пришедших из 1С:

```text
1С = источник истины
```

Если в 1С изменилось:

- имя клиента;
- телефон;
- адрес;
- email;
- или другое синхронизируемое поле,

новое значение должно в итоге попасть в Simple Tickets.

Simple Tickets не определяет, какое значение является правильным.

---

## 6. Почему не требуется отслеживать изменения в 1С

В 1С не требуется:

- добавлять специальный регистр изменений;
- добавлять поле «выгружено»;
- добавлять версию клиента;
- изменять справочник клиентов;
- фиксировать события изменения клиента.

Вместо этого 1С один раз в день выгружает **полный список клиентов**.

Даже если клиентов около 1000, объём такого обмена небольшой.

Пример:

```text
раз в сутки
    |
    v
выгрузить всех клиентов
    |
    v
Integration Service
```

Integration Service сам определяет:

- какие клиенты новые;
- какие изменились;
- какие не изменились;
- какие перестали присутствовать в выгрузке.

---

## 7. Сессия полной выгрузки

Каждая полная выгрузка рассматривается как отдельная сессия.

Например:

```text
sync_run_id = 2026-10-04
```

При получении каждого клиента Integration Service записывает:

```text
last_seen_run = текущая_сессия
```

После завершения выгрузки можно определить клиентов, которых не было в новой выгрузке:

```text
last_seen_run != текущая_сессия
```

Такие клиенты могут быть отмечены:

```text
active_in_1c = false
```

Это не означает автоматическое удаление клиента из Simple Tickets.

На первом этапе удаление или деактивацию можно вообще не синхронизировать.

---

## 8. Определение изменений

Для определения изменения используется hash синхронизируемых данных.

Например hash строится по:

```text
name
phone
email
address
...
```

Порядок и формат полей при расчёте hash должны быть стабильными.

Например:

```text
source_hash
```

— hash актуальных данных, полученных из 1С.

---

## 9. Подтверждённое состояние

Кроме текущего hash хранится:

```text
confirmed_hash
```

Это hash данных, которые были **успешно переданы в Simple Tickets и подтверждены его обычным HTTP-ответом**.

То есть Integration Service хранит два состояния:

```text
source_hash
confirmed_hash
```

### Если:

```text
source_hash == confirmed_hash
```

клиент синхронизирован.

### Если:

```text
source_hash != confirmed_hash
```

в 1С есть данные, которые ещё не были успешно подтверждены Simple Tickets.

---

## 10. Новый клиент

Из 1С приходит новый клиент:

```text
one_c_id          = 000912
simple_tickets_id = NULL

name              = ООО Василёк

source_hash       = CCC
confirmed_hash    = NULL
```

Integration Service видит:

```text
simple_tickets_id == NULL
```

и понимает, что клиента нужно создать.

Он вызывает уже существующий API Simple Tickets:

```text
POST /admin/clients/
```

Simple Tickets создаёт клиента и возвращает обычный ответ, например:

```json
{
    "client_id": 208
}
```

Этот ответ является подтверждением успешного создания.

После этого Integration Service записывает:

```text
one_c_id          = 000912
simple_tickets_id = 208

source_hash       = CCC
confirmed_hash    = CCC
```

Теперь клиент синхронизирован.

---

## 11. Изменение существующего клиента

Допустим, ранее было:

```text
one_c_id          = 000347
simple_tickets_id = 125

name              = ООО Ромашка

source_hash       = AAA
confirmed_hash    = AAA
```

На следующий день из 1С приходит:

```text
one_c_id = 000347
name     = ООО Ромашка-Сервис
```

Integration Service пересчитывает hash:

```text
source_hash = BBB
```

При этом:

```text
confirmed_hash = AAA
```

Получается:

```text
source_hash != confirmed_hash
```

Следовательно, данные необходимо передать в Simple Tickets.

Integration Service вызывает существующий API изменения клиента, например:

```text
PUT/PATCH /admin/clients/125/...
```

Точный endpoint определяется уже существующим API Simple Tickets.

Если Simple Tickets отвечает успешно:

```text
200 OK
```

или другим предусмотренным успешным кодом, Integration Service записывает:

```text
confirmed_hash = BBB
last_error = NULL
last_sync_at = текущее_время
```

Теперь:

```text
source_hash == confirmed_hash
```

и клиент снова считается синхронизированным.

---

## 12. Если данные не изменились

Если 1С присылает клиента:

```text
source_hash = AAA
```

и в Integration Service уже:

```text
confirmed_hash = AAA
```

никаких запросов в Simple Tickets выполнять не требуется.

Таким образом, 1С может каждый день передавать всех клиентов, но в Simple Tickets будут отправляться только:

- новые клиенты;
- изменённые клиенты;
- при необходимости повторные попытки после ошибок.

---

## 13. Ошибка при передаче в Simple Tickets

Если Simple Tickets:

- недоступен;
- вернул ошибку;
- не прошёл валидацию;
- произошла сетевая ошибка,

Integration Service **не изменяет `confirmed_hash`**.

Например:

```text
source_hash    = BBB
confirmed_hash = AAA
```

так и остаётся.

Дополнительно сохраняется:

```text
last_error
```

Например:

```text
HTTP 500
Connection timeout
Validation error
```

Через некоторое время Integration Service может повторить операцию.

Специальный `sync_state` не обязателен, поскольку состояние можно определить непосредственно по данным.

---

## 14. Состояние синхронизации без отдельного `sync_state`

### Нужно создать клиента

```text
simple_tickets_id IS NULL
```

### Нужно обновить клиента

```text
simple_tickets_id IS NOT NULL
AND
source_hash != confirmed_hash
```

### Клиент синхронизирован

```text
simple_tickets_id IS NOT NULL
AND
source_hash == confirmed_hash
```

Таким образом, отдельный статус:

```text
pending_create
pending_update
synced
```

не является обязательным.

При необходимости он может быть вычисляемым представлением для административного интерфейса.

---

## 15. Подтверждение со стороны Simple Tickets

Никаких специальных подтверждений в Simple Tickets не добавляется.

Не требуется:

- новая таблица;
- поле `external_id`;
- поле `1c_id`;
- поле `sync_status`;
- специальный endpoint подтверждения;
- специальный integration entity;
- изменение Client aggregate.

Подтверждением является обычный успешный ответ уже существующего API.

### При создании

Simple Tickets возвращает:

```text
client_id
```

Integration Service сохраняет его как:

```text
simple_tickets_id
```

### При изменении

Успешный ответ API означает, что данные приняты.

После этого:

```text
confirmed_hash = source_hash
```

---

## 16. Simple Tickets ничего не знает о 1С

Для Simple Tickets Integration Service выглядит как обычный API-клиент.

Simple Tickets получает обычные команды:

```text
создать клиента
изменить клиента
получить клиента
```

В доменной модели Simple Tickets отсутствует понятие:

```text
1С
one_c_id
integration
sync
external client
```

Связь между системами существует только в Integration Service.

---

## 17. Авторизация

### 1С -> Integration Service

Специальная прикладная авторизация для 1С не требуется.

Не требуется реализовывать:

- login;
- password;
- JWT;
- refresh token.

Однако Integration Service не должен быть открыт всему интернету.

Доступ желательно ограничить на сетевом уровне:

```text
IP сервера 1С -> разрешено
остальные      -> запрещено
```

или разместить обе системы в:

```text
LAN
VPN
закрытой серверной сети
```

---

## 18. Integration Service -> Simple Tickets

Со стороны Integration Service используется обычная авторизация Simple Tickets.

Желательно создать отдельную техническую учётную запись, например:

```text
integration_1c
```

Ей выдаются только минимально необходимые права для:

- создания клиентов;
- изменения клиентов;
- при необходимости чтения клиентов.

Таким образом:

```text
1С
  |
  | без прикладной авторизации
  | доступ ограничен сетью
  v
Integration Service
  |
  | обычная авторизация Simple Tickets
  v
Simple Tickets
```

---

## 19. Обратное направление в будущем

Архитектура позволяет позднее реализовать:

```text
Simple Tickets -> Integration Service -> 1С
```

Например, если клиент был создан непосредственно в Simple Tickets:

```text
one_c_id          = NULL
simple_tickets_id = 208
name              = ООО Василёк
```

1С сможет периодически запрашивать клиентов:

```text
WHERE one_c_id IS NULL
AND simple_tickets_id IS NOT NULL
```

После создания клиента у себя 1С сможет сообщить Integration Service свой номер:

```text
one_c_id = 000912
```

После этого запись станет:

```text
one_c_id          = 000912
simple_tickets_id = 208
```

Однако на первом этапе это направление реализовывать не требуется.

---

## 20. Важное ограничение: потерянный ответ после создания

Есть один особый случай.

Последовательность:

1. Integration Service вызывает создание клиента.
2. Simple Tickets успешно создаёт клиента.
3. Клиент получает `client_id = 125`.
4. HTTP-ответ не доходит до Integration Service.
5. Integration Service остаётся с:

```text
simple_tickets_id = NULL
```

6. При повторной попытке он может создать клиента ещё раз.

Без каких-либо изменений в Simple Tickets полностью исключить этот сценарий нельзя.

На первом этапе этот риск можно принять как редкий технический случай.

При необходимости позднее можно реализовать сверку через уже существующий API Simple Tickets либо добавить отдельную инфраструктурную защиту от повторного создания, не затрагивая доменную модель Client.

---

## 21. Итоговая логика дневной синхронизации

```text
Начало сессии
    |
    v
1С выгружает всех клиентов
    |
    v
для каждого клиента:
    |
    +--> найти по one_c_id
           |
           +--> нет записи
           |      |
           |      +--> создать запись
           |             simple_tickets_id = NULL
           |
           +--> запись есть
                  |
                  +--> обновить данные
                  +--> пересчитать source_hash
    |
    v
после приёма snapshot:
    |
    +--> simple_tickets_id == NULL
    |       -> создать в Simple Tickets
    |
    +--> source_hash != confirmed_hash
    |       -> обновить в Simple Tickets
    |
    +--> source_hash == confirmed_hash
            -> ничего не делать
```

После успешного ответа Simple Tickets:

```text
confirmed_hash = source_hash
```

---

## 22. Основные принципы решения

1. **1С является источником истины** для клиентов, пришедших из 1С.
2. **Simple Tickets не хранит идентификаторы 1С**.
3. **Simple Tickets не содержит специальной логики синхронизации**.
4. **Integration Service является единственным местом соответствия идентификаторов двух систем**.
5. **1С раз в день выгружает полный snapshot клиентов**.
6. **Integration Service сам определяет изменения по содержимому данных**.
7. **Успешный обычный HTTP-ответ Simple Tickets является подтверждением синхронизации**.
8. **Повторные попытки определяются разницей `source_hash` и `confirmed_hash`**.
9. **Специальный статус синхронизации не обязателен**.
10. **Архитектура допускает будущее обратное направление, но сейчас оно не реализуется**.

---

## 23. Итоговая архитектура

```text
                  полный snapshot раз в сутки
                         без auth
                           |
                           v
+---------+        +---------------------+        +------------------+
|   1С    |------->| Integration Service |------->|  Simple Tickets  |
+---------+        |                     | auth   +------------------+
                   | one_c_id            |
                   | simple_tickets_id    |
                   | client data         |
                   | source_hash         |
                   | confirmed_hash      |
                   | last_error          |
                   +---------------------+
```

Главный архитектурный принцип:

> 1С знает только свой идентификатор клиента.  
> Simple Tickets знает только свой идентификатор клиента.  
> То, что это один и тот же клиент, знает только Integration Service.
