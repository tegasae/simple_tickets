# Подтверждение выполненной работы по области доступа

**Статус** — решение для будущей реализации. Это расширение административной команды `/execute`, подтверждающей результат работы по заявке.

**Снимок консилиума** — ветка `api-new-client-scheme`, коммит `a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50`. Сценарий и проект решения проверили системный аналитик, эксперт по RBAC в Python-бэкенде и инженер QA.

## Действующее поведение

`PATCH /admin/tickets/{ticket_id}/execute` вызывает `TicketApplicationService.execute()`. Прикладной сервис проверяет право `ticket.executed` и вызывает доменную операцию. Внутренняя заявка переходит из `READY_FOR_REVIEW` в `EXECUTED`. Если есть связанная `TicketUser`, она переходит из `WAITING_FOR_CONFIRMATION` в `CONFIRMED_BY_ADMIN`. Статусы обеих карточек и их история сохраняются одной транзакцией. [Маршрут](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/web/routers/admin/tickets.py#L1020-L1049) · [Прикладной сервис](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/application/services/ticket_service.py#L950-L985) · [Соответствие статусов](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/domain/statuses/mapping_statuses.py#L59-L68) · [Сохранение пары](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/application/services/ticket_service.py#L1236-L1259)

Области доступа применяются только к административному подтверждению выполнения. Приём заявки через `/accept` и подтверждение результата пользователем через `/user/tickets/{ticket_user_id}/confirm` имеют свои команды и права.

## Предлагаемые права

| Код права | Область административного подтверждения |
|---|---|
| `ticket.executed` | Любая заявка, готовая к подтверждению. Это действующее глобальное право. |
| `ticket.executed.department` | Заявка из текущего отдела сотрудника. Требуется `actor.department_id > 0` и `actor.department_id == ticket.department_id`. Свою заявку в этом отделе тоже можно подтвердить. |
| `ticket.executed.own` | Заявка, по которой сотрудник является текущим исполнителем. Требуется `ticket.current_executor_id() == actor.employee_id`. |

Права складываются по всем назначенным ролям. Достаточно одного права, область которого совпадает с заявкой. Например, сотрудник с `own` и `department` может подтверждать заявки коллег в своём отделе. Сотрудник с глобальным правом сохраняет глобальный доступ при добавлении любой узкой роли. Чтобы сузить доступ, нужно убрать все назначения ролей, через которые сотрудник получает `ticket.executed`. [Объединение прав ролей](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/domain/rbac/role.py#L13-L26)

`READY_FOR_REVIEW` сохраняет активное назначение до подтверждения. Например, сотрудник А указан исполнителем, а сотрудник Б ретроспективно внёс результат. Запись `READY_FOR_REVIEW` создана от имени Б, а назначение остаётся у А. С одним правом `own` подтвердить заявку сможет А. [Правило состояния](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/domain/statuses/rules/ticket_state_rule.py#L63-L69) · [Определение текущего исполнителя](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/domain/ticket.py#L363-L380) · [Ретроспективная регистрация](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/domain/ticket.py#L650-L697)

## Место проверки

Добавить два кода в `AdminPermission`. Выполнить проверку области в начале существующего `TicketApplicationService.execute()`, внутри текущего `with self.uow`.

1. Загрузить `Admin` по идентификатору из контекста аутентификации и проверить его активность через `can_do_operation()`. Один раз получить объединённый набор его прав через `Authorizer.permissions_of(actor)`.
2. Если среди прав нет ни одного из трёх вариантов подтверждения, завершить команду с `403` до загрузки заявки.
3. Загрузить `Ticket` и проверить область. Глобальное право допускает переход к доменной проверке сразу. Права отдела и исполнителя требуют совпадения соответствующих данных заявки.
4. При отказе выбросить `PermissionError` до загрузки `TicketUser` и изменения истории. Существующий обработчик переводит его в `403`.
5. При подходящей области продолжить текущий сценарий. Домен проверяет статус, связанная карточка синхронизируется, изменения сохраняются одним коммитом. Если статус запрещает переход, сохраняется действующий доменный ответ `400`.

Маршрут, тело запроса и прикладной метод остаются теми же. Клиент передаёт ID заявки и комментарий. Отдел заявки и исполнителя сервер получает из сохранённой заявки. Вызов `require_actor_admin_any()` проверяет только наличие права в роли. Проверка соответствия права конкретной заявке входит в саму команду. [Коды прав](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/domain/rbac/permissions.py#L25-L38) · [Helper проверки прав](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/application/helper/actor_helper.py#L40-L74) · [Коды ошибок](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/web/main.py#L60-L73)

Таблица ролей уже хранит строки разрешений в `roles.permissions`. Для новых кодов достаточно расширить enum и настроить роли. Каталог доступных административных прав строится из этого enum. [Схема SQLite](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/db/schema.sql#L52-L66) · [Каталог прав](https://github.com/tegasae/simple_tickets/blob/a8a5d70ae0f1a864f7e4d6a8fae135826aa9da50/src/web/routers/admin/roles.py#L64-L71)

## Достоинства и компромиссы

| Вариант | Когда подходит | Цена |
|---|---|---|
| Два дополнительных права и проверка в текущей команде | Одна операция с тем же переходом и тремя областями допуска. Сохраняются текущий API, транзакция и совместимость глобальных ролей. | При настройке нужно учитывать права сотрудника из всех ролей. При появлении таких же областей во многих командах могут повторяться проверки. |
| Общая модель «действие и область» | Одинаковые области применяются во многих операциях и их нужно настраивать единообразно. | Нужно определить общее представление областей в ролях, настроить хранение и адаптировать проверки. Для одной команды объём изменений больше. |
| Отдельные команды для подтверждения своей и чужой работы | У действий разные бизнес-результаты, например отдельный этап независимой проверки. | Для одинакового перехода появятся дополнительные входы и повторяющаяся оркестрация. |

Консилиум рекомендует первый вариант. Если продукт потребует независимого проверяющего, запрет на подтверждение собственной работы стоит сформулировать как отдельное правило процесса и отдельно определить его действие для каждой области.

## Приёмочные проверки

Во всех проверках области создавать заявки через штатный процесс, доводить их до `READY_FOR_REVIEW` и вызывать тот же `PATCH /admin/tickets/{ticket_id}/execute`. Слово «только» в таблице относится к правам подтверждения. Для подготовки заявок могут потребоваться отдельные права создания, назначения и работы.

| Права сотрудника и состояние заявки | Ожидание |
|---|---|
| Только старое глобальное право, заявка другого отдела | `200`, переход и история сохранены. |
| Только право отдела, две одинаково готовые заявки в своём и другом отделе | Свой отдел даёт `200`, чужой — `403`. |
| Только право отдела, у сотрудника отсутствует отдел | `403`. Значение `0` обозначает отсутствие отдела. |
| Только право исполнителя, две заявки одного отдела с разными исполнителями | Собственное назначение даёт `200`, назначение коллеги — `403`. |
| Только право исполнителя, работу ретроспективно внёс другой сотрудник с тем же правом | Автор ретроспективной записи получает `403`, текущий исполнитель — `200`. |
| Узкое и глобальное права получены из разных ролей | `200` для чужой заявки другого отдела. После снятия глобальной роли тот же выбор заявки оценивается по узкому праву. Для повторной проверки выбрать другую заявку в `READY_FOR_REVIEW`. |
| Есть право работы над заявкой, ни одного права подтверждения нет | `403`, в том числе у текущего исполнителя. |
| Область подходит, заявка ещё в `AT_WORK` | `400`, подтверждение возможно после перехода в `READY_FOR_REVIEW`. |

После `200` перечитать обе карточки через новое соединение с SQLite. Для связанной пары проверить `EXECUTED` и `CONFIRMED_BY_ADMIN`, по одной новой записи истории с ожидаемым автором и комментарием. После `403` убедиться, что версии, статусы, история и комментарии обеих карточек совпадают с состоянием до вызова.

## Что проверено на базовом снимке

QA прогнал 16 существующих тестов на временной SQLite из `db/schema.sql`. Отдельная проверка маршрута через FastAPI подтвердила `200` с обновлением обеих историй у сотрудника с `ticket.executed` и `403` без изменений данных у текущего исполнителя без этого права. Запрос до `READY_FOR_REVIEW` и повтор успешного подтверждения дали `400`. Таблица выше описывает проверки будущего расширения.
