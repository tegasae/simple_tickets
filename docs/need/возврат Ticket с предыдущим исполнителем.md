## Резюме

Рассматривался сценарий:

```text
READY_TO_WORK executor=25
→ DEFERRED
```

После этого оператору часто нужно вернуть заявку в работу с тем же исполнителем. По оценке, это типичный случай примерно для 70% заявок.

### 1. Не использовать `executor_id=0` как скрытую команду

От идеи:

```text
executor_id=0
→ автоматически найти предыдущего исполнителя
```

лучше отказаться.

Причина: `0` уже имеет нормальный и понятный смысл:

```text
исполнитель отсутствует
```

Не стоит превращать это значение в специальный управляющий сигнал.

---

### 2. «Назначить» и «Вернуть» — разные бизнес-действия

Есть два разных намерения оператора.

Явное назначение:

```text
DEFERRED
→ ASSIGNED / READY_TO_WORK
```

Оператор сам выбирает нового executor.

И возврат:

```text
DEFERRED
→ READY_TO_WORK
```

с восстановлением того executor, который уже был назначен заявке раньше.

Во втором случае `executor_id` оператор не задаёт.

---

### 3. Логика предыдущего исполнителя относится к Ticket

Так как `Ticket` хранит собственную status history, именно доменная модель должна знать:

```text
был ли ранее назначен executor;
какой executor должен считаться предыдущим;
допустим ли возврат с точки зрения собственной истории Ticket.
```

То есть в aggregate имеет смысл иметь операции уровня:

```text
previous_executor_id()
can_resume()
resume(...)
```

Точные имена можно выбрать позже.

Важно: поиск предыдущего исполнителя должен иметь чёткую семантику, а не просто означать:

```text
найти последний ненулевой executor_id где угодно в истории
```

Правило относительно `DEFERRED` надо определить отдельно.

---

### 4. Ticket не может определить актуальную доступность Admin

`Ticket` может знать:

```text
предыдущий executor = 25
```

но не должен знать:

```text
существует ли Admin 25 сейчас;
enabled ли он;
принадлежит ли нужному department;
может ли он сейчас быть executor этой Ticket.
```

Это информация другого aggregate / repository.

Поэтому существуют два уровня проверки.

#### Локальная проверка Ticket

```text
Есть ли смысл операции «Вернуть» по истории Ticket?
```

Например:

```text
READY_TO_WORK executor=25
→ DEFERRED
```

— предыдущий исполнитель есть.

А:

```text
ACCEPTED
→ DEFERRED
```

— возвращать некого.

#### Проверка актуальной допустимости executor

Предыдущий executor найден, но необходимо проверить его текущее состояние:

```text
enabled;
department;
прочие правила назначения.
```

Эта проверка выполняется вне `Ticket`, например через application layer / policy.

---

### 5. Для оператора результат один

Хотя причины могут быть разными:

```text
предыдущего executor никогда не было

или

предыдущий executor был,
но сейчас он недоступен
```

для оператора результат одинаков:

```text
кнопка «Вернуть» недоступна
```

То есть UI может получать итоговое:

```text
can_return = True / False
```

без необходимости показывать разные механизмы.

При необходимости причина может передаваться отдельно.

---

### 6. Саму проверку нужно повторять при выполнении операции

Недостаточно только заранее определить состояние кнопки.

Между:

```text
отображением формы
```

и:

```text
нажатием «Вернуть»
```

предыдущего исполнителя могут отключить или перевести в другой department.

Поэтому при самом `resume` необходимо повторно проверить:

```text
предыдущий executor существует;
он всё ещё допустим;
переход всё ещё разрешён.
```

---

### 7. Итоговая ответственность

```text
Ticket:
    знает историю;
    знает предыдущего executor;
    определяет локальную возможность возврата;
    создаёт новое состояние с восстановленным executor.

Application / Policy:
    проверяет актуальное состояние Admin;
    проверяет enabled / department / внешние ограничения;
    сохраняет изменения.
```

Таким образом, бизнес-смысл операции **«Вернуть»** остаётся в доменной модели, а проверки внешних aggregates не протаскиваются внутрь `Ticket`.

### Открытый вопрос

Отдельно надо определить:

```text
что именно означает «предыдущий executor»
```

для более сложной истории, например:

```text
READY_TO_WORK executor=25
→ DEFERRED
→ SCHEDULED
→ DEFERRED
→ ?
```

То есть разрешено ли искать executor через несколько последующих состояний или возврат относится только к определённому `DEFERRED`-контексту.

Также отдельно позже обсудим судьбу:

```text
planned_start_at
planned_finish_at
```

при операции «Вернуть».
