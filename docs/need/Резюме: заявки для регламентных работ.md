## Резюме

Некоторые `Ticket` желательно выполнять во время регламентных работ.

При этом возможны два случая:

```text
дата регламентных работ известна
дата регламентных работ пока неизвестна
```

Но это не является ограничением на выполнение заявки.

Инженер может выполнить такую заявку раньше:

```text
ASSIGNED → AT_WORK
```

полностью допустим независимо от даты регламентных работ.

---

### 1. Urgency для этого использовать не следует

`urgency` отвечает на другой вопрос:

> насколько срочно / приоритетно нужно выполнить Ticket?

Регламентные работы отвечают на вопрос:

> в каком контексте предпочтительно выполнить Ticket?

Это независимые характеристики.

Например, совершенно допустимо:

```text
urgency = HIGH
maintenance_related = True
```

То есть заявка срочная, хотя её желательно выполнить во время регламентных работ.

---

### 2. Нужен отдельный признак Ticket

Предварительно достаточно отдельного булевого свойства, например:

```python
maintenance_related: bool
```

или другого более подходящего предметного названия.

Его смысл:

```text
False
    обычная заявка

True
    заявку желательно выполнить
    при проведении регламентных работ
```

Это именно предпочтение, а не запрет на выполнение в другое время.

Поэтому название не должно подразумевать обязательность выполнения только во время регламентных работ.

---

### 3. Признак не является workflow status

`maintenance_related` не должен входить в `TicketStatus`.

Он не меняет допустимые переходы:

```text
ASSIGNED → AT_WORK
AT_WORK → READY_FOR_REVIEW
...
```

и вообще не участвует в `TicketState`.

---

### 4. Признак независим от планирования

Возможны варианты:

```text
maintenance_related = True
planned_start_at = None
```

Регламентные работы ещё не назначены.

И:

```text
maintenance_related = True
planned_start_at = ...
planned_finish_at = ...
```

Заявку планируют выполнить во время уже назначенных регламентных работ.

Но даже во втором случае инженер может выполнить её раньше.

---

### 5. Получаются независимые характеристики Ticket

После наших последних решений модель разделяется на несколько независимых аспектов:

```text
workflow
    ACCEPTED
    ASSIGNED
    AT_WORK
    DEFERRED
    READY_FOR_REVIEW
    ...

executor
    кто сейчас назначен

plan
    planned_start_at
    planned_finish_at

urgency
    насколько срочно выполнить

maintenance_related
    желательно ли выполнить
    при регламентных работах
```

Они не должны искусственно кодироваться друг через друга.

---

### Статус решения

Согласовано концептуально:

```text
Не использовать urgency
для обозначения заявок,
связанных с регламентными работами.

Добавить отдельный признак Ticket.

Этот признак:
    не является status;
    не ограничивает ASSIGNED → AT_WORK;
    не зависит от наличия planned_*;
    может использоваться для планирования,
    фильтрации и отображения.
```

Открытым остаётся только точное имя поля и необходимость каких-либо дополнительных правил вокруг него.
