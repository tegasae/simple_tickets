## Профили и workflow

- C‑12 разрешает два наименования. «Обычный сотрудник» — внутренний профиль с базовой ролью; «Ведущий инженер» соответствует учебному «Опытному инженеру». Обычного и главного User клиента описать отдельным разделом. Наборы из `steps.md` иллюстрируют настройку ролей. Назначение другого сотрудника и рекомендация требуют явных свежих прав, а чтение User и выдача клиентских ролей имеют собственные права. Указание отделов и должности само по себе области полномочий не задаёт. [Решения владельца](owner-evidence.md) · [Роли](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/domain/rbac/role.py#L13) · [Права](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/domain/rbac/permissions.py#L14)
- В примере рекомендацию устанавливают до назначения, пока состояние позволяет менять данные. `ASSIGNED` уже не допускает изменения рекомендации. Обычный старт назначенного исполнителя по `ticket.at_work` и специальный `/start-remote-work` следует описывать отдельно. В специальной операции нужны `ticket.at_work_remote`, рекомендация и допустимые статус и назначение. Обычный контракт принимает признак `work_is_remote` для рабочего эпизода; это граница обещания C‑02. Внешняя схема создания тоже принимает рекомендацию, поэтому эксклюзивность диспетчера относится именно к административной смене поля. [Редактирование заявки](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/domain/ticket.py#L492) · [Два обработчика старта](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/application/services/ticket_service.py#L672) · [Схема создания User](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/models/tikcets_user.py#L20)
- Приём, завершение работы и подтверждение результата имеют разные операции. `ticket.executed` глобально. Полномочия собственного назначения и отдела обсуждены для будущей версии. Клиентское подтверждение выполняет User в своей области и синхронизирует обе истории. `SUSPENDED` терминален по текущей модели. ## Установленные тонкости

- Пропуск `department_id` в `PUT /admin/admins/{employee_id}` фактически снимает отдел так же, как явный 0. У сотрудника с действующим назначением попытка будет отклонена. Это расхождение с согласованным C‑06, а безопасный для текущей реализации пример редактирования профиля передаёт сохранённый отдел явно. Маршруты изменения/снятия отдела документировать отдельно. [Модель](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/models/admins.py#L31) · [Преобразование HTTP](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/routers/admin/admins.py#L184) · [Guard](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/domain/services/admin_service.py#L83)
- При отключении User владельца или отдельного контакта заявка в review закрывается в `SUSPENDED` с сохранением обеих карточек. Отключение только аккаунта отзывает refresh и блокирует вход, с сохранением состояния заявки. При отключении Client `AT_WORK` продолжает путь к проверке, и действующий Admin может закончить работу после проверки; уже находившаяся в review пара приостанавливается. Включение User или Client само по себе не восстанавливает статусы заявки. [User](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/domain/services/user_service.py#L352) · [Аккаунт](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/application/services/user_service.py#L277) · [Client](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/domain/services/client_service.py#L230)
- У ранее отключённого и затем включённого сотрудника старые refresh остаются отозванными. Прямой вызов `revoke_subject` при каждом включении текущий сервис не выполняет. Выданный Access проверяется по текущему состоянию сотрудника/аккаунта до истечения собственного срока. Logout в показанном сценарии отзывает refresh. HTTP `401` следует документировать по включённой зависимости, включая Bearer-челлендж. Поле `expires_in` при стандартной конфигурации в свежем примере равно 299 секундам при расчётном сроке 5 минут. [Вход и ротация](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/auth/services/shared_sessions.py#L25) · [Admin auth](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/dependencies/auth.py#L119) · [Включение User](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/application/services/user_service.py#L421)
- Python-карта верно ограничивает миграцию ожидаемой версией схемы и служебными таблицами. Для руководства значимы существующие скрипты и тесты, а rollout на живой БД и старые снимки имеют отдельные предпосылки. Повтор изменённого запроса с тем же ключом даёт простой HTTP `409` с `detail`, без поля `error_type`; формат `409` оптимистической блокировки определяется другим обработчиком. [Миграция](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/scripts/migrate_backend_storage.py#L96) · [Конфликт ключа](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/idempotency.py#L96) · [Ошибки приложения](https://github.com/tegasae/simple_tickets/blob/1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69/src/web/main.py#L60)
