# Независимая карта QA

## Контрольная версия

Фактический контракт относится к опубликованному коммиту `1e69ee8a6368d8bd1bf9971e4a7501f879e2cf69`. Локальные материалы помогают восстановить решения владельца, а совпадение каждого утверждения с кодом проверяется по `published/`. Примеры выполняются через FastAPI TestClient с новым SQLite из `db/schema.sql`, синтетическими пользователями и отдельной средой. Каталоги прошлых ревью и учебные команды служат подсказками для выбора случаев.

## Проверяемые сценарии

| Контракт | Штатные тесты и дополнение |
| --- | --- |
| Вход, Access JWT, refresh, доступ после изменения состояния | `tests/test_creation_and_refresh.py` покрывает отзыв refresh при смене пароля, границы транзакции и повторную проверку доступности Admin. Проверить отдельно через HTTP обе области auth, ротацию и абсолютный срок, разницу отключения сотрудника и аккаунта. |
| Справочники и роли | `tests/test_departments.py` и `tests/test_role_creation.py` проверяют `enabled`, запись роли и историю её создания. Дополнить созданием клиента и сотрудника, охватить пропуск и явный 0 для отдела, проверить роль через реальные строки прав. Шесть названий должностей описывать как согласованные профили, если код не задаёт их автоматически. |
| Внутренняя и внешняя заявки | `tests/test_ticket_workflows.py` проверяет принятие, синхронизацию, клиентское подтверждение и отмену. Сверить фактически все три происхождения внутренней заявки, связь `user_ticket_id` → `ticket_user_id`, автора первой записи, строковый комментарий и контакт с обеих сторон. |

Для примеров проверить назначение другим сотрудником и старт по двум отдельным маршрутам, отсутствие рекомендации, права, актуального назначения и совпадения отдела. Сверить финальные статусы обеих сущностей, доступность User, повторный Admin execute по допустимому состоянию и отзыв refresh. Из кода составить таблицу переходов по исходным статусам с точными границами. |

В примерах сверить простой повтор `201` с тем же результатом и `409` для изменённого запроса, проверить перечень операций по наличию `CreationOperation` и заголовка. |

## Ошибки, которые легко пропустить в документах

- `PATCH /accept` принимает заявку в работу; `PATCH /execute` подтверждает выполнение; клиент отдельно использует `PATCH /user/tickets/{ticket_user_id}/confirm`. В действующем снимке для `execute` действует глобальное `ticket.executed`. Права отдела и собственного назначения описаны в `docs/futher/ticket_execution_permissions.md` как будущие.
- Техническая таблица должна передавать точные enum значений из кода. Внутренний текущий статус берётся из последней записи `statuses`, а внешняя модель также передаёт `current_status`. Старая документация называет внешние статусы иначе и смешивает `planned_at` и этап workflow.
- Отключение сотрудника, аккаунта, отдела и клиента проходит по разным маршрутам и правилам. Изменение пароля отзывает refresh; действующий access дополнительно зависит от актуального статуса входа и живёт до установленного срока. Наличие старых классов/переменных сессий не доказывает отдельный production storage.
- HTTP-коды нельзя выводить из текста сообщения. Формат ошибок зависит от обработчика, например `401` с `WWW-Authenticate: Bearer`, прикладные `400/403/404/409` с `detail` и `error_type`, стандартный FastAPI validation `422` со списком `detail`. Сверить по `src/web/main.py` и реальным ответам.
- По запуску отделить существующие `pytest` из `pytest.ini` от упоминаний `tests_pyramid/` и ревью прошлых снимков. Планы PostgreSQL, async, очередь и 1С маркировать как перспективу.

## Приёмка

Пользовательский документ позволяет пройти шесть согласованных профилей, понять различия прав и выполнить основные задачи шаг за шагом. Технический документ фиксирует модель, полномочия, таблицы переходов, авторизацию, форматы запросов и ошибок и сохраняемое состояние. Для каждого примера указаны предпосылки, субъект, точный метод и путь, минимальный JSON, ожидаемый статус и наблюдаемые изменения. Секреты, служебные БД, детали логинов и переменные идентификаторы заменяются символами. Сверить все пути и схемы с OpenAPI того же коммита, отдельно сверить ограничения runtime, отметить источник тестов и степень подтверждения. Перед приёмкой PDF проверить оглавление, ссылки, читаемость таблиц и кодовых блоков, выдачу русского текста при извлечении и отсутствие обрезанных строк.
