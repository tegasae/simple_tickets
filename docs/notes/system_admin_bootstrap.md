# Simple Tickets. Системный администратор и восстановление доступа

**Статус — проект спецификации для будущей реализации.**

Описано для бэкенда `tegasae/simple_tickets`, ветка `api-new-client-scheme`, коммит `cd71e524965e9be398096d3555d484080dcc7e8d`. Имена команд, таблицы и форматы ниже описывают предлагаемое поведение. [Снимок кода](https://github.com/tegasae/simple_tickets/commit/cd71e524965e9be398096d3555d484080dcc7e8d)

## 1. Зачем нужен системный администратор

При первом запуске с пустой базой нужен первый администратор, который сможет создать персональные учётные записи и выдать им роли. После начала работы тот же системный аккаунт позволяет восстановить доступ, если все обычные администраторы потеряли `role.assign`. Сейчас отзыв последнего назначения роли возможен через штатный API, а для обратного назначения требуется действующее право `role.assign`. [Текущий сервис выдачи и отзыва ролей](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/application/services/admin_service.py#L321-L379)

Предлагается **ровно один защищённый системный Admin на базу**. У него обычный административный `Account`, штатный вход и роль восстановления. Персональные аккаунты остаются основным способом ежедневной работы. Владелец базы использует системный аккаунт для первичной настройки и восстановления.

## 2. Роли и обязательные условия

| Участник | Действия |
| --- | --- |
| Владелец установки | Один раз создаёт системного администратора локальной командой. При необходимости запускает локальную смену его пароля. Для этих команд нужен доступ к выбранной базе и окружению приложения. |
| Системный администратор | Входит через административный login. Находит обычных администраторов, создаёт их при необходимости и управляет их ролями. |
| Обычный администратор | Работает со своими полномочиями. Административные команды над системным аккаунтом проходят отдельную проверку защищённой записи. |

В каждой инициализированной базе должны выполняться следующие условия.

1. Есть одна запись, указывающая на системного `Admin`, его существующий активный `Account` и роль восстановления.
2. Сам `Admin` включён и принадлежит административному контуру. Для восстановления отдел ему не требуется.
3. Зарезервированная роль назначена этому `Admin`. Её нельзя выдавать через штатные команды назначения. Роль и системный статус связываются по постоянным ID.
4. Пароль хранится штатным способом через доменный `Account`. Логин может быть выбран владельцем, например `system-admin`. Имя, логин и числовой ID сами по себе не определяют системный статус.

Для минимальной роли восстановления предлагаются `admin.view`, `admin.operation` и `role.assign`. Первое право позволяет найти нужного администратора, второе — создать или восстановить его учётную запись, третье — выдать роль. В действующей модели `role.assign` даёт широкие полномочия по назначению административных ролей. Набор следует считать полномочиями владельца доступа. Защита зарезервированной роли касается её ID. Выдача обычных ролей с сопоставимыми разрешениями по-прежнему регулируется существующим `role.assign`. [Создание Admin и выдача ролей](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/application/services/admin_service.py#L67-L143) · [Текущий RoleManager](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/domain/rbac/role.py#L41-L61)

## 3. Хранение системного статуса

Предлагается отдельная таблица `system_admin`. Одна строка с фиксированным ключом `slot = 1` обозначает защищённую учётную запись. Такой ключ обеспечивает максимум одну строку. Наличие строки и активных связанных объектов проверяет приложение перед готовностью API.

Пример будущей схемы на основе текущих таблиц.

```sql
CREATE TABLE system_admin (
    slot INTEGER NOT NULL PRIMARY KEY CHECK (slot = 1),
    employee_id INTEGER NOT NULL,
    recovery_role_id INTEGER NOT NULL,
    FOREIGN KEY (employee_id) REFERENCES admins(employee_id) ON DELETE RESTRICT,
    FOREIGN KEY (employee_id) REFERENCES accounts(employee_id) ON DELETE RESTRICT,
    FOREIGN KEY (recovery_role_id) REFERENCES roles(role_id) ON DELETE RESTRICT
);
```

В текущей базе `accounts.employee_id` уникален. Две внешние ссылки по одному ID обеспечивают наличие `Admin` и именно его аккаунта. Ссылки защищают связанные записи от случайного удаления. Признаки активности, административный тип роли и само назначение роли проверяются прикладными правилами в рамках Unit of Work. Прямой доступ на запись в SQLite находится вне границы защиты обычного API. [Базовая схема](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/db/schema.sql#L8-L40) · [Уникальность аккаунта](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/db/schema.sql#L179-L180)

**Важно при интеграции.** Текущий репозиторий `Admin` при полном сохранении удаляет строки его назначений из `admins_roles` и затем записывает их заново. Немедленная внешняя ссылка на конкретную строку в `admins_roles` заблокировала бы такое сохранение, в том числе при смене пароля. В минимальной схеме обязательное назначение контролируется в сервисе и при проверке готовности. Если понадобится ограничение на уровне БД именно для назначения, сначала потребуется сохранять разницу в назначениях. [Сохранение Admin и назначений](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/adapters/repositories/admin.py#L40-L62) · [Вызов при обновлении](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/adapters/repositories/admin.py#L150-L177)

У существующего флага `is_system_role` остаётся его текущее назначение. Зарезервированную роль восстановления предлагается создать с этим флагом, а ограничение её выдачи и отзыва проверять по `recovery_role_id` из `system_admin`. Сейчас флаг защищает сам объект роли при удалении. [Удаление роли](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/application/services/role_service.py#L86-L112)

## 4. Первый запуск и повторная инициализация

Однократная локальная команда входит в первый запуск и выполняется до приёма HTTP-запросов. Пример синтаксиса будущей команды.

```bash
python -m src.cli.system_admin init-admin --login system-admin
```

Пароль вводится скрыто. Для автоматизированного запуска можно предусмотреть чтение из переданного файла секрета. Команда выбирает целевую базу из явно заданного `DATABASE_URL` и использует существующую конфигурацию подключения, а выводит только результат операции и идентификатор системного администратора. Пароль и токены из результата исключаются.

1. Команда проверяет наличие схемы и читает `system_admin`.
2. Если записи ещё нет, она проверяет выбранный логин штатными правилами, создаёт включённый `Admin`, включённый `Account`, роль восстановления, назначение и запись `system_admin`. Все изменения фиксируются одной транзакцией.
3. Если запись уже есть и условия раздела 2 соблюдены, команда возвращает успешный результат «уже инициализировано». Пароль, ID, назначения и сессии сохраняются. Явно переданный другой логин считается ошибкой настройки.
4. Если выбранный логин занят обычной учётной записью, команда сообщает о конфликте. Для инициализации выбирается свободный логин. Повышение привилегий существующей записи по совпадению имени исключено.
5. Если запись `system_admin` существует, но связанная учётная запись отключена или повреждено назначение, команда сообщает, какое условие нарушено. Такое состояние требует отдельного восстановления целостности. Повторная команда инициализации сохраняет идентичность существующей записи.

Конкурирующие запуски проверяются на двух независимых соединениях. Одновременно может успешно зафиксироваться только одна новая запись. После отката проигравшая команда может заново прочитать состояние и сообщить «уже инициализировано», если другая команда успела завершиться. При временной блокировке она сообщает о возможности повторить запуск. Частично созданный Admin, аккаунт или роль после отката отсутствуют.

Штатный старт FastAPI выполняет проверку готовности в обработчике жизненного цикла приложения. Он проверяет системную запись, активность аккаунта и назначение роли. При отсутствии инициализации сообщает о необходимости `init-admin`. При нарушении условий сообщает о состоянии, требующем восстановления. В обоих случаях запуск API останавливается до приёма запросов. Создание и смена пароля остаются явными командами владельца. Вход выполняется через имеющийся административный контур с текущими проверками аккаунта и прав. [Текущая сборка FastAPI](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/web/main.py#L37-L51) · [Admin login](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/web/auth/services/auth_service.py#L70-L101)

## 5. Защита в штатных командах

Предлагается общая прикладная проверка для команд, меняющих цель или её роль. Она читает системную запись в той же транзакции, что и соответствующая операция. При запрете авторизованный запрос получает `403` до записи изменений.

| Операция | Правило для системного администратора |
| --- | --- |
| Список Admin и чтение карточки | Действуют штатные права чтения. Системный статус хранится по ID. |
| Изменение профиля или отдела | Штатные команды записи защищённой цели возвращают `403`. Восстановление не требует отдела или редактируемых полей. |
| Отключение, включение, физическое удаление сотрудника | Штатные команды над защищённым Admin возвращают `403`. |
| Создание, замена, отсоединение, отключение или включение его Account | Проверка действует на все пути, включая `attach_account`, который может заменить логин и пароль существующего аккаунта. |
| Смена пароля системного аккаунта | Выполняется только локальной командой восстановления, включая случай, когда системный Admin уже вошёл через HTTP. |
| Выдача и снятие ролей системного Admin | Штатные команды возвращают `403`. Назначение роли восстановления сохраняется. |
| Выдача зарезервированной роли другому Admin | Запрещена и отдельной выдачей роли, и при создании администратора с начальным списком ролей. Операция целиком откатывается. |
| Изменение зарезервированной роли | Роль защищена от удаления и от изменения состава разрешений через штатное управление ролями. |

Проверка должна охватывать как явную смену пароля, так и замену аккаунта. В действующем сервисе обе операции доступны с `admin.operation`. Прикрепление аккаунта с пустыми реквизитами может привести к его отсоединению. Поэтому привязка защиты только к маршруту смены пароля оставит ещё один путь изменения. [Операции с Account](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/application/services/admin_service.py#L192-L315) · [Доменная обработка аккаунта](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/domain/employee.py#L165-L185)

## 6. Восстановление доступа

Если обычные администраторы потеряли `role.assign`, владелец входит под системным Admin и выдаёт нужную роль обычному аккаунту. Правила выдачи для обычного администратора остаются штатными. После выдачи обычный администратор проверяет доступ к управлению ролями со своим аккаунтом.

Если пароль системного Admin утерян, владелец запускает отдельную локальную команду. Команда выбирает цель по записи `system_admin`. Ввод произвольного ID для смены пароля другого сотрудника не требуется.

```bash
python -m src.cli.system_admin reset-system-admin-password
```

1. Команда проверяет связанные записи и принимает новый пароль через скрытый ввод или файл секрета.
2. Использует штатное хеширование `Account`. Меняет пароль существующей учётной записи и отзывает все её refresh-сессии одной транзакцией.
3. Сохраняет идентичность Admin, логин, Account и назначение роли. Если отзыв refresh-сессий не удался, изменение пароля откатывается.
4. Новый пароль позволяет снова войти через Admin login. Старый пароль и отозванные refresh-токены отклоняются.

В минимальном варианте выданные ранее access JWT продолжают действовать до `exp` при активном аккаунте. Текущий срок составляет пять минут по умолчанию. Проект отдельно должен решить, требуется ли для **системного** аккаунта немедленный отзыв access при восстановлении после компрометации. Если требуется, понадобятся данные версии учётных данных или момент их смены и проверка этих данных при каждом защищённом запросе. Версия для оптимистической блокировки сотрудника служит другим операциям. [Настройка TTL](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/web/config.py#L11-L21) · [Текущий отзыв refresh](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/application/services/admin_service.py#L288-L315) · [Текущая проверка access](https://github.com/tegasae/simple_tickets/blob/cd71e524965e9be398096d3555d484080dcc7e8d/src/web/dependencies/auth.py#L119-L139)

## 7. Существующая база и порядок реализации

Для существующей базы предлагается добавить таблицу и явной командой создать отдельного системного Admin со свободным логином. Текущие сотрудники, назначения и пароли сохраняются. База готова к новой проверке запуска после этой инициализации. Резервная копия и восстановление базы должны включать системную запись и все связанные данные.

| Слой | Предлагаемая работа |
| --- | --- |
| Домен и контракты хранения | Устойчивое представление записи системного Admin и интерфейс её чтения и первоначальной записи. Переиспользовать `Admin`, `Account` и административную `Role`. |
| SQLite | Схема и миграция, SQLite-репозиторий с существующим подходом к Gateway и Mapper, подключение к Unit of Work. |
| Прикладные сервисы | Атомарная инициализация, локальная смена пароля и общая защита штатных операций над зарезервированным Admin и ролью. |
| Точки входа | Локальные команды подключаются к прикладным сервисам напрямую. FastAPI выполняет проверку готовности и использует существующий административный вход. |
| Тесты | Регрессии в штатном pytest на синтетической временной SQLite. |

## 8. Критерии приёмки

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Инициализация новой базы | Создан ровно один системный Admin, одна активная учётная запись и нужное назначение. Вход штатный. Системный Admin создаёт и назначает роль обычному сотруднику. |
| Старт API до инициализации | Проверка готовности сообщает, что требуется первичная инициализация. |
| Повторная и параллельная инициализация | Одна системная запись и один новый набор связанных данных. Второй запуск сохраняет пароль и ID. |
| Сбой между созданием сущностей и записью `system_admin` | Транзакция откатывается целиком. После устранения сбоя команда выполняется обычным запуском. |
| Существующая база и занятый логин | Операция завершает работу с ошибкой конфликта. Старые учётные записи и роли сохраняются. Повтор со свободным логином создаёт отдельную запись. |
| Попытка изменить защищённую цель через API | Проверить отключение Admin и Account, удаление, замену и отсоединение Account, смену пароля, выдачу и снятие ролей. Каждый запрос получает `403`, состав связанных записей сохраняется. |
| Попытка выдать роль восстановления обычному Admin | Отказ как для назначения, так и для создания с начальным набором ролей. Частичных записей после отказа нет. |
| Самоблокировка обычного администратора | Обычный Admin снимает с себя последнюю роль управления доступом. Системный Admin входит и возвращает ему роль штатным маршрутом. |
| Локальная смена пароля | Старый пароль и старый refresh получают отказ. Новый пароль работает. ID и роль сохраняются. Отдельный тест фиксирует выбранную политику для ранее выданного access JWT. |
| Сбой отзыва refresh при смене пароля | Изменение пароля откатывается. Оба эффекта фиксируются вместе после успешного повторения команды. |
| Нарушение обязательной связи или активности | Проверка готовности указывает нарушенное условие. Повторный bootstrap не создаёт второй системный аккаунт. |
| Обычные административные операции | Существующий pytest проходит. Штатное создание, смена пароля, отключение и выдача ролей обычным администраторам сохраняют текущие результаты. |

Приёмка выполняется на временных базах. Проверка владения в реальном проекте представляет собой сценарий восстановления обычной роли через системный аккаунт и через локальный сброс его пароля.
