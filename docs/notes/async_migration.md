## Рекомендация

Сначала перейти на **синхронный Psycopg 3 с пулом соединений**. Переход на PostgreSQL и переход на async — отдельные решения. Асинхронный пилот имеет смысл, если при целевой нагрузке заметная доля задержки приходится на ожидание свободного рабочего потока, а PostgreSQL и CPU сохраняют запас. [Выбор слоя доступа к PostgreSQL](postgresql_persistence.md)

Первый пилот — один маршрут чтения с собственным асинхронным путём от FastAPI до PostgreSQL. Новую интеграцию с несколькими независимыми сетевыми вызовами можно сделать асинхронной отдельно от основного API.

## Что уже делает синхронный API

В проверенном снимке 106 обработчиков в `src/web/routers` объявлены через обычный `def`. FastAPI выполняет такие обработчики и синхронные зависимости в пуле потоков. Поэтому одновременно обслуживается несколько запросов. В текущей реализации `get_uow` открывает обычное SQLite-соединение и закрывает его после запроса. [FastAPI и sync-обработчики](https://fastapi.tiangolo.com/async/#path-operation-functions) · [Зависимость Unit of Work](https://github.com/tegasae/simple_tickets/blob/01d6d19e0b5e513fa02c8d0750ae7dbcbd354f35/src/web/dependencies/services.py#L18-L38)

Механическая замена `def` на `async def` перенесёт синхронные вызовы драйвера в цикл событий и будет его блокировать. Польза возникает при неблокирующем I/O по всему пути выбранной операции. [FastAPI и вызовы обычных функций](https://fastapi.tiangolo.com/async/#very-technical-details)

## Преимущества и ограничения

| Аспект | Потенциальная польза | Цена или ограничение |
| --- | --- | --- |
| Многие запросы одновременно ждут сеть или БД | Ожидание через `await` освобождает цикл событий для другой работы без выделенного рабочего потока на каждое ожидание. | Одновременно выполняемые обращения к PostgreSQL ограничены пулом, пропускной способностью БД и блокировками. |
| Несколько независимых внешних вызовов | Их можно выполнять параллельно с лимитом и таймаутами. Это локально полезно для отдельных интеграций. | Нужно контролировать число запросов, ошибки и отмену. Внешнее ожидание следует держать вне транзакции записи. |
| Асинхронная работа с PostgreSQL | Psycopg 3 предоставляет `AsyncConnection` и `AsyncConnectionPool`. Драйвер и доменные модели можно сохранить. | Переход затрагивает зависимости, чтение прав, сервисы с I/O, репозитории и UoW. Появляются отдельные сценарии отмены и очистки соединения. |
| Запросы с большой вычислительной частью | Асинхронный путь может быть полезен только для его сетевых этапов. | Хеширование пароля и другие синхронные вычисления занимают CPU. В async-маршруте длительные вычисления нужно выполнять вне цикла событий. |
| Параллельные действия с одним агрегатом | Независимые операции можно планировать на отдельных соединениях с ограничением общего параллелизма. | На одном соединении Psycopg запросы сериализуются и разделяют состояние транзакции. `gather` внутри одного UoW не добавит параллельного SQL. |

[Пул потоков Starlette](https://starlette.dev/threadpool/) · [Конкурентность Psycopg](https://www.psycopg.org/psycopg3/docs/advanced/async.html) · [AsyncConnectionPool](https://www.psycopg.org/psycopg3/docs/api/pool.html)

## Что измерить прежде

У списка заявок есть конкретный источник сетевых обменов. Текущая загрузка выполняет один запрос списка и по два дополнительных запроса на заявку для статусов и комментариев. На PostgreSQL сначала измерить этот путь и при необходимости ввести пагинацию и пакетную загрузку. Эффект доступен в обоих режимах драйвера. Вход замерять отдельно, поскольку он выполняет CPU-затратное хеширование PBKDF2. [Чтение списка](https://github.com/tegasae/simple_tickets/blob/01d6d19e0b5e513fa02c8d0750ae7dbcbd354f35/src/adapters/repositories/ticket_repository.py#L428-L443) · [Статусы и комментарии](https://github.com/tegasae/simple_tickets/blob/01d6d19e0b5e513fa02c8d0750ae7dbcbd354f35/src/adapters/repositories/ticket_repository.py#L43-L80) · [PBKDF2](https://github.com/tegasae/simple_tickets/blob/01d6d19e0b5e513fa02c8d0750ae7dbcbd354f35/src/domain/value_objects.py#L344-L370)

Для сравнения использовать одну базу и одинаковый набор данных, эффективный SQL, число процессов и общий лимит подключений. Нагрузка должна включать чтение карточек и списков, создание заявок и отдельный прогон входа. Сравнить p95/p99, пропускную способность, процент ошибок, CPU и память. Время ожидания разложить на очередь пула потоков, получение соединения, SQL и ожидание блокировок. [Метрики пула Psycopg](https://www.psycopg.org/psycopg3/docs/advanced/pool.html#pool-stats)

| Наблюдение | Решение |
| --- | --- |
| На целевой нагрузке растёт ожидание рабочего потока, PostgreSQL и пул соединений сохраняют запас | Проверить async на одном маршруте и измерить эффект. |
| Основное время уходит на SQL, соединение или блокировки | Приоритизировать SQL, форму выборки и границы транзакций. |
| Существенная доля задержки входа приходится на PBKDF2 | Сохранить текущий синхронный путь или использовать ограниченный executor при отдельном переносе входа. |
| Синхронный вариант выполняет цели по задержке и ресурсам | Сохранить его в основном API. Асинхронные интеграции выбирать отдельно по их собственным требованиям. |

## Как проводить пилот

1. Зафиксировать синхронный PostgreSQL как базовый вариант. Сохранить HTTP-контракт, доменные модели и явные транзакционные границы.
2. Выбрать один нагруженный маршрут чтения. Сделать асинхронными только его I/O-зависимости, включая доступ к правам, репозиторий и UoW. Чистые проверки, преобразования данных и переходы статусов сохранить обычными функциями.
3. Использовать `AsyncConnectionPool` с ограниченным числом подключений. Один UoW владеет одним соединением и одной границей транзакции. Сравнить выигрыш на одинаковых запросах и одинаковом лимите соединений.
4. Перед переносом записи отдельно проверить успешное выполнение, ошибку SQL, таймаут, отмену корутины, откат и состояние соединения, возвращённого в пул. Для составных операций сохранить атомарность заявки, истории и идемпотентного результата. При неопределённом исходе коммита повтор клиента проверяется с тем же ключом по существующему контракту.
5. Расширять пилот, если получен устойчивый выигрыш в требуемых сценариях, а правила прав, ошибок и целостности подтверждены интеграционными тестами.
