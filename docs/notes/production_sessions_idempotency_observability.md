# Production: сессии, идемпотентность, повторы и наблюдаемость

## Действующий контракт

Refresh-сессии хранятся в основной SQLite. Смена пароля, отключение аккаунта или сотрудника и замена аккаунта фиксируются вместе с отзывом refresh-сессий в одной транзакции. При удалении аккаунта его сессии удаляет внешний ключ. Ротация refresh сохраняет дедлайн в семь суток от входа. Access JWT действует до пяти минут по умолчанию и проходит действующие проверки аккаунта и прав. Срок уже выданного access JWT сам отзыв refresh не сокращает.

Перед обновлением существующей SQLite остановите записи приложения и сделайте резервную копию. Команда ниже запускается из корня проекта.

```sh
python scripts/migrate_backend_storage.py /path/to/current.sqlite3
```

Миграция добавляет таблицы сессий и результатов создания и приводит старые `NULL`-версии к нулю. Пустой реестр ключей из предыдущего дампа обновляется автоматически. Если реестр уже содержит записи со старым составным ключом, скрипт останавливается и сохраняет их. После обновления пользователи входят заново. Старые refresh-сессии из отдельного файла или памяти процесса не переносятся. Для инициализации БД с сохранёнными данными используйте [dump_migration.sql](../../db/dump_migration.sql).

Все десять маршрутов создания сущностей принимают необязательный `Idempotency-Key`. Клиент генерирует уникальный ключ для каждой новой операции и сохраняет его при повторной доставке. Сервер хранит успешный результат по паре `(employee_id, idempotency_key)` в той же транзакции, что и созданные данные. Повтор той же команды, цели и нормализованного тела при действующих правах возвращает исходный статус и тело. Другая команда, цель или тело под тем же ключом дают `409`. Без ключа маршрут выполняется обычным образом.

Результат хранится 24 часа. Если сервер завершился после фиксации результата до отметки срока, следующее успешное обращение с ключом запускает полный срок хранения. При потере ответа или временной ошибке БД повтор с прежним ключом делает клиент.

## 2. Что остаётся перед production

Отдельно от уже подготовленной инфраструктуры необходимо проверить применение исправлений из аудита: права выдачи и отзыва User-ролей, проверку идентичности refresh, ожидаемые ошибки API, контакты связанных карточек, включение сотрудников в отключённом отделе, авторство комментариев и UTC-даты. Сохранение отчётов и patch-файлов само по себе не применяет эти исправления.

В аудит входили синтетические проверки на SQLite. Успешные тесты этой среды не подтверждают поведение PostgreSQL. До выпуска нужны тесты с фактическим production-драйвером, в том числе две независимые транзакции для назначения исполнителя и одновременного отключения сотрудника или смены его отдела.

Нужен актуальный автоматический набор в CI: изоляция клиентов, доступ к своим и чужим заявкам, жизненный цикл пары Ticket/TicketUser, отключение аккаунтов и клиентов, сессии, ошибки сохранения, откат и конкуренция. Процент полного покрытия и нагрузочные пределы в обсуждении не устанавливались.

## 3. Предлагаемая схема сессий

### 3.1. Общее хранилище

Все workers должны видеть одно состояние сессий. Предлагается хранить production-сессии в основной PostgreSQL через отдельный адаптер существующей абстракции хранения. Тогда изменение аккаунта и отзыв его сессий могут выполняться одной транзакцией, без согласования двух разных систем хранения.

В проверенной версии существуют memory- и SQLite-реализации refresh-хранилища. Memory подходит для изолированных тестов и локального процесса, но не обеспечивает общую сессию между workers и сохранение после перезапуска. Наличие SQLite backend само по себе не означает наличия PostgreSQL-адаптера или немедленного отзыва access JWT.

Предлагаемая запись сессии содержит:

- уникальный ID сессии;
- тип субъекта — Admin или User — и его постоянный ID;
- привязку к конкретному аккаунту, чтобы удаление и повторное присоединение аккаунта не оживляли прежнюю сессию;
- хеш действующего refresh-токена;
- время создания и согласованные сроки действия;
- признак или время отзыва;
- данные для атомарного контроля ротации.

Это описание назначения данных, а не готовая схема таблицы. Открытые значения сроков перечислены в разделе 9. Проверять сессию только по логину нельзя: имя может перейти другому аккаунту.

### 3.2. Проверка access JWT

При входе сервер создаёт сессию. Access JWT содержит ID сессии и идентичность субъекта. На каждом защищённом запросе проверяются подпись, срок, тип субъекта, его актуальное состояние, наличие допустимого аккаунта и действительность сессии в общем хранилище. Для User также сохраняются действующие проверки Client.

Удаление одного refresh-токена не отзывает уже выданный access JWT: без дополнительной серверной проверки он способен работать до своего срока. Короткий TTL уменьшает этот интервал, но не заменяет немедленный отзыв на следующих запросах.

Для первого варианта предлагается проверять общее состояние сессии при каждом запросе. Если позднее вводится кеш, отдельно определяются срок допустимого устаревания и способ распространения отзыва между workers.

Обычный `version` доменной сущности нельзя использовать как версию авторизации: в проекте он изменяется и для optimistic locking/guard операций. Возможная альтернатива отдельной проверке записи сессии — специальная версия авторизации с собственным жизненным циклом; это другой технический вариант, а не дополнительное обязательное поле поверх описанной схемы.

### 3.3. Отзыв и повторное включение

| Событие | Нужное поведение старых сессий |
|---|---|
| Смена пароля | Все сессии этого аккаунта отзываются, включая текущую; требуется новый вход |
| Удаление аккаунта | Старые access и refresh больше не принимаются |
| Отключение сотрудника | Старые сессии отзываются; отключённый сотрудник не выполняет новый вход |
| Повторное включение сотрудника | Отозванные сессии остаются отозванными; допускается только новый вход при выполнении остальных правил |
| Создание нового аккаунта у того же сотрудника | Прежние токены старого аккаунта не восстанавливаются |

Изменение аккаунта/сотрудника и отзыв выполняются атомарно. При ошибке транзакции не должно остаться изменения аккаунта без соответствующего отзыва. Если отключение Client каскадно отключает пользователей, отзыв нужно согласовать с этим же прикладным сценарием.

Критерий для новых запросов после успешного отзыва — старые токены дают 401. Правило для команды, уже прошедшей авторизацию до отзыва, нужно определить отдельно: документ не обещает отмену уже выполняемого запроса или его совершённого COMMIT.

### 3.4. Refresh и ротация

Сервер проверяет сессию, срок, тип субъекта и соответствие постоянных ID. Выдача нового refresh и инвалидирование старого выполняются атомарно. Новые токены возвращаются после успешной фиксации. Две конкурентные попытки не должны обе успешно использовать один старый refresh.

Ошибка сохранения не оставляет промежуточного состояния. Отзыв, конкурирующий с refresh, не должен приводить к появлению действующей сессии взамен отозванной. Атомарная ротация сама по себе не решает потерю ответа: если новый refresh уже сохранён, старый при повторе может быть отклонён. Для этого нужен отдельный согласованный протокол; общую политику повторов бизнес-команд к refresh автоматически не применяем.

### 3.5. Проверки приёмки сессий

1. Вход через один worker, защищённый запрос и refresh через другой.
2. Сессия сохраняется после перезапуска приложения.
3. После каждого события отзыва старые access и refresh получают 401 через любой worker.
4. После повторного включения старые токены по-прежнему получают 401; новый вход работает.
5. Переназначение того же логина другому аккаунту не позволяет обновить старую сессию.
6. Admin/User с одинаковым числовым ID не смешиваются: проверяется и тип субъекта.
7. Два одновременных refresh имеют одного успешного потребителя старого токена.
8. Ошибка сохранения при ротации откатывает все её изменения.
9. Конкурирующие отзыв и refresh не оставляют действующую сессию после отзыва.

Проверки выполняются с синтетическими аккаунтами и временной БД. Токены и пароли не переносятся в отчёты и логи.

## 4. Зачем нужна идемпотентность команд

Идемпотентность относится к логической операции пользователя, а не к совпадению текста заявки. Механизм применим и к другим сущностям: особенно важны создание объектов, добавление комментариев и команды, дописывающие историю. Перечень конкретных маршрутов ещё не утверждён.

### 4.1. Дубликат без ключа

1. Пользователь нажимает «Создать заявку».
2. Клиент отправляет запрос.
3. Сервер проверяет доступ, создаёт TicketUser, Ticket и первоначальную историю.
4. Сервер выполняет COMMIT: заявка уже сохранена.
5. Ответ теряется в сети или клиент прекращает ожидание по таймауту.
6. Клиент не знает, была ли фиксация, и повторяет запрос.
7. Сервер воспринимает его как новую команду и создаёт вторую пару.

Одинаковое тело не доказывает дубликат: пользователь вправе намеренно создать две заявки с одинаковым текстом.

### 4.2. Та же ситуация с Idempotency-Key

1. При начале новой логической операции клиент создаёт случайный ключ, например UUID, и сохраняет его вместе с отправляемыми данными до первой отправки.
2. Клиент отправляет запрос с заголовком `Idempotency-Key`.
3. Сервер выполняет обычную авторизацию и проверку входа, определяет область команды и отпечаток нормализованного запроса.
4. В одной транзакции сохраняются ключ, пара карточек, история и подготовленный результат операции.
5. COMMIT успешно фиксирует всё вместе, но ответ не доходит до клиента.
6. Клиент повторяет тот же запрос с тем же ключом.
7. Сервер снова проверяет авторизацию и возвращает сохранённый результат: тот же ID заявки и согласованный статус ответа. Новых карточек и повторной истории нет.

Новая намеренная заявка получает новый ключ. Кнопка «Повторить отправку» использует прежний ключ; генерация нового ключа на каждую сетевую попытку лишает механизм смысла. Для одного ключа клиент сохраняет первоначальные данные операции, а не незаметно подставляет отредактированную форму.

### 4.3. Контракт хранения и переносимость

Предлагаемая область уникальности — тип и постоянный ID субъекта, команда и ключ. Для действия над существующим объектом адресат входит в область команды либо в проверяемый отпечаток. Ключ не должен зависеть от текущего имени пользователя или конкретного access-токена: одна операция может повториться после обновления токена той же личности.

Отпечаток включает нормализованное тело и существенные параметры операции. Сгенерированные сервером время и ID не должны делать одинаковую повторную доставку другим запросом. Хранятся результат и HTTP-статус исходного выполнения, а не заново собранное текущее состояние изменённой заявки.

Важные правила:

- те же субъект, команда, ключ и содержимое возвращают сохранённый результат;
- тот же ключ в той же области с другим допустимым содержимым даёт конфликт, предлагаемый статус — 409;
- другой ключ с тем же текстом создания заявки обозначает отдельную операцию;
- доменные ограничения и права продолжают действовать; ключ их не обходит;
- повтор со старой отозванной сессией не получает сохранённый ответ вместо отказа авторизации;
- ключ, бизнес-записи, история и результат фиксируются одним COMMIT;
- временная ошибка откатившейся попытки не должна навсегда занимать ключ как успешно выполненная команда.

Алгоритм рассчитан на обычные транзакции, уникальное ограничение и стандартные операции реляционной БД. Vendor-specific UPSERT для прикладного протокола не требуется. При ожидаемом конфликте уникальности нельзя предполагать, что после исключения текущая транзакция пригодна к продолжению: переносимый вариант — полный ROLLBACK и чтение сохранённого результата в новой транзакции. Конкретные типы ошибок драйвера преобразуются в нейтральные исключения адаптером.

При двух одновременных запросах один выполняет бизнес-операцию. Второй должен получить её результат после фиксации либо согласованный временный ответ при исчерпании ожидания. Если первая попытка откатилась, одна из следующих может выполнить команду. Максимальное ожидание и внешний статус незавершённой конкурентной операции ещё нужно выбрать.

TTL записи не выбирается произвольно: он должен покрывать согласованный интервал повторной доставки. После удаления записи по TTL прежний ключ больше не обеспечивает защиту от повторного создания. Набор сохраняемых окончательных бизнес-отказов и поведение после истечения TTL требуют отдельного решения.

## 5. Тестирование через OpenAPI / Swagger UI

OpenAPI описывает контракт, а Swagger UI позволяет отправлять запросы по нему. После реализации на выбранных маршрутах заголовок `Idempotency-Key` нужно включить в схему как параметр запроса. Тогда у него появится поле в Swagger UI. Bearer-авторизация настраивается отдельно через `Authorize`.

Последовательная ручная проверка для создания заявки:

1. Авторизоваться синтетической учётной записью, выбрать создание заявки и указать ключ K1.
2. Выполнить запрос, сохранить ID созданной заявки и результат.
3. Повторить тот же маршрут, тело и K1. Получить прежний результат с тем же ID.
4. Через чтение проверить одну пару карточек и отсутствие второго первоначального набора истории.
5. Отправить K1 с другим допустимым телом. Получить согласованный конфликт 409 без новой записи.
6. Отправить исходный текст с новым K2. При выполненных доменных правилах получить вторую намеренную заявку.
7. Проверить повтор после обновления access-токена той же личности и отказ после отзыва сессии.

Swagger UI удобен для последовательности. Для одновременной отправки и обрыва ответа именно после COMMIT нужны автоматические интеграционные проверки с управляемой синхронизацией и отказами. Само повторное нажатие Execute не доказывает отработку неизвестного результата фиксации.

### 5.1. Запросы без ключа

Отправлять часть запросов без ключа можно, если это допускает контракт маршрута. Отдельного исключения для Swagger нет: действуют те же правила, что и для остальных клиентов.

| Маршрут или режим | Поведение без ключа |
|---|---|
| GET и другое обычное чтение | Ключ не требуется |
| Изменяющий маршрут с необязательным ключом | Обычное выполнение без гарантии устранения повторной доставки |
| Маршрут с обязательным ключом | Отказ до выполнения команды; предложенный единый статус отсутствующего/неверного заголовка — 422 |

Предложение для постепенного внедрения — сначала необязательный ключ и тесты обоих вариантов, затем обязательность на выбранных маршрутах после перевода клиентов. Это пока предложение, а не утверждённый перечень обязательных маршрутов. Существенная часть существующих сценариев может тестироваться без ключа при сохранении такого режима; новые регрессии отдельно проверяют гарантии с ключом.

## 6. Кто делает повторы

### 6.1. HTTP-повторы клиента

Клиент обнаруживает потерю ответа, сетевой сбой или согласованный временный отказ. Для поддерживаемой идемпотентной команды он повторяет тот же адрес, данные и ключ. Нужны ограничение числа попыток и общего времени, увеличивающаяся задержка и соблюдение `Retry-After`, если он возвращён сервером.

При неизвестном результате после COMMIT клиент не должен создавать новый ключ для попытки доставки прежней операции. Пользовательская новая операция отличается от повторной отправки и получает собственный ключ.

Предлагаемая классификация:

| Ситуация | Действие |
|---|---|
| Потеря ответа / сетевой таймаут | Ограниченный повтор с тем же ключом на поддерживаемом маршруте |
| 429 или 503 | Повтор только по согласованной политике, с задержкой и учётом Retry-After |
| 400/422 | Исправить данные; не выполнять слепые автоматические повторы |
| 401/403 | Разобраться с сессией/правами; обычный retry не устраняет причину |
| 409: тот же ключ, другое тело | Исправить использование ключа; автоматический повтор не нужен |
| 409: конфликт версии сущности | Перечитать состояние и разрешить конфликт; это другой контракт, чем повтор доставки |
| Неожиданный 500 | Не считать автоматически временным конфликтом; нужна отдельная политика и диагностика |

Обновление access-токена допустимо лишь в рамках действующей сессии. Автоматическое повторение самого refresh после ротации требует отдельного решения; его нельзя включать в общий retry всех POST без проверки протокола.

### 6.2. Внутренний повтор сервера

Сервер может повторить внутреннюю транзакцию, если достоверно известно, что она полностью откатилась из-за временного отказа. Повторяется вся прикладная команда: новая UoW, свежие агрегаты, повторная авторизация и проверка бизнес-условий. Повтор одного SQL или сохранение прежних мутированных объектов не эквивалентны этому.

Такой retry не отвечает на вопрос, получил ли клиент ответ уже успешного COMMIT. Если фиксация была успешной, от повторного исполнения защищает сохранённый результат по ключу. Внешние необратимые эффекты, если появятся, требуют отдельного согласования с транзакцией.

Предложение для первого этапа:

1. Сервер обеспечивает атомарность, идемпотентность и понятные временные отказы.
2. Клиент выполняет ограниченные HTTP-повторы с прежним ключом.
3. Серверные повторы транзакций добавляются отдельным изменением, если необходимость подтверждена.

Если позднее используются оба уровня, у них должен быть согласованный общий бюджет времени и попыток. Независимые неограниченные циклы будут умножать нагрузку. Численные значения бюджета в обсуждении не утверждены.

## 7. Наблюдаемость, прежний пункт 8

Этот раздел описывает предлагаемый минимальный состав. Наличие настроек на сервере ещё не проверялось.

### 7.1. Диагностические логи

Структурированная запись включает время UTC, уровень, request ID, метод, шаблон маршрута, HTTP-статус, длительность и тип ошибки. Служебный ID субъекта добавляется там, где нужен для расследования, с ограничением доступа к логам. Один request ID связывает прокси, приложение и запись об ошибке.

В логах не должны появляться пароли, access/refresh-токены, Authorization, содержимое `.env` и полные тела заявок/комментариев. Маскирование нужно применить и к внешнему сборщику ошибок. Полезное сообщение о типе отказа не требует печати всего доменного агрегата.

Бизнес-история заявки и технический лог решают разные задачи: первая фиксирует действия в системе, второй помогает найти причину сбоя. Лог не заменяет сохранение истории в транзакции.

### 7.2. Живость и готовность

- Проверка живости показывает, что процесс работает. Её не стоит превращать в повод постоянно перезапускать приложение при общей недоступности БД.
- Отдельная проверка готовности подтверждает, что экземпляр способен обслуживать запросы и обращаться к БД. При неготовности предлагается 503, чтобы прокси не направлял на него новые запросы.
- Проверки должны быть лёгкими и не изменять бизнес-данные. Доступ к их диагностическим подробностям ограничивается.

В проверенной версии `/health` подтверждает живость процесса. Полноценная readiness-проверка БД требует отдельной реализации и проверки.

### 7.3. Метрики и уведомления

Нужно наблюдать число запросов, долю и типы ошибок, задержки, состояние соединений/операций БД, память, CPU и свободное место. Для HTTP-метрик предпочтительны шаблоны маршрутов, а не отдельная метка для каждого Ticket ID.

Ожидаемые 400/401/403/409 отделяются от неизвестных 5xx и временных 503. Отдельно полезна динамика неудачных входов. Сам по себе единичный корректный конфликт версии не означает аварию.

Уведомления нужны как минимум при устойчивой недоступности, росте серверных ошибок и недостатке ресурсов. Следует определить получателя, пороги и время реакции. Конкретный стек сбора логов/метрик и численные пороги не выбраны.

### 7.4. Обновление и откат

Процедура выпуска должна указывать версию приложения, порядок развёртывания, проверку готовности после обновления, контроль ошибок и возврат предыдущей версии. Перед развёртыванием выполняется CI на согласованном наборе. После появления миграций отдельно учитывается совместимость схемы с откатываемой версией.

Критерии проверки наблюдаемости: синтетический сбой находится по request ID; ожидаемый отказ отличается от внутренней ошибки; секреты отсутствуют в диагностике; недоступная БД отражается в готовности; тестовый алерт доходит ответственному; процедура возврата версии проверена на стенде. Этот документ не утверждает, что перечисленные проверки уже выполнены.

## 8. Минимальная матрица проверки идемпотентности и повторов

1. Обычное создание с ключом — одна операция и сохранённый результат.
2. Повтор того же ключа и тела — прежний результат, без новых карточек и истории.
3. Обрыв ответа после COMMIT и повтор — результат первой операции.
4. Тот же ключ с другим допустимым телом — 409 без побочных записей.
5. Другой ключ с тем же текстом создания заявки — отдельная заявка.
6. Два одновременных запроса с одним ключом — один бизнес-эффект, согласованный ответ второй попытке.
7. Отказ до COMMIT — откат ключа и бизнес-записей; следующий допустимый повтор способен выполнить команду.
8. Те же ключи у разных субъектов/типов и разных команд не раскрывают чужие результаты.
9. Утрата прав или отзыв сессии между попытками — обычный отказ доступа, а не выдача кешированного результата в обход проверки.
10. Без ключа — поведение соответствует optional/required контракту конкретного маршрута.
11. Истечение TTL — согласованное и явно проверенное поведение.
12. Клиент прекращает повторы по бюджету, сохраняет данные неизвестного результата и не подменяет ключ.

Эта матрица — план будущих регрессий, не отчёт об их выполнении. Механизм ключей и retry не входил в опубликованную серию десяти патчей аудита.

## 9. Что выбрать перед реализацией

| Параметр | Что ещё нужно определить |
|---|---|
| Маршруты идемпотентности | Конкретные команды, обязательность/необязательность заголовка и этап перевода клиентов |
| Срок ключа | TTL, максимальный срок клиентских повторов и поведение после очистки записи |
| Сохранённый ответ | Статус/тело/существенные заголовки, правила для окончательных бизнес-отказов, минимально необходимый состав данных |
| Конкурентный дубль | Максимальное ожидание результата и внешний временный ответ при превышении ожидания |
| Клиентские повторы | Число попыток, общий таймаут, задержки, перечень временных статусов и поведение UI при неизвестном результате |
| Сроки сессии | Access TTL, refresh TTL, абсолютный срок, скользящее продление и очистка |
| Потеря ответа refresh | Допустимое восстановление после уже успешной ротации, без небезопасного повторного использования старого токена |
| Уже исполняемые команды | Граница отзыва относительно запроса, прошедшего авторизацию до изменения аккаунта |
| Мониторинг | Инструменты, хранение и доступ к логам, пороги алертов, ответственные и время реакции |

Открытые параметры нельзя считать утверждёнными только из-за сохранения этого документа. Реализация потребует отдельного задания и проверок выбранного контракта.
