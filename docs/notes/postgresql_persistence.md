Рекомендация основана на чтении кода и документации библиотек. Прогон проекта на PostgreSQL относится к этапу пилота. [Снимок репозитория](https://github.com/tegasae/simple_tickets/commit/f051170d20b15209d52d08dbcb4e7e3989e7aebd)

## Рекомендация

Для текущего Simple Tickets при PostgreSQL как основной СУБД выбрать **синхронный Psycopg 3 с `psycopg_pool`**. Сохранить текущие доменные модели, интерфейсы репозиториев, Gateway, Mapper и контракт `UnitOfWork`. Менять подключение, исполнение SQL, схему и те места маппинга, которые зависят от формата SQLite.

**SQLAlchemy Core** имеет смысл, если SQLite и PostgreSQL должны оставаться полноценными поддерживаемыми режимами либо проекту нужен общий конструктор сложных запросов. **SQLAlchemy ORM** стоит рассматривать отдельным решением для простых CRUD-моделей или при сознательной переработке слоя хранения. Смена СУБД сама по себе такой переработки не требует.

## Почему этот выбор подходит проекту

Прикладные сервисы уже работают через `UnitOfWork`. В нём доступны репозитории заявок, ролей, refresh-сессий и результатов идемпотентных операций. В Gateway хранится параметризованный SQL, а Mapper преобразует строки в доменные объекты. SQLAlchemy ORM добавила бы собственную `Session` с отслеживанием изменений и сохранением связей. Для `Ticket`, `TicketUser` и `Admin` нужно было бы отдельно доказать сохранность существующих правил версий, истории и порядка записи. [Контракт Unit of Work](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/domain/uow/unit_of_work.py#L24-L89) · [BaseRepository](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/adapters/repositories/base_repository.py#L18-L71) · [Сохранение Admin](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/adapters/repositories/admin.py#L124-L176)

| Вариант | Преимущества | Цена и ограничения |
| --- | --- | --- |
| Psycopg 3 напрямую | Явный SQL и прямой контроль соединения и транзакции. Пул доступен через `psycopg_pool`. Существующий подход Gateway и Mapper сохраняется. | Адаптер отвечает за привязку параметров, преобразование типов и перевод исключений PostgreSQL. |
| SQLAlchemy Core поверх Psycopg 3 | `Engine` даёт пул и общий интерфейс соединений. `text()` поддерживает используемый в проекте вид параметров `:name`. SQL-выражения, типы и `MetaData` полезны для совместно поддерживаемых диалектов. | Добавляется зависимость и её API. При использовании `text()` проект по-прежнему отвечает за совместимость текста SQL и за поведение транзакций в каждом диалекте. |
| SQLAlchemy ORM | `Session` отслеживает изменения и идентичность экземпляров. Связи удобно описывать для обычного CRUD. | Для текущих агрегатов потребуется проверить взаимодействие `flush`, каскадов и версионирования с явным сохранением и синхронизацией истории. Это самый большой объём изменения архитектуры. |

## Что нужно адаптировать для PostgreSQL

### Соединение, параметры и схема

В текущем `Connection` при открытии используются `check_same_thread` и `PRAGMA foreign_keys`, а `Query` получает ID через `lastrowid`. Для PostgreSQL нужен отдельный адаптер выполнения. При прямом Psycopg именованные параметры записываются в форме `%(name)s`. Параметры передаются драйверу отдельно от SQL. После INSERT новый ID возвращается явным `RETURNING`. Количество изменённых строк сохраняется в контракте для оптимистической блокировки. [Соединение](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/utils/db/connect.py#L19-L45) · [Получение результата](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/utils/db/query.py#L18-L46) · [PostgreSQL RETURNING](https://www.postgresql.org/docs/current/dml-returning.html)

Схему PostgreSQL нужно подготовить отдельно. Для каждой таблицы проверить типы, порядок создания внешних ключей, ограничения и правила генерации ID. При переносе существующих данных сохранить первичные ключи, связи и истории. Счётчики новых ID должны учитывать максимальный перенесённый ID и достигнутое значение SQLite-последовательности для таблиц, где важна гарантия неповторения ранее выданных ID. Тело действующего идемпотентного ответа лучше сохранить как `TEXT`, чтобы повтор выдавал те же байты. [Текущая схема](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/db/schema.sql) · [Работа с SQLite-последовательностью](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/scripts/migrate_backend_storage.py#L69-L92)

Схему можно вести версионированными SQL-миграциями. Если в проекте нужен отдельный менеджер истории миграций, подходит Alembic. Его можно использовать с явными миграциями без ORM-моделей. SQLAlchemy при этом остаётся зависимостью инструмента миграций. [Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html)

### Границы транзакций

Сейчас зависимость `get_current_admin` читает состояние Admin и Account до входа в бизнес-транзакцию. Psycopg по умолчанию открывает транзакцию даже при `SELECT`. Если после такого чтения на том же соединении начать блок `conn.transaction()`, он может управлять только savepoint внутри уже открытой транзакции. В новом адаптере предварительное чтение должно иметь явную завершённую границу. Вся бизнес-команда, включая запись связанных заявок и ответа для ключа идемпотентности, выполняется на одном соединении в своей транзакции. [Проверка администратора](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/web/dependencies/auth.py#L119-L139) · [Транзакции Psycopg](https://www.psycopg.org/psycopg3/docs/basic/transactions.html)

В существующих сервисах встречаются явные вызовы `uow.commit()`. При проектировании PostgreSQL-адаптера нужно выбрать, кто управляет завершением транзакции, и сохранить контракт `join_transaction` для составных операций. Возврат соединения в пул выполняется после выхода из транзакции. При выборе Core пулом может владеть `Engine`. При прямом Psycopg эту роль выполняет `psycopg_pool`. [Явная фиксация заявки](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/application/services/ticket_service.py#L1236-L1259) · [SQLAlchemy и соединения](https://docs.sqlalchemy.org/en/20/core/connections.html) · [Пул Psycopg](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)

При ошибке PostgreSQL текущая транзакция должна быть корректно откатана перед продолжением работы. Существующий конфликт резерва ключа уже обрабатывается после выхода из ошибочного UoW. При переносе сохранить эту последовательность и сопоставлять ожидаемые конфликты со стабильными кодами SQLSTATE и соответствующими ограничениями. Уникальность логина и конфликт резерва идемпотентности имеют различное поведение на уровне приложения. [Обработка конфликта ключа](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/web/idempotency.py#L138-L165) · [Коды ошибок PostgreSQL](https://www.postgresql.org/docs/current/errcodes-appendix.html)

### Конкурентность и чтение истории

В PostgreSQL при `READ COMMITTED` два последовательных SELECT внутри одной транзакции могут увидеть разные снимки данных. Сейчас корень заявки, статусы и комментарии читаются раздельно. Это требует проверки под конкурентной записью. Там, где нужен целостный снимок, можно выбрать один запрос, согласованный снимок транзакции или блокировку с обоснованным порядком захвата. Решение зависит от конкретной операции. Версионные проверки записей сохраняются. [Чтение агрегата](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/adapters/repositories/ticket_repository.py#L43-L80) · [Изоляция PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html)

Списки заявок стоит измерить отдельно. Сейчас при загрузке каждой карточки выполняются отдельные запросы статусов и комментариев. Для сетевой базы это увеличивает число обменов. При необходимости помочь может пакетная загрузка или отдельная проекция для списка. [Чтение списка](https://github.com/tegasae/simple_tickets/blob/f051170d20b15209d52d08dbcb4e7e3989e7aebd/src/adapters/repositories/ticket_repository.py#L428-L443)

## Пилот и приёмка

Первый сквозной сценарий — создать связанную пару `Ticket` и `TicketUser` с `Idempotency-Key` и сохранить результат одной транзакцией. Он проверяет получение ID, фиксацию, откат и чтение ранее сохранённого ответа. Существующие прикладные интерфейсы и HTTP-контракт служат контрольной точкой.

| Проверка на реальном PostgreSQL | Ожидаемое свойство |
| --- | --- |
| Успешное создание пары и повтор того же ключа | Связи, история и ответ сохранены, заявка создана один раз. |
| Ошибка после первой записи до коммита | Обе части пары и её результат откатываются вместе. |
| Два запроса с одним ключом через разные соединения | Сохраняется одна пара. Повтор возвращает исходный ответ после фиксации либо получает предусмотренный временный отказ. |
| Две записи по одной ожидаемой версии | Конкурирующая запись получает штатный конфликт. История остаётся согласованной. |
| Ротация refresh одновременно со сменой пароля и отзывом | Отозванная сессия не остаётся действующей после завершения операций. |
| Чтение администратора, бизнес-команда, возврат в пул | Бизнес-команда фиксируется собственной транзакцией. Следующий заимствовавший соединение запрос не получает активную или прерванную транзакцию. |
| Чтение заявки на фоне обновления истории | Данные, которые контракт обещает видеть согласованно, берутся из согласованного снимка. |

Если пилот подтверждает небольшой объём замены в адаптерах, продолжать на Psycopg. Переходить к Core имеет смысл, когда пилот показывает повторяющиеся различия между поддерживаемыми СУБД или значимый объём запросов, которые удобнее строить общими SQL-выражениями.
