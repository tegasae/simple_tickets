# Дубликаты запросов и идемпотентность команд

Заметка фиксирует обсуждённую схему защиты от повторной доставки команд для `simple_tickets`. Алгоритм использует обычные `INSERT`, `SELECT`, `UPDATE`, ограничения уникальности и транзакции с `COMMIT` и `ROLLBACK`. Для production планируется PostgreSQL. Описанный порядок рассчитан на реляционные СУБД с транзакциями и уникальными ограничениями.

## Когда возникает дубликат

1. Пользователь заполнил форму и нажал «Создать заявку».
2. Клиент отправил `POST /user/tickets/` с текстом «Не работает принтер».
3. Сервер проверил авторизацию и данные, затем начал транзакцию.
4. Сервер создал пользовательскую карточку `TicketUser`, внутреннюю карточку `Ticket` и начальные записи истории.
5. Сервер выполнил `COMMIT`. Заявка сохранена.
6. Сервер отправил `201 Created` с результатом создания.
7. Соединение оборвалось до получения ответа клиентом. Аналогичный эффект возникает, если истёк таймаут клиента.
8. Пользователь увидел сообщение о неудачной отправке и нажал «Повторить», либо клиент повторил запрос автоматически.
9. Клиент отправил такое же тело запроса.
10. Сервер обработал доставку как новое создание и сохранил вторую пару карточек.
11. Клиент получил ответ второй операции. В базе оказались две заявки на одно намерение пользователя.

Сравнивать заявки только по одинаковому тексту недостаточно. Пользователь может намеренно создать два обращения с одинаковым содержимым.

## Создание заявки с ключом операции

1. Пользователь нажал «Создать заявку».
2. Клиент создал случайный `Idempotency-Key`, например UUID, и связал его с данными этой операции.
3. Клиент сохранил ключ до начала отправки, чтобы использовать его при повторной доставке.
4. Клиент отправил запрос:

   ```http
   POST /user/tickets/
   Idempotency-Key: 72cc57c4-bbd2-4d46-900e-11ece816f664
   Content-Type: application/json

   {
     "text_of_ticket": "Не работает принтер"
   }
   ```

5. Сервер проверил авторизацию, входные данные и область операции.
6. Сервер применил согласованную нормализацию запроса и вычислил хеш его содержимого.
7. Сервер начал транзакцию и выполнил обычный `INSERT` записи ключа. На область операции и ключ действует уникальное ограничение.
8. Вставка прошла. Сервер создал обе карточки заявки и начальную историю.
9. Сервер подготовил сериализованный результат создания с идентификаторами и HTTP-статусом, затем сохранил его в записи ключа.
10. Один `COMMIT` зафиксировал карточки, историю, ключ, хеш запроса и результат.
11. Сервер отправил ответ, но соединение оборвалось.
12. Клиент повторил запрос с тем же ключом и тем же содержимым.
13. Сервер снова проверил доступ и попытался зарегистрировать ключ.
14. База сообщила о нарушении уникальности ключа. Сервер полностью откатил эту попытку и открыл новую транзакцию.
15. Сервер прочитал сохранённую операцию и сравнил хеш запроса.
16. Хеш совпал. Сервер вернул прежний статус `201 Created` и сохранённый результат первоначального создания.
17. Клиент получил результат первой операции. В базе осталась одна пара карточек с одним набором начальной истории.

Возвращается результат первоначального создания. Последующие изменения заявки могут отражаться отдельным запросом её актуального состояния.

## Область ключа и хранимые данные

Ключ определяется в области субъекта и команды. Для команды над существующим объектом область включает его идентификатор. Если система использует несколько организаций с пересекающимися пространствами идентификаторов, в область входит организация.

| Данные | Назначение |
| --- | --- |
| Тип и устойчивый ID субъекта | Отделяют операции разных пользователей и администраторов |
| Код команды | Различает создание заявки, создание клиента, добавление комментария и другие действия |
| Целевой объект | Разделяет команды над разными существующими объектами |
| `Idempotency-Key` | Обозначает конкретную операцию клиента |
| Хеш нормализованного запроса | Проверяет, что повтор относится к тем же данным |
| HTTP-статус и сериализованное тело ответа | Позволяют вернуть сохранённый результат |
| Значимые заголовки ответа | При необходимости сохраняют договорённый контракт ответа, например `Location` |
| Время создания и срок хранения | Определяют окно поддержки повторной доставки |

На сочетание полей области и ключа действует `UNIQUE` или составной первичный ключ. Все поля этого ограничения заполняются. Для создания целевой объект можно представлять согласованным непустым значением области, например `collection`. Использование NULL в составе ограничения требует учитывать различия СУБД в проверке уникальности.

Нормализация должна быть детерминированной. Она учитывает проверенные поля, применённые значения по умолчанию, согласованную обработку пробелов и устойчивый порядок сериализации. Поля, влияющие на смысл команды, входят в вычисление хеша. Серверные даты, случайные ID результата и время повторной доставки вычисляются отдельно от хеша запроса. Изменения правил нормализации нужно согласовать с уже сохранёнными ключами, например через версию формата.

Сохранённый результат выдаётся после проверки действующего доступа к соответствующей операции. Включение субъекта в область ключа дополняет авторизацию.

## Переносимая обработка конфликта

1. Начать транзакцию.
2. Зарегистрировать ключ обычным `INSERT` до создания сущностей и истории.
3. При успешной вставке выполнить команду, записать её результат и выполнить `COMMIT`.
4. При подтверждённом нарушении уникальности именно ключа идемпотентности полностью выполнить `ROLLBACK`.
5. Открыть новую транзакцию и прочитать операцию по её области и ключу.
6. При совпадающем хеше вернуть сохранённый ответ.
7. При другом хеше вернуть `409 Conflict` с указанием, что ключ уже использован для другой команды с данными в той же области.

Прикладной сервис может опираться на общий класс ошибки:

```python
class IdempotencyKeyAlreadyExists(Exception):
    pass
```

Адаптер репозитория преобразует нарушение соответствующего уникального ограничения в этот класс. Другие нарушения целостности, недоступность соединения, взаимная блокировка и таймаут сохраняют свои причины. После ошибки всегда откатывается вся попытка, а чтение сохранённого результата начинается в новой транзакции.

Типы исключений и сведения о нарушенных ограничениях зависят от Python-драйвера. Их распознавание находится внутри адаптера. Прикладной алгоритм использует общий контракт репозитория и Unit of Work. SQL этой схемы обходится перечисленными стандартными операциями.

## Два запроса с одним ключом пришли одновременно

1. Запрос А начинает транзакцию и вставляет запись ключа.
2. Запрос Б начинает свою транзакцию и пытается вставить такую же область и ключ.
3. База разрешает конкуренцию за уникальную запись. В зависимости от её реализации и настроек запрос Б может ожидать завершения А или получить временную ошибку конкуренции.
4. Запрос А создаёт заявку, историю и результат, затем выполняет `COMMIT`.
5. При подтверждённом конфликте уникальности запрос Б делает `ROLLBACK`.
6. Запрос Б читает зафиксированный результат в новой транзакции, сверяет хеш и возвращает ответ.
7. Если запрос А откатился, его ключ, карточки и история тоже откатились. Следующая допустимая попытка вставить ключ сможет выполнить команду.

Ожидание блокировки ограничивается настройками сервиса. Временный отказ из-за блокировки требует отдельной обработки и при необходимости повторной доставки с прежним ключом. Вывод «операция уже выполнена» делается после чтения её сохранённого результата.

Проверка `SELECT` перед вставкой может служить оптимизацией для уже выполненных запросов. Она оставляет гонку для двух одновременных доставок, поэтому уникальное ограничение остаётся обязательным.

## Откат и неопределённый результат COMMIT

Если выполнение команды завершилось ошибкой до успешной фиксации, транзакция откатывает запись ключа вместе с остальными изменениями. Для следующей попытки создаются свежая транзакция и доменные объекты. Ранее использованные Python-объекты могли сохранить присвоенные ID или увеличенные версии в памяти.

Если соединение потеряно во время `COMMIT`, клиент и приложение могут получить неопределённый исход. Повтор с тем же ключом позволяет запросить результат через новую попытку. Уже зафиксированная запись ключа приводит к возврату прежнего результата. Откатившаяся транзакция допускает новое выполнение. Правило единственного ключа и атомарной фиксации сохраняется в обоих случаях.

Запись успешного результата находится в той же транзакционной БД, что сущности и история. Отдельный кэш с ключами не даёт этой гарантии атомарности. Внешние действия, например отправка уведомления, требуют отдельной гарантии доставки. Один из подходов — запись задания на отправку в ту же транзакцию и последующая обработка с защитой от повторов у получателя.

## Правила клиента и срок хранения

- Новая намеренная операция получает новый случайный ключ.
- Повтор после таймаута или сетевой ошибки использует прежний ключ и прежние данные.
- Двойной щелчок во время отправки привязывается к одной уже начатой операции.
- Для повторов после перезагрузки страницы ключ и данные ожидающей операции сохраняются локально.
- Два намеренных создания с одинаковыми полями и разными ключами выполняются отдельно.
- Изменение данных после уже выполненной операции требует нового ключа.
- Повтор с прежним ключом и изменённым телом в той же области возвращает конфликт.

TTL выбирается по допустимому периоду повторов клиента и стоимости хранения результата. Например, при договорённом окне 24 часа запись ключа хранится как минимум весь этот период. Число 24 часа иллюстрирует настройку, фактический срок для проекта предстоит утвердить.

После удаления записи из-за истечения срока прежний ключ может снова привести к выполнению команды. Клиент и сервер должны согласовать допустимость поздних повторов. Очистка работает с завершёнными записями и учитывает одновременную обработку запросов.

## Применение к другим сущностям

| Команда | Последствие повторного выполнения |
| --- | --- |
| Создание Ticket, Client, User, Admin, Department, Role | Дубликат сущности или конфликт уникальности после фактически успешного запроса |
| Добавление комментария | Дополнительная запись в истории |
| Регистрация выполненной работы | Повторное начисление времени |
| Назначение исполнителя или смена статуса | Дополнительный переход, уведомление или отказ после успешного первого выполнения |
| Отправка сообщения или внешней команды | Повторное внешнее действие |

Установка `enabled=false` идемпотентна по конечному состоянию. Если каждый вызов ещё увеличивает версию, добавляет историю или отправляет уведомление, эти последствия тоже учитываются в контракте повтора. Для команды «добавить время» каждое выполнение увеличивает накопленное значение.

Для проекта приоритет защиты от повторов относится к созданию заявок и регистрации работы. Затем можно расширить механизм на другие создающие команды и комментарии. Уникальные бизнес-ограничения, например уникальность логина, продолжают защищать собственные инварианты.

## Приёмочные проверки будущей реализации

1. Оборвать доставку ответа после успешного `COMMIT`, повторить тот же ключ и подтвердить одну пару карточек, один набор начальной истории и прежний результат.
2. Одновременно отправить два одинаковых запроса с одним ключом через разные соединения. Проверить единственный результат выполнения.
3. Отправить один ключ с разными телами в одной области. Получить конфликт без дополнительных изменений.
4. Отправить одинаковые тела с разными ключами. Подтвердить два намеренных создания.
5. Прервать выполнение между регистрацией ключа и записью результата. Проверить полный откат и возможность следующей попытки.
6. Повторить запрос после перезапуска процесса и прочитать результат из БД.
7. Проверить изоляцию областей разных субъектов, команд и целевых объектов.
8. Проверить временную блокировку отдельно от конфликта уникальности и сохранить прежний ключ при повторной доставке.
9. Проверить очистку по TTL, повтор до истечения срока и согласованное поведение позднего повтора.
10. Подтвердить актуальную авторизацию при выдаче сохранённого результата.
