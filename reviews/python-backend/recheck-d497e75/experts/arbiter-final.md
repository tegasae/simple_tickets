## 1. Принятые оставшиеся дефекты

### F1 — P1: отключение клиента блокируется активной работой и заявкой на проверке

`src/domain/services/client_service.py:226–247` отдельно обходит все открытые Ticket и TicketUser и безусловно приостанавливает их. `src/application/services/client_service.py:177–192` получает Ticket через `get_open(client_id)`, SQL выбирает `date_finished IS NULL` (`src/adapters/repositories/gateways/ticket_gateway.py:58–69`). AT_WORK и READY_FOR_REVIEW открыты, но в `src/domain/statuses/rules/ticket_status_transition.py:76–96,113–119` отсутствует переход SUSPENDED.

Три эксперта согласованно получили HTTP 400 и неизменные данные новым соединением; покрыты отдельная внутренняя заявка и связанная пара. Достижимость — обычные create/accept/assign/start-work или start-remote-work, затем finish-work для второй ветви, затем `PATCH /admin/clients/{id}/disable`. Отказ одной заявки откатывает всё отключение: клиент и пользователи остаются включёнными. Это прежний дефект, файлы ClientService и внутреннего графа побайтно совпадают со старым checkout.

Строка 147 автора однозначно требует при отключении клиента READY_FOR_REVIEW → SUSPENDED. Требование ещё не реализовано во внутреннем графе. Строка 148 реализована: внешний SUSPENDED терминален, восстановление не нужно. Вход WAITING_FOR_CONFIRMATION → SUSPENDED существовал уже раньше: называть его новым исправлением неверно.

Для AT_WORK собственный контракт ClientService (`:52–80`) обещает продолжение работы. **Просто добавить skip в первый цикл недостаточно:** второй цикл всё равно закроет соответствующий IN_WORK TicketUser. Нужно принимать решение на связанную пару и исключить обе стороны продолжающейся работы. Нельзя буквально применить старый патч 12: тот сохранял READY_FOR_REVIEW до продуктового решения, которое теперь изменено автором.

### F2 — P1: успешное отключение пользователя теряет сохранение внешней карточки

`src/domain/services/user_service.py:373–398` создаёт пустой `changed_ticket_users`, вызывает `sync_from_ticket(ticket, ticket_user)`, но не добавляет изменённую карточку в результат. `src/application/services/user_service.py:480–493` сохраняет только возвращённые агрегаты. Через `PATCH /admin/users/{id}/disable` пары CREATED/CREATED_FROM_TICKET_USER и ACCEPTED/IN_WORK становятся SUSPENDED/CREATED либо SUSPENDED/IN_WORK при HTTP 200. Пользователь отключён; внешние история, версия и date_finished не меняются. Повтор 200 не чинит пару, потому что внутренний терминальный Ticket уже исключён из отбора. Независимые SQL-чтения и GET коллеги той же организации подтверждают эффект. Этот код также побайтно совпадает со старым checkout: исправление не применено.

Отдельная ветвь того же каскада: `_should_suspend` (`:435–448`) пропускает AT_WORK и терминальные статусы, но включает READY_FOR_REVIEW. Запрос тогда получает 400 из того же отсутствующего перехода, что F1, и отключение пользователя откатывается. Объединять этот отказ с потерей записи нельзя: первый — атомарный отказ, второй — успешная несогласованная фиксация. Автор прямо определил READY_FOR_REVIEW для отключения клиента; распространение правила на отключение владельца/контактного пользователя нужно закрепить отдельно, не придумывая восстановление SUSPENDED.

### F3 — P2: известные ошибки ввода всё ещё попадают в общий 500

Три независимых прогона подтверждают четыре входа: пробельный текст в обоих POST заявки, пробельный обычный комментарий пользователя и `GET /admin/departments/-1`. `TextOfTicket` и `CommonComment` обрезают пробелы и выбрасывают ValueError (`src/domain/value_objects.py:243–296`), тогда как HTTP-ограничения проверяют другие длины (`src/web/models/tickets.py:24–38`, `src/web/models/tikcets_user.py:16–44`). `DepartmentDTO` выбрасывает базовый ApplicationValidateError (`src/application/dto/department_dto.py:9–21`), но таблица HTTP регистрирует только дочерний TicketInputValidationError (`src/web/main.py:59–83`, `src/application/exceptions.py:20–25`).

В результате ошибка клиента выглядит как серверный сбой. Частичная запись не установлена, корректные операции работают; принимаю P2, а не первоначальный P1 QA. Старое общее замечание об ошибках исправлено частично. Не следует переводить любой ValueError из любого слоя в 400: нормализовать и проверять вход на границе либо преобразовать конкретные известные исключения.

### F4 — P2: ожидаемый 400 содержит целый агрегат заявки

`src/domain/ticket.py:406–415` включает `self` в сообщение отказа перехода. `src/web/execeptions/exception_handlers.py:120–136` передаёт `str(exc)` для ожидаемой ошибки, поэтому detail содержит текст, описание, ID, историю и комментарии. Это подтверждено на штатной авторизованной операции; межорганизационная утечка не доказана и здесь не заявляется. Форматирование существовало раньше, прежний общий 500 тоже раскрывал его. После исправления общего 500 этот отдельный канал ожидаемой ошибки остался. Исправление: короткое сообщение с ID и исходным/целевым статусами; аналогично сократить представление статусной записи TicketUser (`src/domain/ticket_user.py:356–369`).

### F5 — P2 для контракта схемы: default срочности не читается приложением

`db/schema.sql:135` задаёт `urgency_level INTEGER NOT NULL DEFAULT 0`, mapper в `src/adapters/repositories/mappers/ticket_mapper.py:64–78` вызывает строковый TicketUrgency; допустимы normal/urgent/maintenance. SQL-вставка с умолчанием и корректной историей проходит FK, затем GET даёт 500. Штатный POST явно пишет enum и не затронут. Дефект присутствовал в прежнем DDL/mapper; это новое подтверждение, не регрессия. Пересоздание учебной БД не устранит несовместимый default: нужен согласованный строковый тип/default и, при необходимости, CHECK. Количество существующих таких строк неизвестно, инвентаризация реальной БД не проводилась.

Отдельно `src/adapters/repositories/gateways/ticket_gateway.py:163–168` содержит EXISTS_BY_ADMIN_ID с отсутствующим `tickets.admin_id`. Подготовка этого SQL не проходит, но активное удаление администратора проверяет другие ссылки (`ticket_repository.py:385–404`). Это P3 неиспользуемой константы/контрактного набора, не поломка рабочего DELETE.

### F6 — P2: обычный комментарий при создании за пользователя приписывается владельцу

Административное создание передаёт комментарий в TicketUser.create; `src/domain/ticket_user.py:116–124` безусловно использует employee_id=user_id. Внутренняя карточка пишет фактического администратора. Разные ID подтверждены SQL. Фабрика побайтно совпадает со старым checkout, однако прежняя поломка сохранения комментария могла не позволять завершить этот POST. Это ранее скрытый дефект атрибуции, а не доказанная новая регрессия. Для обычного комментария фактический источник должен сохраняться. Для начального статуса CREATED (`:108–112`) ещё надо определить смысл актора: владелец заявки либо инициатор создания. Не подменять этим вопросом уже установленную потерю автора комментария.

### F7 — P2 устойчивости/контракта: временная занятость SQLite остаётся общим 500

Воспроизводимый опыт Python: один писатель удерживает транзакцию, обычный POST второго соединения падает на первом touch до проверки rowcount/CAS. `src/adapters/repositories/base_repository.py:46–95` оборачивает причину в PersistenceError, HTTP даёт общий 500. Запись откатывается, после снятия блокировки свежий повтор успешен. Это было отдельно отмечено в старом аудите, не опровергает исправление COMMIT. Требуется сохранить код SQLite, утвердить временный ответ/timeout и политику повтора всей команды на свежем снимке. Обязательный конкретный код 409 либо 503 из нынешнего требования не следует. Два успешных конкурентных обновления, потерянная запись или дубликат не доказаны.

## 3. Требование о токенах и условные вопросы

**Постоянное refresh-хранилище не реализовано.** Строка 159 — явный запрос, а не гипотетическое пожелание эксперта. Есть TokenStorageMemory и абстрактный TokenStorage; dependencies (`src/web/dependencies/auth.py:39–40`) жёстко используют память. Нужны обе реализации и выбор backend. Два имени в DI указывают на один singleton на процесс (`src/web/auth/storage.py:68–88`), а не два изолированных storage; первый Python-отчёт исправил это во втором раунде. Realm-проверки предотвращают вывод о смешении доступов только из singleton. При рестарте refresh пропадает, разные процессы не делят сессии; фактическое число production worker не устанавливалось. Cleanup определён, вызовов в src нет, поэтому истёкшие невостребованные записи накапливаются до рестарта. Для постоянной реализации нужен TTL и атомарная ротация; пока отсутствие атомарности — задача контракта, а не доказательство двух успешных refresh при гонке. Проверка refresh по username с выпуском по сохранённому ID требует защитной проверки идентичности при смене/переиспользовании логина, но реализованная атака или затронутые данные не заявляются.

**Терминальность и старые данные.** На новой DDL успешный disable → enable → disable больше не ломается из-за внешнего SUSPENDED. Старый SUSPENDED с date_finished=NULL синтетически воспроизводит отказ, потому что SQL считает строку открытой, а гидратированный объект терминален. Наличие таких строк неизвестно; автор разрешил пересоздать учебные данные. Это условная совместимость, не обязательная миграция и не новая регрессия обычного нового жизненного цикла.

**Контакты.** Нулевой административный контакт разрешён схемой HTTP, но для связанной заявки обязателен положительный; пользовательский 0 означает владельца. Исходная потеря контакта устранена. Симметрию этих API нельзя вывести без решения автора. После ACCEPTED внутренний Ticket допускает изменение данных, внешний IN_WORK запрещает, и смена контакта откатывается с 400. Это установленное пересечение правил, не доказанный обход или потеря записи. Если нужно редактирование принятой пары, утвердить его для обеих карточек.

**Кардинальность.** Обратное чтение ожидает один Ticket на TicketUser, FK не обеспечивает UNIQUE. Штатное HTTP-создание всегда выдаёт новую внешнюю карточку, путь к дублю не установлен. Если один-к-одному объявляется инвариантом хранения, добавить UNIQUE для положительной ссылки, сохранив несколько самостоятельных NULL; сейчас это условное усиление схемы.

**Повторы.** Повтор назначения и комментария добавляет историю, повтор финального перехода отвергается. Отсутствие idempotency key само по себе не дефект без требования. Повтор после доказанного rollback и повтор после потери уже успешного ответа — разные контракты. После rollback нельзя считать присвоенные ID/версии старых объектов восстановленными; повторять на свежем снимке.

## 4. Достоверность тестов

Моё первичное наблюдение о несовместимом tests_pyramid подтверждено: `unit/domain/test_domain_services.py:10–15` импортирует удалённые классы/модули; веб-набор импортирует отсутствующий `src.web.models.mappers`; часть фикстур/сигнатур и перечень маршрутов устарели. Корневой pytest.ini указывает tests, run_pyramid.sh — tests_pyramid. Это P2 качества проверки, а не доказательство множества новых продуктовых регрессий. Использовать обход app.routes как единственное доказательство отсутствия endpoint в актуальном FastAPI нельзя; HTTP/OpenAPI у коллег обнаруживают 83 пути.

Координатор сообщил результаты во временной среде: старые целевые проверки **37 из 39**, пирамида **46 passed / 104 failed / 15 errors**. Принимаю их как результаты координатора, не моего запуска. Эти числа нельзя сравнивать со старым архивным прогоном как процент регрессии: менялись интерфейсы и совместимость тестов, часть ошибок возникает при сборке. Два непрошедших старых теста — `test_client_disable_preserves_in_progress_and_review_pairs` и `test_user_disable_keeps_review_and_saves_linked_suspension`: оба относятся к оставшимся каскадам. При этом старое ожидание сохранения клиентского READY_FOR_REVIEW уже не соответствует строке 147 автора, поэтому первый тест требует обновления ожидания, а не возврата к прежней спецификации. Новые целевые регрессии на момент поручения арбитража ещё проверялись. Не заявляю полного зелёного прогона или уже сохранённого в репозитории нового тестового набора. В моём доступном первичном Python pytest отсутствовал.

## 5. Порядок исправлений и критерии приёмки

1. **F1 и F2, одним согласованным решением на пару.** Вернуть изменённый TicketUser в UserDisableResult. Для клиента сохранить обе карточки AT_WORK/IN_WORK, если действует нынешний контракт продолжения работы; добавить согласованный переход READY_FOR_REVIEW → SUSPENDED. При отключении владельца отдельно закрепить судьбу проверки. Не снимать терминальность SUSPENDED и не включать автоEXECUTED. Регрессия на чистой DDL: две команды disable, состояния CREATED, ACCEPTED/IN_WORK, AT_WORK, READY_FOR_REVIEW, терминальная пара, самостоятельная заявка и другой клиент. Независимым соединением проверить флаги клиента/сотрудников/аккаунтов, обе истории, статусы, версии и date_finished; свежими GET — open/closed. Повтор, enable и новый disable не добавляют лишних переходов и не восстанавливают терминальные карточки. Сохранённая AT_WORK должна успешно пройти последующий finish-work. Сбой второго save должен откатить обе стороны и флаги.
2. **F3/F4 и актуальный узкий CI.** Параметризованные HTTP-проверки четырёх некорректных входов дают согласованный 4xx без изменений БД; ни detail, ни error_type не содержат repr заявки/комментариев. Неожиданная ошибка остаётся общим 500. Обновить удалённые импорты/фикстуры, задавать синтетический ключ до импорта, строить БД буквально из DDL, проверять HTTP/OpenAPI, передавать ненулевой статус при ошибке сбора. Старые целевые тесты сохранить вместе с новыми регрессиями, явно указав версии и команды.
3. **Постоянный token backend по строке 159.** Контракт обеих реализаций: выдача и штатный refresh своей синтетической сессии, TTL/очистка, перезапуск, два экземпляра одного storage, отказ записи и атомарная однократная ротация. Защитно закрепить subject_id + subject_type и изоляцию отзыва; авторизация только в согласованных защитных проверках, без воспроизведения обходов.
4. **F5/F6 и документация.** Literal executescript, foreign_key_check, подготовка всех gateway SQL, вставка с default urgency и чтение штатным mapper/GET. Для комментария создать заявку администратором с иным user_id и проверить реального автора нового комментария в обеих историях. Исправить OpenAPI finish-work; два отдельных жизненных цикла завершаются через confirm и execute, после finish-work остаются на проверке.
5. **F7 и устойчивость.** Разделить три теста: удержанный reader срывает COMMIT и после rollback позволяет повторный вход того же соединения со свежими объектами; удержанный writer срывает первый touch и после снятия блокировки свежая команда сохраняет ровно одну пару; ошибка сборщика прикладного DTO откатывает корни/истории/зависимые версии. Отправку результата после commit проверять отдельно согласно будущей идемпотентности. Не добавлять слепой повтор после любого 500.

Приоритеты основаны на достижимости и последствиях: сначала штатные команды, которые не отключают клиента либо фиксируют рассогласованную пару; затем оставшаяся ошибочная классификация и достоверность проверок. Неразрешённые продуктовые вопросы и неизвестные параметры развёртывания не превращены в доказанные уязвимости.
