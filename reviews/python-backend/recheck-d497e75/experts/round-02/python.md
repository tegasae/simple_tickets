## Уточнения к первому раунду

- **Терминальность и старые строки.** На новой БД после успешной приостановки и включения клиента синтетически вернул `user_tickets.date_finished` к `NULL` при сохранённом статусе `SUSPENDED`. Это значение соответствует прежней нетерминальной модели. Следующее обычное отключение клиента вернуло 400 «TicketUser … is in terminal status suspended», снимок SQLite не изменился. Для бизнес-операции старая строка открыта по SQL и закрыта после восстановления. Вывод условен для сохранённых учебных БД. Автор указал пересоздание данных, поэтому обязательность миграции отсюда не следует. ## Какие регрессии дадут наиболее надёжный результат

1. Один параметризованный жизненный цикл через штатные API на свежей DDL. Для клиента в одной фикстуре держать связанную пару в `CREATED`, пару в `AT_WORK` и пару в `READY_FOR_REVIEW`. После отключения проверять оба статуса, дату завершения, обе истории, версии и флаги отдельным соединением. Для `AT_WORK` проверять сохранение обеих открытых карточек, если действует правило продолжения работы. Для `READY_FOR_REVIEW` ожидание по решению автора — обе карточки `SUSPENDED`. Повтор не должен добавлять новый переход, повторное включение не должно возвращать открытость. Отдельно вызвать пользовательский каскад для `CREATED` и `ACCEPTED`, считать историю и проверить обе карточки после повторного запроса.
2. Два теста с блокировкой SQLite. Читающее соединение с коротким таймаутом срывает `COMMIT`. Проверить очищенную транзакцию, неизменность БД и возможность повторного входа на том же соединении с заново загруженными агрегатами. Пишущее соединение срывает повышение блокировки при обычном HTTP-запросе. Полный повтор на свежем снимке должен сохранить ровно одну пару, если первая транзакция гарантированно откатилась. Повтор после потери уже успешного ответа следует тестировать отдельно при наличии согласованной идемпотентности.
3. Контракт схемы делать на `executescript` из репозитория, с `foreign_keys=ON`, подготовкой всех gateway SQL и проверкой фактических значений default. Для связи `tickets.user_ticket_id` FK подтверждён, уникальность ID сама схема не обеспечивает. Если связь один-к-одному обязательна, регрессия должна принимать две самостоятельные строки с `NULL` и отклонять повтор одной положительной ссылки. Для внешней ошибки проверять код и короткий `detail` без текста заявки, а для успешных команд проверять полный результат после закрытия первого соединения.
