## Что принимаю

- **P1, два прежних сбоя отключения.** Наличие `AT_WORK` или `READY_FOR_REVIEW` блокирует отключение клиента с HTTP 400. QA подтвердил это на отдельной заявке, Python и аналитический прогон — на паре. Отключение владельца в `CREATED` или `ACCEPTED` может дать 200 с закрытым `Ticket` и открытым `TicketUser`. Повтор 200 сохраняет разъезд. Отдельное отключение владельца при `READY_FOR_REVIEW` тоже возвращает 400. При исправлении `AT_WORK` нужно исключить обе стороны пары из приостановки, если действует правило продолжения работы. - **Терминальность исправлена.** В `89498c8` уже существовал вход `WAITING_FOR_CONFIRMATION → SUSPENDED`. Текущая правка закрывает внешний статус и убирает его исходящие переходы. Принимаю синтетический тест Python для сохранённой строки `SUSPENDED` с `date_finished=NULL`: каскад выберет её как открытую по SQL, агрегат отвергнет повтор. Наличие таких строк не установлено. Решение автора пересоздавать учебные данные сохраняется. Старый патч 12, который оставлял `READY_FOR_REVIEW`, расходится с новым правилом отключения клиента. Ответ 400 при неверном переходе содержит представление всей заявки. Установленный факт относится к ответу штатному авторизованному актору. ## Что остаётся решить или проверить

1. **Отключение.** Правило автора однозначно для `READY_FOR_REVIEW` при отключении клиента. Уточнить его применимость к отключению одного владельца или контактного пользователя и подтвердить продолжение `AT_WORK`, как указано в домене. На свежей схеме провести через штатное API смешанный набор, где есть отдельная заявка, связанные `CREATED`, `ACCEPTED`, `AT_WORK`, `READY_FOR_REVIEW`, терминальная пара и контрольный клиент. При отключении и повторе сверять отдельным соединением и свежими GET обе истории, `date_finished`, версии, аккаунты и списки. Для сохранённой активной работы вызвать следующий `finish-work`. После включения проверить, что терминальные пары остаются закрыты.
2. **Контакты, история и повторы.** Исправление первоначального разъезда подтверждено. Асимметрия нуля и 400 для изменения контакта принятой пары характеризуют нынешний контракт. Считать их новыми регрессиями оснований нет. Нужны решения о сбросе контакта администратором и редактировании принятой пары, об отображении автора при создании за пользователя, о повторах назначения и комментария. Потеря фактического автора обычного комментария наблюдается после исправления его сохранения. Проверить создание с разными ID владельца и сотрудника, затем чтение поля автора из обеих историй. Закрепить раздельные развилки `confirm` и `execute` после `finish-work` и убрать обещание автоисполнения из OpenAPI.
3. **Схема, ответы и тесты.** На чистой SQLite с FK проверить фактическое умолчание срочности и чтение строки через HTTP. Устаревшую SQL-константу проверить отдельно от живых маршрутов. Если утверждена связь один-к-одному, проверить отклонение дублированной ссылки при допустимых самостоятельных строках с NULL. Двумя соединениями закрепить rollback на `COMMIT` и результат повторного HTTP после гарантированного rollback при `SQLITE_BUSY`. Согласовать код временного отказа и 4xx для ожидаемого ввода. Для воспроизводимого прогона обновить устаревшие импорты и фикстуры веб-пирамиды, готовить базу из опубликованной DDL и проверять маршруты через HTTP и OpenAPI.
4. **Постоянное хранилище refresh.** Согласовать срок сохранения сессий после перезапуска, очистку истёкших записей и однократность обновления. После реализации проверить обычный вход и обновление собственной синтетической сессии после повторного запуска, общую видимость сессии для двух экземпляров и атомарное завершение ротации при отказе записи. Просмотр исходников не доказывает отзыв уже выданного access-токена.
