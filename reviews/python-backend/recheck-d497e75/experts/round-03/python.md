## Что принимаю

- **P1, оба каскада.** Отключение клиента блокируется заявками в `AT_WORK` и `READY_FOR_REVIEW`. Это доказано для отдельной и связанной карточек. Для отдельного пользователя `READY_FOR_REVIEW` аналогично блокирует команду. При допустимой приостановке пользователя возникает более скрытая поломка. HTTP 200 отключает пользователя и закрывает внутренний `Ticket`, но забывает сохранить изменённый `TicketUser`. Повтор сохраняет рассогласование. Оба дефекта уже существовали в `89498c8`. [Каскад клиента](../../../../../src/domain/services/client_service.py#L226-L247) · [Каскад пользователя](../../../../../src/domain/services/user_service.py#L352-L448) · [Внутренний граф](../../../../../src/domain/statuses/rules/ticket_status_transition.py#L76-L125)
- **Решения автора применены частично.** `TicketUser.SUSPENDED` действительно стал терминальным. `WAITING_FOR_CONFIRMATION → SUSPENDED` был разрешён и ранее. Авторское требование приостановить внутреннюю заявку из `READY_FOR_REVIEW` при отключении клиента осталось без перехода. `finish-work` оставляет пару на проверке даже с правом `TICKET_EXECUTED`, отдельные `execute` и пользовательское подтверждение закрывают пару. Устаревший текст автоисполнения остался в сервисе и описании модели OpenAPI. - **P2, ошибки и хранение.** Принимаю общий приоритет P2 для подтверждённых ошибок некорректного ввода. Пробельные тексты заявок, пробельный комментарий и отрицательный ID отдела дают общий 500. Штатная ошибочная команда перехода отдаёт весь `repr` заявки в 400. Доказана избыточность ответа авторизованному сотруднику. Срочность в HTTP исправлена, но прежний числовой default 0 в DDL даёт 500 при чтении допустимой SQL-вставки. Устаревший `EXISTS_BY_ADMIN_ID` воспроизводится в подготовке SQL и не используется рабочим маршрутом удаления. ## Что оставляю вопросом

- Запись контакта в обе карточки при создании и ожидаемых ранних правках исправлена. Административный ноль для связанной пары и запрет менять контакт в `ACCEPTED / IN_WORK` имеют наблюдаемую, но продуктово неоднозначную семантику. Потерю фактического автора обычного комментария при создании сотрудником считаю установленной. Для поля актора внешнего `CREATED` ещё нужно согласовать, хранит оно владельца или исполнителя действия. [Смена контакта](../../../../../src/application/services/ticket_service.py#L324-L370) · [Правило IN_WORK](../../../../../src/domain/statuses/ticket_user_status.py#L49-L59) · [Начальная история](../../../../../src/domain/ticket_user.py#L99-L124)
- Старое `SUSPENDED` с `date_finished=NULL` синтетически доказано как блокер повторного клиентского каскада. Вывод относится к сохранённым данным прежнего формата. Для пересоздаваемых учебных БД миграцию не считаю требованием. FK `tickets.user_ticket_id` присутствует. Уникальность положительной ссылки нужно закрепить отдельно, если один-к-одному считается инвариантом базы. Штатный HTTP-путь создания дублирующих связей не установлен. [SQL отбора](../../../../../src/adapters/repositories/gateways/ticket_user_gateway.py#L30-L39) · [Восстановление](../../../../../src/domain/ticket_user.py#L145-L169) · [FK](../../../../../db/schema.sql#L123-L154) · [Обратный поиск](../../../../../src/adapters/repositories/ticket_repository.py#L126-L141)
- Два успешных назначения и два комментария добавляют историю. Повтор уже состоявшегося закрывающего перехода получает 400. Идемпотентность и класс временного HTTP-ответа при `SQLITE_BUSY` следует определять для конкретных команд. Результат о занятой SQLite не доказывает необходимость повторять запрос после успешной фиксации с потерянным ответом. Поведение списков со старыми строками и число затронутых записей остаются непроверенными.

## Точные оставшиеся проверки

1. Параметризованный HTTP-сценарий `disable client` и `disable user` на SQLite, созданной из опубликованной DDL. Покрыть `CREATED`, `ACCEPTED / IN_WORK`, `AT_WORK`, `READY_FOR_REVIEW`, закрытую пару и отдельную контрольную организацию. Через отдельное соединение проверить `clients.enabled`, `employees.enabled`, `accounts.enabled`, оба текущих статуса, обе истории, версии и `date_finished`. Подтвердить продолжение и последующее завершение `AT_WORK`, если сохраняется правило докстринга. Для клиента ожидание автора в `READY_FOR_REVIEW` — обе карточки `SUSPENDED`. Для отключения конкретного владельца ожидание в этом состоянии ещё нужно утвердить. Повтор и включение должны подтвердить терминальность, повторный запрос должен проверять число переходов отдельно от версии корня.
2. Три самостоятельные транзакционные регрессии. Читающее соединение вызывает ошибку `COMMIT` и проверяет возможность повторного входа на том же соединении с заново загруженными объектами. Пишущее соединение вызывает временный отказ в HTTP-команде, после снятия блокировки свежий повтор сохраняет ровно одну пару и один набор дочерних записей. Инъекция ошибки сборщика DTO подтверждает откат двух корней, историй и изменений связанных версий. Сбой отправки уже зафиксированного результата проверяется отдельно по согласованному контракту повтора.
3. Контракт схемы поднимает чистую БД с FK и готовит все gateway SQL. Отдельно тестирует умолчание срочности через вставку и обычный GET, а также дубли положительной ссылки при решении про уникальность. HTTP-регрессия проверяет согласованные 4xx без текста заявки в `detail` и OpenAPI-описание `finish-work`. Существующий веб-набор требует привести импорты и фикстуры к действующему API до использования его результата как сигнала. Если появится постоянный refresh backend, его контракт проверяют на перезапуске между выдачей и штатным refresh, с двумя экземплярами, TTL и целостностью ротации.
