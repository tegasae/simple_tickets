# Раунд 3. Заключение QA Python и FastAPI

Сверил полные отчёты аналитика, Python-разработчика и QA за второй раунд. Сохраняю два P1 из старого аудита: отключение клиента блокируется при `AT_WORK` и `READY_FOR_REVIEW`, отключение пользователя с открытой заявкой возвращает 200 и оставляет пару рассогласованной. Для клиента подтверждение есть с парой и с отдельной внутренней заявкой. Для пользователя повторная команда не чинит пару. Принимаю уточнение коллег: переход `WAITING_FOR_CONFIRMATION → SUSPENDED` уже был, исправление состоит в терминальности внешнего `SUSPENDED`. Решение автора о приостановке заявки на проверке при отключении клиента ещё не реализовано во внутреннем графе. Сценарий с сохранённым старым статусом `SUSPENDED` и пустой датой доказан только на синтетических данных. Пересоздание учебной БД снимает вопрос обязательной миграции. [Клиентский каскад](../../../../../src/domain/services/client_service.py#L226-L247) · [Пользовательский каскад](../../../../../src/domain/services/user_service.py#L352-L398) · [Внешний граф](../../../../../src/domain/statuses/ticket_user_status_transitions.py#L34-L70)

Принимаю P2 для валидируемых входов, которые дают 500: пробельный текст в двух POST, пробельный комментарий и отрицательный ID отдела. Общий текст 500 исправлен. Полный `repr` заявки в 400 остаётся дефектом публичного ответа при обычной авторизованной операции. Вывод об утечке между организациями не установлен. Несогласованная запись контакта устранена в проверенных командах. Семантика нулевого контакта и право менять контакт после `ACCEPTED / IN_WORK` требуют решения автора. Атрибуция обычного комментария владельцу существовала в прежнем коде и стала наблюдаемой после починки записи. Для начального статуса отдельно нужно определить, означает ли поле автора фактического инициатора или владельца. Повторы успешных команд сами по себе не доказывают дефект идемпотентности. По авторизации принимаю общий вывод: отзыв по имени теперь связан с ID и типом проверенного субъекта. Два имени в DI ссылаются на одно хранилище в процессе. Постоянного хранилища и плановой очистки нет. При сравнении с прошлым аудитом следует разделять восстановление транзакции после сбоя COMMIT, ранний `SQLITE_BUSY` и ошибку HTTP-сериализации после COMMIT. Старый SQL для `tickets.admin_id` не проходит подготовку, хотя активный HTTP использует другие запросы. Числовое умолчание срочности воспроизводимо ломает чтение, но штатный POST его не использует. ## Оставшиеся проверки

1. Считать исправление каскада подтверждённым после двух типов HTTP-команд на чистой DDL с новой, активной и ожидающей проверки парой, закрытой контрольной заявкой и контрольной организацией. Сверить HTTP, оба статуса, флаги, версии, `date_finished`, переходы и списки новым соединением. Повторить отключение и включение. После отключения клиента проверить, что активная пара проходит последующий `finish-work`, если сохраняется правило продолжения работ. Для заявки на проверке при отключении отдельного пользователя подтвердить ожидаемое продуктовое правило.
2. Для `finish-work` проверить Swagger/OpenAPI и два независимых жизненных цикла до пользовательского подтверждения и административного `execute`. Для валидации проверить согласованный 4xx и стабильный короткий `detail`. Числа веб-пирамиды относятся к частичному прогону в закреплённой среде. Полный зелёный прогон ещё требует устранения ошибок сбора и актуальных фикстур.
3. Проверить конкуренцию двумя разными сценариями, с удержанием записи перед первым `touch` и с удержанием чтения перед COMMIT. Для хранилища refresh после определения контракта нужны проверки перезапуска, двух экземпляров, истечения срока и атомарной ротации на синтетических сессиях.
