# Повторный аудит заявок. Системный аналитик, раунд 1

Ветка `api-new-client-scheme`, коммит `d497e75d4937e8edea98783a5af924c247622e06`. Проверил HTTP-команды через FastAPI TestClient, штатные прикладные сервисы, репозитории и опубликованную DDL на отдельных временных файлах SQLite. Акторы задавались тестовыми зависимостями, имели штатные роли и разрешения. Состояние после запроса сверял отдельным соединением. Проверок обхода авторизации не проводил. Сравнение ниже относится к добавлениям автора, включая строки 147–150. Дату появления остальных дефектов по одной ревизии установить нельзя.

## Отключение и состояние двух карточек

### P1. Заявка на проверке блокирует отключение всей организации

Путь через API: пользователь создаёт заявку через `POST /user/tickets/`. Сотрудник задаёт отдел, принимает заявку, начинает работу и вызывает `PATCH /admin/tickets/{id}/finish-work`. Все шаги успешны. Пара оказывается в `READY_FOR_REVIEW` и `WAITING_FOR_CONFIRMATION`. Затем `PATCH /admin/clients/{id}/disable` возвращает 400 с причиной `ready_for_review -> suspended`. Повтор даёт тот же результат. SQLite сохраняет клиента и пользователей включёнными, а обе карточки открытыми.

Подтверждена только половина решения из строки 147 заметок. Переход пользовательской карточки из `WAITING_FOR_CONFIRMATION` в `SUSPENDED` реализован. В графе внутренней заявки из `READY_FOR_REVIEW` разрешены `ASSIGNED`, `CONFIRMED_BY_USER`, `EXECUTED`, `CANCELLED` и `ACCEPTED`. Клиентский каскад вызывает `suspend` для каждой открытой внутренней заявки раньше, чем обрабатывает пользовательские карточки. Отключение отдельного пользователя при такой заявке тоже возвращает 400, потому что пользовательский каскад включает `READY_FOR_REVIEW` в предикат приостановки. См. `src/web/routers/admin/clients.py:151–170`, `src/application/services/client_service.py:163–222`, `src/domain/services/client_service.py:226–246`, `src/domain/statuses/rules/ticket_status_transition.py:113–125`, `src/domain/statuses/ticket_user_status_transitions.py:62–70`, `src/web/routers/admin/users.py:350–368`, `src/domain/services/user_service.py:352–392,435–448`.

### P1. Активная работа также блокирует отключение клиента

Тот же путь с отключением сразу после `start-remote-work` даёт 400 для `at_work -> suspended`. Клиент и пользователи остаются активными. Пара остаётся в `AT_WORK` и `IN_WORK`. Правило в докстринге клиента сохраняет начатую работу. Реализация пытается приостановить все открытые внутренние заявки, включая `AT_WORK`. В этом статусе перехода в `SUSPENDED` нет. Для починки важно проверять и связанную пользовательскую карточку: её текущий `IN_WORK` входит в отдельную выборку открытых `TicketUser`. Если просто пропустить внутреннюю заявку в клиентском цикле, следующий цикл всё равно приостановит её пару. См. `src/domain/services/client_service.py:52–80,223–247`, `src/domain/statuses/rules/ticket_status_transition.py:76–96`, `src/adapters/repositories/gateways/ticket_gateway.py:58–69`, `src/adapters/repositories/gateways/ticket_user_gateway.py:30–39`.

### P1. Отключение отдельного пользователя отвечает 200 и расходится между карточками

После `POST /user/tickets/` вызвал `PATCH /admin/users/{id}/disable` дважды. Оба ответа 200. В БД пользователь отключён, внутренний `Ticket` в `SUSPENDED` с `date_finished`, а `TicketUser` остался `CREATED` без `date_finished` и с прежней версией. Для пары, принятой до отключения, наблюдался тот же разъезд с пользовательским `IN_WORK`. В домене `sync_from_ticket` меняет пользовательский объект в памяти, но `changed_ticket_users` остаётся пустым. Сервис приложения сохраняет только записи из результата. Повтор не чинит пару, поскольку терминальный внутренний `Ticket` исключается из каскада. Следующее отключение всей организации в сценарии с одной такой парой закрыло оставшийся открытым `TicketUser`. См. `src/domain/services/user_service.py:352–398,435–448`, `src/application/services/user_service.py:458–495`, `src/domain/services/ticket_sync_service.py:40–70`.

### Терминальный `SUSPENDED` подтверждён

Клиентский каскад для новой пары закрывает обе карточки и отключает пользователей. Второй вызов возвращает 200 без новых записей статусов. Корневая версия клиента при этом увеличивается. После отдельного включения клиента и владельца обе карточки остаются закрыты. Попытки принять внутреннюю или отменить пользовательскую заявку возвращают 400. Пользовательский `/open` её исключает, `/closed` содержит `suspended`. Это соответствует строке 148 заметок. См. `src/application/services/client_service.py:114–143,177–222`, `src/domain/statuses/rules/ticket_status_transition.py:121–146`, `src/domain/statuses/ticket_user_status_transitions.py:34–70`, `src/domain/ticket.py:940–945`, `src/domain/ticket_user.py:486–492`.

## Завершение, контакты и повтор команд

- **`finish-work` фактически соответствует решению автора.** Сотрудник с `TICKET_EXECUTED` получает 200 и оставляет внутреннюю заявку в `READY_FOR_REVIEW`, связанную в `WAITING_FOR_CONFIRMATION`. Оба статуса открытые. Далее испытал два отдельных сценария. `/user/tickets/{id}/confirm` закрывает обе карточки в `CONFIRMED_BY_USER`, а `/admin/tickets/{id}/execute` закрывает их как `EXECUTED` и `CONFIRMED_BY_ADMIN`. Повтор каждой команды возвращает 400 без дальнейшего изменения статуса. Устарели два описания автоматического `EXECUTED`: докстринг прикладного сервиса и описание модели запроса, попадающее в схему HTTP. См. `src/web/routers/admin/tickets.py:912–942,982–1011`, `src/application/services/ticket_service.py:791–838,895–930`, `src/web/models/tickets.py:181–187`, `src/domain/statuses/mapping_statuses.py:59–68`.
- **Контакт по умолчанию и запись контакта в две карточки подтверждены для создания и открытой новой пары.** Через оба API создания контакт без явного значения равен владельцу в обеих карточках. У администратора с `TICKET_ACCEPTED` создание сразу дало `ACCEPTED` и `IN_WORK`. Изменение администратором на второго пользователя в статусе `CREATED_FROM_TICKET_USER` даёт 200, отдельный GET пользовательской карточки видит новый контакт. Остался разный контракт для одинакового `contact_user_id=0`: пользователь сбрасывает на владельца с 200, сотрудник получает 400 для связанной заявки. Обе HTTP-модели принимают 0. После принятия положительный новый контакт получает 400 с обеих сторон для связанной пары, хотя внутренний `ACCEPTED` разрешает изменение данных. Ограничение задаёт `TicketUser.IN_WORK.can_change=False`. Согласовать, должен ли сотрудник иметь право менять контакт принятой пары, требуется на уровне продукта. См. `src/domain/ticket.py:88–137,465–482`, `src/domain/ticket_user.py:69–105,228–241,428–438`, `src/web/models/tickets.py:91–95`, `src/web/models/tikcets_user.py:50–53`, `src/application/services/ticket_service.py:324–370`, `src/application/services/ticket_user_service.py:265–309`, `src/domain/statuses/rules/ticket_state_rule.py:41–43`, `src/domain/statuses/ticket_user_status.py:44–59`.
- **Повторы подчиняются конкретным переходам.** Два одинаковых `PATCH /admin/tickets/{id}/executor` для того же исполнителя возвращают 200 и добавляют две записи `ASSIGNED` во внутреннюю историю. У пользовательской карточки остаётся одна запись `IN_WORK`, но её версия увеличивается при каждом сохранении. Два вызова отмены созданной пользовательской заявки дают 200 и затем 400. Авторское требование идемпотентности не установлено, но клиенту API полезно знать о разном результате при повторах после сетевого сбоя. См. `src/web/routers/admin/tickets.py:745–775`, `src/application/services/ticket_service.py:581–630,1181–1202`, `src/domain/statuses/rules/ticket_status_transition.py:63–74`, `src/domain/services/ticket_sync_service.py:40–70`, `src/domain/ticket_user.py:356–369,433–438`.
- **Содержание ошибок перехода требует сокращения.** В испытанных допустимых действиях с неверным состоянием HTTP 400 содержит весь `repr` карточки, включая текст заявки, идентификаторы, историю и вложенные комментарии при их наличии. Доменное сообщение использует `f"Ticket {self} ..."`, а публичный обработчик передаёт текст ожидаемой ошибки. У пользовательского перехода сообщение включает `repr` новой статусной записи и лишнюю букву `f`. Это наблюдение о форме ответа авторизованному актору. См. `src/domain/ticket.py:406–415`, `src/domain/ticket_user.py:356–369`, `src/web/main.py:59–83`, `src/web/execeptions/exception_handlers.py:120–132`.

## Дополнительные подтверждения и границы выводов

- `PATCH /admin/users/{id}/account/disable` и `/enable` возвращали 200, отдельное чтение `accounts.enabled` подтвердило 0 и 1. Оба сохранения находятся внутри UoW. Удаление самостоятельной и связанной заявок вернуло 204, независимая проверка не нашла удалённых карточек в корневых таблицах. - Пользовательские списки ограничивают загружаемые карточки клиентом или владельцем до чтения истории. Фильтр открытости применяется в памяти к этому набору, хотя репозиторий уже содержит адресные SQL-выборки. Административные `/open` и `/closed` в сценарии после исполнения показали корректное распределение. См. `src/application/services/ticket_user_service.py:518–611`, `src/adapters/repositories/ticket_user_repository.py:175–228`, `src/application/services/ticket_service.py:1111–1139`.
- В схеме определён FK `tickets.user_ticket_id → user_tickets.user_ticket_id`, штатный SQLite-коннектор включает проверку FK. Однозначность обратного поиска `get_by_user_ticket_id` опирается на текущий путь создания пары, поскольку схема не задаёт уникальность ссылки. Для обычных HTTP-команд второго способа привязать существующую пользовательскую заявку не нашёл. Это ограничение хранения, а не подтверждённый сбой API. Миграцию не оценивал в соответствии с заметкой автора. См. `db/schema.sql:123–154,179–186`, `utils/db/connect.py:18–31`, `src/adapters/repositories/ticket_repository.py:126–141`, `src/application/services/ticket_user_service.py:141–205`, `src/application/services/ticket_service.py:152–189`.
