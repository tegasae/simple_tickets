# Повторный аудит Python и SQLite

Ветка `api-new-client-scheme`, коммит `d497e75d4937e8edea98783a5af924c247622e06`. Первый независимый раунд. Изучал текущий код и замечания автора. Сценарии API проверял через FastAPI TestClient, штатный вход синтетических пользователей и фактические SQLite-репозитории. Новую временную БД создавал из `db/schema.sql`, проверял результат отдельным соединением. Python 3.12.14. Сценарии с синтетической блокировкой и с подменой сборщика DTO указаны отдельно. Авторизацию как предмет аудита разбирал статически.

## Что осталось или обнаружено в текущем коде

1. **P1. Отключение клиента блокируется, пока хотя бы одна заявка в работе или ждёт проверки.** `PATCH /admin/clients/{id}/disable` выбирает все внутренние заявки с `date_finished IS NULL` и вызывает `ticket.suspend()` для каждой. Из `AT_WORK` и `READY_FOR_REVIEW` переход в `SUSPENDED` отсутствует. Для клиентской карточки переход из `WAITING_FOR_CONFIRMATION` уже добавлен. Через обычный API создал связанную пару, начал работу и получил 400 на отключении. Завершил работу до `READY_FOR_REVIEW` и снова получил 400. После обоих запросов отдельное чтение подтвердило прежние состояния клиента, пользователей и обеих карточек. При отключении с заявкой в `CREATED` обе карточки ушли в `SUSPENDED`, появилось `date_finished`. Включение клиента оставило обе карточки закрытыми. Заметка 147 расходится с выполнением команды, решение из заметки 148 реализовано. Для `AT_WORK` нужна явная бизнес-ветка, если активную работу следует оставлять исполнителю. 4. **P2. При конкурирующем писателе штатное создание заявки отвечает общим 500.** Два соединения с одним временным файлом. На первом начата запись. На втором обычный `POST /admin/tickets/` после чтения пытается поднять блокировку на первом `touch`. SQLite возвращает `database is locked`, слой репозиториев оборачивает исключение в `PersistenceError`, обработчик даёт общий 500. Снимок до/после показывает отсутствие изменений. После освобождения блокировки повтор вернул 201. Регистрация `OptimisticLockError` как 409 полезна при фактическом расхождении версий, но этот сценарий падает на уровне SQLite до проверки `rowcount`. Для различения временного конфликта и реальных ошибок хранилища необходимо сохранить код SQLite и отдельно классифицировать занятость. 6. **P2. DDL исполняется, но SQL-контракты и значения по умолчанию совместимы частично.** На пустой SQLite `executescript` успешно создал 15 прикладных таблиц и `sqlite_sequence`, `PRAGMA foreign_key_check` чист. Из 116 строковых SQL-констант, собранных тем же способом, что текущий контрактный тест, одна не готовится. `TicketGateway.EXISTS_BY_ADMIN_ID` ссылается на отсутствующий `tickets.admin_id`. Активный путь удаления администратора использует проверку акторов, исполнителей и комментариев, поэтому доказательство относится к мёртвой константе и контрактному тесту. Синтетическая строка с корректной стартовой историей и стандартным SQL-значением срочности сохраняется с включёнными FK, затем обычный `GET /admin/tickets/{id}` выдаёт 500. Контрактный тест копирует `db/admins.db` и потому не проверяет схему из файла.
