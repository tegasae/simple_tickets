# Транзакции, повторы и refresh-сессии

## Где обрывается команда

| Ситуация | Что видит клиент | Что делать |
| --- | --- | --- |
| Ошибка домена, репозитория или сборщика DTO до успешного COMMIT | Команда возвращает ошибку. Проверки подтвердили, что строки и история откатываются | Повторить команду только с новой транзакцией и свежим состоянием. Старый Python-объект может сохранить присвоенные ID или версии |
| Вторая пишущая транзакция получает `SQLITE_BUSY` при переходе от чтения к записи | Общий 500, хотя версия могла ещё не сравниваться | Сохранить код SQLite на границе адаптера. Для временной блокировки рассмотреть 503, а 409 оставить для подтверждённого конфликта версии |
| Успешный COMMIT, затем потеря ответа, таймаут или ошибка сериализации ответа | Клиент не может определить, записалась ли операция | Для создания и добавления комментария нужен контракт определения повтора. Слепой повтор может добавить ещё одну запись |

Текущий HTTP создаёт новое соединение на запрос. Внутри Python вызовы `save` назначают ID и версии сразу после SQL, поэтому после исключения данные в объекте и в БД могут отличаться. Переоткрытие UoW исправляет состояние соединения. Чтобы повторить операцию, перечитать корни и заново вычислить переход вместе с проверками. Для двух параллельных запросов проверять разные исходы. При удержанной блокировке новый POST должен либо дождаться разрешённого повтора, либо вернуть временный отказ, который клиент понимает. При реальном устаревании версии нельзя автоматически накатывать старое изменение поверх новой истории. `utils/db/connect.py:46–109`, `src/adapters/uow/sqlite_unit_of_work.py:76–158`, `src/adapters/repositories/ticket_repository.py:291–334`.

**Предложение для повторяемых команд.** Клиент генерирует один `Idempotency-Key` на новое нажатие кнопки «создать». При повторной доставке сохраняет его. Сервер хранит ключ в области действия субъекта и команды, хеш нормализованного тела и результат. Сохранение заявки, её истории и ключа проходит в одном COMMIT. Повтор с тем же субъектом, командой, ключом и телом возвращает сохранённый результат. Повтор с тем же ключом и другим телом даёт конфликт. Два намеренно отправленных одинаковых текста с разными ключами остаются двумя операциями. Перед разработкой утвердить подходящие маршруты и TTL записи. Для проверки оборвать ответ после COMMIT, повторить тот же ключ и подтвердить единственную пару и единственный набор истории. Отдельно проверить два одновременных повторения. В эту серию патчей механизм ключей и автоматические повторы не входят.

## Два хранилища refresh-сессий

В текущем коде две глобальные переменные указывают на один экземпляр `TokenStorageMemory` в процессе из-за `__new__`. Проверки realm и субъекта по-прежнему действуют. Удаление старой сессии предшествует генерации и сохранению новой. Состояние сессий теряется при перезапуске процесса, разные процессы не делят память. Вызов очистки TTL отсутствует в активном login-пути. [Код хранилища](../../../src/web/auth/storage.py#L54-L143) · [Вызовы ротации](../../../src/web/auth/services/services.py#L42-L93) · [Патч 03](patches/03-refresh-token-storage.patch)

Патч 03 добавляет настройку `REFRESH_TOKEN_BACKEND` с вариантами `memory` и `sqlite`. По умолчанию сохраняется локальный режим. `create_app` создаёт один экземпляр для приложения и выдаёт его обеим auth-зависимостям. Для SQLite указать `REFRESH_TOKEN_SQLITE_PATH` на отдельный файл в каталоге, где у сервиса есть право записи. Несколько процессов одного сервиса могут использовать один файл на общем локальном диске. Режим подходит для одного хоста. Для нескольких реплик на разных машинах нужен общий транзакционный сервер хранения. При переключении режима старые refresh-сессии из другого хранилища не переносятся.

```text
REFRESH_TOKEN_BACKEND=sqlite
REFRESH_TOKEN_SQLITE_PATH=/path/to/service-data/refresh.sqlite3
```

SQLite хранит хеш случайного refresh-токена, время истечения, область и метаданные субъекта. Сырой токен не записывается на диск. Новый JWT и ответ строятся до замены сессии. In-memory backend выполняет замену под одним замком. SQLite backend проверяет действительность предыдущей записи и вставляет новую с удалением прежней в одной транзакции. Если запись преемника не удалась, прежняя сессия остаётся. Штатный вход запускает удаление просроченных, использованных или отозванных записей. Для установки с редкими входами таймер очистки можно добавить отдельно. Обе реализации сохраняют публичные login, refresh и logout endpoints и их форму ответа. Синхронные обработчики auth используют рабочие потоки FastAPI для вычисления хеша пароля и SQLite.

Проверки охватывают законную ротацию между двумя экземплярами FastAPI, которыми используется один временный файл, отзыв новой собственной сессии, отсутствие сырого токена в строке SQLite, отказ кодирования в памяти, отказ вставки SQLite и независимость двух экземпляров in-memory backend. Восстановление после потери HTTP-ответа и политика переиспользованного логина требуют отдельных решений. Фактический режим развёртывания этой ветки неизвестен.
