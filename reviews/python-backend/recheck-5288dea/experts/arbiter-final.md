24 ноября 2026 года. Арбитр `gpt-6.2-sol`. Снимок `tegasae/simple_tickets`, ветка `api-new-client-scheme`, `5288dea85d8f7e7e4c84d4801781d297e0e14475`.

**Снимок проходит проверенные основные сценарии Ticket/TicketUser и все 70 регрессий предыдущего аудита в их прежнем объёме. Приёмка по последним требованиям остаётся открытой.** Четыре предлагаемых патча исправляют автора начальной записи, формат административных комментариев, политику сроков для новых сессий и пропуск контроля версии при самоназначении. ### Как изменён первичный вывод об actor

В своём первичном A1 я распространил новое правило на внутренний `CREATED_FROM_TICKET_USER` при саморегистрации. Эту квалификацию снимаю. `tickets.md:215–241,292–306,338–348,1682–1692` прямо различает автора внешнего `TicketUser.CREATED` и автоматическое создание внутренней карточки. Внутренний 0/NULL обозначает SYSTEM_GENERATED, исходный User уже сохранён во внешней истории. Последнее уточнение §2 называет `CREATED.actor` в контексте прежнего исправления обычного комментария, которое оставляло открытым авторство внешней записи при регистрации Admin. Явного расширения на автоматическую запись нет. Патч 01 правильно оставляет внутреннюю семантику и её проверку без изменения. ## Конкуренция и условные риски

- **Самоназначение и remote из ACCEPTED.** На исходном коде измеренное изменение `employees.version` для self, другого Admin и remote-self равно 0, 1 и 0. По коду у двух самостоятельных ветвей пропущен общий контроль версии Admin, используемый при назначении другого исполнителя и при сохранении Admin. Поэтому при переносе этого протокола на READ COMMITTED возможно сохранение по устаревшему состоянию сотрудника. Патч 04 добавляет контроль обеим ветвям. В SQLite цели сохраняются с увеличением версии, при отказе контроля откатываются назначение и обе истории. Для PostgreSQL успешное запрещённое состояние и его устранение не проверены. Штатный API в этом снимке открывает только SQLite UoW. Источники `src/application/services/ticket_service.py:592–636,700–728`, `src/adapters/repositories/admin.py:140–167,233–247`, `src/web/dependencies/services.py:22–32`. [Патч 04](../patches/04-executor-version-guard.patch)
- **Схема допускает NULL в version.** В синтетически допустимых строках Admin/Department чтение падает с 500, а User/Client после нормализации к 0 ложно конфликтуют с SQL NULL. Механизм воспроизведён на репозиториях и HTTP. Достижимый путь создания таких строк штатным API и наличие их в поддерживаемых данных не установлены. Это условная несовместимость схемы, маппинга и CAS. Она не отменяет исправление старой группы 23 у Ticket/TicketUser. Источники `db/schema.sql:5,17,48`, `src/adapters/repositories/mappers/admin_mapper.py:42`, `department_mapper.py:23`, `user_mapper.py:37`, `client_mapper.py:33–36`, `src/adapters/repositories/gateways/employee_gateway.py:19–22`, `client_gateway.py:21–23`. [HTTP QA](round-02/qa.md)
- Ненулевой Department без `touch` достижим в прямой прикладной ветви создания User Ticket. Активная модель HTTP не содержит поля и отклоняет extras, что QA подтвердил ответом 422. Списки и нагрузка, readiness с БД, несколько production workers и отдельные серверы остаются за границами испытаний. Ошибки блокировок прямого SQLite refresh storage лежат вне исправленной F11 классификации основной БД. [Ограничения Python](round-03/python.md) · [Ограничения QA](round-03/qa.md)

Сохранённая AT_WORK проходит `finish-work` до READY_FOR_REVIEW и закрывается отдельной командой Admin. ## Условия закрытия

Патчи 01–03 можно принимать по их проверенному объёму с явным переходным решением для старых refresh. Патч 04 устраняет пропуск общей версии в исследованных ветвях, его PostgreSQL-приёмка требует прогона с двумя соединениями и управляемой конкуренцией изменения Admin и назначения. [Патч 01](../patches/01-created-actor.patch) · [Патч 02](../patches/02-admin-comment-json.patch) · [Патч 03](../patches/03-session-lifetime.patch) · [Патч 04](../patches/04-executor-version-guard.patch)

Первоочередная работа — обеспечить необратимый отзыв в общей транзакции с mutation, включая каскад Client, и согласовать выдачу и ротацию с отзывом. Приёмка должна показать rollback обеих частей, отсутствие старого refresh после enable и смены Account, а также корректность конкурентной выдачи. Для идемпотентности нужна общая фиксация бизнес-изменений, истории и исходного ответа. Приёмка включает повтор по тому же ключу на всех десяти маршрутах, изменённое тело, разные области, потерю ответа после COMMIT, один эффект при конкуренции, rollback и 24-часовое хранение. Согласованная модель оставляет HTTP-повтор клиенту. [План 05](../patches/05-refresh-revocation-plan.md) · [План 06](../patches/06-idempotency-plan.md)

Отсутствие готовых diff 05/06 означает, что комплект исправлений неполон. Вызов отзыва после COMMIT оставляет изменение и отзыв разнесёнными во времени, а запись ключа после ответа оставляет окно повторной бизнес-записи. Такие частичные изменения не обеспечили бы принятые гарантии и в комплект не включены.
