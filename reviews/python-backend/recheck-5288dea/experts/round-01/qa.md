## Результат

### QA-01. Refresh не отзывается при смене пароля и оживает после enable — высокий приоритет

**Путь API → код.** `PATCH /admin/users/{id}/password` → `src/application/services/user_service.py:286`, изменение пароля на строках 306–310 и обычное сохранение на 316–318. Аналог Admin: `PATCH /admin/admins/{id}/password` → `src/application/services/admin_service.py:271`, изменение на 288 и сохранение после него. Отключение User → `src/application/services/user_service.py:446`, вызов domain disable на 482; отключение Admin → `src/application/services/admin_service.py:420`, вызов на 436. В этих командах нет обращения к refresh storage. `POST /auth/{admin|user}/refresh` → `src/web/auth/services/services.py:241` проверяет лишь актуальную допустимость субъекта, затем строка 249 ротирует прежний refresh.

**Условия и воспроизведение.** Для обоих realm получен refresh настоящим login. Другой авторизованный Admin меняет пароль: HTTP 200. Старый refresh сразу успешно даёт новую пару: HTTP 200. В отдельном сценарии получен новый refresh, субъект отключён: disable 200, refresh в отключённом состоянии 401; после enable 200 тот же прежний refresh снова даёт 200. Воспроизведено и для User, и для Admin с постоянным SQLite-хранилищем сессий.

**Ожидаемое / факт.** Решения §5.2 требуют окончательного отзыва при смене пароля/отключении и отсутствия восстановления после включения. Сейчас существует временный запрет по enabled, но отзыв отсутствует. Это не претензия к отсутствию немедленного sid-check access: такой check не требуется владельцем.

**Последствие.** Смена пароля не завершает ранее выданную refresh-сессию. Повторное включение возвращает доступ обладателю старого refresh без нового входа. Учитывая QA-02, срок риска может продлеваться ротациями.

**Граница.** Удаление/отвязка Account и каскад Client имеют такой же архитектурный пробел: например, `src/application/services/user_service.py:236` и `src/application/services/admin_service.py:231` удаляют Account без отзыва. Их полный HTTP-сценарий удаления и последующего восстановления здесь не исполнялся; не выдаю это за отдельное воспроизведение. `TokenStorageSQLite._connection` (`src/web/auth/storage_sqlite.py:40`) открывает своё соединение, общей транзакции UoW с изменением аккаунта также пока нет.

**Регрессия.** Параметризовать Admin/User: login → change-password → старый refresh отклонён; login → disable → enable → старый refresh отклонён. Повторить для удаления Account и каскада Client. Проверить атомарность изменения и отзыва при отказе COMMIT, затем отдельными конкурентными тестами refresh/login против отзыва.

**Уверенность:** высокая, реальные HTTP-запросы после настоящего login.

### QA-02. Ротация продлевает абсолютный срок refresh и выдаёт access за его пределы — высокий приоритет

**Путь API → код.** `/auth/{realm}/refresh` → `AuthManager.refresh` → `TokenService.renew_tokens`, `src/web/auth/services/services.py:85`. Создаётся совершенно новая пара без переноса первоначальной даты окончания. `RefreshToken.create`, `src/web/auth/tokens.py:237`, назначает `now + REFRESH_TOKEN_EXPIRE_DAYS`; `AccessToken.create`, строка 78, независимо назначает `now + ACCESS_TOKEN_EXPIRE_MINUTES`.

**Условия и воспроизведение.** В настройках стенда явно установлены согласованные 5 минут и 7 суток. Получен настоящий User login. Часы token-модуля сдвинуты примерно к `t0 + 6 суток 23 часа 59 минут`, затем обычный HTTP refresh: 200. Дата окончания нового refresh оказалась примерно на 604740 секунд позже окончания первоначального. Новый access истекает примерно на 240 секунд позже первоначального конца сессии. Несколько секунд зависят от времени исполнения и округления JWT.

**Ожидаемое / факт.** §5.1: refresh всегда заканчивается через 7 суток от входа, ротация срок не продлевает; access в конце сессии не выходит за абсолютный предел. Сейчас окно сессии скользит при каждой ротации; ограничения access первоначальным пределом нет. Это воспроизводится даже при правильных конфигурационных значениях и поэтому не устраняется только исправлением defaults из QA-03.

**Последствие.** Регулярные обновления позволяют сохранять сессию дольше согласованных 7 суток. Последний access также продолжает доступ за абсолютный срок.

**Регрессия.** Управляемые часы и оба realm: login в t0; refresh в t0+6 суток сохраняет исходное expires_at; refresh в t0+7 суток отклонён; access, выданный за минуту до предела, истекает не позднее предела. Проверить переживание перезапуска и несколько последовательных ротаций.

**Уверенность:** высокая. Реальный HTTP login/refresh; только часы управляемые. Claims собственной выданной пары прочитаны для измерения, а не для обхода проверки запроса.

### QA-03. Действующие defaults сроков токенов расходятся с 5 минутами / 7 сутками — средний приоритет

**Путь API → код.** Login обоих realm → `src/web/auth/tokens.py:78` и `:237`; источник параметров — активный `src/web/config.py:18` (`30` минут) и `:19` (`1` сутки). Корневой `config.py` не является настройками подключённого FastAPI приложения.

**Условия и воспроизведение.** Приложение создано с новым случайным ключом, собственной БД и SQLite refresh backend, без env-переопределения сроков. Настоящий Admin login: JWT `exp - iat = 1800` секунд. Настоящий User login: сохранённый refresh `expires_at - created_at = 86400` секунд.

**Ожидаемое / факт.** Согласованы 300 секунд и 604800 секунд. Приложение по своим defaults выдаёт 1800 и 86400. У реального сервера env мог переопределять параметры; .env и его конфигурация не исследовались, поэтому фактические сроки production не заявляю.

**Последствие.** Запуск без дополнительных переопределений увеличивает допустимое окно старого access до 30 минут и преждевременно завершает не обновляемую refresh-сессию через сутки.

**Регрессия.** Проверить штатную конфигурацию через реальный login и сроки выданной пары обоих realm; отдельно контролировать развёртываемую конфигурацию. Не дублировать численные константы по методам.

**Уверенность:** высокая для defaults кода и стенда, без вывода о секретной конфигурации сервера.

### QA-04. Первоначальный CREATED.actor не всегда фактический инициатор — средний приоритет

**Ветвь User.** `POST /user/tickets/` → `src/web/routers/user/tickets.py:132` → `TicketUserApplicationService.create_from_user` → `Ticket.create_from_ticket_user`. В `src/domain/ticket.py:277` жёстко записан `actor_employee_id=0`. Правило `src/domain/statuses/ticket_status_record.py:91` даже требует ноль для user_action. После реального login User 3 создал заявку: внешняя карточка имеет CREATED.actor=3; `GET /admin/tickets/1` возвращает внутренний `created_from_ticket_user.actor_id=0`, в SQL строка actor NULL.

**Ветвь Admin.** `POST /admin/tickets/` с `user_id=3` при actor Admin 1 → `src/application/services/ticket_service.py:153`, вызов `TicketUserService.create` без инициатора → `src/domain/ticket_user.py:111` записывает владельца `user_id`. HTTP 201 вернул внутренний Ticket 3 с `user_ticket_id=3`; SQL внешней истории показывает `(user_ticket_id=3, actor_employee_id=3, status='created')`. Действительный инициатор — Admin 1. Внутренняя CREATED_FROM_REQUEST_USER при этом правильно указывает Admin 1.

**Ожидаемое / факт.** §2 требует фактического инициатора начального статуса, владелец хранится отдельно. Две ветви теряют либо подменяют автора в одной из карточек.

**Последствие.** История не позволяет достоверно определить, кто первоначально зарегистрировал заявку. Исправление обычного комментария этого не исправляет: в проверенном Admin create обычный комментарий уже принадлежит Admin 1.

**Регрессия.** Матрица User self-create / Admin for User / standalone Admin: проверить обе доступные карточки и строки истории после повторного чтения из БД; ожидаемый CREATED.actor — инициатор, владелец — отдельный user_id. Изменение user_action-валидации должно согласовываться с новой семантикой именно CREATED.

**Уверенность:** высокая, HTTP и SQL одной временной БД.

### QA-05. Административный JSON комментариев содержит объект вместо строки — средний приоритет

**Путь API → код.** `GET /admin/tickets/{id}` и ответы команд → `TicketAssembler.to_dto`, `src/application/assemblers/assembler.py:58` и `:67`: в словарь переносятся value objects. `TicketResponse` допускает `dict[str, Any]` в `src/web/models/tickets.py:282` и `:286`, поэтому контракт не обнаруживает подмену типа.

**Воспроизведение.** Реальный `GET /admin/tickets/1` вернул `statuses[0].comment = {"value":""}`. При Admin create с комментарием HTTP 201 вернул `comments[0].comment = {"value":"Admin comment"}` и аналогичный объект в комментарии статуса accepted. Пользовательский ответ на создание содержит строку `"QA comment"`.

**Ожидаемое / факт.** §2 требует строки в административном JSON, как в User API. Доменный object может оставаться внутри. Сейчас объект сериализуется как вложенный JSON.

**Последствие.** Единый клиентский контракт комментария нарушен; потребитель строки получает объект. Ошибки HTTP 500 здесь нет: ответы успешны, но формат неверен.

**Регрессия.** Реальные HTTP-ответы admin create/add-comment/read/status command: для каждого `comments[*].comment` и `statuses[*].comment` проверять `isinstance(value, str)`, включая пустой комментарий и повторное чтение. Сравнить с User API. Явные модели вложенных элементов помогут фиксировать контракт.

**Уверенность:** высокая, реальные JSON-ответы.

### QA-06. Отсутствует обязательная идемпотентность созданий — высокий приоритет; отсутствующая функция

**Категория.** Это отсутствие обязательного механизма, а не поломка существующей реализации ключей. Обязательность установлена дополнением владельца (§6–8): ключ необязателен, результат 24 часа после COMMIT, все создания кроме отдельного Account; комментарии включены.

**Путь API → код.** `POST /user/tickets/` → `src/web/routers/user/tickets.py:117`, DTO на строке 127 и `create_from_user` на 132; заголовок не читается и в команду не передаётся. `POST /user/tickets/{id}/comments` → сервис на `src/web/routers/user/tickets.py:324`, аналогично. Прочитанные routers/services не содержат протокола ключей; в `db/schema.sql` нет хранения результата. OpenAPI активного приложения содержит 83 path и ни одного параметра `Idempotency-Key`.

**Воспроизведение.** После настоящего User login два одинаковых `POST /user/tickets/` с одним ключом дали два HTTP 201 и `ticket_user_id` 1 и 2; в БД две пары с собственной начальной историей. Два одинаковых `POST /admin/clients/` с одним ключом дали HTTP 201 и client_id 3 и 4. Два одинаковых добавления User-комментария с одним ключом дали HTTP 200; число комментариев увеличилось с 1 до 2. Таким образом, заголовок фактически игнорируется в трёх разных видах создания.

**Ожидаемое / факт.** Повтор той же операции/субъекта/тела с прежним ключом в пределах 24 часов должен возвращать первоначальный результат без повторного бизнес-эффекта. Сейчас каждый повтор исполняется заново.

**Область инвентаризации.** Точно видимые создания: `/admin/clients/`, `/admin/admins/`, `/admin/users/`, `/admin/departments/`, `/admin/roles/admin`, `/admin/roles/user`, `/admin/tickets/`, `/user/tickets/`, два маршрута добавления комментариев. Account attach отдельно исключён соглашением; включённый в Admin/User Account должен входить в родительскую операцию. Login/refresh не считаю автоматически бизнес-идемпотентностью.

**Последствие.** Повтор после потери успешного ответа создаёт дубли заявок, сущностей и комментариев. Это не устраняется UNIQUE на связи Ticket/TicketUser; отсутствие такого UNIQUE само по себе не считаю ошибкой с учётом будущего 1:N.

**Регрессия.** Для всех согласованных созданий: тот же ключ+тело → тот же ID/результат; другое допустимое тело → конфликт без записей; новый ключ → новая намеренная операция; отсутствие ключа → обычное выполнение; исходный субъект после refresh → та же область; разные субъекты/команды изолированы. Отдельно 24 часа от успешного COMMIT, rollback, потеря ответа после COMMIT, конкурентный дубль, отсутствие двойной истории. Точные пока не выбранные временные статусы/лимиты не выдумывать.

**Уверенность:** высокая для отсутствия механизма в активном surface и трёх HTTP-воспроизведений; остальные создания охвачены статической инвентаризацией, а не отдельным повторным HTTP-тестом каждого маршрута.
