## Подтверждённые находки

### A-01. Refresh сохраняет доступ после смены пароля, отключения/включения и замены Account

**Важность: высокая. Тип: подтверждённое неправильное поведение и отсутствующая обязательная координация. Уверенность: высокая.**

Требование: полное решение 5.2–5.3 и OWNER-CONFIRMATION требуют постоянного отзыва refresh при смене пароля, удалении Account и отключении сотрудника, в том числе каскадном; повторное включение не оживляет refresh. Идентичность Account и субъекта должна проверяться по постоянным ID и типу.

Точные места:

- `src/application/services/user_service.py:217–247` — detach Account; `:286–318` — password; `:482–501` — disable сохраняют бизнес-сущности без обращения к refresh-хранилищу.
- Аналогичные ветки Admin: `src/application/services/admin_service.py:231–237`, `:288–295`, `:436–447`.
- `src/application/services/client_service.py:192–220` — каскад отключает/сохраняет User, Ticket, TicketUser, затем Client, без отзыва сессий.
- `src/web/auth/services/services.py:225–250` — refresh проверяет токен, realm и текущее существование/активность; факт предшествовавшей смены пароля/отключения не проверяет.
- `src/web/auth/services/auth_service.py:105–113`, `:180–189` — проверяется login и employee_id, но не прежний account_id.
- `src/web/auth/tokens.py:200–215` — RefreshToken не хранит account_id. `src/adapters/uow/sqlite_unit_of_work.py:50–69` не содержит репозитория сессий; `src/web/auth/storage_sqlite.py:37–40` открывает собственное соединение/транзакцию.

Путь: `PATCH /admin/users/{id}/password` → UserApplicationService → UserService → User/Account → save; позднее `POST /auth/user/refresh` → AuthManager.refresh → UserAuthService.validate_user_exists → TokenService.renew_tokens. Аналогично disable/enable и DELETE/POST Account.

Доказательство на постоянном SQLite refresh backend:

1. Login User, затем Admin делает disable и enable User; старый refresh даёт HTTP 200.
2. Admin меняет пароль User (HTTP 200); ранее выданный refresh даёт HTTP 200.
3. Admin удаляет Account, затем прикрепляет новый Account с тем же login к тому же User. В основной БД account_id изменился. Refresh старого Account даёт HTTP 200.

Ожидание во всех трёх случаях — отказ обновления и необходимость нового входа. В отсутствие refresh во время отключения сессия не исчезает и после enable вновь действует. Это позволяет владельцу старого refresh получать новый access вопреки отзыву; это гораздо шире разрешённого владельцем окна действия **уже выданного** access. Проверка активности в каждом запросе сохранена и сама по себе эту проблему не решает. Отсутствие общей UoW также означает, что обязательная атомарность mutation+revocation пока не реализована. Гонка rotation/revocation отдельно не проверялась.

Локальное направление исправления: связать сессию с постоянным Account и субъектом, выполнять отзыв в авторизованных мутациях той же UoW; отдельно согласовать конкурентную выдачу/ротацию с отзывом. Немедленный `sid` check каждого access-запроса **не требуется** и в находку не включён.

### A-02. Ротация продлевает refresh на новый полный срок и выдаёт access за абсолютным пределом

**Важность: высокая. Тип: подтверждённое неправильное поведение. Уверенность: высокая.**

Требование: полное решение 5.1 — access 5 минут, refresh и абсолютная сессия 7 суток от первого входа; ротация не сдвигает предел; access в конце сессии также ограничен абсолютным пределом.

Точные места: `src/web/auth/services/services.py:85–94` при renew вызывает `JWTToken.create` заново, не переносит первоначальную конечную дату; `src/web/auth/tokens.py:228–239` вычисляет refresh `now + settings.REFRESH_TOKEN_EXPIRE_DAYS`; `:71–80` вычисляет access независимо от даты сессии. Отдельно текущие рабочие defaults в `src/web/config.py:18–19` равны 30 минутам/1 суткам, что расходится с согласованными 5 минутами/7 сутками.

Путь: `POST /auth/{admin|user}/refresh` → AuthManager.refresh → TokenService.renew_tokens → JWTToken.create → AccessToken.create + RefreshToken.create → storage.replace.

Проверка устойчивой логики проведена **даже с правильной конфигурацией 5 минут/7 суток**: сохранена синтетическая действующая сессия, у которой первоначальный срок истекает через минуту (первый вход почти семь суток назад). Реальный `renew_tokens` создаёт successor почти на семь суток от текущего момента; новый access истекает позже первоначального предела. Итоговый JSON содержит `access_beyond_absolute: true`. Таким образом, переопределение defaults конфигурацией не устраняет нарушение. Defaults проверены отдельно через реальные Settings приложения без TTL overrides; они дали 30 и 1. Реальная production-конфигурация не исследовалась, поэтому утверждение о её конкретных TTL не делается.

Последствие: активная ротация поддерживает сессию дольше согласованного абсолютного срока, а выданный под конец access пересекает его. Направление исправления: сохранить исходный предел и ограничить им оба новых токена; привести единые именованные параметры к согласованным значениям.

### A-03. Обязательная 24-часовая идемпотентность созданий отсутствует на всех проверенных маршрутах

**Важность: высокая. Тип: отсутствующая обязательная функция с подтверждёнными последствиями. Уверенность: высокая.**

Требование: полное решение 6–10 и OWNER-CONFIRMATION. Необязательный `Idempotency-Key` должен охватывать все создания сущностей и комментариев, кроме отдельного Account; результат хранится 24 часа после COMMIT, ключ scoped по типу/ID субъекта и команде, пара TicketUser/Ticket и история имеют один эффект.

Точные примеры входа: `src/web/routers/user/tickets.py:114–138`, `src/web/routers/admin/tickets.py:71–98`, `src/web/routers/admin/clients.py:69–83`. Они принимают body/actor/service без заголовка, передают DTO в обычное создание. `src/application/services/ticket_user_service.py:114–219` создаёт и сохраняет новую пару при каждом вызове; `src/application/services/ticket_service.py:121–239` делает то же для административного создания. Комментарии входят через `src/web/routers/admin/tickets.py:379–401` → `src/application/services/ticket_service.py:246–275`. В `src`, `utils` и `db/schema.sql` отсутствует обработка ключа, footprint/result storage или idempotency protocol; в полном OpenAPI строка `Idempotency-Key` отсутствует.

Проверка: один и тот же субъект дважды отправляет одинаковое тело и одинаковый заголовок в каждой строке таблицы.

| Маршрут | Результат повторов |
|---|---|
| `POST /user/tickets/` | 201/201, TicketUser ID 2/3; это две разные пары |
| `POST /admin/tickets/` | 201/201, Ticket ID 8/9 |
| `POST /admin/clients/` | 201/201, Client ID 3/4 |
| `POST /admin/admins/` | 201/201, employee ID 6/7 |
| `POST /admin/users/` | 201/201, employee ID 8/9 |
| `POST /admin/roles/admin` | 201/201, role ID 3/4 |
| `POST /admin/roles/user` | 201/201, role ID 5/6 |
| `POST /admin/departments/` | 201/409 из-за уникального имени, сохранённый первый результат не возвращается |
| `POST /admin/tickets/{id}/comments` | 200/200, количество комментариев растёт 2 → 3 |

Пользовательский comment endpoint по тому же статическому пути тоже не принимает ключ; повтор именно этого endpoint отдельно не исполнялся. Проверка 24-часового удержания не имеет предмета, поскольку механизма нет. Отсутствие ключа должно продолжать работать обычным образом — это не дефект; отсутствие UNIQUE на связи пары тоже не объявляется дефектом.

Последствие: после потери ответа успешного COMMIT даже правильно использующий K клиент создаёт дубликаты бизнес-сущностей/истории или получает неожиданный отказ уникальности вместо исходного результата. Требование поддержки ключа отсутствует целиком; это следует учесть как реализацию согласованного протокола, не как локальный SQL UNIQUE только для Ticket.

### A-04. Начальная TicketUser.CREATED при регистрации Admin приписана владельцу User

**Важность: средняя. Тип: подтверждённое нарушение бизнес-истории. Уверенность: высокая.**

Требование: решение 2 — инициатор начального CREATED фактический: Admin при регистрации за пользователя, User при собственном создании; владелец хранится отдельно.

Точные места: `src/application/services/ticket_service.py:152–160` вызывает общий `TicketUserService.create` с владельцем User и без actor; `src/domain/services/ticket_user_service.py:62–69` передаёт user_id в TicketUser.create; `src/domain/ticket_user.py:99–113` всегда записывает `actor_employee_id=user_id`. Начальная обычная комментарийная запись уже отделена: application `:161–165` добавляет её от реального Admin; это **не** исправляет начальный status record.

Путь: `POST /admin/tickets/` с `user_id > 0` → TicketApplicationService.create_ticket → TicketUserService.create → TicketUser.create → user_tickets.save → затем создание Ticket.

Проверка: синтетический Admin employee 1 создал за User employee 3. Из `user_tickets_status_record` для новой карточки прочитан initial CREATED actor 3 вместо 1, при этом owner User = 3 корректен, обычный комментарий Admin имеет actor 1. При самостоятельном создании User начальный actor действительно User и соответствует правилу. Начальный статус внутренней Ticket, созданной Admin, также содержит Admin; находка касается именно TicketUser.CREATED.

Последствие: долговечная история сообщает, что User инициировал операцию, которой он не выполнял. Нужна передача фактического инициатора в фабрику отдельно от владельца; переписывать владельца не требуется.

### A-05. Административные comments и status comments сериализуются объектом вместо строки

**Важность: средняя. Тип: подтверждённое нарушение API-контракта. Уверенность: высокая.**

Требование: решение 2 — текст административного JSON комментария должен быть строкой, как в пользовательском API; domain VO допускается внутри приложения.

Точные места: `src/application/assemblers/assembler.py:58`, `:67` передают `record.comment`/`comment.comment` как VO. `src/web/models/tickets.py:282–288` разрешает `dict[str, Any]`, а `TicketResponse.from_dto` не нормализует вложенный текст. Для сравнения пользовательский assembler на `:124–132`, `:141–146` извлекает строку.

Путь: любой административный endpoint, возвращающий TicketResponse → TicketAssembler.to_dto → TicketResponse.from_dto → FastAPI JSON serializer.

Проверка `POST /admin/tickets/` с `comment="Admin initial comment"` вернула `comments[0].comment = {"value":"Admin initial comment"}`, а не строку. Это HTTP 201 с неправильным контрактом, не 500. Для status comments та же ошибка доказана статически тем же assembler path, а не отдельным HTTP assertion.

Последствие: consumers строкового контракта получают объект, а пустой VO также может иметь другой вид. Исправление требуется на границе DTO/web, сохраняя валидную domain-модель.

## Существенный подтверждённый риск, без PostgreSQL runtime-доказательства

### A-R01. Самоназначение и удалённое самоназначение не участвуют в общем guard исполнителя

**Потенциальная важность: высокая. Уверенность в отсутствии guard: высокая; в воспроизведённом запрещённом PostgreSQL-состоянии: не заявляется.**

Требование/инвариант: исполнитель активен и из отдела Ticket; смена отдела запрещена при текущем назначении; решение 3 указывает необходимость согласования назначения с изменением Admin.

Точные места: `src/application/services/ticket_service.py:605–610` берёт self actor; `:628–631` делает `admins.touch(executor)` только для другого исполнителя. `:714–721` для `start_remote_work` из ACCEPTED проверяет actor, но touch не выполняет. Общий SQL guard существует в `src/adapters/repositories/gateways/admin_gateway.py:69–75`; изменение Admin выполняет CAS по employees.version (`employee_gateway.py:11–22`).

Путь: `PATCH /admin/tickets/{id}/executor` с executor_id == actor ID или `PATCH /admin/tickets/{id}/start-remote-work` из ACCEPTED → application → TicketService.ensure_can_assign → Ticket mutation → save пары без CAS Admin. Для назначения другого Admin touch имеется.

Проверка на SQLite: оба self endpoint успешно исполнены в синтетических допустимых условиях; employees.version до/после изменился на 0. Это подтверждает обход общего guard. Реального concurrency-теста с двумя PostgreSQL-соединениями не было; SQLite locks нельзя выдавать за доказательство безопасности или за успешный PostgreSQL exploit. В текущем API wiring (`src/web/dependencies/services.py:22–30`) подключается только sqlite3/SQLiteUoW, поэтому PG нельзя включить одной DATABASE_URL.

Условный READ COMMITTED interleaving: T1 читает валидный self Admin; T2 до появления назначения видит отсутствие текущих Ticket, меняет отдел/отключает Admin и COMMIT; T1 сохраняет Ticket на устаревшей проверке без сравнения Admin.version. Версия Ticket не обнаруживает изменение другого aggregate. Возможный результат — назначенный неактивный исполнитель либо несовпадение отделов.

Узкое направление исправления — общий CAS/touch на всех ветках нового назначения в той же транзакции и реальный PG barrier test; это не утверждение о достаточности такого guard для всей конкурентной модели приложения.

## Не считать доказанными дефектами / вопросы согласования

1. `tickets.md` прямо помечен как смесь текущей и целевой модели. Его раздел 3.3 и `src/tikcetuser.md` говорят, что подтверждение User не меняет Ticket; текущие status graph, domain/application и `docs/steps/steps.md:2855` и далее показывают terminal CONFIRMED_BY_USER в Ticket. Подтверждён сам runtime и документационное расхождение, но нельзя по одному старому целевому фрагменту однозначно требовать иной workflow. Нужна фиксация выбранного контракта. Последние решения владельца не переопределяют этот случай явно.
2. Отсутствие UNIQUE `tickets.user_ticket_id` не дефект: решение 4 оставляет возможность будущего 1:N, текущий API её не обещает. Вызовы get-by-user-ticket возвращают одну карточку; много-Ticket aggregate, удаление общей TicketUser и агрегация статусов требуют будущего отдельного контракта, а не ретроактивного запрета модели.
3. Возврат из SUSPENDED новым lifecycle, ticket_relations, возврат прежнему executor, server-side search/pagination, current_status projection и история планирования описаны в technical debt/need. Они не объявляются уже реализованными или обязательными только по наличию предложения. SUSPENDED в текущем коде terminal и это соответствует последним решениям.
4. Реальные настройки HTTPS, секретов, сервера, workers, бэкапов и production PostgreSQL не проверены. SQLite допускается последним документом как промежуточное хранилище. Нельзя объявлять production проверенным по TestClient/SQLite. `/health` (`src/web/main.py:105–107`) проверяет только процесс; БД readiness в коде нет. Отдельные метрики/оповещения/пороги ещё не выбраны; отсутствие наблюдаемости отмечается как эксплуатационный пробел, а не выдуманный runtime-инцидент.
5. Кешированного продления истёкшего access в текущем web пути не обнаружено: AccessToken.decode в dependencies проверяет подпись/exp при запросе. Не предъявляется требование немедленно навсегда отзывать ранее выданный access после быстрого disable/enable: владелец допускает оставшийся TTL. A-01 относится к выдаче **новых** access через старый refresh.
6. Производительность больших списков, исчерпание ресурсов, многопроцессные rotation races и любые PostgreSQL-инварианты не измерялись. Наличие тяжёлых загрузок/TODO без измерений не доказывает неприемлемую скорость.

## Приоритет следующего раунда

Сначала проверить/исправить отзыв и устойчивую идентичность refresh, абсолютный срок сессии, затем атомарный idempotency protocol согласованных созданий. Автор CREATED и JSON имеют узкие воспроизводимые исправления. Guard самоназначения требует закрытия обеих веток и реального PostgreSQL-теста; широкой переработки остальных workflow из результатов первого раунда не следует.
