## PY-01 — отсутствует обязательная идемпотентность создания; повтор с тем же ключом создаёт новую заявку

**Категория:** отсутствующая обязательная функция с воспроизведённым последствием. **Важность:** высокая. **Уверенность:** высокая.

**Путь вызова:** `POST /admin/tickets/` → `TicketApplicationService.create_ticket` → доменная фабрика → `TicketRepositorySQLite.save` → INSERT tickets/history → COMMIT.

**Текущий код:** `src/web/routers/admin/tickets.py:65–93` не принимает и не передаёт Idempotency-Key; `src/application/services/ticket_service.py:110–237` выполняет создание на каждом вызове; `src/application/dto/ticket_dto.py:13–50` не содержит ключа; `src/adapters/uow/sqlite_unit_of_work.py:44–71` и весь `db/schema.sql` не содержат репозитория/таблицы результата идемпотентности. Поиск `idempot` по application/UoW/DDL не нашёл реализации. Это системный пробел, а не только ошибка одного маршрута.

**Условие:** два авторизованных POST с одинаковыми допустимыми телом и `Idempotency-Key` в одной области субъекта/команды.

**Факт/ожидание:** HTTP-тест получил `201`, `201`, различные `ticket_id=3` и `4`; в OpenAPI параметра ключа нет. По §§6–10 полного документа ожидается исходный результат без второго бизнес-эффекта и истории, атомарное хранение результата 24 часа после COMMIT. Обязательная область также включает другие API-создания и комментарии, кроме самостоятельного Account. Без ключа дубликаты допустимы — этот случай дефектом не считался.

**Последствие:** потеря ответа и штатный клиентский повтор дублируют сущности/историю даже с явно переданным ключом. Нельзя обеспечить договорённый клиентский протокол повторов.

**Доказательство:** `check_http_auth.py`, фактический FastAPI TestClient и реальная SQLite: `HTTP duplicate 201 201 ids 3 4`, `OpenAPI key parameter False`.

## PY-02 — смена пароля и отключение не отзывают refresh; после enable старый refresh снова работает

**Категория:** воспроизведённая ошибка обязательного протокола сессий. **Важность:** высокая. **Уверенность:** высокая.

**Путь вызова:** `AdminApplicationService.change_password/disable/enable` → `AdminService`/Admin → `AdminRepositorySQLite.save` → employees/accounts; независимо `AuthManager.refresh` → `AdminAuthService.validate_user_exists` → `TokenService.renew_tokens` → refresh storage.

**Текущий код:** `src/application/services/admin_service.py:271–299` меняет пароль и сохраняет Admin без отзыва; `:420–450` отключает, `:387–418` включает без работы с сессиями. Аналогично detach/delete и пользовательские/клиентские каскады не подключены к хранилищу refresh. `src/adapters/uow/sqlite_unit_of_work.py:44–71` не предоставляет session repository. `src/web/auth/services/services.py:241–250` проверяет текущую допустимость субъекта и обновляет токен, но не версию пароля/учётной записи. `src/web/auth/storage_sqlite.py:37–40,113–123` умеет отзывать токены через собственное соединение; прикладные операции этот метод не вызывают. `src/web/auth/services/auth_service.py:105–113` проверяет login и постоянный subject ID, а не идентичность прежнего Account.

**Условие:** выданный refresh ещё не истёк; меняется пароль либо сотрудник отключается и повторно включается.

**Факт/ожидание:** тест с persistent SQLite token storage сохранил старый refresh, выполнил реальную `AdminApplicationService.change_password`, затем `AuthManager.refresh` успешно выдал новую пару. Второй тест выполнил реальную прикладную disable/enable от другого уполномоченного Admin; ранее выданный refresh снова успешно обновился. По §5.2 ожидается необратимый отзыв refresh при смене пароля/удалении/отключении, отсутствие оживания после enable. Допускаемая задержка access это нарушение не оправдывает.

**Последствие:** прежняя сессия переживает изменение пароля; отключение временно блокирует только текущую проверку enabled, но не прекращает refresh-сессию. Атомарность бизнес-изменения и отзыва также не реализована. Реальные гонки выдачи/ротации с отзывом отдельно не проверялись.

**Доказательство:** `check_http_auth.py`: `refresh after password change succeeded True`; `refresh after disable/enable succeeded True`. Credentials и токены не печатались.

## PY-03 — ротация начинает срок refresh заново, access не ограничен абсолютной датой; defaults тоже расходятся с 5 минутами/7 сутками

**Категория:** воспроизведённая ошибка сроков. **Важность:** высокая. **Уверенность:** высокая.

**Путь вызова:** login/refresh → `TokenService.create_token_pair/renew_tokens` → `JWTToken.create` → `AccessToken.create`, `RefreshToken.create`.

**Текущий код:** `src/web/auth/services/services.py:78–94` при refresh вызывает фабрику новой пары без старой абсолютной даты. `src/web/auth/tokens.py:228–239` задаёт refresh `created_at=now`, `expires_at=now+REFRESH_TOKEN_EXPIRE_DAYS`; `:77–80` задаёт access `now+ACCESS_TOKEN_EXPIRE_MINUTES` без cap по исходной сессии. `src/web/config.py:18–19` defaults составляют 30 минут и 1 сутки.

**Условие:** refresh выполняется до истечения текущего токена, в том числе за 45 секунд до первоначальной семисуточной границы.

**Факт/ожидание:** даже при явной настройке согласованных 5 минут/7 суток преемник получил срок примерно ещё 7 суток: превышение прежней границы `604755` секунд; новый access также вышел за исходную абсолютную дату. По §5.1 ротация сохраняет конец первоначальных 7 суток и access не продлевает доступ за эту дату. В отдельной проверке Settings с синтетическим ключом и без dotenv/TTL overrides выдаёт 30 минут/1 сутки. Настройки реального deployment неизвестны; ошибка абсолютного срока сохраняется и с правильными overrides.

**Последствие:** последовательно обновляемая сессия может жить неограниченно долго; соблюдение абсолютного срока невозможно одной настройкой TTL. Система с defaults дополнительно выдаёт несогласованные сроки.

**Доказательство:** `check_http_auth.py`: `default lifetimes minutes/days 30 1`, `rotation extends absolute expiry seconds 604755`, `access exceeds original absolute expiry True`.

## PY-04 — TicketUser.CREATED при регистрации Admin ошибочно приписывается владельцу User

**Категория:** воспроизведённая ошибка истории. **Важность:** средняя. **Уверенность:** высокая.

**Путь вызова:** административное создание с user_id → `TicketApplicationService.create_ticket` → `TicketUserService.create` → `TicketUser.create` → INSERT user_tickets_status_record.

**Текущий код:** `src/application/services/ticket_service.py:152–160` передаёт владельца User, но не фактического actor; `src/domain/services/ticket_user_service.py:39–70` не принимает отдельного инициатора; `src/domain/ticket_user.py:108–113` безусловно записывает `actor_employee_id=user_id`. Обычный комментарий в `src/application/services/ticket_service.py:161–165` уже записывается с правильным Admin actor, что не исправляет CREATED.

**Условие:** Admin 1 регистрирует заявку за User 2.

**Факт/ожидание:** в БД `user_tickets_status_record`: `(2,'created')`, затем `(1,'in_work')`; первая запись должна содержать фактического Admin 1, владелец при этом остаётся User 2. Внутренний Ticket правильно получил Admin 1 для `created_from_request_user`. Для самостоятельного User-создания TicketUser.CREATED остаётся фактическим User — этот путь не объявляется сломанным.

**Последствие:** постоянная история неверно сообщает, кто зарегистрировал заявку; просмотр истории и последующие проверки авторства получают ложные данные.

**Доказательство:** `check.py`, реальная прикладная команда и SELECT истории после COMMIT. Начальный комментарий Admin авторство не потерял.

## PY-05 — административные комментарии сериализуются объектом `{value: ...}`, а не строкой

**Категория:** воспроизведённая ошибка контракта JSON. **Важность:** средняя. **Уверенность:** высокая.

**Путь вызова:** создание/чтение Ticket → `TicketAssembler.to_dto` → `TicketResponse.from_dto` → FastAPI/Pydantic JSON.

**Текущий код:** `src/application/assemblers/assembler.py:58,67` оставляет CommonComment/Empty в словарях status/comment; `src/web/models/tickets.py:282–288` использует свободные `dict[str,Any]`, поэтому вложенный VO не превращается в строковый текст. Пользовательский assembler извлекает `.value`: `src/application/assemblers/assembler.py:122–128,132–139`.

**Условие:** административная заявка содержит непустой обычный или статусный комментарий.

**Факт/ожидание:** реальный POST вернул `comments[0].comment = {"value":"text by operator"}`; ожидается строка по обязательному правилу §2. Сохранение VO внутри домена допустимо — ошибка на границе ответа.

**Последствие:** несовместимый формат administrative/user API и нарушение согласованного JSON-контракта. Клиент получает объект вместо текста.

**Доказательство:** `check.py` показал тип DTO `CommonComment`; `check_http_auth.py` подтвердил фактический HTTP JSON. Это не только статическое предположение о сериализаторе.

## Условные риски и границы доказательств

### R-01 — неполный межагрегатный guard исполнителя; PostgreSQL-гонка не воспроизводилась

**Путь:** assign(self)/start_remote_work из ACCEPTED → чтение Admin → проверка enabled/department → сохранение Ticket. В `src/application/services/ticket_service.py:603–631` touch Admin делается только для другого исполнителя; в `:714–727` самоназначение через remote не делает touch вообще. `AdminRepositorySQLite.touch` (`src/adapters/repositories/admin.py:233–247`) и сохранение Admin используют версию employees. Следовательно, общий CAS, который синхронизировал бы назначение с disable/сменой отдела, пропущен на этих двух путях.

**Ожидание/последствие:** по §3 необходима защита от фиксации назначения по устаревшему Admin. На PostgreSQL READ COMMITTED это создаёт обоснованный риск назначения уже отключённого/переведённого сотрудника. **Уверенность:** высокая в пропуске guard, но успешное нарушение инварианта на PostgreSQL или SQLite в этой работе не показано. SQLite snapshot/write locking нельзя выдавать за доказательство PostgreSQL-безопасности; здесь применяется только фактический SQLite adapter. Дополнительно пользовательское создание читает Department без touch (`src/application/services/ticket_user_service.py:181–184`); межагрегатный протокол для него также нуждается в отдельной проверке.

### R-02 — nullable версии DDL неодинаково поддерживаются mapper/CAS

**Путь:** чтение существующего User/Client/Department/Admin → rehydrate → save/touch. DDL допускает NULL version (`db/schema.sql:5,17,48`); `src/adapters/repositories/mappers/user_mapper.py:37` и `client_mapper.py:33–36` нормализуют NULL в 0, но `src/adapters/repositories/gateways/employee_gateway.py:19–22`, `client_gateway.py:21–23,57–61`, `user_gateway.py:74–79` сравнивают `version=:version` без COALESCE. `department_mapper.py:23` и `admin_mapper.py:42` делают `int(None)` до нормализации.

**Реальный тест:** в временной SQLite легально установлен NULL version: User/Client загружаются с 0, а touch получает OptimisticLockError без конкурента; Department падает TypeError уже при загрузке. **Уверенность:** высокая для этого условия. Подтверждения, что фактические старые поддерживаемые данные содержат NULL version, нет. Поэтому это условный риск совместимости, а не утверждение о массовой поломке текущих данных. При обычных version=0 основной CAS работает. Ticket/TicketUser SQL уже использует COALESCE, поэтому одинаковую проблему на них не переношу.
