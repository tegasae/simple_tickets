## 1. Требуемое сужение QA-04: TicketUser.CREATED и системная Ticket — разные записи

С административной веткой QA-04 и с PY-04 согласен: фактический Admin теряется именно при создании `TicketUser.CREATED`. `src/application/services/ticket_service.py:152–160` не передаёт actor в фабрику, `src/domain/ticket_user.py:108–113` всегда берёт владельца User. Это непосредственно нарушает правило последнего полного решения, строка 27: «Начальный CREATED.actor — фактический инициатор». Мой независимый HTTP/SQL-тест первого раунда получил тот же результат: Admin 1 → owner User 3, но TicketUser.CREATED.actor 3. Обычный комментарий и начальный статус внутренней Ticket указывают Admin корректно; их не следует объединять с ошибочной записью внешнего CREATED.

**Не согласен с повышением второй ветви QA-04 до подтверждённого дефекта:** наличие `actor_employee_id=0` в автоматически сформированной внутренней `Ticket.CREATED_FROM_TICKET_USER` доказано как факт, но нормативная неправильность этого нуля из приведённых доказательств не следует.

Адресные основания:

- В текущем коде `src/domain/ticket.py:273–281` системный actor передаётся осознанно, наряду с отдельным `user_id`.
- `tickets.md:210–241` прямо определяет ноль как SYSTEM_GENERATED, а не неизвестного автора, и называет автоматическое создание Ticket на основании TicketUser причиной этого обозначения.
- `tickets.md:1685–1689` отдельно предписывает начальный реальный User actor для TicketUser и actor 0 для автоматически созданной Ticket в той же транзакции.
- Последняя формулировка полного решения (`simple_tickets-decisions-2026-11-24-full.md:27,36`) требует фактического CREATED.actor, но не называет автоматическое внутреннее событие и не говорит явно, что прежняя системная семантика этого события отменена. Эту формулировку нельзя автоматически распространить на оба независимых журнала при наличии отдельного прямого описания системного события.
- В самостоятельно созданной User карточке фактический User уже сохраняется в `TicketUser.CREATED`; история пары не лишена сведений об инициаторе. Нельзя говорить, что из-за внутреннего нуля инициатора вообще невозможно определить.

Поэтому рекомендую оставить в общем выводе подтверждённую административную подмену автора TicketUser.CREATED; внутренний ноль — вопрос границы нового требования до явного уточнения. Не предлагаю менять `TicketStatusRecord.user_action`/валидацию или заменять внутренний actor на User только на основании QA-04. PY-04 в этой части сформулирован точнее.

## 3. Критика условных рисков Python

### R-01: отсутствие guard верно; у Department необходимо ограничить достижимость

Подтверждаю основной вывод о self assign и remote self assignment: `application/services/ticket_service.py:628–631` исключает self из touch, `:714–727` не добавляет guard для remote. Мой первый раунд также измерил `employees.version` до/после обоих успешных команд: delta 0. Это обоснованный межагрегатный риск; успешное запрещённое PostgreSQL interleaving ни одним из этих проверочных наборов не показано. Классификация Python как риска, а не воспроизведённого PostgreSQL-багa, корректна.

Добавление про Department в User creation (`application/services/ticket_user_service.py:181–184`) требует более узкой оговорки. Поле есть в application DTO, и прямой application caller может задать его; однако активный `UserTicketCreateRequest` (`web/models/tikcets_user.py:20–35`) не содержит `department_id`, имеет extra=forbid через базовую модель, а router `user/tickets.py:127–130` передаёт только model_dump. Обычный User POST не может выбрать ненулевой Department и всегда остаётся в empty-department ветке. Поэтому этот пропуск нельзя включать в подтверждённую **публично достижимую** гонку текущего User HTTP API. Для application API риск заслуживает отдельного теста и проверки caller scope.

### R-02: NULL version воспроизведён, условность поддерживаемых данных сохранена

Независимо подтвердил R-02 на новой SQLite по текущему DDL, в собственной `/tmp/analyst-5288dea-pGU0Sr`, с `PYTHONDONTWRITEBYTECODE=1`. Новый скрипт `probe_r2_nulls.py` создаёт валидные объекты текущими factories/repositories, затем SQL-фикстурой задаёт допускаемый DDL NULL version и повторно вызывает реальные repositories/UoW.

Результат: User и Client загружены с version=0, их touch получает `OptimisticLockError` без конкурента; Department и Admin падают `TypeError` при чтении. Это совпадает с `user_mapper.py:37`, `client_mapper.py:33–36`, `department_mapper.py:23`, `admin_mapper.py:42` и сравнением NULL с параметром version в gateway.

Классификацию Python поддерживаю: это реальное нарушение согласованности DDL/mapper/CAS **при наличии NULL**, но пока не доказанный сбой нормального создания через текущий API. Текущие factories задают 0 и repositories записывают его явно; штатный API-путь появления NULL не показан. Нет доказательства, что поддерживаемая существующая БД содержит NULL или что внешние записи с NULL входят в контракт. Не следует повышать R-02 до массового production-дефекта без этого условия. Возможны два узких исправления контракта данных: строгое NOT NULL с нормализацией поддерживаемых старых данных либо последовательная нормализация NULL во всех reads/CAS; выбор зависит от подтверждённого data contract, не от одного теста.

## 4. Ограничения общих заверений

- SQL smoke Python по 115 строкам полезен для синтаксиса, колонок и bind-параметров. Он не доказывает бизнес-правильность всех результатов SELECT, валидность каждого ссылочного инварианта или переносимость на PostgreSQL. Автор отчёта не должен расширять эту проверку до таких гарантий.
- Один победитель concurrent refresh QA подтверждает атомарную rotation одного токена в SQLite backend. Это не проверяет rotation против disable/password change/revoke, несколько app workers, рестарт и несколько серверов; соответствующие договорённости остаются непроверенными.
- Положительные результаты отключения/finish/отдельного execute совпадают с моими независимыми наблюдениями. Это действительно допустимый редкий workflow; нельзя требовать автоматический EXECUTED после finish.
- Readiness/метрики/пороги преимущественно сформулированы как предложения и ещё не выбранные параметры. `/health` без БД — подтверждённый предел liveness, но не доказанный production-инцидент. Не предлагаю искусственно расширять этим список подтверждённых ошибок.

## Решение для консолидации

Принять общие находки по refresh revoke/identity, абсолютному сроку, defaults, идемпотентности, автору TicketUser.CREATED при регистрации Admin и административному JSON. Системный ноль внутренней автоматически созданной Ticket не считать доказанным дефектом без прямого нормативного расширения требования. Self assignment оставить существенным неподтверждённым на PostgreSQL риском; NULL version — условным риском данных с независимо воспроизведённым механизмом. Исходные отчёты и код не изменялись.
