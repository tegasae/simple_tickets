## Scope CREATED.actor: две разные записи, два разных вывода

Последнее прямое правило (`simple_tickets-decisions-2026-11-24-full.md:27`) говорит: «Начальный CREATED.actor — фактический инициатор: Admin при регистрации заявки за пользователя, User при самостоятельном создании». Это однозначно исправляет внешнюю `TicketUser.CREATED`: владелец и инициатор — разные поля. `TicketUserStatusRecord` всегда хранит реального положительного employee ID.

Но в системе есть и **отдельное автоматическое создание внутреннего Ticket**. Исходный `tickets.md` прямо определяет `0 == SYSTEM_GENERATED`, «0 не означает неизвестного автора» (`:210–241`), и указывает для автоматически созданной пары TicketUser.CREATED с User ID, а Ticket с системным actor 0 (`:294–306,338–347`). Документ смешивает текущую/целевую модель, что оговорено в его начале; тем не менее это явное правило смысла actor, поддержанное текущим кодом: `ticket.py:273–278`, `TicketStatusRule.user_action` и `TicketStatusRecord._check_rules` (`ticket_status_record.py:91–96`). Последний полный документ не говорит прямо, что отменяет SYSTEM_GENERATED именно у `CREATED_FROM_TICKET_USER`.

Следовательно, доказанный баг — неверный Admin actor во внешней CREATED. Для User-создания внешняя CREATED уже верна; внутренняя `CREATED_FROM_TICKET_USER` с 0 соответствует прежнему явно описанному системному событию. Если владелец намеревался распространить новое правило и на внутреннюю автоматическую запись, это дополнительный scope изменения; доказательства такого точного расширения пока недостаточно. Не предлагаю молча менять весь `user_action`-валидатор: он также обслуживает CONFIRMED_BY_USER и CANCELLED_BY_USER, и такое изменение затронет существующую историю/rehydrate. В сводном отчёте следует оставить узкий подтверждённый пункт A-04 и отдельно обозначить эту неопределённость, а не считать две доказанные ошибки по одной формулировке.

## Положительные результаты и границы, с которыми согласен

Согласен с общей оценкой коллег: последовательный SQLite lifecycle действительно работает, включая обязательный контакт с fallback на владельца, запрет очистки, запрет смены отдела при назначении и отдельный execute после завершения работы отключённого клиента. В моих пробах также прошли rollback после первого сохранения пары и CAS устаревшей Ticket без дублирования истории. Это не покрывает все комбинации и не доказывает PG-конкуренцию.

Правильно не превращены в дефекты: отсутствие UNIQUE пары при будущем 1:N; отсутствие немедленного sid-check access; технические идеи search/pagination/monitoring; отсутствие явного commit в create_from_user при наличии UoW auto-commit. Согласен с A, что спор старой документации о User confirmation и terminal Ticket требует выбранного контракта, а не немедленного переписывания workflow. Само отсутствие readiness — наблюдаемый факт, но не доказанный production-инцидент и не обязательно утверждённая реализация из раздела «предлагаются».

Мой условный риск NULL version остаётся дополнительным: реальная SQLite допускает NULL по DDL, User/Client mapper дают 0, CAS сравнивает с NULL и ложно конфликтует; Department/Admin mapper могут падать `int(None)`. Наличие NULL в поддерживаемых старых данных не доказано, поэтому без такого подтверждения не повышаю риск до безусловного дефекта обычных записей. Исправление COALESCE/mapping можно рассмотреть отдельно с небольшой совместимой регрессией.

## Реалистичный объём исправлений — без создания patches

### Узкие и достаточно безопасные изменения

1. **Строки комментариев:** извлечение строкового `.value` для CommonComment/Empty в административном assembler. 1 production-файл, точечная HTTP-регрессия обычных/статусных/пустых комментариев после создания и повторного чтения. Модель VO и persistence не меняются. Строгие вложенные модели ответа полезны, но не обязательны для минимального исправления.
2. **Фактический Admin в TicketUser.CREATED:** передать отдельный initiating actor через `TicketUserService.create` в `TicketUser.create`; административный application path передаёт Admin, User path — себя. Около 3–4 production-файлов плюс матрица создания/rehydrate/SQL. Не менять user_id владельца, не переписывать старую историю без достоверного источника actor, не затрагивать внутренний системный actor до разрешения scope.
3. **Defaults:** две именованные настройки 5/7 в активном config; регрессия реального login. Это самостоятельный малый patch, который не закрывает скользящий абсолютный срок и не удостоверяет внешние env overrides.
4. **Guard новых назначений:** убрать исключение self из touch и добавить touch на remote-ветви нового назначения из ACCEPTED. Несколько строк в application service; SQLite-регрессия должна проверить increment и rollback при CAS failure. Для заявления о закрытой PG-гонке нужен настоящий PG barrier test; малость diff не означает доказанность PG-runtime.
5. **Абсолютная дата:** локально осуществимо в tokens/service: при ротации переносить исходный предел refresh, cap access через `min(now+accessTTL, absolute_end)`, проверять истечение до создания преемника. Это уже согласованный multi-method patch, а не одна константа. Нужны несколько ротаций, граница срока, SQLite сериализация/перезапуск и гонка двух refresh. У существовавших до исправления уже ротированных сессий истинная дата первого login потеряна; нельзя восстановить её из текущего created_at. Для строгой гарантии нужен явный переходный режим, практически — завершить старые сессии и потребовать login. Это следует назвать при подготовке patch, не обещать бесшовное восстановление неизвестных дат.

### Отзыв refresh — полноценное сквозное изменение

Одного вызова `revoke_user_tokens` после сохранения Account недостаточно: он откроет свою транзакцию и нарушит атомарность; login/refresh могли уже проверить старый Account и записать новую сессию после отзыва.

Минимально законченный объём: session repository в общем UnitOfWork и основной БД; постоянный account_id + subject_type/subject_id в сессии и auth результате; охват Admin/User password, detach/delete/disable, каскада Client; единая транзакция проверки/выдачи или ротации сессии; общий version/lock-протокол с отзывом. `AuthManager.login` сейчас сначала завершает `authenticate_user` UoW, затем создаёт/сохраняет пару (`services.py:195–209`), поэтому менять нужно и эту границу. Нужно обеспечить стабильный account_id после создания/сохранения (текущий `_sync_account` не присваивает ID новому Account в памяти). Memory backend остаётся отдельным тестовым/процессным режимом, без обещания атомарности с постоянными аккаунтами.

Это затрагивает auth orchestration/models/storage, UoW contracts/adapters/schema, account persistence и три группы application services. Требуются failure injection до COMMIT, rollback обеих частей, restart/multi-worker и конкурирующие login/refresh против password/disable/delete. Не требуется вводить sid-check каждого access. Не следует выдавать короткий post-commit revoke-hook за выполнение §5.3.

### Идемпотентность — общий протокол десяти создающих маршрутов

Нужны scoped key `(subject_type, subject_id, command, key)`, request fingerprint с target ID для комментариев, таблица/репозиторий результата в той же UoW, подготовленный исходный response и атомарная запись бизнес-эффекта/истории/result, срок 24 часа после успешного COMMIT. Область коллег верна: восемь созданий сущностей и два comment endpoint; отдельный Account исключён, встроенный Account покрывается родителем.

Потребуются изменения router/OpenAPI, командных данных, application boundary и UoW/schema/storage. У текущих `_save_and_to_dto` есть внутренние commit: middleware, который сохраняет ключ отдельно после ответа, не обеспечит атомарность. Нужно разместить сохранение результата до единственного успешного COMMIT. При unique conflict откатить всю попытку и открыть свежую UoW для replay; не продолжать транзакцию после native error и не переиспользовать мутированные aggregates. Автоматический серверный retry не вводить.

Минимальные проверки — все десять маршрутов, тот же/другой payload, новая область субъекта/команды, новый ключ, отсутствие ключа, 24 часа, rollback, потеря ответа после COMMIT и конкурентный дубль. Точные key limits/нормализация, ожидание и временный HTTP-статус, политика окончательных business failures ещё выбираются; не объявлять их утверждёнными числами. Готовый patch нельзя честно ограничить двумя маршрутами Ticket или одним UNIQUE на связь пары.

Итого: принять пять общих проблем (с отдельным малым пунктом defaults), сохранить PG guard как значимый непроверенный runtime-риск; User-ветвь QA-04 не добавлять к безусловным нарушениям без точного scope. Узкие исправления возможны отдельно, но ключи и атомарный отзыв требуют полного сквозного завершения и интеграционных доказательств.
