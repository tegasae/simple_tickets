## Исправление нормативной границы моего QA-04

В моём первом отчёте QA-04 объединены две фактические особенности, но одинаковая нормативная оценка им не доказана.

1. **Подтверждённый дефект остаётся:** Admin регистрирует заявку за User, а `TicketUser.CREATED.actor` получает владельца User. Полный документ §2 буквально называет «Начальный `CREATED.actor`» и требует фактического инициатора, включая Admin при регистрации за пользователя. Путь `src/application/services/ticket_service.py:153` → `src/domain/services/ticket_user_service.py:62` → `src/domain/ticket_user.py:111` не передаёт отдельного actor. Коллеги А и Б обоснованно ограничили находку этой записью.

2. **Автоматический internal `CREATED_FROM_TICKET_USER.actor=0` не считать подтверждённым нарушением текущего договора.** Ноль действительно наблюдался в HTTP и задан в `src/domain/ticket.py:277`; это факт исполнения. Но поздний документ прямо называет CREATED и отдельно различает статусы происхождения, когда хочет говорить о них. Явного требования заменить системного actor у `CREATED_FROM_TICKET_USER` на User во всех внутренних карточках не найдено. Историческое `tickets.md:210–241` прямо определяет 0 как SYSTEM_GENERATED и применяет это к автоматическому созданию Ticket из TicketUser; таблица `tickets.md:344–347` также разделяет User actor внешней карточки и системного actor внутренней. Этот документ смешивает старую/целевую модель и старые имена статусов, поэтому не доказывает весь новый контракт, но не позволяет уверенно объявить системного actor ошибкой только по общей фразе об инициаторе.

Следовательно, **снимаю подтверждённую нормативную претензию из User-ветви моего QA-04**. Наблюдение actor=0 остаётся описанием текущего механизма. Если владелец намерен расширить новое правило на автоматические внутренние записи, нужен явный контракт; до него не предлагать правку user_action-валидатора и не писать регрессию, требующую положительного actor именно там. Замороженный раунд 1 не переписан; это уточнение имеет приоритет для синтеза.

## Адресное подтверждение A-01: замена Account

Новый HTTP-сценарий после настоящего User 4 login:

| Шаг | Факт |
|---|---|
| `DELETE /admin/users/4/account` от Admin | 200 |
| Старый refresh, пока Account отсутствует | 401 |
| `POST /admin/users/4/account` с прежним login и новым синтетическим паролем | 200 |
| SQL-проверка идентичности | Новый account_id отличается от первоначального |
| Прежний refresh удалённого Account | 200, новая пара выдана |

Тем самым расширение А про замену Account независимо подтверждено HTTP. Точная причина в refresh validation: `src/web/auth/services/auth_service.py:105–113` и `:180–189` сопоставляют login/employee_id; `RefreshToken` в `src/web/auth/tokens.py:200–215` не содержит account_id. Сам employee_id здесь не меняется, поэтому защита только по subject ID не обнаруживает замену Account. Нельзя устранять проблему лишь запретом переиспользовать логин: обязательный отзыв должен выполняться при удалении, а login не является устойчивой идентичностью сессии.

Варианты с удалением всего Employee, каскадным Client и гонкой revoke/refresh этим новым сценарием не воспроизведены. Их архитектурные предпосылки не подменяют дополнительные HTTP/concurrency-доказательства.

Его не следует включать наравне с двумя реально достигаемыми self endpoint без этой оговорки.

## PY R-02: NULL version — подтверждённое условное несоответствие DDL и persistence

Согласен с условной квалификацией Б. DDL разрешает явный NULL version; defaults 0 не запрещают NULL. В стандартном API create NULL не создаётся. Для проверки в моей временной БД SQL-фикстурой задан NULL только у выбранного объекта; Admin-инициатор оставался валиден. Затем выполнены обычные HTTP-запросы, по одному условию за раз.

| Условие фикстуры | Реальный HTTP-запрос | Факт |
|---|---|---|
| Department 1 version=NULL | `GET /admin/departments/1` | **500**, `{"detail":"Internal server error"}` |
| Admin 2 version=NULL | `GET /admin/admins/2` от другого Admin | **500**, тот же безопасный публичный detail |
| Client 2 version=NULL | `GET /admin/clients/2` | 200 |
| Тот же Client | `PUT /admin/clients/2/contact` с допустимым name | **409**, Client version mismatch, конкурента нет |
| User 4 version=NULL | `GET /admin/users/4` | 200 |
| Тот же User, настоящий ранее полученный Bearer | `POST /user/tickets/` с допустимым текстом | **409**, User was changed by another transaction, конкурента нет |

Источник 500 точный: `src/adapters/repositories/mappers/department_mapper.py:23` выполняет `int(row['version'])` до `or 0`; `admin_mapper.py:42` также делает int(None). Источник ложного 409: mapper User/Client принимает NULL за 0, но CAS в `src/adapters/repositories/gateways/user_gateway.py:75–80` и `client_gateway.py:21–23` сравнивает SQL NULL с 0 без COALESCE. Это не произвольная догадка про 500: выше указан достигнутый HTTP и конкретные условия БД.

**Предел вывода:** существование NULL в поддерживаемых старых/рабочих данных не установлено; настоящий API create с нормальной версией этим сценарием не ломается. Поэтому итоговая формулировка — «условная несовместимость допустимого DDL значения с mapper/CAS», а не массовая поломка API или доказанная production-авария. Текущая схема формально допускает такие данные; необходимо выбрать единый контракт: запрет NULL на уровне схемы либо согласованная нормализация чтения и CAS. Локальный `int(value or 0)` без изменения SQL ложные конфликты не устранит.

**Будущие регрессии:** штатный version=0 и явный NULL отдельно для четырёх агрегатов; read+touch/save через новую UoW; по выбранному контракту либо DDL отклоняет NULL, либо полная операция работает без ложного version conflict. Не переносить проблему на Ticket/TicketUser, где SQL использует COALESCE, без отдельного доказательства.
