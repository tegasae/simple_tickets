# Независимое первичное заключение арбитра

24 ноября 2026 года. Модель арбитра — `gpt-6.2-sol`. Заключение подготовлено вслепую, до получения выводов остальных участников и материалов прошлых аудитов.

- Код `tegasae/simple_tickets`, ветка `api-new-client-scheme`, коммит `5288dea85d8f7e7e4c84d4801781d297e0e14475`. Вход `/workspace/work/input-5288dea`, 205 записей манифеста проверены пофайлово. SHA-256 манифеста `00c005b64c36f100382334212b0f71e2e7bc390a31cb0e08001f2e81672717bf`.
- Требования `/workspace/work/audit4-requirements`, две записи манифеста проверены пофайлово. SHA-256 манифеста `ed4dd4e6ad341b1713b8bf404c9f19dba239425375793b1f973e0a9cd3b5d287`. Полный документ решений от 24.11.2026 и подтверждение владельца «Все последние договорённости уже обязательны» имеют приоритет. Файл в коммите насчитывает 95 строк и обрывается на §5.3. В корневом `readme.md` перечислены TODO. Пометки FIXED в `INPUT-NOTES.md` приняты как заявления, подлежащие проверке.
- Динамические проверки выполнены на собственной временной копии кода с Python 3.12 из согласованного venv, `PYTHONDONTWRITEBYTECODE=1`, случайными синтетическими настройками, новой БД из `db/schema.sql` и временным SQLite-хранилищем refresh. Запросы прошли через штатное `src.web.main:app` и FastAPI TestClient с настоящими зависимостями, токенами и UoW. Для контроля времени и проверки rollback поставлены точечные заглушки тестового времени и ошибки второго сохранения. Производственный сервер и PostgreSQL вне измерений. Материалы прошлых аудитов, фронтенд, архивы и рабочие БД не использовались.

## Решение о соответствии

Снимок поддерживает штатное парное создание, сохранение положительного контакта и рассмотренный сценарий закрытия после отключения клиента. Снимок расходится с обязательными требованиями по авторству начальных записей, JSON комментариев, срокам и жизненному циклу refresh и обработке повторной доставки создающих команд. Для двух путей самоназначения подтверждено отсутствие общего контроля версии исполнителя. Нарушение рабочего инварианта на PostgreSQL остаётся условным результатом переноса.

## Подтверждённые функциональные ошибки

### A1. Начальная история пары теряет фактического инициатора

Серьёзность средняя. Уверенность высокая. Решения §2.

- При регистрации за User административный `POST /admin/tickets/` вернул внутренний `created_from_request_user` с actor Admin. Чтение связанной карточки показало внешний `created` с actor владельца User. При создании внешней карточки `TicketApplicationService.create_ticket` передаёт владельца, но не ID Admin, и `TicketUser.create` записывает `user_id` как автора. Обычный начальный комментарий на обеих карточках при этом был подписан Admin. Источники `src/application/services/ticket_service.py:152–167,181–194`, `src/domain/services/ticket_user_service.py:63–70`, `src/domain/ticket_user.py:99–123`, `src/domain/ticket.py:220–241`.
- При самостоятельном `POST /user/tickets/` внешний `created` имел actor User, а связанный внутренний `created_from_ticket_user` на административном чтении имел actor 0. Внутренний фабричный метод явно задаёт 0, правило статуса требует старое представление User-действия, SQL-маппер сохраняет 0 как NULL. Исправление только HTTP-представления оставило бы историю неполной. Источники `src/application/services/ticket_user_service.py:152–206`, `src/domain/ticket.py:250–287`, `src/domain/statuses/rules/ticket_status_rule.py:49–75`, `src/domain/statuses/ticket_status_record.py:87–100`, `src/adapters/repositories/mappers/ticket_mapper.py:112–117,164–173`.
- В первом сценарии история ошибочно приписывает действие владельцу, во втором внутренняя история теряет инициатора. При изменении правила внутреннего статуса необходима проверка чтения ранее сохранённых записей с 0/NULL и согласованное правило для старых данных. Уточнение владельца относится к начальной записи, поэтому оно само по себе не меняет семантику всех последующих User-переходов.

### A2. Административное API возвращает объект в поле текста комментария

Серьёзность средняя. Уверенность высокая. Решения §2.

Для одной созданной пары административный ответ на создание вернул объект с ключом `value` у обычного комментария и у непустого статусного комментария. Пользовательское чтение той же пары вернуло строку в обоих местах. `TicketAssembler` передаёт доменный объект в `dict[str, Any]`, в пользовательском DTO берётся его строковое значение. Клиент административного API получает другой тип поля. Источники `src/application/assemblers/assembler.py:44–71,117–139`, `src/web/models/tickets.py:282–288`, `src/web/routers/admin/tickets.py:65–93`. Формат поля можно исправить на границе DTO/ответа с сохранением доменного value object.

### A3. Сроки по умолчанию и абсолютный срок сессии расходятся с решением

Серьёзность высокая. Уверенность высокая. Решения §5.1.

- При штатном входе без переопределения TTL измерены 1800 секунд у access JWT и сутки у строки refresh. Действующие требования задают 300 секунд и семь суток. Источники `src/web/config.py:18–19`, `src/web/auth/tokens.py:70–83,219–240`. Настройки реального развёртывания не проверялись.
- При ротации через другой экземпляр приложения с тем же файлом сессий и тестовым временем на шесть часов позже срок сессии сдвинулся на те же шесть часов. При конфигурации 5 минут / 7 суток штатный refresh за 60 секунд до исходного дедлайна снова выдал access на 300 секунд и перенёс дедлайн refresh. Настройка правильных чисел исправляет длительности первичной выдачи, но ротация по-прежнему вызывает конструктор новой пары от текущего времени. Это допускает продление сессии и выход access за исходный абсолютный предел. Источники `src/web/auth/services/services.py:66–95`, `src/web/auth/tokens.py:219–240,292–320`.
- TTL каждого выданного JWT проверяется через декодирование на штатных бизнес-маршрутах. `sid`-проверка на каждый access по действующим соглашениям не требуется. Источники `src/web/auth/tokens.py:120–155,159–168`, `src/web/dependencies/auth.py:125–165`, решения §5.2.

## Отсутствующие обязательные функции

### A4. Отзыв refresh не связан с транзакциями жизненного цикла аккаунта

Серьёзность высокая. Уверенность высокая. Решения §§5.2–5.4, 12.

Штатная смена пароля User, отключение с последующим включением сотрудника и удаление его отдельного аккаунта завершились HTTP 200. После каждого изменения в хранилище осталась одна запись текущей сессии с флагом `revoked=0`. Результат подтверждает отсутствие записи отзыва. В штатном refresh проверяются login, тип, постоянный ID сотрудника и текущие флаги. Постоянного `account_id` в сессии нет, что подтверждено по сохранённой метаинформации и модели. Пока аккаунт или сотрудник отключён либо аккаунт отсутствует, текущая проверка может отказать. После включения она снова допускает refresh по сохранившейся записи с прежним ID и login до её собственного истечения. При смене пароля проверка существования вообще не сравнивает состояние старой сессии с изменением пароля. Источники `src/web/auth/services/services.py:185–209,211–251,253–284`, `src/web/auth/services/auth_service.py:94–113,169–189`, `src/web/auth/tokens.py:196–209`, `src/web/auth/storage_sqlite.py:21–40,89–96,113–123`.

Смена пароля, detach, disable и delete в прикладных сервисах Admin/User и каскадное отключение Client сохраняют бизнес-состояние без вызова отзыва. Реально применяемый отзыв есть в logout. SQLite-ротация атомарна относительно строки самой сессии благодаря `BEGIN IMMEDIATE`, но её соединение отделено от SQLite UoW бизнес-операций. Даже общий путь к файлу не сделает их одной транзакцией. Для целевого решения требуется согласовать отзыв с конкурентной выдачей и ротацией, так как бизнес-идентичность проверяется до отдельной записи сессии. Утверждён результат отзыва, конкретный механизм согласования остаётся на выбор. Источники `src/application/services/admin_service.py:211–295,420–447,544–580`, `src/application/services/user_service.py:217–318,447–501,507–538`, `src/application/services/client_service.py:163–222`, `src/adapters/uow/sqlite_unit_of_work.py:44–70`, `src/web/auth/storage_sqlite.py:37–40,73–75,89–96`.

Штатный SQLite-бэкенд прошёл чтение и ротацию сессии через второй экземпляр приложения на том же файле. Это частичная проверка устойчивости, без отдельного многопроцессного прогона. Memory установлен по умолчанию и является процессным режимом. Источники `src/web/config.py:23–30`, `src/web/main.py:39–52`. Само наличие memory-режима этому соглашению не противоречит.

### A5. Ключ идемпотентности отсутствует на границе и в UoW

Серьёзность высокая. Уверенность высокая. Решения §§6–9.

Два последовательных штатных `POST /user/tickets/` с тем же заголовком `Idempotency-Key`, тем же субъектом и телом вернули два HTTP 201 с разными ID. SQL подтвердил две разные пары. OpenAPI приложения не объявляет этот заголовок. В маршрутах создания, UoW и DDL отсутствуют обработка ключа, запись успешного результата и его TTL. Запросы без ключа продолжают штатно создавать карточки. Источники `src/web/routers/user/tickets.py:111–138`, `src/web/routers/admin/tickets.py:65–93`, `src/application/services/ticket_user_service.py:152–206`, `src/application/services/ticket_service.py:152–231,1183–1204`, `src/adapters/uow/sqlite_unit_of_work.py:44–70`, `db/schema.sql:1–186`.

OpenAPI показывает кандидатов на покрытие — создание Client, Admin, User, Department, AdminRole и UserRole, обе команды создания заявок и оба добавления обычных комментариев. Отдельные команды attach Account исключены. Аккаунт, созданный внутри Admin/User, входит в результат родительской команды. Для команд grant roles нужна явная классификация по бизнес-смыслу создания связей при окончательной инвентаризации. Сам HTTP-метод недостаточен для классификации. Необязательность ключа, область по субъекту и команде, единый эффект и хранение 24 часа после COMMIT уже определены. Точный временный ответ, предел ожидания, формат нормализации и удержание окончательных отказов остаются открытыми. Клиентский повтор HTTP согласован, внутреннего автоматического повтора в рассмотренных бизнес-командах нет.

## Существенные риски с границами доказательства

### A6. Самоназначение не участвует в общем контроле версии Admin

Высокая уверенность в статическом пробеле, средняя в реализации последствия после переноса. Решения §3. После обычных последовательных команд через HTTP измерены приращения `employees.version` для исполнителя. Самоназначение — 0. Назначение другого сотрудника — 1. Удалённое самоназначение из ACCEPTED — 0, при этом обе записи ASSIGNED и AT_WORK сохраняются. Обычный assign выполняет `touch` только для другого Admin. Remote из ACCEPTED проверяет возможность назначения, но проходит в сохранение без `touch`. Смена отдела и отключение читают текущие назначения и сохраняют Admin с проверкой его версии. Версия Ticket сравнивает только состояние Ticket. При READ COMMITTED и переносе такого же протокола одна транзакция сможет сохранить назначение на основании снимка Admin, уже изменённого другой транзакцией. Успешная гонка на SQLite или PostgreSQL в этой проверке не воспроизводилась. Источники `src/application/services/ticket_service.py:592–636,700–728`, `src/domain/services/ticket_service.py:255–268`, `src/application/services/admin_service.py:425–446,471–503,658–675`, `src/adapters/repositories/admin.py:140–167,233–247`, `src/adapters/repositories/gateways/admin_gateway.py:69–75`, `src/adapters/repositories/gateways/ticket_gateway.py:128–142`.

Проверенному API штатная зависимость создаёт только SQLite UoW с `sqlite3` и SQLite PRAGMA. Backend Docker запускает именно этот API. Поэтому поддержка выбранного production PostgreSQL в снимке не обнаружена. Оценка последствий PostgreSQL относится к переносу. Источники `dockerfiles/backend/Dockerfile:19`, `src/web/dependencies/services.py:22–32`, `utils/db/connect.py:19–36`, полный документ §§1, 5.4.

### Дополнительные границы

- На бизнес-транзакциях есть маппинг временной DB-ошибки в 503, на SQLite-хранилище refresh прямые операции идут мимо этого адаптера. При исчерпании ожидания записи SQLite обычное исключение может попасть в общий 500. Это статический риск классификации сбоев, без динамического подтверждения в первичном раунде. Источники `src/adapters/repositories/base_repository.py:30–71`, `src/web/auth/storage_sqlite.py:37–40,89–96`, `src/web/main.py:85–101`.
- `/health` возвращает статическое состояние процесса. Пригодность отдельной readiness-пробы, структурированные логи и SLO остаются элементами плана. Извлечение всех агрегатов с историей наблюдается в коде, но значимая деградация на ожидаемой нагрузке не измерялась. Источники `src/web/main.py:105–107`, `src/adapters/repositories/ticket_repository.py:143–146,209–263`, решения §11.
- В старом `ticket_application_service_api.md:231–246` аварийное удаление описано с условным сохранением будущего TicketUser. Текущий маршрут физически удаляет обе карточки с их историей. Новейший документ не определяет отдельную политику удаления. Это различие требует выяснения применимости старого описания, поэтому самостоятельное подтверждённое нарушение не выставляю. Источники `src/web/routers/admin/tickets.py:1046–1068`, `src/application/services/ticket_service.py:970–988`, `src/adapters/repositories/ticket_user_repository.py:324–354`.

## Проверенные согласованные сценарии

- Обе формы создания сохраняют положительный контакт. Если контакт отсутствует во входном теле, им становится владелец. Обе карточки поддерживают замену в ACCEPTED и DEFERRED. Через Admin ноль отклоняется с 400, через User ноль означает возврат к владельцу и не обнуляет сохранённое поле. Проверка внутреннего состояния остаётся у Ticket, а карта статусов относит ASSIGNED, AT_WORK и PAUSED к тому же внешнему IN_WORK. Код также допускает редактирование ряда начальных статусов. Формулировка §2 про ACCEPTED/DEFERRED относится к согласованным окнам, запрет редактирования до принятия отдельно не сформулирован. Источники `src/domain/ticket.py:88–100,465–482,867–880`, `src/domain/ticket_user.py:65–75,199–205,228–248`, `src/application/services/ticket_user_service.py:278–309`, `src/domain/statuses/rules/ticket_state_rule.py:24–65`.
- Смена отдела Admin заблокирована даже в ASSIGNED. Обычное включение Admin с отключённым назначенным отделом вернуло 400. Доменные методы update, change и remove используют общий факт текущего назначения. Документация `rules.md:39,69,75,86` всё ещё сужает правило до AT_WORK. Это расхождение документации, отделённое от конкурентного риска A6. Источники `src/application/services/admin_service.py:134–175,387–418,453–538,658–675`, `src/domain/services/admin_service.py:83–119,170–179,207–257`.
- При отключении Client одна проверяемая заявка, уже находившаяся на проверке, стала `suspended/suspended`, вторая в AT_WORK сохранила работу. Отдельный `finish-work` перевёл вторую в READY_FOR_REVIEW, после самостоятельной команды Admin `execute` пара стала `executed/confirmed_by_admin`. При проверке второй карточки после отключения использовано чтение временной БД. Доменный путь отключения владельца также исключает AT_WORK из остановки и синхронизирует подлежащие остановке связанные карточки. Источники `src/domain/services/client_service.py:230–258`, `src/domain/services/user_service.py:352–393,435–448`, `src/application/services/ticket_service.py:813–840,908–932`, `src/domain/statuses/mapping_statuses.py:55–69`.
- Искусственная ошибка сохранения внутренней карточки после первой записи внешней дала HTTP 500. Для обоих создающих маршрутов остались прежними количества строк обеих карточек и четырёх таблиц истории/комментариев. Общий UoW с rollback и проверка версий агрегатов дают основу для атомарной бизнес-команды. Источники `src/adapters/uow/sqlite_unit_of_work.py:76–127`, `src/application/services/ticket_user_service.py:152–206`, `src/application/services/ticket_service.py:168–194,1183–1204`, `src/adapters/repositories/ticket_repository.py:283–327`, `src/adapters/repositories/ticket_user_repository.py:283–305`.
- Внешний ключ связи есть, уникальности `tickets.user_ticket_id` нет. Это соответствует решению о возможном будущем 1:N. Текущие методы часто выбирают одну внутреннюю карточку. Поддержку 1:N потребуется определять до его включения. Источники `db/schema.sql:123–154`, `src/adapters/repositories/gateways/ticket_gateway.py:32–34`, `src/adapters/repositories/ticket_repository.py:126–141`, решения §4.
