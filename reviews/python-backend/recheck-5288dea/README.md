## Оценка архитектуры и совместной работы

Разделение FastAPI, прикладных команд, доменных правил, репозиториев и SQLite UoW позволяет проследить бизнес-операцию и проверить её транзакционно. Создание TicketUser/Ticket с историей, восстановление из БД, оптимистический конфликт и откат частичного сохранения подтверждены. Контакт, назначение, работа, завершение и каскад отключения согласованы в исследованных сценариях. Переписывание архитектуры целиком из этих результатов не следует.

Главный незавершённый стык — бизнес-UoW и auth: аккаунт изменяется в одной транзакции, refresh хранится и выдаётся отдельно. Другой системный пробел — отсутствие результата команды в той же транзакции, что сущность и история. Это объясняет N01 и N06. Локальный post-commit hook либо HTTP-кеш не обеспечат принятых гарантий. Более узкие проблемы N02–N05 исправляются без перестройки проекта. Общая версия исполнителя применяется непоследовательно; последствия для PostgreSQL требуют отдельной конкурентной проверки.

Охват: Python `src`, Python `utils`, точки запуска, DTO/assembler, policies, repositories/gateways/mappers, основная SQLite DDL, refresh storage, относящиеся документы и доступные backend-тесты. Фронтенд и его архивы, рабочие БД, `.env`, реальные секреты и персональные данные не использовались. Все динамические проверки — синтетические данные и временные SQLite. Внешние HTTPS/production workers, PostgreSQL, нагрузка и контейнер Python 3.14 не проверялись. Проверочный runtime — Python 3.12.14 / SQLite 3.53.1; версии зависимостей в [environment.json](tests/environment.json).

### N01. Постоянный отзыв refresh не связан с изменением аккаунта

**Путь:** настоящий login → `PATCH /admin/users/{id}/password` либо disable/enable сотрудника/аккаунта → `POST /auth/user/refresh` с прежним refresh. Отдельно: detach Account → attach нового Account тому же User с прежним login → refresh. В Admin realm проверены смена пароля и disable/enable другим авторизованным Admin. Оба backend: memory и SQLite.

**Источник:** [User mutations, user_service.py:217–318](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/services/user_service.py#L217-L318), [Admin password, admin_service.py:271](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/services/admin_service.py#L271), [AuthManager:185–251](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/services/services.py#L185-L251), [проверка employee ID:94–113,169–189](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/services/auth_service.py#L94-L113), [RefreshToken:196–215](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/tokens.py#L196-L215), [отдельные соединения storage:37–40](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/storage_sqlite.py#L37-L40).

**Факт и последствие:** мутация возвращает 200; старый refresh снова выдаёт access с 200. Во время отключения есть 401, после включения запрет исчезает. При замене Account employee ID совпадает, account_id уже другой, но сессия к нему не привязана. Смена пароля не прекращает возможность выпускать новые токены. Требуется постоянный отзыв, который enable не отменяет. Допущенное владельцем остаточное время уже выданного access к этому не относится.

**Доказательство:** восемь параметризованных User-сценариев в `test_account_lifecycle_permanently_rejects_old_refresh` и четыре Admin-сценария в [test_admin_refresh_revocation.py](tests/test_admin_refresh_revocation.py). Все 12 падают на исходнике и после малых патчей на финальном ожидании 401; первая мутация и необходимые промежуточные условия проходят.

**Исправление и проверка:** session repository с Account identity в основной UoW; отзыв вместе с password/detach/delete/disable и каскадом Client до одного COMMIT; общий протокол login/rotation против revoke. Нужны rollback обеих частей и конкуренция выдачи с отзывом, а не вызов текущего storage после COMMIT. [План 05](patches/05-refresh-revocation-plan.md) описывает точки изменения, совместимость и приёмку. Полный patch не подготовлен: изменение пересекает схему, auth orchestration, UoW и несколько бизнес-команд; безопасного отдельного hook для заявленной атомарности нет. Тесты Client cascade/revoke races ещё не выполнялись и не считаются пройденными.

### N02. Ротация продлевает абсолютный срок сессии

**Путь:** login в момент t0 с явными настройками 5 минут / 7 суток → refresh незадолго до t0+7 суток → новая пара. [TokenService.renew_tokens:66–95](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/services/services.py#L66-L95) вызывает [JWTToken.create:292–320](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/tokens.py#L292-L320), а [RefreshToken.create:219–240](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/tokens.py#L219-L240) заново задаёт created_at/expires_at от текущего времени. [AccessToken.create:63–83](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/auth/tokens.py#L63-L83) не учитывает исходный дедлайн.

**Факт и последствие:** за минуту до первоначального окончания выдаётся ещё 7 суток refresh и полный access на 300 секунд. Регулярная ротация позволяет продлевать сессию без нового login. Требуется один исходный предел t0+7 суток, включая токены последней ротации.

**Исправление:** [03-session-lifetime.patch](patches/03-session-lifetime.patch) переносит исходные даты refresh и ограничивает access этим дедлайном. Encode выполняется до атомарной замены. Legacy naive dates трактуются UTC так же, как в существующей валидации. **Истинный t0 уже ротированных прежним кодом сессий может быть утрачен**: patch его не восстанавливает. Для строгого перехода нужно завершить такие сессии либо использовать достоверный внешний источник даты входа. Уже выданный access с прежним exp сам не меняется.

**Доказательство/проверка:** [test_session_lifetime.py](tests/test_session_lifetime.py), реальные refresh обоих backend с управляемым временем: несколько ротаций, сохранение даты при повторном открытии storage, отказ на границе, предел access, legacy metadata. Ошибки encode и INSERT преемника не теряют старый refresh. Вместе с N03: **до 6 passed / 5 failed, после 11 passed**. Это проверка текущих SQLite/memory реализаций, без production-часов и PostgreSQL.

### N03. Настройки по умолчанию расходятся с принятыми сроками

**Источник:** [src/web/config.py:18–19](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/config.py#L18-L19).

**Путь и факт:** запуск без TTL overrides → штатный login → access на 1800 секунд, refresh на сутки. Требуется 300 секунд / 7 суток. Наблюдение относится к defaults кода; значения production `.env` не читались и не утверждаются.

**Исправление:** в том же [патче 03](patches/03-session-lifetime.patch) изменены только два центральных defaults. Тест default-policy в [test_session_lifetime.py](tests/test_session_lifetime.py) падает до патча и проходит после. Наличие правильных defaults не закрывает N02 или N01; параметры фактического развёртывания проверяются отдельно без публикации секретов.

### N04. При регистрации за пользователя неверно атрибутирован начальный CREATED

**Путь:** `POST /admin/tickets/` с действительными client_id и user_id → [TicketApplicationService:152–167](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/services/ticket_service.py#L152-L167) → [TicketUserService.create:63–70](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/domain/services/ticket_user_service.py#L63-L70) → [TicketUser.create:99–123](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/domain/ticket_user.py#L99-L123) → сохранение истории.

**Факт и последствие:** владельцем правильно остаётся User, ordinary comment правильно принадлежит Admin, но автор начального внешнего статуса равен User. История показывает действие не того участника. Требуется действительный инициатор — Admin при регистрации за User, User при самостоятельном создании.

**Исправление:** [01-created-actor.patch](patches/01-created-actor.patch) добавляет optional actor отдельно от owner; прикладная Admin-ветвь передаёт проверенного инициатора. Старые вызовы без параметра сохраняют self-create, actor не принимается произвольно из HTTP-body. Комментарий фабрики также использует инициатора. Старые строки не переписываются: реальный инициатор по одному owner не восстанавливается.

**Доказательство/проверка:** `test_staff_is_the_actual_initial_actor_but_owner_is_preserved` и матрица [test_history_and_json.py](tests/test_history_and_json.py), включая сохранение/чтение, User self-create, обратную совместимость и старую историю. Внутренний автоматический actor0 оставлен SYSTEM_GENERATED: это отдельная документированная семантика. Набор истории/JSON с патчами 01+02: **до 4 passed / 5 failed, после 9 passed**.

**Путь:** создать standalone либо связанный Ticket с комментарием → получить карточку, добавить комментарий или изменить статус → [TicketAssembler:44–71](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/assemblers/assembler.py#L44-L71) → [TicketResponse.statuses/comments:282–288](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/models/tickets.py#L282-L288).

**Факт и последствие:** ответ успешен, но comment — объект `{"value": "текст"}`, а для пустого статусного комментария также не строка. Пользовательский [assembler:117–139](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/assemblers/assembler.py#L117-L139) уже возвращает текст. **Исправление:** [02-admin-comment-json.patch](patches/02-admin-comment-json.patch) извлекает текст на границе assembler; пустой статусный комментарий становится `""`. Domain VO и хранение истории не меняются. Это необходимое изменение Admin API по прямому решению владельца; потребители должны читать строку.

**Доказательство/проверка:** реальный GET/create/add-comment/status, обычные и пустые комментарии, обе карточки, standalone и readback в [test_history_and_json.py](tests/test_history_and_json.py), плюс `test_admin_comment_and_status_comment_are_plain_strings`. До патча строковый контракт падает, после проходит; сводный результат 01+02 указан выше.

### N06. Переданный Idempotency-Key не влияет на создание

**Источник и путь:** [User POST:111–138](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/routers/user/tickets.py#L111-L138), [Admin POST:65–93](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/web/routers/admin/tickets.py#L65-L93) и остальные создания не принимают ключ в команду. [Сохранение Ticket:1183–1204](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/services/ticket_service.py#L1183-L1204) фиксирует сущности/историю без записи результата. В [db/schema.sql](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/db/schema.sql) и UoW нет хранилища ключей. Заголовка нет в OpenAPI.

**Воспроизведение:** после успешного первого POST повторить тот же URL, тело, авторизованного субъекта и ключ. У Ticket/UserTicket появляются дополнительные карточки и начальная история; у comments — повторный комментарий. Для Department или вложенного Account обычная уникальность может вместо дубля дать 409/400, но исходный успех не воспроизводится. Тот же ключ с изменённым текстом заявки также создаёт новую пару вместо конфликта. Все первые операции в регрессиях успешны, поэтому это не отказ невалидной фикстуры.

**Последствие и требование:** потерянный после COMMIT ответ или повторная доставка дают повторный эффект. Ключ необязателен, но переданный должен работать в области субъекта/команды с отпечатком нормализованного запроса и сохранённым результатом на 24 часа. Новые ключи остаются отдельными командами с обычными доменными ограничениями. Вложенный Account входит в команду родителя, отдельного Account-key не требуется.

Проверенный inventory из [test_creation_idempotency.py](tests/test_creation_idempotency.py):

| Команда | Маршрут |
|---|---|
| Client | `POST /admin/clients/` |
| Department | `POST /admin/departments/` |
| Admin, в том числе с Account | `POST /admin/admins/` |
| User, в том числе с Account | `POST /admin/users/` |
| Admin Role / User Role | `POST /admin/roles/admin`, `POST /admin/roles/user` |

**Доказательство:** 24 replay-кейса по inventory и обоим refresh backend, ещё три повторения/конфликта в [test_current_contracts.py](tests/test_current_contracts.py) падают до и после малых патчей. Положительные контроли без ключа/с разными ключами проходят. Тесты считают эффекты в БД и историю, сравнивают первоначальный ответ. Полный TTL, потеря ответа на транспортном уровне, конкуренция одинаковых ключей и isolation всех scopes ещё не проверены: механизма пока нет.

**Исправление:** [план 06](patches/06-idempotency-plan.md): объявленный optional header, repository в business UoW, ключ/результат/бизнес-данные/история в одном COMMIT, replay после повторной авторизации. Ожидаемый unique conflict полностью откатывает попытку, результат читается в новой UoW; vendor UPSERT и серверные повторы бизнес-команды не нужны. Полный patch не подготовлен: требуется согласовать транзакцию всех десяти маршрутов и формирование ответа до COMMIT. Middleware, записывающий ключ после ответа, оставит исходное окно дубля. 409 для другого тела — предлагаемый HTTP-статус теста; обязательный контракт — конфликт без второго эффекта, числовой статус отдельно владельцем не утверждён.

## Условные риски и проверенные границы

**R01, версия исполнителя при self-assign/remote.** [ticket_service.py:603–631,714–722](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/application/services/ticket_service.py#L603-L631): обычное назначение другого Admin вызывает touch; назначение себя и remote из ACCEPTED его пропускают. Измеренные изменения Admin.version — 0/1/0. При переносе схемы на READ COMMITTED возможна запись назначения по устаревшему состоянию Admin после его отключения/перевода. Запрещённая успешная PostgreSQL-последовательность в этой среде не воспроизводилась; действующий dependency открывает SQLite UoW.

[04-executor-version-guard.patch](patches/04-executor-version-guard.patch) вводит общий контроль для обеих ветвей. [test_executor_guard.py](tests/test_executor_guard.py): **1 passed / 4 failed → 5 passed**, включая rollback назначения и обеих историй при отказе CAS. Это подтверждает участие в протоколе версии на SQLite. Для PostgreSQL нужны два соединения, барьер после чтения Admin, параллельное отключение/перевод и проверка обоих порядков COMMIT. Ни patch, ни слово touch сами по себе не заменяют такую приёмку.

**R02, NULL-version других агрегатов.** DDL допускает NULL в версиях Employee/Department/Client. В синтетических допустимых DDL-строках [admin_mapper.py:42](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/adapters/repositories/mappers/admin_mapper.py#L42) и [department_mapper.py:23](https://github.com/tegasae/simple_tickets/blob/5288dea85d8f7e7e4c84d4801781d297e0e14475/src/adapters/repositories/mappers/department_mapper.py#L23) дают 500, User/Client нормализуются к 0 и ложно конфликтуют с SQL NULL. Реальный путь появления таких строк обычным API и наличие поддерживаемых старых данных не установлены. Условный риск совместимости; отдельный patch без решения о поддерживаемых данных не предложен. Прежнее исправление NULL-version Ticket/TicketUser этим не опровергается.

**R03, тестовый запуск/документы.** Прежние тесты удалены; root pytest не является актуальным зелёным CI: в очищенном source-пакете exit5 без тестов, в Git-layout с историческими review/tests — exit2 на двух старых импортирующих `old_review_tests` модулях. Семь backend Python-файлов из legacy-архива также устарели. Старое число тестов/процент покрытия не переносится на новый код. Оба shell launcher с явно выбранными последними 70 регрессиями собирают набор; конкретный layout и команды сохранены в [tests/README.md](tests/README.md). Фронтенд-архивы не открывались.

Прямой application DTO допускает Department при User create без общего guard, но текущий HTTP request такого поля не содержит и отклоняет его с 422. Это латентный риск будущего caller, не подтверждённая обычная HTTP-гонка. Нагрузка списков, DB-readiness и прямые transient errors отдельного refresh storage остаются вне доказанного исправления F11.

## Разногласия и вопросы владельцу

В первичных QA/арбитражном заключениях новое правило CREATED было слишком широко распространено на автоматический внутренний Ticket.actor0. После проверки прямого определения SYSTEM_GENERATED эта квалификация отозвана в раундах 2/3 и [финальном арбитраже](experts/arbiter-final.md). Первичные тексты не исправлялись. Финальное несогласие не разрешалось голосованием. PostgreSQL-гонка и происхождение legacy NULL остаются условными до указанных выше проверок.

Последние решения владельца уже обязательны; повторно утверждать 5 минут/7 суток/24 часа, область созданий, optional key и клиентские повторы не нужно. Для реализации/перехода остаются конкретные вопросы:

1. Допустимо ли завершить все старые refresh при переходе на неизменный семисуточный срок? У уже ротированных старым кодом сессий исходная дата входа может отсутствовать. Без неё бесшовный точный пересчёт невозможен.
2. Требуется ли поддерживать в существующих данных NULL-version Employee/Department/Client? Если да — нужны нормализация и совместимый CAS с отдельным тестом; наличие таких рабочих строк здесь не проверялось.
3. Для конкурентного повтора одного ключа какой предел ожидания и временный HTTP-ответ выбрать? 409 для изменённого тела — предлагаемый стандарт; ограничения длины ключа, время ожидания и политика сохранения окончательных бизнес-отказов ещё технически не выбраны. Первое обязательное успешное повторение уже однозначно задано.
4. При переводе refresh в общую БД нужен ли перенос существующего отдельного файла или допустим новый login? Это определяет переход, а не отменяет требование общей транзакции.
