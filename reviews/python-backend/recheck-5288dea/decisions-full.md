# simple_tickets: согласованные правила и подготовка к production

Дата: **24 ноября 2026 года**, Europe/Moscow.

Документ объединяет обсуждение после повторного аудита Python-бэкенда и последние уточнения владельца. Он предназначен для скачивания и дальнейшей постановки задач. Решения ниже не означают, что соответствующий код уже реализован или прошёл production-проверки.

Основание аудита — снимок `bbf7a392dafe0fede2d5d017af36281b6f4f40a2` репозитория `tegasae/simple_tickets`, ветка `api-new-client-scheme`. Последующие ответы владельца уточняют требования и имеют приоритет над открытыми вопросами прежних отчётов.

## 1. Состояние подготовки

Со слов владельца:

- запуск приложения подготовлен на отдельном сервере;
- HTTPS и сетевой доступ подготовлены;
- конфигурация и работа с секретами подготовлены;
- для production выбран PostgreSQL;
- миграции сейчас не требуются, но будут использоваться при последующих изменениях схемы.

Настройки реального сервера в рамках этого обсуждения не проверялись. Параметры резервирования и восстановления отдельно не согласованы.

## 2. Бизнес-правила, которые теперь определены

| Тема | Согласованное правило |
|---|---|
| Контакт заявки пользовательского происхождения | Если Ticket создан из пользовательской заявки — `CREATED_FROM_TICKET_USER` или `CREATED_FROM_USER_REQUEST` — положительный `contact_user_id` обязателен и сохраняется на всём жизненном цикле. Очистка контакта до отсутствующего значения запрещена |
| Изменение контакта | Через обе карточки разрешено менять контакт при внутреннем `ACCEPTED/DEFERRED`. Внешний `IN_WORK` представляет несколько внутренних состояний, поэтому проверка внутреннего Ticket сохраняется |
| Начальный `CREATED.actor` | Фактический инициатор: Admin при регистрации заявки за пользователя, User при самостоятельном создании. Владелец заявки хранится отдельно |
| Обычный комментарий | Автором является тот, кто ввёл текст; комментарий Admin не приписывается владельцу User |
| Смена отдела Admin | Пока у сотрудника есть текущее назначение исполнителем, менять отдел нельзя. Документацию, упоминающую только `AT_WORK`, нужно привести к этому правилу |
| Включение Admin | Нельзя включить сотрудника в отключённом назначенном Department. Сначала включить отдел либо снять назначение в отдел |
| JSON комментария | В административном ответе текст должен быть строкой, как в пользовательском API. Доменный value object может сохраняться внутри приложения |
| Отключение владельца или клиента | Заявки, уже находящиеся на проверке, закрываются как финальный `SUSPENDED` в обеих карточках; активная работа продолжается |
| Завершение сохранённой активной работы отключённого клиента | Сотрудник завершает работу, заявка остаётся в `READY_FOR_REVIEW`. Проверку и дальнейшую административную финализацию выполняет Admin отдельной командой. Это допустимый редкий сценарий |
| Автоматический `EXECUTED` | После `finish-work` не требуется: сохраняется отдельный этап проверки |

Требование о фактическом инициаторе начального статуса уточнено после аудита. Ранее предложенный патч автора обычного комментария сам по себе это поле не исправлял. Формат административного JSON следует изменять на границе ответа, сохраняя корректную доменную модель.

## 3. Контроль конкурентного назначения исполнителя

### Проблема

На PostgreSQL READ COMMITTED возможен следующий порядок:

1. T1 читает включённого Admin из отдела А и проверяет возможность назначения.
2. T2 не видит ещё не сохранённого назначения, отключает Admin либо переводит его в другой отдел и фиксирует изменения.
3. T1 сохраняет Ticket на основании старого состояния сотрудника.

Версия Ticket не обнаруживает изменение другого объекта — Admin. В проверенном коде общий guard исполнителя пропущен для `assign(self)` и ветки удалённого самоназначения из `ACCEPTED`. Успешное нарушение такого инварианта на SQLite не показано; реальная PostgreSQL-проверка ещё нужна.

### Предлагаемое исправление

Для этой гонки достаточно общего `touch` исполнителя при выполнении всех условий:

- touch условно изменяет версию строки Admin при совпадении с прочитанной версией; несовпадение даёт конфликт;
- отключение и смена отдела сохраняют Admin с проверкой той же версии;
- проверка условий, touch, сохранение Ticket и истории выполняются одной транзакцией;
- конфликт откатывает всю команду;
- новая попытка использует свежие объекты и повторяет проверки.

Общий guard нужен и при назначении себя, и при назначении другого сотрудника. Простое повторное чтение перед записью не заменяет его: между чтением и записью остаётся окно изменения.

Проверка: два PostgreSQL-соединения, управляемый барьер после чтения, назначение против отключения/смены отдела. Обе команды не должны успешно фиксировать запрещённое сочетание. Это направление исправления конкретной гонки, а не утверждение о проверенной безопасности всех конкурентных операций приложения.

## 4. Одна или несколько внутренних заявок

Владелец допускает, что в будущем из одного TicketUser будет формироваться несколько Ticket. Сейчас обычный сценарий создаёт одну внутреннюю карточку.

Поэтому UNIQUE на `tickets.user_ticket_id` не предлагается как постоянное правило модели. Внешний ключ продолжает проверять существование указанной пользовательской карточки. Отсутствие уникальности с учётом выбранного направления не считается самостоятельным дефектом.

До включения сценария «один TicketUser — несколько Ticket» нужно доработать методы, возвращающие одну внутреннюю карточку, и определить агрегирование общего статуса, завершения, отмены и истории. Существующий API не объявляется уже поддерживающим этот сценарий.

## 5. Токены и отзыв сессий

### 5.1. Утверждённые сроки

| Параметр | Значение |
|---|---|
| Access JWT | **5 минут** |
| Refresh-сессия | **7 суток от первоначального входа** |
| Абсолютный срок сессии | **Те же 7 суток**, без бесконечного продления |

При refresh меняется токен, но конечная дата сессии сохраняется. Ротация на шестые сутки не даёт ещё семь суток. После абсолютного срока нужен новый вход. Access-токен, выдаваемый в конце сессии, не должен продлевать доступ за согласованный абсолютный срок.

Сроки задаются именованными параметрами в одном месте. Числовые значения не распределяются по методам. В дальнейшем источник параметров переносится в конфигурацию без изменения логики авторизации.

### 5.2. Что означает отзыв

Смена пароля, удаление аккаунта и отключение сотрудника отзывают его refresh-сессии. Повторное включение не восстанавливает отозванные refresh. Аккаунт и субъект проверяются по постоянным идентификаторам и типу, а не только по логину.

Владелец допускает задержку прекращения действия ранее выданного access на несколько минут. Поэтому рабочая схема не требует отдельной проверки серверного `sid` при каждом запросе: access ограничен своим сроком, а обновить его через отозванный refresh нельзя. Существующие проверки активности сотрудника/аккаунта/клиента и прав сохраняются и могут отказать раньше истечения JWT.

Это уточняет раннее предложение немедленно проверять серверную сессию на каждом запросе. Ранний вариант остаётся технической возможностью, но больше не является обязательным требованием. Подпись и срок JWT проверяются всегда; кеш не должен продлевать истёкший access.

Важно различать гарантии: refresh после повторного включения не оживает; ранее выданный access оценивается обычными проверками до своей исходной даты окончания. Если сотрудника быстро отключить и включить до этой даты, немедленная неизменяемая инвалидизация старого access этим вариантом не обещается.

### 5.3. Общая БД и UoW

Предлагается хранить аккаунты и refresh-сессии в одной БД. Для атомарного изменения они используют одно соединение и одну UoW. Недостаточно указать одинаковый путь к файлу, если хранилище самостоятельно открывает другую транзакцию.

Пример смены пароля:

1. Начать транзакцию.
2. Проверить полномочия и загрузить необходимые данные.
3. Изменить и сохранить пароль.
4. Отозвать refresh-сессии этого аккаунта.
5. Выполнить один COMMIT.

Ошибка до успешного COMMIT откатывает оба изменения. Удаление аккаунта и отключение сотрудника организуются аналогично. Отзыв при каскадном отключении Client нужно включить в соответствующую прикладную операцию.

В текущей реализации SQLite-хранилище refresh открывает собственные соединения. Для описанных операций нужен репозиторий сессий, использующий общую транзакцию UoW. Можно добавить или перенести таблицу refresh-сессий в основную БД; несколько таблиц необязательны. Конкретную схему следует выбирать при реализации.

Атомарность сама по себе не устраняет конкурентные гонки. Ротация refresh и выдача сессии на основании проверки аккаунта должны согласовываться с отзывом, чтобы устаревшая проверка не оставила действующую refresh-сессию после него. Протокол версий или блокировок проверяется отдельно.

### 5.4. SQLite сейчас, PostgreSQL позже

Один устойчиво сохраняемый SQLite-файл допустим как промежуточное общее хранилище одного сервера, если все workers действительно используют этот файл. Нужно проверить перезапуск, конкурентную ротацию и отзыв через разные workers. Независимые локальные файлы на разных серверах общим хранилищем не являются.

При переходе на PostgreSQL сохраняется контракт репозитория и общей UoW. Нужно заранее выбрать, переносить действующие сессии или завершить их и потребовать новый вход. Memory-реализация остаётся режимом отдельного процесса/тестов и не обеспечивает атомарность с постоянной БД аккаунтов.

## 6. Идемпотентность: область и сроки

Утверждено:

- механизм относится ко всем API-командам создания сущностей, а не только Ticket;
- **Account исключён из отдельной идемпотентности**: самостоятельный ключ для него не вводится;
- если Account создаётся вместе с Admin/User, он входит в общую транзакцию и результат родительской команды;
- добавление комментариев также входит в область создания;
- `Idempotency-Key` необязателен;
- результат хранится **24 часа после успешного COMMIT**;
- составная команда создания TicketUser/Ticket и истории использует один ключ на всю операцию.

Точный список маршрутов следует сопоставить со всеми такими прикладными командами при реализации, без произвольного ограничения двумя маршрутами заявок. Login/refresh имеют отдельный протокол ротации и не объявляются автоматически покрытыми механизмом бизнес-команд.

Запрос без ключа работает обычным образом. Защита от повторной доставки для него не гарантируется. После истечения срока хранения результата прежний ключ также не обеспечивает прежнюю гарантию.

## 7. Почему появляются дубликаты и как работает ключ

### Без ключа

1. Клиент отправляет создание заявки.
2. Сервер сохраняет TicketUser, Ticket и историю одним COMMIT.
3. Ответ теряется либо клиент прекращает ожидание по таймауту.
4. Клиент не знает результата и отправляет запрос ещё раз.
5. Сервер создаёт вторую пару с новыми ID.

Уникальность связи Ticket/TicketUser не решила бы этот случай: повтор создаёт новую пользовательскую карточку. Сравнение по тексту тоже неверно — две одинаковые заявки могут быть намеренными.

### С ключом

1. Клиент создаёт ключ K1 для новой логической операции и сохраняет его вместе с данными до отправки.
2. Сервер проверяет доступ и входные данные.
3. В одной транзакции сохраняются ключ, отпечаток запроса, бизнес-записи, история и подготовленный результат.
4. После успешного COMMIT ответ теряется.
5. Клиент повторяет тот же запрос с K1.
6. Сервер снова проверяет доступ и возвращает сохранённый результат, без новых карточек и повторной истории.

Область ключа включает тип и постоянный ID субъекта и команду. Адресат команды над существующим объектом входит в область или отпечаток. Результат нельзя искать только по глобальному значению ключа либо по логину.

Тот же ключ и то же содержимое возвращают исходный результат. Тот же ключ в той же области с другим допустимым содержимым даёт конфликт, предлагаемый статус — 409. Новый ключ с тем же текстом создания заявки обозначает отдельную намеренную операцию. Права и доменные ограничения продолжают действовать.

Ключ не создаётся заново на каждую сетевую попытку. Изменённая форма не должна незаметно отправляться со старым ключом. Сохранённый ответ отражает исходный результат операции; текущее состояние карточки читается отдельно.

## 8. Транзакции и переносимость механизма ключей

Используются обычные транзакции и уникальное ограничение на область операции с ключом. Vendor-specific UPSERT для прикладного протокола не требуется. Native ошибки преобразуются адаптером в нейтральные типы.

При ожидаемом конфликте уникальности переносимый порядок — полностью откатить попытку и открыть новую транзакцию для чтения сохранённого результата. Продолжение работы после исключения в той же транзакции нельзя считать одинаково допустимым для всех драйверов.

Два одновременных повторения должны дать один бизнес-эффект. Вторая попытка получает результат после фиксации первой либо согласованный временный ответ при исчерпании ожидания. Если первая попытка откатилась, следующая может выполнить команду. Откатившаяся временная ошибка не должна навсегда занимать ключ как успешная операция.

Максимальное ожидание конкурентной команды, точный временный статус и правила сохранения окончательных бизнес-отказов ещё нужно выбрать. Бизнес-записи, история и успешный результат обязаны фиксироваться атомарно.

## 9. Повторы выполняет клиент

Выбранный первый вариант: клиент повторяет HTTP-запрос, сервер обеспечивает атомарность, идемпотентность и понятную классификацию отказов. Внутренние автоматические повторы сервера пока не вводятся.

На новом запросе сервер создаёт новую UoW, заново читает существующие сущности и создаёт новые объекты для ещё не выполненного создания. После rollback нельзя повторно сохранять старые мутированные объекты: в них могли остаться присвоенные ID, версии и ID истории, уже отсутствующие в БД.

| Результат попытки | Предлагаемое действие клиента |
|---|---|
| Сетевой сбой / неизвестный результат | Ограниченный повтор с прежним ключом на поддерживаемом маршруте |
| Согласованный временный 429/503 | Повтор с задержкой и учётом Retry-After, если он указан |
| Ошибка входных данных | Исправление данных; слепой повтор не нужен |
| Отказ авторизации / прав | Разрешение причины отказа; обычный retry её не устраняет |
| Конфликт того же ключа с другим телом | Исправление использования ключа |
| Конфликт версии сущности | Перечитать состояние и разрешить конфликт, не смешивать с повторной доставкой |
| Неожиданный 500 | Не считать автоматически временной ошибкой |

Нужны ограничение числа попыток и общего времени, увеличивающаяся задержка и определённое поведение UI при неизвестном результате. Численные параметры пока не утверждены. Если позже появятся серверные повторы транзакций, их бюджет согласуется с клиентским.

Повтор самого refresh после потери ответа требует отдельного решения: старый токен мог уже смениться. Политику повторов создания заявок нельзя автоматически распространить на все auth-запросы.

## 10. Проверка через OpenAPI / Swagger UI

После реализации заголовок `Idempotency-Key` включается в OpenAPI выбранных маршрутов как необязательный параметр. Swagger UI показывает поле ключа; Bearer-авторизация настраивается отдельно через Authorize.

Последовательный сценарий:

1. Авторизоваться синтетической учётной записью и создать заявку с K1.
2. Запомнить ID и результат.
3. Повторить тот же маршрут, тело и K1: получить тот же результат и ID.
4. Проверить отсутствие новой пары и повторной первоначальной истории.
5. Изменить допустимое тело при K1: получить конфликт без новой записи.
6. Отправить исходный текст с K2: получить вторую намеренную заявку.
7. Повторить после обновления access той же личности: область бизнес-ключа не должна зависеть от конкретного access-токена.
8. Отправить запрос без ключа: получить обычное выполнение без гарантии устранения повторной доставки.

Обычное чтение работает без ключа. Отдельных правил только для Swagger нет. Обрыв ответа после COMMIT и параллельные запросы проверяются автоматическими интеграционными тестами с управляемыми отказами и барьерами.

## 11. Наблюдаемость и обновление

Минимально предлагаются:

- структурированные логи: UTC, request ID, метод, шаблон маршрута, статус, длительность и тип ошибки;
- исключение паролей, токенов, Authorization, содержимого .env и полных текстов заявок из диагностических логов и внешних сборщиков ошибок;
- отдельные проверки живости процесса и готовности обслуживать запросы с БД;
- метрики ошибок, задержек, операций/соединений БД, памяти, CPU и свободного места;
- уведомления об устойчивой недоступности, росте серверных ошибок и нехватке ресурсов;
- воспроизводимая выкладка, контроль после обновления и возврат предыдущей версии.

В аудированном снимке `/health` подтверждает живость процесса; readiness с проверкой БД требует отдельной реализации. Проверки должны быть лёгкими и не менять бизнес-данные. Ожидаемые отказы доступа и конфликты версий отделяются от внутренних аварий. Бизнес-история сохраняется в своей транзакции и не заменяется техническими логами.

Производительность списков нужно измерить на синтетических объёмах, похожих на ожидаемые: крупный клиент, длинная история, несколько одновременных пользователей. По измерениям выбираются пагинация, облегчённые проекции списка, пакетная загрузка и индексы. Наличие TODO само по себе не доказывает дефект или неприемлемую скорость.

Инструменты, пороги уведомлений, сроки хранения логов и ответственные ещё не определены. Документ не утверждает, что мониторинг уже настроен.

## 12. Проверки перед реализацией и приёмкой

Это план будущих проверок, а не отчёт об их выполнении:

1. PostgreSQL: назначение против отключения/смены отдела с двумя соединениями и проверкой общего guard.
2. Бизнес-правила: обязательный контакт, допустимые окна изменения, запрет смены отдела при назначении, фактический CREATED.actor, строковые комментарии, административное завершение редкой ситуации отключённого клиента.
3. Сессии: общий файл между workers, перезапуск, стабильная идентичность аккаунта и абсолютная дата окончания.
4. Смена пароля/удаление/отключение: атомарное изменение и отзыв refresh, отсутствие восстановления отозванных refresh после включения.
5. Конкурирующие refresh и отзыв: отсутствие действующей сессии, возникшей по устаревшей проверке после отзыва.
6. Access: срок 5 минут, обычные проверки доступа сохранены, допустимое окно до exp явно учитывается.
7. Идемпотентность всех согласованных созданий: повтор результата, другое тело, новый ключ, откат, обрыв ответа после COMMIT, конкурентный дубль, изоляция субъектов/команд, отсутствие ключа и истечение 24 часов.
8. Клиентские повторы: сохранение ключа и данных, задержка, бюджет и прекращение попыток.
9. Мониторинг: ошибка находится по request ID, секреты отсутствуют, готовность отражает недоступность БД, тестовое уведомление доходит ответственному.

Используются временные БД и синтетические объекты. Рабочие базы, реальные токены, пароли и персональные данные в документ не включены.

## 13. Что ещё остаётся выбрать

Основные бизнес-правила, сроки токенов, необязательность ключа, 24-часовое хранение и исключение отдельного Account уже согласованы. Перед конкретной реализацией остаются технические параметры:

- инвентаризация API-команд создания и способ объявления заголовка в OpenAPI;
- формат/ограничение длины ключа и точная нормализация отпечатка;
- время ожидания конкурентного выполнения и соответствующий временный HTTP-ответ;
- состав сохраняемого ответа и политика окончательных бизнес-отказов;
- бюджет и задержки клиентских повторов, поведение при исчерпании попыток;
- восстановление после потери ответа refresh;
- технический протокол конкуренции отзыва с выдачей/ротацией;
- судьба действующих сессий при переходе SQLite → PostgreSQL;
- инструменты и параметры наблюдаемости.

В этом документе отсутствуют реализация, SQL-миграции и обещание готовности production. Он фиксирует актуальные договорённости и основания для следующего задания.
