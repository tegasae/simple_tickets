# N01: полный отзыв refresh — объём необходимого исправления

Статус: **обязательный функциональный разрыв подтверждён; готовый unified diff полного исправления в этом проходе не подготовлен и не проверен**. Это план следующего сквозного изменения. Малый post-commit вызов текущего storage не выполняет согласованную атомарность и потому не выдаётся за исправление.

## Что воспроизведено

Реальные login → password-change → refresh и disable → enable → refresh проходят со старым refresh в Admin/User и обоих backend. После detach/reattach тому же User с новым account_id старый refresh также принимается. Пользователь допустил окно старого access до5мин; это не разрешение продолжать выпуск новых access через отозванный refresh.

Источник: application/services/admin_service.py и user_service.py (password/disable/detach), client_service.py (cascade); web/auth/services/auth_service.py (employee ID вместо Account identity), services.py (отдельные проверки/выдача), storage_sqlite.py (собственные соединения). Общий UoW не содержит репозитория сессий.

## Минимально законченный объём

1. Постоянная сессия привязана к subject_type, subject_id и конкретному сохранённому account_id. Не восстанавливать идентичность старой сессии по текущему владельцу login. При создании токенов использовать реально сохранённый Account, а не неперечитанный объект с account_id=0.
2. Репозиторий сессий включается в основную UoW. Аккаунт и сессии изменяются через одно соединение/транзакцию. Одинаковый SQLite path при двух независимых соединениях этого не гарантирует. Настройка прежнего отдельного refresh-файла требует явного переходного решения, а не молчаливого разделения COMMIT.
3. Auth orchestration охватывает проверку аккаунта и выдачу/ротацию одной согласованной транзакцией. Сейчас authenticate_user завершает свою UoW раньше TokenStorage.put. Нельзя просто разрешить произвольное вложение UoW: нужно явно разделить владельца транзакции и внутренние операции, сохранив запрет случайного nesting и прежние публичные вызовы по возможности.
4. Все необходимые мутации Admin/User и каскад Client выполняют отзыв до единственного COMMIT: password, detach/delete Account, disable Account/сотрудника, удаление субъекта. Enable не снимает отзыв. Удаление Account должно корректно обрабатывать FK сессий и не оживлять их при новом Account того же сотрудника.
5. Login/refresh и отзыв используют общий version/lock-протокол для Account/сессии. Проверка активности до COMMIT отзыва не должна позволить записать действующий successor после отзыва. Одной группировки изменений транзакцией для этого недостаточно.
6. Сохраняются разделение realm, безопасные401 и проверка текущей активности/прав. Дополнительный sid-check каждого access не требуется; разрешённое окно access ограничено5мин и его исходным exp.
7. Memory backend остаётся отдельным процессным/тестовым режимом. Его нельзя выдавать за общий постоянный production-store либо обещать атомарность памяти с durable аккаунтами без отдельного механизма. Общий production-контракт проверяется на persistent backend.

## Совместимость и переход

Новые схемные поля и таблицы потребуют версии схемы/подготовки чистой учебной БД и определения поведения старого token payload без Account identity. Безопасный вариант — завершить такие старые сессии и потребовать login; принимать их с подставленным текущим account_id нельзя. Данные рабочих БД не читались и не мигрировались.

Настоящий first-login timestamp уже ротировавшейся старой сессии мог быть утрачен. Patch03 сохраняет имеющийся дедлайн и не продлевает его, но не восстанавливает неизвестную историю. Для строгого семисуточного правила с момента первого входа необходим явный переходный режим.

## Доказательства будущего исправления

Падающие сейчас tests/test_admin_refresh_revocation.py и lifecycle-параметры test_current_contracts.py являются частью контракта, без xfail. Требуется дополнить их каскадом Client, удалением субъекта, failure injection на второй части и COMMIT, restart/multi-worker, login/refresh против revoke на двух независимых соединениях и проверкой Account identity. Необходимо показать сохранность обеих сторон при rollback.

Почему нет малого готового diff: нужен согласованный session repository/UoW/schema, интерфейсы auth, несколько business mutation paths и конкуренция выдачи/отзыва. Hook после COMMIT, удаление только по username либо изменение только refresh endpoint оставляют воспроизведённые пути или нарушают атомарность. Неполный patch создал бы ложную гарантию отзыва. Реализация не подменена patch03, который исправляет только срок.
