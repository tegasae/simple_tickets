# N06: идемпотентность всех созданий — объём необходимого исправления

Статус: **отсутствующая обязательная функция подтверждена; готовый unified diff полного протокола в этом проходе не подготовлен и не проверен**. Ни middleware после ответа, ни UNIQUE связи карточек не выполняют требование. Здесь приведён конкретный объём следующего изменения и его приёмка.

## Область

Создания Client, Department, Admin, User, обеих Role, административного Ticket, пользовательской пары и оба add-comment endpoint. Account не является отдельной командой ключей; Account внутри Admin/User входит в результат и транзакцию родителя. Ключoptional, результат24чпослеуспешногоCOMMIT. Login/refresh имеют отдельный протокол.

В tests/test_creation_idempotency.py зафиксированы10 маршрутов и два дополнительных родительских варианта с Account; все первые операции успешны. Сейчас повтор даёт новый объект/комментарий либо ошибку уникальности вместо прежнего результата. Тесты проверяют и положительные обычные создания без ключа/с разными ключами.

## Требуемое сквозное изменение

1. Объявить optional Idempotency-Key в OpenAPI и передать его в application command. Не прятать контракт в неописанном глобальном middleware.
2. После текущей авторизации, но до повторного исполнения изменяемых бизнес-предусловий, определить scope: subject_type, subject_id, command и согласованное включение target ID для комментария. Уже созданный login/Department не должен мешать replay успешно выполненной операции. Доступ/активность/права проверяются заново и при replay.
3. Нормализовать тело и существенные параметры адресата детерминированно. Server-generated ID/время исключаются. В родительских созданиях есть пароль: не хранить raw body/пароль в result-table или логах; выбрать отпечаток, который не превращает запись в быстрый offline password verifier, например keyed HMAC с отдельным управляемым ключом. Это технический выбор реализации, а не утверждение о существующей утечке.
4. Добавить таблицу и репозиторий операции в ту же UoW, что бизнес-записи и история. Уникальное ограничение покрывает scope+key, а не Ticket.user_ticket_id. Поддерживать состояния только в соответствии с одним протоколом COMMIT/rollback.
5. Зарегистрировать ключ, выполнить бизнес-команду и подготовить воспроизводимый исходный response до единственной успешной фиксации. Текущие внутренние commit helpers должны быть согласованы с этой границей. Сохранение ключа отдельно после ответа оставляет окно COMMIT→потеря ответа→дубликат.
6. Replay возвращает сохранённый статус/тело/необходимые заголовки, без повторного сохранения aggregate/history. Тот же scoped key с другим допустимым запросом даёт конфликт;409 — предлагаемый стандартный статус, а не отдельно подтверждённое владельцем число. Новый ключ не отменяет обычных доменных ограничений уникальности.
7. Expected unique conflict откатывает всю попытку. Сохранённый результат читается в новой UoW; не продолжать PostgreSQL-транзакцию после native exception, не пересохранять мутированные объекты. Использовать стандартные транзакции/ограничения; vendor UPSERT не требуется.
8. При конкурентной незавершённой операции нужен согласованный предел ожидания и временный ответ. Это обработка повторной доставки, не автоматический повтор бизнес-команды сервером. Общие server retry не вводить.
9. TTL связан с успешной фиксацией результата, а не временем начала первой попытки или сроком токена. Очистка не удаляет действующее выполнение/результат раньше гарантий. После24часов прежний ключ не гарантирует устранения новой доставки.
10. Отсутствующий ключ оставляет обычное поведение всех существующих вызовов. Invalid key, ограничения длины, ожидание и политика окончательных business failures описываются явно; ещё не утверждённые значения не подменяются случайными константами.

## Регрессии и ограничения

Должны пройти все replay-проверки текущих tests/test_creation_idempotency.py и три ключевых сценария test_current_contracts.py. Дополнительно требуются: разные subject/realm/command/target, обновление access той же личности, отзыв доступа перед replay, другой payload, ровно один эффект и набор истории, forced rollback до COMMIT, обрыв ответа после COMMIT, concurrent duplicate и TTL после24часов. Сейчас проверена только воспроизводимость отсутствия функции; проверка её TTL невозможна без реализации хранилища результата и не считается пройденной.

Почему нет малого готового diff: правильная реализация затрагивает все10 маршрутов, DTO/application, repository/UoW/schema и подготовку response до commit. Оборачивание только двух Ticket POST либо кеш на уровне HTTP не закрывают родительские Account/комментарии/историю/атомарность и дали бы ложное выполнение решения владельца. До выбора нескольких оставшихся параметров и полного before/after не предлагается небезопасная частичная реализация.
