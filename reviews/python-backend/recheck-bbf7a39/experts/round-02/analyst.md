Но утверждение «sqlite error code теряется» буквально слишком сильное: через `__cause__/__context__` у меня сохранился исходный `sqlite3.OperationalError` с `sqlite_errorcode=5`. Теряется **явная типизированная классификация на прикладной/HTTP границе**, а не обязательно вся информация о первопричине. Это не опровергает 500. |

| **PY-05: local naive → UTC** | **Согласен, условие non-UTC существенно.** Источник `src/domain/department.py:27`, employee `src/domain/employee.py:23,97`, account `src/domain/account.py:30`; mapper чтения использует `datetime_from_db`, который приписывает UTC (`src/domain/datetime_check.py:86–89`). Я явно задал TZ только локальному тестовому процессу (`Etc/GMT-3`, без изменения хоста): Department create был naive, после штатного mapper round-trip время отличается от реального UTC на 10800 секунд. На UTC-хосте ошибка скрывается. Автор правильно не распространяет это на JWT expiry/Ticket/TicketUser и не требует миграции рабочих БД. Сам переход mapper на datetime_to_db недостаточен, если оставить naive local factories: этот helper также приписывает UTC (`datetime_check.py:26–29`). В отчёте предложены обе части, это верно. |
| **R-01: guard remote self-assignment для PostgreSQL** | **Согласен с риском и границей SQLite/PostgreSQL, но область шире.** У обычного `assign` touch тоже пропускается при executor=actor: `src/application/services/ticket_service.py:599–600,622–625`. Поэтому формулировка «в отличие от обычного assign» требует уточнения: защищено назначение **другого** executor, а не все обычные назначения. Исправление только start-remote-work оставит тот же пробел у `PATCH /admin/tickets/{id}/executor` с self-id. Проверка/guard должны покрывать оба пути. Невалидное назначение на нынешней SQLite этим не доказано; проверка PostgreSQL interleaving нужна отдельно. |

С предлагаемой трактовкой повторов согласен: обычный SQLite busy можно явно представить как конфликт/временную недоступность, но ни обязательный код 409 для всех busy, ни автоматический retry не следуют из требований владельца. Если retry вводится, повторяют всю транзакцию с новыми чтениями и повторной проверкой условий. Автоматически повторять неизвестный результат commit или уже мутированные aggregate objects нельзя. Это проектное решение, не аргумент против работающего текущего rollback.

Положительные проверки Python не противоречат коду и моим данным: одна Connection внутри UoW, rollback при исключении, терминальность SUSPENDED, finish-work→READY_FOR_REVIEW, последовательная проверка отдела при remote-start. Сохранность данных после искусственного сбоя и 115 SQL EXPLAIN принимаю в заявленных автором узких границах; не выдаю за собственный повтор этих конкретных harness-проверок. Успешный EXPLAIN не доказывает семантику SQL, как показывает PY-04; автор это уже указал.
