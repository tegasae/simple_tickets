## Адресная критика analyst.md

- **A1 — согласен с наблюдением, сохраняю оговорку о бизнес-решении.** Дополнительно воспроизведено через весь HTTP/auth pipeline: связанная ACCEPTED-заявка → PATCH contact-user с активным User того же Client даёт **400**, оба контакта после повторного GET остались прежними. Эквивалентная standalone ACCEPTED-заявка меняет контакт с **200**. Причина ровно указанная: `Ticket` разрешает данные (`ticket_state_rule.py:41–47`), но `_sync_contact` (`ticket_sync_service.py:137–142`) вызывает `TicketUser.change_contact_user`, запрещённый для IN_WORK (`ticket_user_status.py:57`). Это подтверждённая коллизия shared-data use case; без решения матрицы нельзя утверждать, что именно расширение прав User — необходимое исправление. Поддерживаю разделение пользовательского редактирования и доверенной административной синхронизации. Регрессия должна сравнивать linked/standalone и проверять rollback, а не только ждать успеха.
- **A2 — согласен, теперь подтверждён и реальный User response.** `POST /admin/tickets/` за User с комментарием: Admin actor=1; initial actor Ticket=1; owner TicketUser=4, initial actor TicketUser=4 и автор начального комментария=4. Это видит `GET /user/tickets/{id}`. `TicketUser.create` (`src/domain/ticket_user.py:99–124`) приписывает реальное действие/текст владельцу. Докстринг `TicketUserStatusRecord` действительно обещает actual actor, включая Admin (`ticket_user_status_record.py:51–77`), поэтому это сильнее, чем субъективное пожелание UI. Реального автора следует сохранить, отдельно решив, как показывать его User. Нужны две регрессии: самостоятельная регистрация User и регистрация Admin за User.
- **A3 — согласен как с риском/пробелом политики.** Дополнительный HTTP-прогон: disable Admin→disable Department→enable Admin дал **200/200/200**, затем `department.enabled=false`, `admin.enabled=true`. Путь enable (`admin_service.py:387–408`) не загружает Department; запрет disable Department при enabled Admin есть (`domain/services/department_service.py:77–98`). Нельзя из этого выводить, что уже доказано исполнение Ticket в выключенном отделе: открытые Ticket блокируют само выключение. Запрет повторного enable требует отдельного решения, как аккуратно и указано в первичном тексте.
- **A4 — согласен с классификацией «расхождение границы правила», не с автоматическим ослаблением реализации.** `ASSIGNED/AT_WORK/PAUSED/READY_FOR_REVIEW` действительно имеют `has_executor=True` (`ticket_state_rule.py:51–65`), а смена отдела Admin использует факт любого текущего назначения (`application/services/admin_service.py:476–483`). Сам по себе более строгий запрет не доказывает дефект. До решения владельца не делать замену фильтра только на AT_WORK: она может разрешить несовпадение отделов у уже назначенной заявки.

Поддерживаю только классификацию конкретного PostgreSQL READ COMMITTED риска. Успешная порча инварианта текущей SQLite этим не доказана. ## Адресная критика python.md

- **PY-01 — согласен с внешним дефектом классификации конкуренции; целостность транзакции не опровергнута.** `Query._execute` (`utils/db/query.py:21–27`) превращает SQLite-ошибку в DBOperationError; `_exec` (`base_repository.py:50–57`) — в PersistenceError; в HTTP зарегистрирован только OptimisticLockError как 409 (`web/main.py:78`), прочее даёт 500. Заявленные два PATCH/барьер дают достижимый конфликт read→write upgrade, который возникает раньше rowcount optimistic lock. Самостоятельный повтор этого HTTP contention будет отдельным артефактом тестов; в данной критике не приписываю себе его выполнение. Техническая оговорка: исходное SQLite-исключение не уничтожено безвозвратно — оно остаётся в цепочке `__context__`; однако его код не представлен стабильным типизированным контрактом. Для временного SQLite busy/locked нужен отдельный тип и **503 без автоматического retry**. Нельзя механически повторять уже мутированный aggregate или один SQL. Дополнение про Department тоже верно: `department_repository.py:85–86` ошибочно переводит **любую** PersistenceError в duplicate; это самостоятельный сценарий для теста, а не доказательство duplicate при реальной contention в данном QA-прогоне.
- **PY-02 — согласен; дубликат QA-04 моего первичного заключения.** HTTP self-disable и удаление system role уже независимо воспроизведены как 500. Дополнительно в том же классе отрицательные ClientDTO/RoleDTO. Исправлять точным mapping `ApplicationValidateError`, не всех ApplicationError/StoreError.
- **PY-03 — согласен; частичный дубликат QA-03.** В моём первом раунде подтверждены HTTP PATCH description **для обеих карточек** с 4001 символом, плюс короткий пароль Admin/User, недопустимый login при attach и неизвестный permission роли. Ограничивать исправление одним description недостаточно: общий источник — непреобразованный ValueError ожидаемого входа. Глобальный ValueError→400 скрывает ошибки программирования. Нужны ограничения схемы плюс точное доменное преобразование, границы 4000/4001 и неизменность БД после отказа.
- **PY-04 — согласен, независимо подтверждён.** На моей синтетике User-роль назначена только User: реальный `uow.roles_user.is_assigned(4)` дал **False**, `DELETE /admin/roles/user/4` дал **500**, строка роли после отказа существует. SQL `COUNT(admins_roles) UNION ALL COUNT(users_roles) LIMIT 1` (`gateways/role_gateway.py:32–44`) неизбежно выбирает первый scalar count, даже нулевой. Это отдельная ошибка от PY-02: после исправления SQL сработает ApplicationValidateError, который тоже нуждается в 4xx mapping. FK защищает данные, потери роли нет. Регрессия должна раздельно проверять обе причины и состояния 0/admin-only/user-only; вариант «оба» полезен на уровне SQL-предиката, даже если корректная модель realm его обычно не создаёт.
- **PY-05 — согласен, независимо подтверждён HTTP на Department.** POST вернул `2026-11-23T22:36:42.742052` без offset, следующий GET — то же wall time с `Z`; отклонение от измеренного перед POST UTC — **10800 секунд**. Mapper действительно приписывает UTC naive времени (`department_mapper.py:22,35`, `datetime_check.py:86–89`). Аналогичные factories Employee/Account подтверждаются кодом, но не нужно выдавать их за независимо исполненные здесь HTTP-варианты. Утверждение про времена JWT не делается и не следует из этой ошибки. Регрессия нужна с явным TZ UTC и UTC+03, с неизменностью абсолютного времени и aware POST/GET.
- **R-01 — принимаю с расширением из A5:** guard отсутствует также у assign(self). В формулировке «в отличие от обычного assign» следует явно написать **assign(other)**, чтобы не создать ложное впечатление защищённости другого самоназначения.
- **R-02 — совпадает с A3**, дополнительно подтверждён моим HTTP-прогоном; сохраняю статус вопроса политики.
- **R-03 — согласен как с реальным различием JSON и неполнотой схемы.** `TicketAssembler` передаёт VO (`assembler.py:58,67`), TicketUser — `.value`/строку (`:122–136`). Это видно и в JSON моего первичного прогона (`comment:{"value":""}` у Ticket). Без контракта конкретного потребителя не называю доказанной поломкой фронтенда. Типизированные вложенные response-модели и проверка реального JSON нужны до изменения формы.

Положительные результаты Python об одной UoW, rollback, optimistic version и исполнении OWNER-NOTES согласуются с кодом и моими workflow-проверками. EXPLAIN действительно не проверяет истинность SQL-предиката; полезно, что PY-04 не был принят за корректный лишь из-за компиляции. Наличие двух refresh backend также подтверждается кодом; полный auth lifecycle этим не доказан.
