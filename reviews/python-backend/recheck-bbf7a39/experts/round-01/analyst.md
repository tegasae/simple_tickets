## Подтверждённые функциональные коллизии

### A1. Контакт принятой связанной заявки нельзя изменить из административного API

**Класс:** воспроизводимая коллизия правил двух карточек; средняя существенность. Поведение подтверждено. Окончательную матрицу редактирования контакта по статусу и типу инициатора нужно зафиксировать.

**API-путь:** `PATCH /admin/tickets/{ticket_id}/contact-user` → `src/web/routers/admin/tickets.py:438–470` → `TicketApplicationService.change_contact_user`, `src/application/services/ticket_service.py:324–370` → `TicketService.change_contact_user`, `src/domain/services/ticket_service.py:162–175` → `Ticket.change_contact_user`, `src/domain/ticket.py:465–482` → `TicketSyncService._sync_contact`, `src/domain/services/ticket_sync_service.py:59–68,137–142` → `TicketUser.change_contact_user`, `src/domain/ticket_user.py:228–241,428–432`.

**Условия:** Ticket связан с TicketUser; Ticket находится в ACCEPTED либо DEFERRED, TicketUser — IN_WORK; новый контакт — существующий активный User того же Client; actor — активный Admin с TICKET_OPERATION. Это штатное состояние: Admin с TICKET_ACCEPTED автоматически получает ACCEPTED сразу при создании (`src/application/services/ticket_service.py:210–220`).

**Что происходит:** Ticket допускает изменение данных в ACCEPTED/DEFERRED (`src/domain/statuses/rules/ticket_state_rule.py:41–47`), его контакт сначала меняется в памяти. Затем синхронизация пытается изменить контакт TicketUser; у IN_WORK `can_change=False`, и setter отклоняет операцию (`src/domain/statuses/ticket_user_status.py:52–59`). Нормальный rollback сохраняет оба старых контакта. Для эквивалентной несвязанной ACCEPTED-заявки тот же административный endpoint успешно меняет контакт.

**Наблюдение:** `linked_accepted_contact_change` даёт `DomainOperationError: ... TicketUser 1 can't change status status in_work`; `contact_change_rollback` показывает прежний контакт в обеих карточках; `standalone_accepted_contact_change` успешен. По действующему HTTP mapping это 400 (`src/web/main.py:68–81`); HTTP-код непосредственно не измерялся.

**Последствие:** возможность исправить контакт зависит от происхождения заявки. Для принятого обращения клиента оператор не может заменить контакт даже тогда, когда сама Ticket объявляет изменение допустимым. Это не рассинхронизация сохранённых данных, а отказ требуемого shared-data use case.

**Исправление:** согласовать одну матрицу. Если Admin должен редактировать контакты в ACCEPTED/DEFERRED, разделить пользовательское редактирование и административную/системную проекцию контакта: ограничение CREATED для User не должно автоматически блокировать доверенную синхронизацию. Если запрет намеренный — сделать его явным в Ticket-side policy и контракте API. Простое снятие ограничений TicketUser расширит пользовательские права редактирования, поэтому это плохая механическая правка.

**Проверка:** CREATED, ACCEPTED, DEFERRED, ASSIGNED, AT_WORK, READY_FOR_REVIEW, терминальные статусы × linked/standalone × Admin/User; успешное изменение сохраняет одинаковый контакт у обеих карточек, отказ сохраняет старые данные. Уверенность в воспроизведении **высокая**, в том, что именно разрешение для Admin является желаемой политикой, **средняя/высокая** — явного решения владельца о всей матрице нет.

### A2. Заявка, зарегистрированная сотрудником за User, приписывает User действие создания и текст сотрудника

**Класс:** подтверждённая потеря достоверного автора в пользовательской истории; средняя существенность.

**API-путь:** `POST /admin/tickets/` с `user_id > 0` → `src/web/routers/admin/tickets.py:65–93` → `TicketApplicationService.create_ticket`, `src/application/services/ticket_service.py:124–188` → `TicketUserService.create`, `src/domain/services/ticket_user_service.py:40–70` → `TicketUser.create`, `src/domain/ticket_user.py:99–124` → сохранение TicketUser; чтение User-истории идёт через `GET /user/tickets/{ticket_user_id}`, `src/web/routers/user/tickets.py:266–292`, и `TicketUserAssembler`, `src/application/assemblers/assembler.py:117–139`.

**Условия:** Admin A регистрирует обращение за User U, A != U. Если A передаёт начальный `comment`, его текст также попадает в TicketUser.

**Что происходит:** actor Admin загружен и проверен, но не передан в фабрику TicketUser. Фабрика ставит `actor_employee_id=user_id` у CREATED и `employee_id=user_id` у начального комментария. Во внутренней Ticket тот же запрос корректно записывает Admin (`src/domain/ticket.py:233–247`). Получаются две разные версии авторства одной регистрации. В локальном сценарии actor=1, Ticket initial actor=1, TicketUser initial actor=4, TicketUser comment actor=4.

**Основание:** собственный контракт `TicketUserStatusRecord` говорит, что `actor_employee_id` хранит реального исполнителя действия, User или Admin (`src/domain/statuses/ticket_user_status_record.py:48–77`), а owner уже отдельно хранится в `TicketUser.user_id`. Сейчас история не различает «User сделал» и «Admin внёс за User». В `TicketUserStatusRule.CREATED.user_action=True` (`src/domain/statuses/ticket_user_status.py:52–55`) также зашито предположение только о пользовательском источнике.

**Последствие:** в пользовательском журнале сотрудник выглядит как User; комментарий сотрудника выдаётся за слова клиента. Внутренняя Ticket позволяет восстановить Admin по другой истории, но это не делает неверный `actor_id` пользовательского журнала достоверным.

**Исправление:** отдельно передавать реального actor регистрации и реального автора комментария, сохраняя `user_id` как владельца запроса. Зафиксировать семантику CREATED/источника и `user_action`, чтобы UI мог правильно представить регистрацию сотрудником. Если User в этом поле намеренно означает представляемого заказчика, переименовать/описать эту семантику и хранить реального автора отдельно; текущему контракту «real actor» это не соответствует.

**Проверка:** User U создаёт сам → U в обеих релевантных пользовательских записях; Admin A создаёт за U → owner=U, actual actor/comment author=A; round-trip через repositories и User response сохраняет различие. Уверенность в поведении и противоречии текущему контракту **высокая**. Решение о внешнем показе Admin ID остаётся отдельным вопросом продукта.

## Существенные риски и несогласованные правила

### A3. В отключённом отделе можно снова включить сотрудника

**Класс:** подтверждённый обход lifecycle-политики отдела; бизнес-оценка требует явно распространить правило на повторное включение. Средняя существенность, не доказательство возможности создать/назначить Ticket в отключённом отделе.

**API-путь:** `PATCH /admin/admins/{id}/disable` → `PATCH /admin/departments/{department_id}/disable` (`src/web/routers/admin/departments.py:153–172`) → `DepartmentApplicationService.disable_department`, `src/application/services/department_service.py:142–170` → `DepartmentService.disable`, `src/domain/services/department_service.py:68–98`; затем `PATCH /admin/admins/{id}/enable`, `src/web/routers/admin/admins.py:362–381` → `AdminApplicationService.enable`, `src/application/services/admin_service.py:387–408` → `AdminService.enable`, `src/domain/services/admin_service.py:169–174`.

**Условия и результат:** в D нет открытых Ticket и включённых Admin, но есть выключенный Admin A с `department_id=D`. Отдел D успешно отключается. Затем A успешно включается, состояние D вообще не загружается. Синтетический результат: `admin_enabled=true`, `department_enabled=false`.

**Последствие:** невозможное непосредственно при disable(D) сочетание становится доступно следующим штатным действием. Создание/перевод Admin в disabled D запрещены (`rules.md:30–32`), но возвращение уже связанного Admin к работе разрешено без решения о том, что значит выключенный отдел. Включение также включает account через `src/domain/employee.py:152–160`.

**Граница вывода:** формулировка «нельзя назначать Admin в отключённый отдел» не буквально тождественна «нельзя включать Admin с сохранённой привязкой». Поэтому фиксирую воспроизводимый риск и пробел правила, а не приписываю владельцу отсутствующее явное требование. В текущем последовательном API `disable(D)` запрещён при открытых Ticket; из этого сценария нельзя вывести возможность начать работу по открытой Ticket в disabled D.

**Решение/проверка:** либо запрещать enable(A), пока D выключен, с загрузкой/проверкой/guard отдела, как сделано для User/Client; либо явно разрешить такое сочетание и определить доступные действия Admin. Проверить disable→enable, disabled Admin без отдела, включение после переноса в active D, конкурирующие enable(A)/disable(D). Уверенность в поведении **высокая**, в трактовке как нарушения принятого требования — **средняя**.

### A4. Запрет смены отдела Admin шире описанного ограничения AT_WORK

**Класс:** подтверждённое расхождение текущей политики и текстовой границы в `rules.md`, не безусловная ошибка реализации.

**API-путь:** `PATCH /admin/admins/{id}/department`, `src/web/routers/admin/admins.py:404–424` → `AdminApplicationService.change_department`, `src/application/services/admin_service.py:461–493` → `_has_current_executor_tickets`, там же `648–665` → `TicketRepositorySQLite.get_by_current_executor`, `src/adapters/repositories/ticket_repository.py:246–253` → SQL `WHERE current_executor_id=:current_executor_id`, `src/adapters/repositories/gateways/ticket_gateway.py:52–54` → `AdminService._ensure_not_current_executor`, `src/domain/services/admin_service.py:303–313`.

**Условия и результат:** у Admin есть только ASSIGNED-заявка; ни одной AT_WORK нет. Смена на другой активный отдел отклоняется. Аналогично блокируются PAUSED и READY_FOR_REVIEW, потому что все они имеют активного исполнителя (`src/domain/statuses/rules/ticket_state_rule.py:51–65`). `PUT /admin/admins/{id}` и удаление отдела Admin используют тот же факт (`src/domain/services/admin_service.py:106–110,232–252`).

**Основание:** `rules.md:38–41,69–75,86` специально упоминает текущего исполнителя именно AT_WORK. Текущий код явно принимает более строгую политику — «любая Ticket с активным назначением». Проверка именно текущего, а не исторического исполнителя реализована правильно.

**Последствие:** сотрудника нельзя перевести между отделами, пока не сняты все назначения, включая ожидающие проверки работы. Это может быть разумным способом сохранять равенство отделов, но такого расширения следует добиться явным решением, а не воспринимать его как реализацию только AT_WORK-проверки.

**Решение/проверка:** выбрать: запрет для всех активных назначений; либо запрет только AT_WORK плюс атомарное снятие/переназначение остальных заявок. Простая фильтрация по AT_WORK без обработки ASSIGNED/PAUSED создаст невалидное назначение между отделами. Матрица: current ASSIGNED/AT_WORK/PAUSED/READY_FOR_REVIEW, только прежнее назначение, actor/comment без назначения. Уверенность в поведении **высокая**, в необходимости ослабить правило — **не установлена**.

### A5. Самоназначение не участвует в том же optimistic guard, что назначение другого сотрудника

**Класс:** подтверждённая асимметрия протокола; значимый риск будущего PostgreSQL READ COMMITTED, не воспроизведённая порча текущей SQLite.

**API-пути:** `PATCH /admin/tickets/{id}/executor` → `TicketApplicationService.assign`, `src/application/services/ticket_service.py:581–630`; и `PATCH /admin/tickets/{id}/start-remote-work` → `start_remote_work`, там же `694–722`. При выборе actor как executor используется закэшированный Admin (`599–600`), а `admins.touch(executor)` выполняется только для чужого executor (`622–625`). В remote self-assignment touch вообще отсутствует. `EmployeeActorHelper._get_admin`, `src/application/helper/actor_helper.py:239–257`, проверяет enabled, но не продвигает/проверяет версию.

**Условия возможного нарушения:** T1 прочитала A в D и ещё не записала самоназначение; T2 проверила отсутствие текущих заявок A, сменила его отдел/отключила и закоммитилась; T1 сохраняет Ticket со старой информацией о A. На PostgreSQL READ COMMITTED одна запись Ticket не конфликтует с записью Admin, и отсутствует проверка версии A. В результате может сохраниться исполнитель другого отдела/отключённый исполнитель. У другого executor аналогичный конфликт должен обнаруживаться touch.

**Граница:** нынешняя SQLite с транзакционным snapshot и конфликтом записи может отклонить одну транзакцию на уровне блокировки. Здесь не заявляется, что указанное interleaving успешно портит данные в текущем SQLite runtime. Production на PostgreSQL обозначен в `OWNER-NOTES.md:33`, поэтому протокол должен быть проверен до переноса.

**Исправление/проверка:** включить actor/executor в guard ровно один раз в транзакции либо применить единый cross-aggregate locking protocol. При появлении PostgreSQL adapter — двухсессионные проверки assign(self)/remote-start против change_department/disable, а также контрольный assign(other). Исход: либо назначение видит новое состояние и отклоняется, либо изменение Admin проигрывает/повторяется; невалидная пара не коммитится. Уверенность в отсутствии guard **высокая**, сценарий PostgreSQL — **высоковероятный статический риск**, фактического PostgreSQL-теста нет.

## Что проверено и не подтвердилось как ошибка

На новой синтетике с реальными repository/UoW проверены следующие наблюдения:

1. User create создаёт обе карточки; User cancel из CREATED переводит обе в CANCELLED_BY_USER.
2. finish-work оставляет Ticket READY_FOR_REVIEW, TicketUser WAITING_FOR_CONFIRMATION. Авто-EXECUTED нет, что соответствует решению владельца.
3. Отключение владельца из READY_FOR_REVIEW переводит обе карточки в SUSPENDED; `is_closed=True`, `date_finished` заполнен у обеих. Возврат через accept отклоняется.
4. Отключение Client переводит готовую к проверке связанную пару в SUSPENDED, а отдельная AT_WORK-заявка продолжает быть AT_WORK — это действующий контракт, не дефект.
5. Удалённый старт из ACCEPTED для Admin без отдела отклонён по несовпадению отдела; для Admin правильного отдела выполнены назначение и AT_WORK.
6. Ретроспективная работа 12 минут сохраняет 720 секунд; подтверждение User закрывает обе карточки; `current_executor_id=0`, `last_executor_id` сохраняет предыдущего исполнителя.
7. Отказ изменения контакта A1 откатывает изменения обеих карточек; сохранённой рассинхронизации в этом сценарии не обнаружено.

Статически подтверждены отсутствие исходящих переходов из всех терминальных состояний (`src/domain/statuses/rules/ticket_status_transition.py:122–127`, `src/domain/statuses/ticket_user_status_transitions.py:70–78`), обязательность активного Admin из того же непустого отдела при обычном назначении (`src/domain/services/ticket_service.py:254–269`), отсутствие автоматического восстановления SUSPENDED. Это не заявление о полном переборе всего графа/всех конкурентных сценариев.

## Решения, которые нужны отдельно от исправлений

- **Отключение Admin.** `rules.md:12` предлагает возврат его работ в начальное состояние; сейчас код вообще запрещает disable при любом текущем назначении (`src/domain/services/admin_service.py:178–195`). Это ещё один конфликт TODO/действующей политики. Не предлагаю молча реализовывать каскад без определения статуса возврата, рабочего времени и судьбы текущего исполнения.
- **Работа после отключения участника.** AT_WORK специально сохраняется. Не определено, что делать после её дальнейших pause/finish/reassign и нужно ли автоматически SUSPENDED при выходе из AT_WORK. Нельзя объявлять сам факт продолжения работы дефектом; требуется таблица для последующих команд.
- **Физическое удаление и история.** `DELETE /admin/tickets/{id}` (`src/web/routers/admin/tickets.py:1046–1071`) вызывает `TicketApplicationService.delete` (`src/application/services/ticket_service.py:964–982`) и физически удаляет обе карточки с историей при TICKET_CANCELLED, без проверки состояния. `db/schema.sql:102–108,167–177` и `src/adapters/repositories/ticket_user_repository.py:324–355` подтверждают удаление children. Это достоверное поведение, но требования неизменяемого аудита/retention и отдельного права DELETE не заданы, данные учебные. Перед production надо выбрать, допустимо ли удалять AT_WORK/завершённую заявку и достаточно ли права отмены. Без такого решения это риск сохранности истории, а не доказанная ошибка относительно действующего контракта.
- **Повтор команды/идемпотентность.** Запрет повтора уже выполненного перехода не считаю дефектом сам по себе: отдельная реализация идемпотентности не поручена (`OWNER-NOTES.md:34,39–41`). Нужны договорённости о response после потерянного ответа и о повторной регистрации work interval; не скрытый автоматический retry любой команды.
- **Планирование и «Вернуть».** Документы `docs/need` содержат ещё не согласованные детали. Отсутствие нового resume с предыдущим executor или отдельного поля current_status не считаю подтверждённым отказом текущего API; последнее также указано как отложенный долг в `docs/dept/simple_tickets_technical_debt.md`.
