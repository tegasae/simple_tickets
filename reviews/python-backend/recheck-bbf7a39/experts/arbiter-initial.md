## Транзакции, повторы и решения для согласования

В парной команде обе записи идут через один UoW. `src/application/services/ticket_service.py:1177–1198` сохраняет TicketUser, затем Ticket и формирует внутренний DTO до commit. Исключение до commit приводит к откату по `src/adapters/uow/sqlite_unit_of_work.py:107–127`. Через API вызвал отмену пары на проверке, установив в временной БД синтетический сбой вставки финального статуса Ticket. После 500 обе карточки сохранили начальные статусы `READY_FOR_REVIEW/WAITING_FOR_CONFIRMATION`. Проверка покрывает отказ второй записи после первой.

Преобразование DTO в веб-модель и выдача ответа происходят после commit, например `src/web/routers/admin/tickets.py:86–93`. Потерянный ответ и отказ до commit внешне могут быть неотличимы. Повтор перехода обычно валидируется по текущему состоянию и может дать другой результат. Повтор POST создания проходит обычный insert с новой идентичностью. Если нужен безопасный повтор команды после потери ответа, отдельный проектный контракт может сохранять ключ, отпечаток запроса и результат атомарно с бизнес-записями. Проверять конкурентный дубль, повтор после потерянного ответа, повтор после отката и конфликт одного ключа с разными данными. Это решение не следует из требований снимка.

Схема разрешает несколько Ticket на один TicketUser, а `get_by_user_ticket_id` молча берёт одну строку через fetchone. Обычные обе команды создания заводят новую пару, поэтому дефект достижимости из API не установлен. Если отношение подтверждено как строго один к одному, добавить UNIQUE на ненулевой `tickets.user_ticket_id` и проверить повторную привязку, внутренние Ticket без пары и удаление пары. `db/schema.sql:123–153,179–186`, `src/adapters/repositories/gateways/ticket_gateway.py:32–34`, `src/adapters/repositories/ticket_repository.py:126–141`, `utils/db/query.py:64–75`.

В refresh сверка активности опирается на логин, а новый токен наследует прежний числовой субъект. Если допустимы удаление/смена учётной записи и повторное использование логина, стоит отдельно зафиксировать требуемое поведение старых сессий. Текущая связка чтения по login и выдачи по subject_id создаёт риск несогласованного жизненного цикла, а доступ к защищённым обработчикам дополнительно проверяется по ID и активности. Для регрессии достаточно защитного утверждения, что отозванная или заменённая учётная запись не обновляет сессию. Реальная эксплуатация не проверялась. `src/web/auth/services/auth_service.py:101–107,172–179`, `src/web/auth/services/services.py:85–95,225–250`, `src/web/dependencies/auth.py:125–165`.
