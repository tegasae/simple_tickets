## Подтверждённые направления, требующие окончательного свода

- Обход `role_user.assign` при создании User с ролями: проверяется только user.operation.
- Отзыв User-роли ошибочно дополнительно требует role.assign.
- Часть ожидаемых ошибок ввода и ApplicationValidateError возвращает 500. Старые исправления текста/комментариев/ID отдела работают, но охват неполон.
- RoleGateway.EXIST с двумя COUNT UNION ALL LIMIT 1 игнорирует users_roles; FK предотвращает удаление, API отвечает 500.
- Неверный автор обычного начального комментария, введённого Admin за User. Начальный CREATED.actor по прежнему контракту отражает владельца и не должен автоматически меняться тем же патчем.
- Контакт принятой пары блокируется внешним IN_WORK. Теперь владелец явно разрешил сценарий.
- Включение Admin в отключённом Department достижимо последовательными командами. Теперь владелец явно запретил сценарий.
- Новые Department/Employee/Account создают local naive datetime, mapper приписывает UTC. Non-UTC probe показал сдвиг 10800 секунд.
- Refresh проверяет активность аккаунта по логину, но выдаёт JWT по прежнему subject_id. Переназначение того же логина другому User через реальные API даёт 200 на старый refresh вместо отказа. Не объявлять это доказанным захватом аккаунта: защищённые запросы дополнительно проверяют исходный ID/активность.
- SQLite read-to-write contention даёт generic500 раньше version comparison. Rollback корректен, потери истории не показаны. PostgreSQL ведёт себя иначе; непроверенный риск guard при assign(self)/remote-start выделить отдельно.

Дополнительные наблюдения не надо автоматически повышать до ошибок: разная JSON-форма comment Ticket/TicketUser, правило смены отдела Admin шире AT_WORK в документации, отсутствие UNIQUE пары (публичный дубль пары не показан), идемпотентность как будущий отдельный контракт. Все нормативные разногласия должны попасть в итог.
