# Достижимые сценарии и доказательства

Все номера строк — исходный `bbf7a392dafe0fede2d5d017af36281b6f4f40a2`. Статусы описывают код **до** предлагаемой серии. Все динамические сценарии выполнялись на новой SQLite по `db/schema.sql` с синтетическими сущностями. Имена тестов относятся к [tests/](tests/). Несколько падающих параметров одного теста не являются несколькими независимыми дефектами.

## F01. Создание пользователя обходит право выдачи User-ролей — P1

**Условия:** активный Admin имеет `user.operation`, не имеет `role_user.assign`; существуют Client и User-роль. **Путь:** POST `/admin/users/` → `src/web/routers/admin/users.py:69–87` → `UserApplicationService.create_user`, `src/application/services/user_service.py:74–116` → `RoleManager.grant_roles`, `src/domain/rbac/role.py:51–55`. В блоке непустых `roles` повторно проверяется `USER_OPERATION` вместо отдельного права выдачи ролей.

**Наблюдение:** отдельный POST назначения тем же сотрудником получает 403, создание с тем же role_id — 201 и сохранённую связь. Это нарушение существующего разделения полномочий, подтверждённое несколькими экспертами. Пользователь может получить расширенные права в области Client, к которому его создали. Межклиентный обход или получение Admin-ролей этим сценарием не показаны.

**Рекомендация:** до создания с ролями проверить дополнительное право, затем передавать его RoleManager; создание без ролей оставить разрешённым. [Патч01](patches/01-user-role-permissions.patch). `test_create_user_cannot_bypass_role_assignment_permission` проверяет 403 и неизменное число User, затем оба допустимых варианта. На исходнике падает, после серии проходит. Уверенность высокая. Причина существовала до нынешнего изменения каскадов, впервые выделена этим аудитом.

## F02. Отзыв User-роли требует право Admin-ролей — P2

**Условия:** у Admin есть только `role_user.assign`, целевой User имеет роль. **Путь:** DELETE `/admin/users/{id}/roles` → router `users.py:330–345` → application `user_service.py:363–392` → RoleManager. На `:369–372` проверяется `ROLE_USER_ASSIGN`, на `:380–388` — `ROLE_ASSIGN`.

**Наблюдение/последствие:** роль выдать можно, отозвать тем же оператором нельзя — 403; связь сохраняется. Для штатного снятия пользовательских полномочий приходится предоставлять несвязанное право управления Admin-ролями. Два повторных HTTP-сценария подтвердили поведение.

**Рекомендация:** согласовать обе проверки на `ROLE_USER_ASSIGN`. [Патч01](patches/01-user-role-permissions.patch). `test_revoke_user_role_does_not_require_admin_role_permission` проверяет успех при включённом и отключённом Client, отсутствие роли после чтения новой транзакцией и 403 без нужного права. Уверенность высокая; впервые описанный дефект, не доказанная новая регрессия.

## F03. SQL не учитывает назначенные User-роли — P2

**Путь:** DELETE `/admin/roles/user/{role_id}` → `src/web/routers/admin/roles.py:229–246` → application `role_service.py:84–108` → repository `role_repository.py:89–95` → `RoleGateway.EXIST`, `gateways/role_gateway.py:32–44` → `fetchone`.

Два scalar COUNT соединены `UNION ALL … LIMIT 1`. Первая строка существует даже при нуле Admin-назначений; вторая строка User-назначений не читается. Синтетическая роль, выданная только User, получает `is_assigned=False`; DELETE доходит до FK и возвращает 500. **Данные не потеряны:** RESTRICT в `db/schema.sql:68–73` сохраняет роль и назначение. Ошибочны предикат и внешний отказ.

**Рекомендация:** одна строка CASE с EXISTS каждой junction-таблицы; после этого ожидаемый запрет удаления отображать через F04. [Патч03](patches/03-role-assignment-query.patch) + [02](patches/02-expected-input-errors.patch). Регрессии `test_role_assignment_predicate_checks_both_assignment_tables` и `test_delete_role_assigned_to_user_is_rejected_before_delete`: отсутствие/наличие назначений, 400 при попытке удаления, обе записи сохраняются. Высокая уверенность. Это новое обнаружение старой причины.

## F04. Ожидаемые application-отказы превращаются в 500 — P2

`ApplicationValidateError` — базовый класс обычных отказов, `src/application/exceptions.py:11–24`. HTTP-реестр `src/web/main.py:68–92` знает только его частный `TicketInputValidationError`, затем общий Exception→500.

**Достижимые сценарии:** PATCH `/admin/admins/{own_id}/disable` → `admin_service.py:410–421`; DELETE системной/назначенной роли → `role_service.py:96–105`; GET `/admin/clients/-1` → `client_dto.py:22–23`; GET `/admin/roles/admin/-1` → `roles_dto.py:19–21`. Настоящие авторизованные запросы получили 500. Действия запрещаются и откатываются, но клиент видит серверную аварию вместо ошибки команды.

**Рекомендация:** обработать конкретный базовый тип ожидаемой ошибки как 400. Не переводить все ApplicationError или все исключения Python в 4xx. В ветке неуспешного сохранения Client используется ApplicationStoreError, чтобы внутренняя неисправность оставалась 500. [Патч02](patches/02-expected-input-errors.patch). `test_expected_application_rejection_returns_client_error` и пользовательская назначенная роль проверяют внешний статус и сохранность. Уверенность высокая. Продолжение прежней частично исправленной группы06.

## F05. Необработанный ValueError из входных данных — P2

Независимая от F04 причина: web-модель принимает значение, VO выбрасывает обычный ValueError. Подтверждены реальные входы:

| Вход | Внутренний путь и условие | Наблюдение |
|---|---|---|
| PATCH `/admin/admins/{id}/password`, `/admin/users/{id}/password` | router `admins.py:272–293`, `users.py:288–305` → application → `employee.py:199–201` → `Account.change_password`, `account.py:78–83` → Password; короткое значение | 500, прежний пароль не изменён |
| POST `/admin/{admins,users}/{id}/account` | application → `employee.py:167–179` → `Account.create`, `account.py:47–56`; свободный login с внутренним пробелом | 500; новый Account не сохранён |
| POST `/admin/roles/{admin,user}` | `web/models/roles.py:13–40,68–96` → domain `services/role_service.py:13–46`; неизвестный enum permission | 500 |
| PATCH `/admin/tickets/{id}/description` | `web/models/tickets.py:88–91` → application/domain → `ticket.py:484–490` → Description, `value_objects.py:218–240`; 4001 символ | 500 |
| PATCH `/user/tickets/{id}/description` | собственная пара в CREATED → `ticket_user_service.py:237–263` → domain facade → `ticket_user.py:207–226`; тот же размер | 500. Для IN_WORK раньше сработает другое ограничение, поэтому это не произвольная открытая заявка |

**Последствие:** исправимая ошибка формы выглядит как сбой, может побуждать к бесполезным повторным отправкам. Частичная запись этим не показана.

**Рекомендация:** единый DescriptionText с strip и пределом домена для создания/редактирования; permissions типизированы соответствующим enum; Account-команды переводят только ожидаемые VO ValueError в ItemValidationError. Не устанавливать глобальный ValueError→400. [Патч02](patches/02-expected-input-errors.patch). Проверены прежний пароль/отсутствие записи после отказа, 400/422, 4000 значимых символов с внешними пробелами при create/update. Регрессии в `test_rbac_and_validation.py`. После серии все проходят. Высокая уверенность; старые исправления text/comment/ID отдела работают, но общий класс проблемы закрыт не полностью.

## F06. Смена контакта принятой пары отклоняется — P2

**Путь Admin:** PATCH `/admin/tickets/{id}/contact-user` → application `ticket_service.py:324–370` → domain `services/ticket_service.py:162–175` → `Ticket.change_contact_user`, `ticket.py:465–482` → `TicketSyncService._sync_contact`, `ticket_sync_service.py:137–142` → `TicketUser.change_contact_user`, `ticket_user.py:228–241` → `_can_change`, `:428–432`. ACCEPTED/DEFERRED разрешают изменения внутренней карточки, но проецируются во внешний IN_WORK, запрещающий их. **Путь User** проходит обе связанные сущности через `application/services/ticket_user_service.py:265–309` и сталкивается с той же коллизией.

**Наблюдение:** другой активный контакт того же Client отклоняется с 400; транзакция возвращает оба прежних контакта. Повтор текущего контакта может пройти, поскольку синхронизация не нужна. Это отказ нужной операции, а не сохранённое рассогласование.

В предыдущем проходе правило было открытым вопросом. **Теперь владелец явно разрешил смену через обе стороны при ACCEPTED/DEFERRED.** [Патч05](patches/05-paired-contact-edit.patch) вводит отдельный `can_change_contact` во внешних CREATED/IN_WORK. Проверка внутреннего Ticket сохраняется, поэтому разрешение не распространяется на ASSIGNED/AT_WORK/PAUSED/review. Общий `can_change` описания не расширяется. 22 параметризованные проверки контактов/отделов включают успешную смену в обе стороны и атомарный отказ поздних состояний. Нулевой Admin-контакт этим решением не определён. Высокая уверенность после ответа владельца.

**Рекомендация:** загрузить назначенный отдел в этой UoW, проверить совпадение/активность и включить его в guard версии. [Патч09](patches/09-admin-enable-department.patch). Тесты проверяют 400 без изменения флагов/версии, затем 200 после обоих способов устранения причины; Admin без отдела включается. Высокая уверенность; новая подтверждённая политика, а не предположение эксперта.

## F09. Refresh проверяет владельца имени вместо сохранённого субъекта — P2

**Сценарий:** User входит → Admin отсоединяет его Account через DELETE `/admin/users/{id}/account` → присоединяет тот же свободный login к другому активному User → старый refresh отправлен в POST `/auth/user/refresh`.

`AuthManager.refresh`, `services/services.py:225–249`, строит LoginRequest по сохранённому username. `UserAuthService.validate_user_exists`, `services/auth_service.py:163–179`, проверяет того, кто сейчас найден по этому имени. Затем `TokenService.renew_tokens`, `services/services.py:85–95`, использует старый subject_id. Обе подготовительные команды и refresh вернули200 в memory и SQLite-режиме. Проверка допуска и идентичность выдаваемого токена относятся к разным людям.

**Граница последствий:** доступные API дополнительно перечитывают исходный ID и Account в `web/dependencies/auth.py:125–165`. Смена login не превратила JWT в токен нового владельца; захват чужого аккаунта не доказан. Подтверждена неверная проверка сессии и успешная ротация после потери соответствия имени субъекту.

**Рекомендация:** проверять сохранённый ID вместе с realm при обновлении. [Патч06](patches/06-refresh-subject-identity.patch) добавляет keyword `expected_subject_id` и сверяет его в обоих concrete auth services. `test_refresh_is_bound_to_same_subject_after_login_is_reassigned[memory/sqlite]`: исходник200, патч401. Штатная ротация существующего субъекта сохраняется. Отзыв при reattach тому же ID, переустановке пароля и повторном включении остаётся отдельной политикой. Старый статический риск теперь подтверждён обычным API-сценарием.

## F10. Local naive даты ошибочно становятся UTC — P2

**Проверенный HTTP-путь:** POST `/admin/departments/` → application `department_service.py:59–77` → `Department.create`, `department.py:27,32–46` → mapper `department_mapper.py:29–35` → SQLite → GET → mapper `:17–23` → `datetime_from_db`, `datetime_check.py:86–89`. Новое значение local naive сохраняется без offset; при чтении ему приписывается UTC без конверсии.

На UTC+03 create-ответ без offset и следующий ответ с Z обозначают разные абсолютные моменты; подтверждён сдвиг10800 секунд. Аналогичные defaults/fallbacks — `employee.py:23,97`, `account.py:30,76`. Ticket/TicketUser и токены используют отдельные aware UTC даты и этому конкретному дефекту не приписываются.

**Рекомендация:** новые даты создавать через `datetime.now(UTC)`. [Патч07](patches/07-utc-dates.patch). 15 проверок SQL-предиката/времени: 9 failed,6 passed → 15 passed отдельно на03+07. В общем прогоне UTC/UTC+03, HTTP и новый Connection подтверждают неизменность момента; явные исторические даты сохранены. Для старой naive БД нужно знать исходную timezone; миграция учебных данных не поручена. Высокая уверенность; новая найденная причина в прежнем коде.

## F11. Классификация конкурентного отказа SQLite — P2

**Обычный сценарий:** два настоящих PATCH `/admin/tickets/{id}/description` синхронизированы после `_get_ticket`; разные request-scoped подключения успевают прочесть одну версию. `Connection.begin_transaction`, `utils/db/connect.py:46–59`, использует отложенный BEGIN. При повышении read-транзакции до write SQLite может отказать раньше, чем UPDATE с version вернёт rowcount.

`Query`, `utils/db/query.py:17–41`, и `BaseRepository`, `base_repository.py:46–57`, сворачивают тип в общий PersistenceError. Нативное исключение и код могут оставаться в exception chain; неверно говорить, что вся первопричина уничтожена. Реальный HTTP-результат —200+500, один commit, версия+1, нет частичной истории. Ошибка клиента здесь не повреждение атомарности, а неразличимый внешний серверный отказ.

**Отдельное проявление:** `DepartmentRepositorySQLite.save`, `department_repository.py:58–86`, любой PersistenceError выдаёт за duplicate имени. Настоящая блокировка при уникальном имени даёт ложный409; неизвестная ошибка сохранения также может попасть в эту ветку. Инъекция сбоя в синтетической таблице подтверждает неверную классификацию неизвестного отказа.

**Рекомендация:** выбран контракт503 для определённого временного отказа откатившейся команды. [Патч08](patches/08-database-error-classification.patch) сохраняет типизированные причины через Query/repository, распознаёт native code только в адаптере, оставляет409 для unique и500 для неизвестного сбоя. Общая прикладная ошибка не требует SQL UPSERT или проверки текста сообщения драйвера. PostgreSQL-адаптеру понадобится собственное преобразование его ошибок.

Проверены200+503 без скрытого повтора, версия/сохранённое описание победителя, COMMIT с удержанным reader и повторный вход после rollback, блокированные вставки Department/Role/User, настоящий duplicate и неизвестный сбой. Старый COMMIT-тест также проходит с сохранённым контекстом операции. **Отдельный TokenStorageSQLite использует собственные соединения и патчем08 не охвачен.** Автоматические повторы, идемпотентность и PostgreSQL-конкуренция не реализованы. Прежний известный риск, не новая ошибка после исправлений.

## F12. Shell-запуск ссылается на удалённые тесты — P3

Удалённые `tests_pyramid/` и его pytest.ini отсутствуют в Git-дереве. Оба `run_pyramid.sh:3` и `run_coverage.sh:3` всё ещё передают `-c tests_pyramid/pytest.ini tests_pyramid`. Настоящий запуск каждого во временной копии заканчивается exit4 ещё до тестов.

**Рекомендация:** убрать жёсткий target, сохранить переданные пользователем параметры и ненулевой exitcode. [Патч10](patches/10-current-test-launchers.patch). После него оба скрипта с явно указанным `recheck_tests --collect-only` собирают70 тестов, exit0. Это небольшое исправление инструмента, не восстановление удалённого набора и не полноценный default CI.

При обычном pytest в полном воспроизведённом Python-layout старые review-файлы отдельно дают2 ошибки сборки из-за импорта временного имени `old_review_tests`. Корневой pytest.ini указывает отсутствующий `tests/` и включает fallback discovery. Для обычного CI нужен выбранный актуальный набор и явная команда. Новые предложения тестов лежат только в разрешённом review-каталоге. Высокая уверенность; прослеживается связь с удалением тестового дерева.

## Существенные риски, не выданные за доказанные ошибки

1. **PostgreSQL guard:** `application/services/ticket_service.py:599–625,694–722`. Для self-assign и remote-start нет touch строки Admin. Возможный READ COMMITTED порядок: T1 читает enabled Admin/отдел → T2 проверяет отсутствие назначений и отключает/переводит Admin, commit → T1 сохраняет назначение по старому объекту. Для проверки нужны два PostgreSQL-соединения, барьер после чтения и затем сохранение; обе команды не должны успешно фиксировать запрещённую пару. На SQLite такой успешный interleaving не установлен. Направление небольшого исправления — общий guard исполнителя для assign(self) и для ветки remote самоназначения, с проверкой версий и свежим повторным чтением после отказа. Непроверенный PostgreSQL-патч в проверенную серию не добавлен.
2. **Контракты:** административный contact=0; смысл initial CREATED.actor; более широкий запрет смены отдела Admin, чем отдельная формулировка AT_WORK в документах; структура JSON comment; дальнейшее завершение сохранённой активной заявки отключённого клиента. Текущий патч не вводит решений за владельца.
