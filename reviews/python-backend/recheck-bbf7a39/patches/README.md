# Предлагаемые изменения

Все diff относятся к исходному `bbf7a392dafe0fede2d5d017af36281b6f4f40a2`, пути внутри diff — исходные пути проекта. Они не применены к рабочим исходникам. Каждый файл прошёл `git apply --check --whitespace=error-all` отдельно против исходника, затем весь набор последовательно проверен и применён в свежей `/tmp` копии. Общий результат — 128 passed,2 deselected; новые регрессии —70 passed. Два исключения требуют отменённого сохранения READY_FOR_REVIEW при отключении.

Изменения не включают миграции рабочих данных, идемпотентность, автоматические повторы, новый PostgreSQL-драйвер или переработку архитектуры. Прикладной SQL предиката роли — стандартный CASE/EXISTS. Код native SQLite error находится только на границе драйвера; прикладные команды не получают SQL-специфических ветвлений.

## 01 — права User-ролей

[01-user-role-permissions.patch](01-user-role-permissions.patch) меняет только UserApplicationService. При непустом `roles` дополнительно проверяется ROLE_USER_ASSIGN **до** первой записи User; RoleManager получает то же право. Пустой набор ролей по-прежнему требует только USER_OPERATION. При отзыве исправлена повторная проверка с ROLE_ASSIGN на ROLE_USER_ASSIGN.

HTTP-маршруты, тела и успешные ответы не меняются. Запрещённое ранее отдельной командой назначение больше нельзя провести через create. Отзыв по-прежнему возможен при отключённом Client. Проверки: атомарный отказ без User, успех разрешённых вариантов, revoke с ограниченными правами и403 без них.

## 02 — ожидаемые ошибки ввода и отказов

[02-expected-input-errors.patch](02-expected-input-errors.patch) устраняет две разные причины500:

- Реестр FastAPI обрабатывает базовый ApplicationValidateError как400. Ошибка фактического сохранения Client переводится в ApplicationStoreError и остаётся500. Все ApplicationError или ValueError глобально не перехватываются.
- Account.create/change_password переводят конкретные ожидаемые ошибки Login/Password VO в ItemValidationError. Публичные HTTP-ответы становятся400; сигнатуры команд и сами правила пароля не меняются. Account.rehydrate не смягчает ошибочные данные хранения.
- Permissions HTTP-запросов типизированы AdminPermission/UserPermission; неизвестное значение даёт422 до домена. Имя роли проверяется тем же Name VO.
- Общий TicketDescriptionText использует strip и предел Description.MAX_LENGTH. Он применяется к созданию и изменению обеих карточек. Значимые4000 символов с внешними пробелами разрешены,4001 даёт422.

Проверены сохранность прежнего пароля/описания, отсутствие нового аккаунта/роли после отказа, нормальные границы, оба realm. Это не обещание полного аудита любого ValueError всех возможных API-полей.

## 03 — наличие назначений роли

[03-role-assignment-query.patch](03-role-assignment-query.patch) заменяет UNION двух COUNT с LIMIT1 одной строкой CASE/EXISTS для обеих junction-таблиц. Сигнатура и форма результата `one` сохранены; нет SQLite/PostgreSQL UPSERT.

Отсутствие роли в admins_roles больше не маскирует users_roles. FK не снимается. Вместе с02 DELETE назначенной User-роли выдаёт ожидаемый400 до удаления. Проверены неназначенная, Admin-назначенная, User-назначенная роли и сохранность роли/связи после HTTP-отказа.

## 04 — обычный комментарий сотрудника

[04-staff-comment-author.patch](04-staff-comment-author.patch) оставляет фабрике TicketUser создание запроса, а обычный первоначальный текст добавляет через существующий TicketUserService.add_comment с ID проверенного Admin до сохранения. Комментарий внутреннего Ticket сохраняет прежнее поведение.

Initial CREATED.actor внешней карточки не меняется: это сохранение существующего поведения, а не новое решение о семантике истории. Требование к этому actor нужно отдельно уточнить. Обычный комментарий при самостоятельном создании User остаётся за User. Проверки читают новую транзакцию/пользовательский GET и реальный author ID.

## 05 — контакт принятой пары

[05-paired-contact-edit.patch](05-paired-contact-edit.patch) добавляет отдельный флаг can_change_contact в таблицу правил TicketUser для CREATED/IN_WORK. Setter контакта проверяет этот флаг и нетерминальность. Общий can_change для description не расширяется.

Оба прикладных пути всё ещё вызывают проверку внутреннего Ticket, поэтому внешний IN_WORK не разрешает изменения во всех представляющих его состояниях. Это реализует ответ владельца для внутреннего ACCEPTED/DEFERRED. Схема HTTP, смысл contact=0 и история статусов не меняются. Проверены две стороны, успешные состояния и атомарные отказы ASSIGNED/AT_WORK/PAUSED/review/terminal; description в IN_WORK остаётся закрытым.

## 06 — стабильная идентичность refresh

[06-refresh-subject-identity.patch](06-refresh-subject-identity.patch) добавляет необязательный keyword `expected_subject_id` к validate_user_exists абстракции и обоих concrete auth services. AuthManager.refresh передаёт сохранённый ID; успешная проверка по логину дополнительно требует тот же ID. Проверка realm уже существовала.

Существующие прямые вызовы без keyword сохраняются. Если вне проверенного репозитория есть собственные реализации AuthServiceAbstract, им нужно принять новый optional keyword. Поиска сторонних реализаций аудит не проводил. Нельзя приписывать этому патчу полное решение revocation: повторное присоединение аккаунта тому же ID, повторное включение, пароль и абсолютный срок сессии требуют отдельного контракта. Проверены реальные account detach/attach и отказ401 старому refresh в memory/SQLite; штатная ротация прежних тестов проходит.

## 07 — новые даты UTC

[07-utc-dates.patch](07-utc-dates.patch) меняет defaults/fallbacks новых Department/Employee/Account на datetime.now(UTC). Сигнатуры и поля сущностей не меняются. Явно переданное историческое время сохраняется; строки старой БД не переписываются.

Изменение wire datetime нового Department с naive на aware — необходимая часть исправления абсолютного времени. Проверены UTC и UTC+03, новые доменные объекты, сохранение/чтение сотрудников и аккаунтов, HTTP create/get. Преобразовывать неизвестную историческую local timezone в UTC этим патчем нельзя.

## 08 — ошибки основной БД

[08-database-error-classification.patch](08-database-error-classification.patch) проводит узкую классификацию через существующий путь Connection/Query → repository → HTTP:

1. Нейтральные DBTransientError/DBUniqueConstraintError наследуют DBOperationError. SQLite-коды BUSY/LOCKED, включая extended BUSY_SNAPSHOT, и UNIQUE/PRIMARYKEY преобразуются в отдельном utils/db/sqlite_errors.py. Причина сохраняется через explicit exception chaining. Текст ошибки драйвера не используется как классификатор.
2. BaseRepository переводит их в соответствующие PersistenceError subclasses. Репозитории, чьи широкие catch прежде оборачивали эти типы, сохраняют их. DepartmentRepository переводит в duplicate только UniqueConstraintError.
3. Begin/commit также классифицируют временный отказ и сохраняют название фазы для диагностики. UoW продолжает ловить DBOperationError, выполнять rollback и очищать флаги. Частичные COMMIT и продолжение изменённой транзакции не разрешаются.
4. Для временных ошибок выбран HTTP503 с фиксированным публичным detail. Version-CAS по-прежнему409, истинный duplicate отдела409, неожиданный сбой500. Код не выполняет повтор SQL или целой команды.

Изменения пересекают11 небольших файлов, поскольку без сохранения типа во всех этих обёртках исходная причина снова становилась бы общим500 либо ложным409. Новой схемы хранения и изменений доменного workflow нет.

Проверены два HTTP-писателя с барьером, блокированные вставки Department/Role/User, busy на COMMIT и rollback/новый запрос, настоящий duplicate и неизвестный отказ. Прежний тест automatic COMMIT/повторного входа также проходит. TokenStorageSQLite использует собственные соединения и сюда не входит. Для будущего PostgreSQL нужен собственный адаптер native ошибок в эти нейтральные типы и его реальные двухтранзакционные тесты; результат для него не заявлен.

## 09 — включение Admin и отдел

[09-admin-enable-department.patch](09-admin-enable-department.patch) загружает назначенный Department, проверяет соответствие Admin.department_id и enabled в доменном сервисе, затем touch-ит отдел в той же UoW. Admin без отдела получает пустой разрешённый Department. Это закрывает новый явный запрет владельца и связывает конкурирующее решение об отделе с его версией.

HTTP-интерфейс сохранён. Внутренний AdminService.enable теперь требует аргумент Department; единственный действующий прикладной вызов обновлён. Если появились внешние прямые вызовы, они должны передать отдел — иначе новый межагрегатный инвариант проверить невозможно. Проверены отказ400 без изменений, оба способа исправить причину, отсутствие назначения и version touch при успехе.

[10-current-test-launchers.patch](10-current-test-launchers.patch) убирает ссылку на отсутствующие tests_pyramid/pytest.ini и tests_pyramid, сохраняет set -euo pipefail, пользовательские аргументы и coverage-флаги.

Проверено: оба скрипта до патча exit4, после с явно заданным recheck_tests --collect-only — exit0,70 collected. Default discovery в полном checkout всё ещё требует решения о постоянном наборе; старые review-тесты предполагают специальное временное размещение. Патч не обещает зелёный CI без явного target и не восстанавливает удалённые устаревшие тесты.
