## #13. Дата создания роли

Для новых SQLite-баз патч заменяет `date_created TEXT` на `date_created TEXT NOT NULL` в таблице `roles`. Это согласует схему с маппером и защитит список от строки без даты. Оба типа ролей используют этот столбец. Приложение уже выставляет дату в UTC и передаёт её в INSERT, поэтому значение по умолчанию в SQL не требуется. В синтетической SQLite с предложенной схемой вставки с `NULL` и пропуском поля отклонены, ISO-дата в UTC сохранена. Патч рассчитан на базы, создаваемые с обновлённой схемой. ## #28. Права первой линии удалённой поддержки

Патч разделяет диспетчерское назначение, изменение рекомендации и работу на горячей линии. Методы, URL и поля запросов сохраняются. [Патч #28](patches/28-remote-first-line-permissions.patch) · [Тесты #28](tests/test_issue_28.py)

### Роли и новые полномочия

| Право | Что разрешает |
| --- | --- |
| `ticket.at_work_remote` | Самоназначение и удалённую работу по рекомендованным заявкам. |
| `ticket.assign_executor` | Назначение другого сотрудника независимо от рекомендации при соблюдении действующих правил отдела, исполнителя и статуса. |
| `ticket.set_remote_recommendation` | Смену рекомендации там, где редактирование разрешено статусом, и выставление `true` при создании заявки от имени администратора. |
| `ticket.at_work` | Обычную работу назначенного исполнителя. Существующее право сохраняет действие для обеих форм работы, независимо от рекомендации. |

Первая линия получает `ticket.at_work_remote` и нужные права просмотра, создания или комментариев. Общее `ticket.operation` по-прежнему требуется для ряда действий с заявкой, включая комментарии, но само по себе не даёт прав назначения и изменения рекомендации. Ретроспективное внесение работы остаётся отдельным полномочием `ticket.at_work_retrospective`. Права складываются из всех ролей сотрудника. Для `/executor` сервер выбирает одно право по запрошенному исполнителю. Свой ID требует полномочия горячей линии и проверки рекомендации даже при совмещении ролей. ID другого сотрудника проверяется по полномочию диспетчера. [Каталог прав на исходном снимке](https://github.com/tegasae/simple_tickets/blob/84049ffc2da5545b425b844c0d1a4cf024f5db67/src/domain/rbac/permissions.py)

### Поведение HTTP

В таблице первая линия имеет только узкое право работы. Тикеты и пользователи удовлетворяют обычным проверкам статуса и отдела, если в строке не оговорено другое.

| Команда | Условие | Ответ и состояние |
| --- | --- | --- |
| `PATCH /admin/tickets/{id}/executor` с `{"executor_id": <свой ID>}` | Рекомендация есть, заявка в `ACCEPTED` или уже в `ASSIGNED` у отправителя | `200`. Заявка назначена этому сотруднику. |
| Та же команда | Самоназначение без права горячей линии | `403`, в том числе для диспетчера. |
| Та же команда | При самоназначении рекомендации нет, исполнитель уже другой или статус не подходит | `400`. Состояние и история сохранены. |
| Тот же маршрут с `{"executor_id": <ID другого сотрудника>}` | Право `ticket.assign_executor` и допустимое назначение | `200`, в том числе без рекомендации. Без права возвращается `403`. |
| `PATCH /admin/tickets/{id}/start-remote-work` с `{}` | Право `ticket.at_work_remote`, рекомендация есть, а заявка в `ACCEPTED` или уже назначена на отправителя | `200`. В `ACCEPTED` назначение и старт фиксируются вместе. Без рекомендации `400`. Отсутствие права даёт `403` и при предварительном назначении. |
| `PATCH /admin/tickets/{id}/start-work` | Текущий исполнитель с `ticket.at_work` | Обычный старт сохраняется для обоих значений `work_is_remote`. При одном праве горячей линии маршрут возвращает `403`. |
| `PATCH /admin/tickets/{id}/resume-work` с `{"work_is_remote": true}` | Текущий исполнитель с одним правом горячей линии и действующей рекомендацией | `200` из `PAUSED`. Без рекомендации `400`. При `false` или пропуске поля требуется обычное право работы. |
| `PATCH /admin/tickets/{id}/pause-work` и `finish-work` с `{}` | Текущий исполнитель выполняет живую удалённую работу | `200`. Можно поставить свой рабочий эпизод на паузу или передать его на проверку. |
| `PATCH /admin/tickets/{id}/remote-work-recommended` с `{"remote_work_recommended": true}` | У отправителя нет отдельного права изменения рекомендации | `403`. Общего `ticket.operation` недостаточно. |
| `POST /admin/tickets/` с `remote_work_recommended: true` | У отправителя есть право создания, но нет права на рекомендацию | `403`. Это проверяется и при повторе с `Idempotency-Key`. Поле по умолчанию остаётся `false`. |

В `/executor`, `/start-work` и `/start-remote-work` выполняется одна проверка права. Для паузы, возобновления и завершения, где действуют два полномочия, сначала проверяется обычное право работы. При его отсутствии допускается проверка права горячей линии в той же UoW.

Пользовательское создание заявки сохраняет действующий контракт. Если рекомендация приходит от пользователя с новой заявкой, она по-прежнему передаётся во внутреннюю карточку. Патч ограничивает полномочия сотрудников административного контура. [Создание пользователем](https://github.com/tegasae/simple_tickets/blob/84049ffc2da5545b425b844c0d1a4cf024f5db67/src/application/services/ticket_user_service.py#L182-L194)

В отдельном клоне или временной рабочей копии выполните из корня репозитория.

```bash

git apply --check "$patch_dir/"*.patch
git apply "$patch_dir/"*.patch
```

Патч #13 действует при создании SQLite из `db/schema.sql`.

Для #28 обновите все экземпляры приложения до записи новых разрешений в существующие роли. Выдайте `ticket.assign_executor` диспетчерам, а `ticket.set_remote_recommendation` тем, кто устанавливает рекомендацию. Для рабочей роли первой линии используйте `ticket.at_work_remote`. Проверьте суммарные права остальных ролей сотрудника. [Каталог разрешений](https://github.com/tegasae/simple_tickets/blob/84049ffc2da5545b425b844c0d1a4cf024f5db67/src/web/routers/admin/roles.py#L64-L71)

На исходном снимке SQLite принимала `NULL` и пропуск даты у обоих типов ролей. После патча обе вставки отвергаются, а штатное создание и чтение ролей проходят. Исходные проверки #28 показывали, в частности, успешное самоназначение на нерекомендованную заявку и возможность установить рекомендацию при создании без отдельного права.

Регрессии уточнённого #28 включают запрет самоназначения диспетчером, проверку совмещённых прав и отказ в удалённом старте до выдачи права заранее назначенному сотруднику. Последний сценарий проверяет и успешный старт после выдачи права с тем же токеном.
