# Независимый аудит Python-бэкенда

Снимок `main` `89498c8318d587f197b0ae584d95899d5939c8d8`. Область проверки — доменные переходы, прикладные сервисы, SQLite, версии и история. Прикладные проверки выполнялись через `ApplicationServiceFactory` со штатным `SQLiteUnitOfWork`, реальными репозиториями и синтетическими ролями. Для прикладных сценариев тестовая копия DDL в памяти исключала одну строку с `sqlite_sequence`, поскольку буквальный скрипт останавливается на ней. Проверки блокировок использовали отдельную временную БД. Выводы об HTTP основаны на привязке маршрутов и обработчиков в коде.

## Подтверждённые ошибки на рабочих путях

### P1. Создание связанной заявки сохраняет разные контакты в двух агрегатах

- **Путь и условие.** `POST /user/tickets/` с действующим контактом, отличным от автора, даже когда оба относятся к одному клиенту. `TicketUserApplicationService.create_from_user` загружает контакт и передаёт его в создание обеих записей. Доменный `TicketUserService.create` записывает ID автора независимо от переданного контакта, а внутренний `Ticket` получает выбранный ID. Административный `POST /admin/tickets/` использует тот же доменный метод при создании связанной пары.
- **Последствие.** Создание через пользовательский маршрут успешно фиксирует пару с разными контактами. Пользовательская отмена такой заявки завершается доменной ошибкой и откатывается. Подтверждение также проверяет равенство контактов. Каскад отключения пользователя отвергает такую пару при валидации. В административной ветке с автоматическим принятием синхронизатор может исправить контакт до перехода, поэтому там результат зависит от прав и состояния.
- **Код.** `src/web/routers/user/tickets.py:111–140`; `src/application/services/ticket_user_service.py:141–163,181–206,395–419`; `src/domain/services/ticket_user_service.py:40–66`; `src/domain/services/ticket_service.py:104–133`; `src/domain/services/ticket_sync_service.py:72–104,158–172`; `src/application/services/ticket_service.py:141–188,209–224`; `src/domain/services/user_service.py:475–500`.
- **Доказательство.** При обычном вызове пользовательского сервиса временная БД сохранила `Ticket.contact_user_id=3` и `TicketUser.contact_user_id=2`. Затем отмена через прикладной сервис вернула `DomainOperationError` с сообщением о разных контактах. Административная ветка и подтверждение прослежены статически.
- **Исправление и проверка.** Один раз нормализовать контакт и передавать одно значение в оба агрегата, валидируя принадлежность контакта клиенту. Использовать существующую логику `_validate_contact_user` как отправную точку. Для уже записанных пар сверить источники перед миграцией. Проверить создание без контакта, с контактом-владельцем и с другим контактом того же клиента, затем повторное чтение и отмену пары.

### P1. Пользовательский PATCH контакта успешно сохраняет прежний контакт

- **Путь и условие.** `PATCH /user/tickets/{ticket_user_id}/contact-user` для собственной редактируемой заявки. Маршрут отдаёт DTO с новым ID, но сервис создаёт пустые `User` и `Client` и игнорирует ID. Доменный метод создаёт два исключения без `raise`, меняет только `TicketUser`, после чего синхронизация из `Ticket` восстанавливает прежнее значение.
- **Последствие.** Операция возвращает успешный DTO с прежним контактом, а сохранение обеих строк увеличивает их версии. Повтор запроса ведёт к тому же результату. Отдельно у административного PATCH значение 0 проходит схему запроса, но доменный метод отвергает пустой объект даже для отдельной заявки, которую агрегат допускает оставить без контакта.
- **Код.** `src/web/routers/user/tickets.py:369–398`; `src/application/services/ticket_user_service.py:265–307,910–929`; `src/domain/services/ticket_user_service.py:107–136`; `src/domain/services/ticket_sync_service.py:29–70,137–142`; `src/web/models/tickets.py:100–103`; `src/application/services/ticket_service.py:323–369`; `src/domain/services/ticket_service.py:162–174`; `src/domain/ticket.py:465–482`.
- **Доказательство.** Вызов штатного пользовательского сервиса с выбором контакта 3 для пары с контактом 2 вернул 2. После коммита обе строки содержали 2. Административная ветка 0 подтверждена статически.
- **Исправление и проверка.** Загружать клиента и выбранного пользователя по DTO, проверять допустимость и изменять источник общего значения `Ticket`, затем применять обычную синхронизацию в той же транзакции. Проверить смену, повтор и сброс контакта на владельца в связанной паре, а также очистку у отдельной внутренней заявки.

### P1. Отключение клиента или пользователя блокируется открытой заявкой в допустимом рабочем состоянии

Прикладной сервис загружает открытые заявки, а `ClientService.disable` безусловно вызывает `suspend` для каждой, хотя его контракт оставляет начатую работу активной. Дополнительно клиентский каскад меняет все открытые `TicketUser` независимо от решений по соответствующим внутренним заявкам. Исправление одним фильтром на внутренних заявках оставило бы рассинхронизацию.

- **Доказательство.** Синтетический прикладной вызов отключения клиента с `AT_WORK` получил `DomainOperationError` и оставил клиента включённым. Независимый прикладной вызов отключения пользователя с согласованной парой в `READY_FOR_REVIEW` отверг переход `ready_for_review -> suspended` и оставил пользователя включённым.
- **Исправление и проверка.** Явно определить поведение каскада для `READY_FOR_REVIEW` и согласовать его с графом домена. Переводить связанную пару по одному решению, используя `TicketSyncService`. Проверить обе операции для всех открытых состояний, включая смесь `CREATED`, `AT_WORK` и `READY_FOR_REVIEW`, и наличие истории после повторной загрузки.

### P1. Удаление отдельной внутренней заявки всегда откатывается

- **Путь и условие.** `DELETE /admin/tickets/{ticket_id}` для созданной администратором заявки без `TicketUser`. Сервис удаляет строку `Ticket`, затем безусловно читает `ticket_user.ticket_user_id`. Загрузчик возвращает `None` при отсутствующей связи.
- **Последствие.** `AttributeError` приводит к HTTP 500 и откату удаления, включая каскад истории и комментариев. Связанная ветка корректно требует порядок удаления сначала внутренней заявки из-за внешнего ключа.
- **Код.** `src/web/routers/admin/tickets.py:1046–1068`; `src/application/services/ticket_service.py:964–981,1153–1170`; `src/adapters/repositories/ticket_repository.py:339–347`; `db/schema.sql:103–105,149–151,168–170`.
- **Доказательство.** Реальный сервис в памяти создал отдельную заявку, удаление вызвало `AttributeError`, контрольный SELECT вернул исходную строку.
- **Исправление и проверка.** Вызывать удаление пользовательской записи только для существующей связи. Проверить обе ветки удаления, каскад истории и полный откат при ошибке удаления второй записи.

### P2. Сборка ответа после коммита допускает ошибку при фактически сохранённой операции

- **Путь и условие.** Общие пути изменения заявок администратора и пользователя. `_save_and_to_dto`, `_save_ticket_user` и `_save_pair` фиксируют транзакцию до сборки DTO. После этого исключение выходит из `with`, но UoW уже считает транзакцию завершённой. Вызывающий получает ошибку после успешного применения операции.
- **Последствие.** Повтор создания или добавления комментария после ошибки способен дать дубликат. Повтор перехода workflow получает изменённое состояние. Для ошибки сборки DTO потребовалась инъекция отказа. Обычный конкретный вход, при котором текущий ассемблер падает после коммита, не установлен.
- **Код.** `src/application/services/ticket_service.py:209–224,1176–1202`; `src/application/services/ticket_user_service.py:893–929`; `src/application/services/department_service.py:279–292`; `src/adapters/uow/sqlite_unit_of_work.py:97–120,127–151`.
- **Доказательство.** Подмена `TicketAssembler.to_dto` на `RuntimeError` при штатном создании оставила новую строку в SQLite, несмотря на исключение сервиса.
- **Исправление и проверка.** Собирать DTO до выхода из контекста, оставив один владелец коммита. Проверить откат при отказе сборки DTO. Для транспортной потери ответа отдельно определить контракт повторов создания и комментариев, поскольку транзакция не может гарантировать доставку ответа.

### P2. Конкурирующие записи SQLite обходят обработку конфликта версии, а ошибка COMMIT оставляет транзакцию активной

- **Путь и условие.** Запросы получают отдельные соединения. UoW открывает `BEGIN TRANSACTION` и читает агрегаты до записи. В SQLite конкурирующий держатель блокировки может прервать повышение читающей транзакции до пишущей до того, как UPDATE проверит `version`. Ошибка превращается в общий `PersistenceError`. При ошибке автоматического COMMIT `__exit__` сбрасывает флаги UoW, оставляя на `Connection` активный незавершённый SQL. Повторный `__enter__` принимает `False` от `begin_transaction` за успешное открытие.
- **Последствие.** Обычные одновременные изменения могут закончиться HTTP 500 без управляемого контракта повтора. В HTTP-пути финальный `conn.close()` обычно откатывает незавершённый SQL. При повторном использовании того же UoW в Python следующая операция может нечаянно зафиксировать изменение предыдущей неуспешной операции.
- **Код.** `src/web/dependencies/services.py:22–32`; `src/web/main.py:73–78`; `utils/db/connect.py:46–109`; `src/adapters/uow/sqlite_unit_of_work.py:76–120`; `utils/db/query.py:17–41`; `src/adapters/repositories/base_repository.py:46–57`; `src/adapters/repositories/gateways/ticket_gateway.py:162–176`.
- **Доказательство.** Два соединения с временной SQLite и отключённым ожиданием блокировки для детерминированности. UPDATE с условием версии вернул `PersistenceError: database is locked`. Автоматический COMMIT на втором соединении вернул `DBOperationError`, после чего `Connection.in_transaction()` был истинным, а UoW неактивным. Следующий контекст того же UoW зафиксировал запись из предыдущего неуспешного контекста.
- **Исправление и проверка.** Явно откатывать транзакцию при отказе COMMIT и не входить в UoW без владения новой транзакцией. Сохранять код ошибки SQLite при преобразовании, отличать `SQLITE_BUSY` от конфликта версии и повторять только всю безопасную операцию с новой транзакцией и повторным чтением. Проверить алгоритм двумя соединениями на одном файле.

## Восстановление и дополнительные дефекты адаптеров

### P1. DDL снимка не разворачивается на пустой SQLite

- **Путь и условие.** Восстановление или первоначальное развёртывание последовательным выполнением `db/schema.sql`. После первой таблицы с `AUTOINCREMENT` сам SQLite создаёт служебную таблицу. Строка 8 явно пытается создать объект с зарезервированным именем.
- **Последствие.** SQLite останавливает скрипт до создания `employees` и остальных таблиц. Вариант без внешней транзакции может оставить созданную таблицу `departments`.
- **Код и доказательство.** `db/schema.sql:1–9`. Буквальный `sqlite3.connect(':memory:').executescript(schema)` вернул `object name reserved for internal use: sqlite_sequence`. Основные прикладные проверки выполнены с той же схемой за исключением этой строки в памяти. Использование файла в конкретном развёртывании не установлено.
- **Исправление и проверка.** Убрать ручное создание служебной таблицы из исходного DDL, создать пустую БД буквальным скриптом и проверить `PRAGMA foreign_key_check` и основные операции записи и чтения.

### P2. Допускаемые схемой NULL делают часть истории и версий нечитаемой или необновляемой

- **Путь и условие.** Повторное чтение внутренней заявки из данных, где `ticket_status_records.duration IS NULL`. Схема допускает NULL без значения по умолчанию. Маппер сначала строит `timedelta(seconds=None)`, и его запасное значение не вычисляется. В аналогичной ситуации с `tickets.version IS NULL` или `user_tickets.version IS NULL` маппер читает 0, но `WHERE version = 0` не совпадает с NULL.
- **Последствие.** История с NULL блокирует чтение и изменение агрегата. NULL-версия выглядит как постоянный оптимистический конфликт. Текущий штатный путь записи проставляет duration и version. Наличие таких строк в действующей БД не проверялось.
- **Код.** `db/schema.sql:111–139,156–166`; `src/adapters/repositories/mappers/ticket_mapper.py:64–79,100–124,162–185`; `src/adapters/repositories/mappers/ticket_user_mapper.py:53–70`; `src/adapters/repositories/gateways/ticket_gateway.py:162–176,218–223`; `src/adapters/repositories/gateways/ticket_user_gateway.py:70–79,100–105`.
- **Доказательство.** Синтетическая строка истории с NULL воспроизвела `TypeError` на `TicketRepositorySQLite.get`. Конфликт NULL-версии подтверждён семантикой SQL и сверкой мапперов с предикатами обновления.
- **Исправление и проверка.** Нормализовать отсутствующую длительность до нуля до вызова `timedelta`. Выполнить проверяемую миграцию NULL-версий и добавить ограничения `NOT NULL DEFAULT 0` к соответствующим полям. Проверить чтение старой истории с фактическими интервалами и штатный конфликт двух разных версий после миграции.

### P3. Пакетные запросы Ticket расходятся по порядку столбцов с маппером

- **Путь и условие.** `TicketRepositorySQLite.iter_get_all` и `iter_by_client_id` получают непустую выборку. `SELECT_*_BATCH` выдаёт 15 полей вместо 13 и ставит `description` на место `urgency_level`, повторяя другие поля. Общий `Query` связывает по позиции через `zip` без проверки длины.
- **Последствие.** Пакетное чтение может завершиться ошибкой перечисления либо загрузить неверные описание и версию. Эти методы не найдены среди вызовов прикладных сервисов снимка. Также неактивные на штатных маршрутах фильтры `TicketGateway.SELECT_BY_FINISHED_CLIENT_ID` и `TicketUserGateway.SELECT_BY_FINISHED_CLIENT_ID` возвращают открытые записи, второй ещё и фильтрует по `user_id` вместо `client_id`.
- **Код.** `src/adapters/repositories/gateways/ticket_gateway.py:58–69,74–120`; `src/adapters/repositories/gateways/ticket_user_gateway.py:28–37`; `src/adapters/repositories/ticket_repository.py:150–206,265–277`; `src/adapters/repositories/mappers/ticket_mapper.py:12–27,64–80`; `utils/db/query.py:43–55`.
- **Доказательство.** Штатный `iter_get_all` на временной БД вернул `ValueError: None is not a valid TicketUrgency`. Ошибки предикатов подтверждены статически.
- **Исправление и проверка.** Переиспользовать список столбцов обычной выборки для пакетной. Сравнить по полям результаты одиночного и пакетного чтения на разных размерах страниц. Проверить каждый отложенный фильтр на смеси закрытых и открытых строк разных клиентов.

## Условные риски и вопросы контракта

- **Повтор сохранения того же объекта после отката.** Репозитории назначают ID корней и детей и увеличивают версии сразу после SQL, до общего коммита. Новый элемент определяется нулевым ID. Если вызывающий сохранит тот же объект в новой транзакции после отката, объект может выглядеть сохранённым, запись истории будет пропущена либо UPDATE получит непредвиденный конфликт версий. Штатные HTTP-операции заново загружают агрегаты. Проверка для будущего retry — вызвать ошибку между записью истории и коммитом пары, затем подтвердить повтор через свежую загрузку, с отсутствием дубликатов или пропавших записей. `src/adapters/repositories/ticket_repository.py:86–108,296–326`, `src/adapters/repositories/ticket_user_repository.py:108–136,262–306`, `src/domain/ticket.py:393–400`.
- **Кардинальность связи и восстановление пары.** Сервисы предполагают одну внутреннюю заявку на `TicketUser`, а внешнего ключа без уникального ограничения для этого недостаточно. Чтение выбирает одну строку. Нормальные проверенные создания получают новый ID `TicketUser` в той же транзакции, поэтому сценарий дубликата через штатный HTTP не установлен.
