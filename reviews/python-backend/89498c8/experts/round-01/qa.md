# Первый раунд. QA Python и FastAPI

Снимок `main` — `89498c8318d587f197b0ae584d95899d5939c8d8`. Проверял ASGI-приложение `src.web.main:app`, его входы пользователя и администратора, JSON-контракт и состояние после запросов. Для HTTP-проверок использовал FastAPI 0.143.0, Pydantic 2.14.1 и временный файл SQLite с синтетическими учётными записями, созданный из `db/schema.sql` без служебного `CREATE TABLE sqlite_sequence`. Запросы шли через `TestClient` и штатные зависимости, вход выполнялся с синтетическими данными. Проверки авторизационных рисков ниже статические.

## Подтверждённые ошибки

### QA-01. Изменение состояния учётной записи пользователя теряется после HTTP 200

**Высокий приоритет. HTTP и повторное чтение SQLite.** Администратор с `user.operation` через `PATCH /admin/users/{employee_id}/account/disable` для существующего активного аккаунта получил `200` и `enabled_login: false`. Другое соединение SQLite сразу после запроса прочитало прежнее `accounts.enabled=1`. При `PATCH /admin/users/{employee_id}/account/enable` для отключённого аккаунта ответ дал `200` и `enabled_login: true`, а другое соединение прочитало `accounts.enabled=0`. Оба метода открывают транзакцию только на чтение, а мутацию и сохранение вызывают после выхода из UoW. Закрытие соединения отменяет незафиксированную запись. Ссылки: `src/web/routers/admin/users.py:241–284`, `src/application/services/user_service.py:242–282,624–636`, `src/adapters/uow/sqlite_unit_of_work.py:91–122`, `src/web/dependencies/services.py:22–32`.

**Исправление и регрессия.** Перенести мутацию и сохранение обоих методов внутрь того же `with self.uow`. Проверять оба перехода через реальные маршруты, отражение в ответе и новое чтение через отдельный HTTP-запрос или соединение. При ошибке сохранения проверять отсутствие частичных изменений.

### QA-02. Пользовательский маршрут изменения контакта возвращает 200 с прежним контактом

**Высокий приоритет. HTTP и повторное чтение SQLite.** При наличии прав на собственную открытую заявку и валидного нового контакта той же организации `PATCH /user/tickets/{ticket_user_id}/contact-user` принимает идентификатор, но сервис его не читает. Вместо него передаются пустые `User` и `Client`. Доменный метод сначала меняет контакт пользовательской заявки, затем синхронизация из внутренней заявки снова записывает её прежний контакт. В проверке переключение с владельца на другого пользователя дало `200` с прежним идентификатором, обе сохранённые заявки остались с прежним контактом. Обратный пример также наблюдался на ранее рассогласованной паре. Ссылки: `src/web/routers/user/tickets.py:369–398`, `src/application/services/ticket_user_service.py:265–307`, `src/domain/services/ticket_user_service.py:107–136`, `src/domain/services/ticket_sync_service.py:29–70,137–142`.

**Исправление и регрессия.** Загрузить клиента заявки и выбранного пользователя по DTO, проверить принадлежность и активность, единообразно обработать сброс контакта `0`. Обновлять обе связанные записи в одной транзакции в согласованном направлении. Проверять смену на другого активного пользователя того же клиента, сброс контакта к владельцу, отказ для отключённого контакта и чужого клиента, и сохранённые значения обеих записей.

### QA-03. Создание заявки с явно выбранным контактом сохраняет разные контакты в связанных записях

**Высокий приоритет. HTTP и запрос к синтетической SQLite.** В `POST /user/tickets/` существующий контакт той же организации был передан как `contact_user_id=3` при владельце `2`. HTTP 201 вернул `contact_user_id=2`. Сразу после записи SQLite показала пару контактов `(2, 3)` для пользовательской и внутренней заявок соответственно. Та же сохранённая пара подтверждена через `POST /admin/tickets/` с `user_id>0` для администратора с правом создания и без права автоматического принятия. Ссылки: `src/web/models/tikcets_user.py:16–33`, `src/application/services/ticket_user_service.py:141–196`, `src/domain/services/ticket_user_service.py:39–66`, `src/domain/services/ticket_service.py:103–132`, `src/application/services/ticket_service.py:141–188,209–224`. Тестовое ожидание согласованности уже есть в архивном `integration/application/test_active_services_sqlite.py:136–168`, но сам тест передаёт устаревшие `urgency_level` и `is_remote`.

**Исправление и регрессия.** Рассчитать итоговый ID контакта один раз после проверки кандидата. Передавать его обоим агрегатам и проверять ответ и сохранённую пару немедленно после создания для пользователя и администратора, со стандартным контактом и явно выбранным контактом. Вызовы последующих переходов должны опираться на согласованную пару.

### QA-04. Ожидаемые ошибки клиента превращаются в 500, ответ раскрывает внутренние детали

**Высокий приоритет. HTTP и статический анализ.** На реальном приложении неправильный пароль дал `500/InvalidCredentialsError`, отсутствующая заявка в пользовательском и административном маршрутах дала `500/ItemNotFoundError`, отрицательный ID дал `500/ApplicationValidateError`. Без Bearer-заголовка FastAPI штатно вернул 401. У зарегистрированного приложения единственный прикладной обработчик — `Exception -> 500`; пользовательский маршрутизатор перебрасывает исключение, а обработчик возвращает `str(exc)` и класс. Через общий обработчик может уходить, например, путь из `DBConnectError`. Ссылки: `src/web/main.py:43–78`, `src/web/routers/user/tickets.py:39–79,266–294`, `src/web/execeptions/exception_handlers.py:94–135,323–344`, `utils/db/connect.py:26–35`. Архивный `integration/web/test_api_smoke.py:127–138` ожидает 400 для `DomainOperationError`, но весь модуль сейчас падает при импорте.

**Исправление и регрессия.** Зарегистрировать в производственной фабрике конкретные классы ошибок. Проверять 401 для невалидных учётных данных и токена, 403 для отказа RBAC, 404 для отсутствующего ресурса, 400/422 для ошибок валидации и 409 для конфликта версии. Зафиксировать единый контракт ответа, применять `WWW-Authenticate: Bearer` для отказа Bearer-аутентификации и возвращать стабильное общее сообщение при неожиданной ошибке. В тесте непредвиденной ошибки утверждать, что синтетический путь и класс исключения отсутствуют в ответе.

### QA-05. Входные модели административного создания и планирования допускают несовместимые значения

**Средний приоритет. HTTP и проверка моделей.** `POST /admin/tickets/` с неизвестной срочностью проходит через `TicketCreateRequest`, где `urgency` — строка, и падает на `TicketUrgency(...)` с HTTP 500. `PATCH /admin/tickets/{ticket_id}/schedule` с ISO-датой будущего дня и валидным смещением `+03:00` даёт HTTP 500. Модель создания нормализует то же значение в UTC, а модель планирования передаёт смещение без нормализации, которое отвергает домен. Ссылки: `src/web/models/tickets.py:17–49,118–132`, `src/application/services/ticket_service.py:174–203,423–450`, `src/web/routers/admin/tickets.py:579–608`, `src/domain/ticket.py:516–526,918–934`, `src/domain/datetime_check.py:8–16`.

**Исправление и регрессия.** Использовать enum для срочности при создании и общую нормализацию timezone-aware дат для создания и планирования, сохранив доменную проверку календарного ограничения. Проверять валидные ненулевые смещения, границу перехода календарного дня при нормализации, дату без смещения и неизвестную срочность. Для идентификаторов применять ограничения в HTTP-модели с учётом маршрутов, где ноль действительно обозначает отсутствие связи.

### QA-06. Точки запуска и проверка тестов расходятся

**Средний приоритет. Команда и статический анализ.** Корневой `main.py:1–5` безусловно вызывает pytest и завершает процесс без его кода возврата. Из пустого рабочего каталога он собрал 0 тестов и завершился с 0, тогда как отдельный pytest вернул 5. При запуске `python -m src.web.main` встроенный Uvicorn использует `main:app` вместо `src.web.main:app`, а также одновременно задаёт перезагрузку и несколько workers (`src/web/main.py:87–96`). ASGI-импорт по полному пути и `GET /health` дали успешный результат в изоляции. При инициализации пустой SQLite опубликованная SQL-схема останавливается на `db/schema.sql:8` с `object name reserved for internal use: sqlite_sequence`. Для smoke-теста временно исключил эту строку из загружаемого текста схемы. `pytest.ini:1–4`, `run_pyramid.sh:1–3` и `run_coverage.sh:1–4` ссылаются на директории, отсутствующие в Git-дереве снимка.

**Исправление и регрессия.** Документировать канонический запуск `uvicorn src.web.main:app`, проверить его smoke-тестом. Тестовая команда должна возвращать код pytest, включая пустой сбор и ошибку коллекции. Хранить актуальные тесты в обычном дереве и собирать их в CI. Убрать служебный SQL и проверить инициализацию пустой базы перед HTTP smoke.

## Подтверждённые чтением кода риски авторизации

- **QA-07. Отзыв всех refresh-сессий без удостоверения личности.** Оба logout-маршрута принимают `username` без текущего principal. Менеджер передаёт строку в общий отзыв, а хранилище выбирает записи только по имени. Два номинальных хранилища образуются из singleton и остаются одним объектом. Следствие — потеря возможности обновить сессии, в том числе по обе стороны разделения admin/user при совпадении логинов. Ветка предъявленного refresh-токена также не сверяет тип субъекта, в отличие от `refresh`. Ссылки: `src/web/routers/auth.py:92–102,126–133`, `src/web/auth/models.py:8–10`, `src/web/dependencies/auth.py:25–36,95–117`, `src/web/auth/services/services.py:209–248,250–272`, `src/web/auth/storage.py:65–85,153–170`. Исправление — субъект берётся из проверенного контекста, отзыв привязывается к типу и неизменяемому ID, хранилище или его ключи разделяются. Проверки должны утверждать авторизацию операции, неизменность сессий другого субъекта и совпадающих логинов другого типа.
- **QA-08. Проверка access-токена не учитывает состояние аккаунта.** Обычные маршруты используют `get_current_admin/user`, которые проверяют JWT и тип. Актор сервиса повторно загружается и проверяется RBAC, но `can_do_operation()` проверяет только `employee.enabled`. Отключение или отвязка именно аккаунта у активного сотрудника не влияет на доступ по ранее выданному JWT в пределах TTL при сохранённых ролях. Вход и обновление токенов проверяют также аккаунт, а для пользователя клиента. Списки доступных административных permissions опираются только на тип токена. Ссылки: `src/web/dependencies/auth.py:129–162`, `src/application/helper/actor_helper.py:239–277`, `src/domain/employee.py:148–160`, `src/domain/policies/{admin,user}.py:9–23`, `src/web/routers/admin/roles.py:24–28,57–74`. Исправление — общее правило актуальности principal для защищённых операций. Проверки — отзыв доступа после деактивации или отвязки аккаунта, отключения сотрудника, и обновление прав после отзыва роли без ожидания окончания JWT. Ошибка QA-01 отдельно препятствует сохранению изменения состояния аккаунта пользователя.
- **QA-09. Конфигурация токенов и сохранение секретов.** В `src/web/config.py:8–23` есть встроенный JWT-ключ, применяемый при отсутствии внешнего значения. В `src/domain/value_objects.py:342–368` для паролей используется быстрый SHA-256 без соли, подключённый к `Password` в том же файле. В условиях утечки копии хранилища такой хеш удешевляет проверку вариантов пароля. Требовать внешний JWT-ключ при запуске, использовать современную схему хранения пароля с солью и миграцией существующих хешей по мере подтверждённых входов. Проверять отказ запуска при отсутствии обязательной конфигурации, проверку новых хешей и миграцию старых. Фактическая конфигурация развёртывания в рамках аудита не проверялась.
- **QA-10. Refresh-сессии привязаны к процессу.** При перезапуске либо обслуживании логина и последующего refresh разными workers корректная сессия недоступна. В хранилище предусмотрена очистка просроченных токенов без вызывающего кода в текущем приложении. Ссылки: `src/web/dependencies/auth.py:35–36`, `src/web/auth/storage.py:51–108,122–140`, `src/web/auth/services/services.py:42–93`, `src/web/main.py:27–84,87–96`. Хранить хеш refresh-токена в разделяемом хранилище с TTL и атомарной ротацией. Проверять работу двух экземпляров приложения и повторное предъявление уже ротированного токена.

## Сопоставление тестов и гипотезы

- В снимке присутствуют `simple_tickets_test_pyramid.zip`, `simple_tickets_test_pyramid_dropin.zip` и `ticket_regression_tests.zip`. Для сверки по именам просмотрел списки всех трёх, для чтения и выборочного запуска извлёк Python-тесты из drop-in во временную директорию. Архивный HTTP smoke не собирается, поскольку импортирует `get_ticket_user_service`, тогда как текущая функция называется `get_application_ticket_user_service` (`integration/web/test_api_smoke.py:14–18,141–158`, `src/web/dependencies/services.py:41–44`). Фикстуры JSON также используют прежние `ticket_id`, `is_remote` и `urgency_level`, а пользовательский запрос передаёт запрещённый текущей моделью `client_id`. Из пяти выборочно запущенных тестов обработчиков и зависимости четыре прошли, один упал на устаревшем моке без `settings` (`unit/web/test_dependencies_and_errors.py:46–67`). Тесты раздельности хранилища проверяют класс менеджера и тип субъекта, без проверки отдельного хранения (`unit/web/test_dependencies_and_errors.py:70–77`). Архивные SQLite-интеграции, которые копируют существующий `db/admins.db`, в этом раунде не запускал. Для регрессий HTTP стоит инициализировать SQLite из поддерживаемой схемы и выполнять штатный login с раздельными ролями.
- **Риск масштаба, без замера.** `GET /user/tickets/`, `/all`, `/open` и `/closed` читают все пользовательские заявки и для каждой загружают историю и комментарии до фильтрации по клиенту и сотруднику (`src/application/services/ticket_user_service.py:465–509,525–548,565–658`, `src/adapters/repositories/ticket_user_repository.py:50–102,161–171`). Даже данные другой организации повышают нагрузку запроса. Перенести фильтры в SQL и проверить запросы на наборе из двух клиентов, включая размер результата и число запросов. При переходе на существующий закрытый фильтр по клиенту следует исправить условие `SELECT_BY_FINISHED_CLIENT_ID`, которое сейчас проверяет `user_id` и открытость (`src/adapters/repositories/gateways/ticket_user_gateway.py:34–37`).
- **Формат вложенных полей наблюдался, статус контракта требует подтверждения.** Ответ администратора передаёт `comments[].comment` и `statuses[].comment` как объект с `value`, тогда как пользовательский ответ содержит строки (`src/application/assemblers/assembler.py:44–70,111–140`, `src/web/models/tickets.py:285–293`, `src/web/models/tikcets_user.py:75–78`). Динамически это видно при создании заявки с комментарием. Зафиксировать контракт для действующих потребителей и добавить вложенные типизированные модели с сериализационным тестом. Доказательств поломки клиента в рамках Python-аудита нет.
