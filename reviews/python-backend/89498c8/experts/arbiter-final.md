## Решение по рабочим HTTP-путям

### F1. P1 — состояние аккаунта User не сохраняется при успешном ответе

Принимаю QA-01, подтверждённую также Python-проверкой отдельного соединения. `src/application/services/user_service.py:242–282` завершает `with self.uow` до `UserService.enable_account/disable_account` и `_save_and_to_dto`. На `:624–636` сохранение уже вне явной транзакции; `src/adapters/repositories/user_repository.py:130–153` выполняет UPDATE сотрудника и аккаунта. SQLite открывает неявную транзакцию, а `utils/db/connect.py:95–109` не делает commit; закрытие сырого соединения отменяет запись. `src/web/dependencies/services.py:22–32` закрывает соединение после запроса.

Доказанный эффект: оба `PATCH /admin/users/{id}/account/{enable,disable}` отвечают 200 с новым флагом; новое соединение видит прежние account.enabled и employees.version. Контрпример: аналогичные методы Admin держат мутацию внутри UoW (`src/application/services/admin_service.py:239–269`), поэтому обобщать на все аккаунты нельзя. Исправить отступы/границу транзакции, сохранить проверку Client при включении. Проверять оба направления и ровно одно увеличение версии после закрытия исходного соединения.

### F2. P1 — создание связанной пары расходится по контакту; ранняя отмена откатывается

Принимаю A3 и совпадающие выводы всех трёх экспертов. `src/domain/services/ticket_user_service.py:59–65` подставляет автора вместо переданного контакта; `src/application/services/ticket_user_service.py:147–196` передаёт выбранный объект во внутренний Ticket. На HTTP доказаны 201 и разные сохранённые контакты для пользователя и административного создания без автопринятия. Ранняя отмена затем получает ошибку контактов из `src/domain/services/ticket_sync_service.py:158–172` с откатом обеих записей.

**Ограничение:** административное автопринятие (`src/application/services/ticket_service.py:209–224`) и обычный `/accept` выравнивают контакт до проекции статуса. Поэтому тезис «этот POST неизбежно ломает последующее подтверждение пользователя» отклоняю: нормальный путь к WAITING_FOR_CONFIRMATION проходит синхронизацию. Для такого отказа нужна пара, рассогласованная уже на проверке. Отсутствие явного commit в пользовательском POST не дефект: UoW коммитит успешный выход.

Исправление: единожды нормализовать контакт, передать один ID обоим агрегатам, проверить согласованность до фиксации. Регрессии: контакт автора/коллеги/0, оба POST, автопринятие в двух вариантах прав, немедленная отмена и повторное чтение. Для старых пар требуется решение об авторитетном контакте до миграции.

### F3. P1 — пользовательский PATCH игнорирует новый контакт

Принимаю A2 с уточнением. `src/application/services/ticket_user_service.py:265–307` подставляет пустые User/Client и не читает новый ID. `src/domain/services/ticket_user_service.py:120–127` создаёт исключения без raise; на `:132–135` меняет TicketUser и тут же синхронизирует его из Ticket (`ticket_sync_service.py:138–142`). HTTP доказал 200 с прежним контактом и ростом обеих версий на согласованной паре.

**Контрпример к «всегда ничего не меняет»:** на рассогласованной паре PATCH может записать в TicketUser старый контакт Ticket независимо от запроса. Чинить нужно загрузку DTO, валидацию, направление проекции и сохранение редактируемости вместе. Административный PATCH с 0 — отдельное подтверждённое расхождение внешней схемы и фасада даже для самостоятельной заявки: `src/web/models/tickets.py:100–103`, `src/domain/services/ticket_service.py:162–174`, `src/domain/ticket.py:465–482`. Смысл 0 для административной связанной заявки ещё следует утвердить.

### F4. P1 — три отдельных дефекта каскадов отключения

1. `src/domain/services/client_service.py:223–247` безусловно приостанавливает открытые Ticket. Граф `src/domain/statuses/rules/ticket_status_transition.py:76–119` не разрешает AT_WORK/READY_FOR_REVIEW → SUSPENDED. User исключает AT_WORK, но не READY_FOR_REVIEW (`src/domain/services/user_service.py:435–448`). QA подтвердил отказ HTTP и сохранение активного Client в обоих состояниях, User — на READY_FOR_REVIEW. Откат всего каскада штатен; дефект — несовместимость команды с графом, а не частичная фиксация отказавшего перехода.
2. Успешный User-disable на ранней согласованной паре теряет внешнее изменение. `src/domain/services/user_service.py:373–398` синхронизирует TicketUser в памяти, но не добавляет его в changed_ticket_users. `src/application/services/user_service.py:480–499` сохраняет только возвращённые элементы. HTTP и независимые прикладные проверки показывают отключённого User, Ticket=SUSPENDED, TicketUser=CREATED с прежней историей. Это безусловный технический дефект, не вопрос графа.
3. После успешного Client-disable внутренний SUSPENDED закрыт, внешний открыт. Следующий disable после enable снова выбирает внешний SUSPENDED и падает на запрещённом самопереходе (`src/domain/statuses/ticket_user_status_transitions.py:34–42,69–75`, `src/adapters/repositories/gateways/ticket_user_gateway.py:31–32`). HTTP и прикладные опыты подтверждают, что после enable клиент остаётся активен. Немедленный повтор команды — отдельный вопрос идемпотентности, но последовательность disable → enable → disable уже демонстрирует поломку обычного сценария.

Исправлять одним решением на связанную пару. Возвращать и сохранять изменённый TicketUser; пропускать уже обработанные пары. Для AT_WORK docstring Client обещает продолжение работы, User уже реализует пропуск. Для READY_FOR_REVIEW продукт должен решить судьбу проверки. Проверить все состояния, смешанный набор, повтор после enable, обе истории и полный откат при отказе второй записи. Объявлять внешний SUSPENDED закрытым без согласования не требуется для исправления технических сбоев.

### F5. P2 — DELETE самостоятельного Ticket падает; связанная ветвь работает

`src/application/services/ticket_service.py:964–981,1153–1170`: загрузчик возвращает None для user_ticket_id=0, затем приложение безусловно читает ticket_user.ticket_user_id после первого DELETE. Доказаны HTTP 500/AttributeError и сохранение строки/истории после rollback. Контроль QA: связанная заявка удаляется с 204 и исчезают обе строки. Аргумент `ticket_id` соответствует сигнатуре `src/adapters/repositories/ticket_user_repository.py:324–352`; считать его ошибочным нельзя. Порядок удаления соответствует внешнему ключу `db/schema.sql:149–151`.

Исправить условие наличия связи; проверить обе ветви и отказ второго DELETE. Выбор TICKET_CANCELLED для физического удаления и разрешённые статусы — отдельный контракт, не доказанная уязвимость.

### F6. P1 — прикладные ошибки классифицируются как 500 и раскрывают внутренний текст

Принимаю A7 и расширение QA. `src/web/main.py:43–78` регистрирует только общий Exception → 500; `src/web/execeptions/exception_handlers.py:119–135,323–347` возвращает str(exc) и тип. Пользовательский `_domain_error` перебрасывает ошибку. HTTP-опыты QA доказывают симптом для неверного пароля, отсутствующей заявки и отрицательного ID; другие доменные отказы следуют из проверенной статической цепочки.

**Контрпример:** стандартный HTTPException, отсутствие Bearer и Pydantic-валидация имеют собственные 401/403/422. Нельзя писать «все ошибки FastAPI дают 500». Кроме регистрации обработчиков нужно сохранить классы ошибок: голые except в `src/application/services/user_service.py:624–636` и `admin_service.py:639–651` маскируют, например, OptimisticLockError как ApplicationValidateError.

Регрессии отдельно для login и Bearer, RBAC, 404, конфликтов workflow/версии, SQLite busy и неожиданной ошибки. Согласовать 400/422 и 409; для неожиданных 500 — стабильное сообщение без класса, пути и внутренних деталей.

### F7. P2 — UTC и срочность расходятся между HTTP-моделями и доменом

`src/web/models/tickets.py:17–49` нормализует planned_at при создании, но `:129–133` не делает этого для schedule, `:201–228` принимает AwareDatetime без нормализации ретроспективного интервала. `src/domain/datetime_check.py:8–16` требует нулевое смещение. HTTP и прикладные проверки показали отказ +03:00 и успех тех же моментов в Z; при отказе история не меняется. Для schedule нужно дополнительно выдержать календарное ограничение UTC, для ретроспективы — прошедший корректный интервал. Сама aware-дата с ненулевым offset не ошибочна.

Неизвестная urgency — другая причина: создание принимает str, а TicketUrgency строится внутри сервиса (`src/application/services/ticket_service.py:174–203`). Исправить enum на входе и общий преобразователь дат. Проверить эквивалентные моменты, полночь UTC, naive datetime, неизвестную urgency и отсутствие побочных записей.

## Авторизация: статические решения, без воспроизведения

### S1. P1 — logout всех сессий не связан с удостоверенным субъектом

A1 сохраняю. `src/web/routers/auth.py:92–102,126–133` не требует principal; `src/web/auth/models.py:8–10`, `src/web/auth/services/services.py:250–272`, `src/web/auth/storage.py:153–170` допускают отзыв по переданному username. Это доказанный кодом пробел контроля доступа, не гипотеза о требованиях. Два storage в `dependencies/auth.py:35–36` — один singleton (`storage.py:65–85`).

**Поправка к ранним формулировкам:** `db/schema.sql:180–181` запрещает два текущих аккаунта с одинаковым login глобально. Межролевой эффект совпадающего имени требует дополнительного условия, например оставшейся сессии после переиспользования имени. Неосновной сценарий не нужен для самого вывода об отзыве по непроверенной идентичности. Отзыв удаляет refresh в данном процессе, не прекращает немедленно access JWT. Предъявление opaque refresh может быть самостоятельным полномочием на отзыв именно этой сессии; требовать principal во всех таких ветвях — выбор API, но realm/принадлежность следует определить явно.

Исправить массовый отзыв: брать устойчивый subject_type + subject_id из проверенного контекста. Защитные регрессии после изменения проверяют изоляцию субъектов и realms; уязвимые запросы не разрабатывались и не выполнялись.

### S2. P2 — access и login/refresh проверяют разные признаки актуальности

`src/web/dependencies/auth.py:129–156` проверяет JWT/тип. `src/application/helper/actor_helper.py:239–277` перечитывает актора, `src/domain/employee.py:148–150` проверяет enabled сотрудника; роли в обычных сервисах читаются актуально. Состояние/наличие аккаунта проверяется login/refresh в `src/domain/policies/{admin,user}.py`, но не этой цепочкой access.

Статическое расхождение подтверждено. Его серьёзность зависит от утверждения немедленного прекращения доступа либо остаточного TTL. QA-01 — отдельный дефект фиксации аккаунта, его устранение само по себе не меняет политику JWT. Каталоги enum permissions не выдают актору новые права; отсутствие доменной проверки там — узкое свойство, не доказательство повышения привилегий. Закрыть вопрос решением о сроке отзыва, затем защитными тестами, предварительно удостоверив реальное сохранение отключения.

### S3. P1/P2 — конфигурация подписи, пароли и refresh требуют отдельных задач

В `src/web/config.py:8–23` подтверждено встроенное резервное значение ключа; реальное развёртывание не исследовалось, секрет здесь не воспроизводится. Требовать явную конфигурацию для production. `src/domain/value_objects.py:342–368,438–465` подтверждает SHA-256 без соли для Password; нужна миграция на Argon2id/scrypt/bcrypt с сохранением возможности входа старых пользователей. Это не замечание к SHA-256 случайных opaque refresh.

`src/web/auth/storage.py:51–108` хранит сессии в процессе: restart теряет refresh, разные процессы не делят их. Реальные workers неизвестны; `reload=True, workers=4` не доказывает четыре активных процесса. Ротация `services.py:67–93` неатомарна: удаление предшествует выпуску. Два успешных результата гонки не доказаны — второе delete может отказать. `services.py:235–247` валидирует username, но выпуск на `:88–92` использует прежний ID: возможное несовпадение идентичности условно на смену/переиспользование имени. Проверять и хранить стабильный ID/тип, использовать shared storage с атомарной ротацией и TTL. Защитные проверки — обязательность конфигурации, миграция хеша, отказ хранения и непрерывность сессии двух экземпляров.

P2: канонический ASGI-start, актуальные тесты и ненулевой CI при пустом сборе/ошибке коллекции. |

## Оставшиеся разногласия и решения, которые их закроют

1. **Удалённое самоназначение и отдел.** Механизм подтверждён статически: обычный `TicketService.assign` проверяет отделы (`src/domain/services/ticket_service.py:236–264`), путь start_remote_work (`src/application/services/ticket_service.py:673–718`, `src/domain/ticket.py:790–850`) из ACCEPTED добавляет ASSIGNED без этого правила. Из ASSIGNED проверяется текущий исполнитель. Аналитик оценивает P1, Python/QA условнее. Мой вердикт: подтверждённое расхождение с явным общим правилом `src/domain/department.py:18–21` и `rules.md:53–64`, P2 до оценки влияния, без доказанного исключения для remote. Это не находка об отсутствии permission: специальный permission есть. Закрыть письменным утверждением исключения либо общей валидацией только новой ветви назначения; затем защитная матрица отсутствующего/равного/другого отдела и атомарности двух записей.
2. **Принадлежность контакта/владельца Client.** Статически нет проверки в активных фабриках и административном PATCH; `_validate_contact_user` с таким правилом вызывается только из неиспользуемого `_validate_create_references` (`ticket_user_service.py:745–844`; административные пути `ticket_service.py:133–187,323–363`). Это установленный пробел относительно собственного описанного контракта, но не доказанное раскрытие данных и не общий обход RBAC. Аналитик считает уже ошибкой целостности, Python сохраняет оговорку о допустимости межклиентского контакта. Мой вердикт: исправление как P2 общего инварианта предпочтительно; если межклиентские контакты нужны, необходимо явное продуктовое исключение и правила видимости/каскадов. Закрыть выбором политики отдельно для владельца и контакта, затем защитными проверками каждой точки записи. Исправленный пользовательский PATCH должен включать эту проверку сразу.
3. **READY_FOR_REVIEW, внешний SUSPENDED, восстановление и повтор disable.** Технические сбои F4 доказаны. Не решено, продолжать ли проверку, кто её выполняет после отключения, считать ли внешний SUSPENDED открытым, восстанавливать ли пары при enable и должен ли немедленный повтор disable быть идемпотентен. Нужна утверждённая таблица действий для каждого состояния и regression disable → enable → disable. Не менять терминальность лишь по сходству имён.
4. **Автоматический EXECUTED, комментарии, физическое удаление.** `finish_work` реально делает READY_FOR_REVIEW даже с TICKET_EXECUTED, `/execute` работает (`ticket_service.py:787–834,891–926`). Дефект docstring доказан, требование автоматического исполнения — нет. Административный `{value: ...}` и пользовательская строка комментария подтверждены, поломка потребителя не установлена. Публичность ретроспективного комментария, права/статусы физического DELETE и 0 административного связанного контакта требуют решения владельца API и типизированных контрактных тестов.
5. **Один Ticket на TicketUser.** Предположение заложено в чтение одной строки (`ticket_repository.py:126–141`), UNIQUE отсутствует (`db/schema.sql:124–155`). Штатное создание использует свежий TicketUser, HTTP-дубликат не показан. Закрыть инвентаризацией поддерживаемых импортов, утверждением кардинальности и проверкой миграции UNIQUE с NULL для самостоятельных Ticket.
6. **Эксплуатационные предпосылки.** Неизвестны реальный JWT-ключ, число процессов, объём данных, наличие исторических NULL и официальный путь восстановления. Нужны разрешённая конфигурационная проверка без раскрытия значений, описание запуска, синтетический нагрузочный замер и отдельная разрешённая миграционная инвентаризация. Из нынешнего обзора нельзя выводить компрометацию production или повсеместную потерю данных.

## Порядок исправления

1. S1, обязательная production-конфигурация подписи и F1: связать отзыв с principal и устранить ложное сохранение аккаунта. Политику актуальности access оформить отдельно, не считать её исправленной отступами UoW.
2. F2/F3 и потеря внешнего сохранения F4: согласованность контакта и статусов обеих карточек; проверить новое соединение и обе истории. Перед ремонтом старых данных утвердить источник контакта.
3. Каскады F4 по таблице состояний; F5 как небольшая самостоятельная правка. Ошибки не маскировать успешным ответом и не отключать проверки графа целиком.
4. F6 и F7: контракт ошибок, сохранение их типов, нормализация UTC и enum. Отдельно классифицировать busy и version conflict.
5. Буквальная схема, канонический запуск и достоверный CI; миграция паролей и устойчивое shared refresh storage. До эксплуатации multi-process проверить ротацию и перезапуск.
6. Адаптерные фильтры/проекции, UoW после ошибок и миграционные NULL; затем SQL-фильтрация пользовательских списков с измерением. Неподключённые пакетные методы не ставить выше доказанных HTTP-потерь записи.

Существенные исходные расхождения к третьему раунду в основном сняты уточнением условий. Нерешёнными остаются перечисленные продуктовые правила и неизвестные параметры развёртывания. Ни «самый строгий» вариант, ни гипотезы об обходе доступа здесь автоматически не приняты за спецификацию.
