# Независимое первичное заключение арбитра Codex

Снимок: `89498c8318d587f197b0ae584d95899d5939c8d8`, корень `/workspace/simple_tickets_copy`. Анализ выполнен независимо: материалы других ревьюеров и прежние отчёты не читались. Исходники не менялись. `.env`, реальные базы и история/архивы фронтенда не открывались. Авторизация исследована только статически, без запросов и воспроизведения уязвимостей. Проверки SQLite использовали исключительно `:memory:` и синтетическую строку.

## Подтверждённые проблемы

### A1. P1: публичный logout позволяет отзывать сессии по произвольному имени

`src/web/routers/auth.py:92–102,126–133`: оба обработчика принимают `LogoutRequest`, не требуют authenticated principal. `src/web/auth/models.py:8–10` разрешает username без refresh token. `src/web/auth/services/services.py:264–267` передаёт это имя в отзыв всех токенов. `src/web/auth/storage.py:153–168` выбирает токены только по username. Следствие: операция отзыва не привязана к личности вызывающего. Это подтверждённый статический дефект контроля доступа; эксплуатация не проводилась.

Дополнительное нарушение предполагаемой изоляции realms: `src/web/dependencies/auth.py:35–36` создаёт два storage, но `storage.py:65–85` реализует единый singleton на класс. Оба менеджера используют общий словарь, а отзыв по username не фильтрует subject_type. Возможность совпадения имён зависит от данных; глобальный UNIQUE login в текущей схеме снижает этот конкретный сценарий, но не исправляет отсутствие авторизации.

Исправление: logout всех устройств требует текущего principal, берёт subject_id и realm из него; storage индексируется по паре realm/id. Logout одной сессии проверяет принадлежность. Не принимать произвольный username как полномочие.

### A2. P1: смена контакта пользовательской заявки не реализует заявленный эффект

Рабочая цепочка: `PATCH /{ticket_user_id}/contact-user`, `src/web/routers/user/tickets.py:369–400` → `src/application/services/ticket_user_service.py:265–307`. После проверки доступа приложение создаёт `User.create_empty()` и `Client.create_empty()` (288–289), полностью игнорирует новый contact_user_id и не загружает выбранного пользователя/клиента. Доменный метод `src/domain/services/ticket_user_service.py:120–127` дополнительно конструирует исключения без `raise`. На 132 меняет только TicketUser; на 133 вызывает sync_from_ticket, который в `src/domain/services/ticket_sync_service.py:138–142` копирует прежний контакт Ticket обратно. Поэтому даже исправление загрузки сущностей само по себе оставит успешный запрос без изменения контакта.

Исправление: загрузить клиента и выбранного пользователя; проверить принадлежность; изменить канонический контакт Ticket, затем синхронизировать пару; добавить raise. Проверять успешную смену на отличный ID, равенство обоих агрегатов после сохранения и повторного чтения.

### A3. P1: создание пары Ticket/TicketUser игнорирует выбранный контакт и сохраняет несогласованную пару

`src/domain/services/ticket_user_service.py:59–65` всегда передаёт `contact_user_id=user.employee_id` вместо contact_user.employee_id. При этом `src/application/services/ticket_user_service.py:147–159` загружает контакт из DTO, затем на 184–191 передаёт его во внутренний Ticket. Для отличного от автора контакта агрегаты получают разные contact_user_id. Комментарий приложения 175–178 обещает использование нормализованного контакта TicketUser, но фактический вызов ему не соответствует. После сохранения пары синхронизации нет (200–206). Проверка соответствия на `ticket_sync_service.py:164–167` позднее обнаружит расхождение либо другая операция молча перезапишет контакт.

Исправление: единая нормализация контакта, проверка клиента контакта и проверка инвариантов пары до commit. Обязательно покрыть контакт автора, другой контакт и отсутствие contact_user_id.

### A4. P1: пакетные выборки SQLite несовместимы с позиционным mapper

`src/adapters/repositories/gateways/ticket_gateway.py:74–96,99–120` возвращают 15 колонок, с description перед urgency_level и повторами user_ticket_id/description. `src/adapters/repositories/mappers/ticket_mapper.py:13–27` ожидает 13 колонок в другом порядке. `utils/db/query.py:52–53` без проверки делает dict(zip(...)). Реальные потребители: `src/adapters/repositories/ticket_repository.py:150–206` — iter_by_client_id / iter_get_all.

Проверено синтетически через настоящий BaseRepository._get_many и SQLite :memory:. При description='description', urgency_level=0, version=7 результат содержит urgency_level='description', description=0, version=None. Следующий mapper на `ticket_mapper.py:75` вызовет ValueError для TicketUrgency('description'). Даже если описание случайно числовое, данные/версия отображаются неверно. Это не теоретическая ошибка форматирования SQL.

Исправление: переиспользовать SELECT_BASE с одним согласованным списком колонок; избегать позиционного zip либо проверять длину и имена. Проверить реальные итераторы с непустым описанием и ненулевой версией. Наличие вызовов этих итераторов из текущих HTTP-путей отдельно не подтверждено: дефект публичного API репозитория подтверждён, масштаб пользовательского воздействия требует проверки.

### A5. P2: get_finished(client_id) одновременно использует неверный фильтр и теряет bind-параметр

`src/adapters/repositories/gateways/ticket_gateway.py:69` строит SELECT_BY_FINISHED_CLIENT_ID из SELECT_BY_OPEN, поэтому выбирает date_finished IS NULL. `src/adapters/repositories/ticket_repository.py:265–273` при ненулевом client_id выбирает SQL с placeholder, но не передаёт params в _load_many_tickets. Вызов соответствующего SQL через настоящий BaseRepository на временной SQLite дал PersistenceError / Incorrect number of bindings supplied. После исправления bind останется логическая подмена закрытых заявок открытыми.

Исправление: основа SELECT_BY_FINISHED, передача client_id; проверить две заявки одного клиента — открытую и закрытую — и изоляцию от второго клиента. Текущий application-вызов на `src/application/services/ticket_service.py:1133` использует get_finished() без клиента; поэтому не утверждаю, что этот дефект уже затрагивает конкретный HTTP-список.

### A6. P2: исходная схема не разворачивается на пустой SQLite

`db/schema.sql:8`: CREATE TABLE sqlite_sequence(name,seq). Это зарезервированная внутренняя таблица SQLite; предыдущий AUTOINCREMENT уже создаёт её. Прямой `sqlite3.connect(':memory:').executescript(schema)` завершился OperationalError: object name reserved for internal use: sqlite_sequence. Для остальных синтетических SQL-проверок удалялась только эта строка из строки схемы в памяти; файл не изменялся.

Исправление: убрать внутреннюю таблицу из схемы, проверить полное создание новой базы официальной командой инициализации. Наличие отдельного альтернативного установочного пути не проверено; утверждение относится к поставляемому schema.sql.

### A7. P2: ошибки auth попадают в общий HTTP 500

`src/web/main.py:51–66` содержит закомментированную регистрацию TokenError/InvalidCredentialsError и прочих ожидаемых ошибок; активен только общий Exception → 500 на 73–76. Login/refresh на `src/web/routers/auth.py:71–88,106–123` исключения не преобразуют. Зависимости auth также пропускают TokenError вверх. Следствие: обычный отказ авторизации, неверные учётные данные или просроченный токен будут представлены как сбой сервера. Статическое подтверждение, auth-запросы не выполнялись.

Исправление: явные обработчики 401 с корректным WWW-Authenticate, 403 для недостаточных прав, 409 для конфликтов optimistic locking; сохранить общий 500 для неожиданных ошибок и не раскрывать внутренний текст исключения.

## Существенные риски и границы вывода

* Refresh storage находится только в памяти процесса (`storage.py:51–63`, `dependencies/auth.py:35–36`): перезапуск инвалидирует refresh, несколько workers не делят сессии. Это подтверждённое свойство реализации, production-влияние зависит от фактического запуска.
* Проверка refresh повторно ищет principal по username (`auth/services/services.py:235–244`, `auth_service.py:101–107,172–179`), но renew использует прежний subject_id (services.py:88–92). При переименовании/удалении и повторном использовании имени нужно исключить несовпадение идентичности. Сценарий не воспроизводился; конкретная достижимость зависит от правил удаления/изменения login.
* У UnitOfWork commit в __exit__ (`sqlite_unit_of_work.py:106–120`) при ошибке commit не вызывает rollback непосредственно, а лишь сбрасывает флаги. В веб-пути connection.close() в finally даёт дополнительную защиту (`dependencies/services.py:29–32`, `utils/db/connect.py:100–104`). Не считаю это доказанным самостоятельным дефектом атомарности HTTP-пути без инъекции commit failure и проверки жизненного цикла других потребителей.
* Проверки целостности клиента/контакта в доменных фабриках требуют более широкого аудита; отсутствие проверки в домене само по себе не доказывает обход авторизации при наличии application-проверок. Нельзя автоматически объявлять все методы сервисов доступными неавторизованному пользователю.
