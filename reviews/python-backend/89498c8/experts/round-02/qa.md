## Контакты и жизненный цикл заявок

- **Создание рассогласованной пары подтверждено.** Дополнительный HTTP-тест подтвердил существенное последствие в обоих отчётах. Пользователь создал заявку с контактом-коллегой и получил `201`. Немедленная отмена через `PATCH /user/tickets/{id}/cancel` вернула `500` с ошибкой несовпадения контактов. Оба статуса и версии остались прежними. Затем административный `/accept` успешно выровнял контакт и сохранил `accepted/in_work`. Автопринятие при административном создании с `TICKET_ACCEPTED` сразу сохранило одинаковые контакты. Поэтому сам факт рассогласования при создании подтверждает сбой отмены до принятия. Для сбоя подтверждения потребуется пара, оставшаяся рассогласованной уже в `READY_FOR_REVIEW`; обычный административный переход синхронизирует её раньше. Ссылки: `src/application/services/ticket_user_service.py:367–419`, `src/application/services/ticket_service.py:209–224,479–512`, `src/domain/services/ticket_sync_service.py:29–70,72–104,158–172`. Регрессия — создать пару с явным контактом, проверить обе записи, отменить ещё до принятия. Отдельно проверить административное создание с разрешением автопринятия и без него.
- **Пользовательский PATCH контакта подтверждён.** По штатному маршруту HTTP `200` сохранил прежний контакт в согласованной паре и поднял обе версии с `0` до `1`, как отмечено в Python-отчёте. Исправление загрузки DTO должно идти вместе со сменой направления обновления. Перед мутацией внутренней заявки следует проверить редактируемость пользовательского агрегата и не полагаться на проверку совпадения ID как побочный эффект синхронизации. Ссылки: `src/application/services/ticket_user_service.py:265–307,910–929`, `src/domain/services/ticket_user_service.py:107–136`, `src/domain/services/ticket_sync_service.py:59–70,137–142`. Регрессия — успешная смена и сброс, неизменное состояние при отклонённом запросе, отказ записи второй части пары с полным откатом.
- **Административный сброс контакта воспроизводится.** Для редактируемой отдельной заявки с контактом `PATCH /admin/tickets/{id}/contact-user` с ID 0 дошёл до домена и дал `500/DomainOperationError`. Схема принимает ноль, а отдельный агрегат допускает очистку. Для связанной заявки отдельно решить, должен ли этот же запрос выбирать владельца или возвращать предсказуемую ошибку. Ссылки: `src/web/models/tickets.py:100–103`, `src/application/services/ticket_service.py:323–369`, `src/domain/services/ticket_service.py:162–174`, `src/domain/ticket.py:465–482`. Регрессия — два теста нулевого значения с отдельной и связанной заявками.
- **Принадлежность клиента и отдела.** Статически подтверждены расхождения, указанные аналитиком. Активные фабрики проверяют индивидуальную активность сущностей, тогда как проверка принадлежности у пользовательского сервиса есть в отдельном невызываемом методе. Административное обновление контакта проверяет активность выбранного пользователя и не сверяет клиента. Разрешённость назначения контакта другой организации следует зафиксировать отдельно от ошибочной записи разных контактов. Доказательств передачи данных другой организации наружу нет. Удалённый старт имеет собственный permission и проверяет рекомендацию, состояние и текущего исполнителя из `ASSIGNED`; ветвь из `ACCEPTED` создаёт назначение без применяемой в обычном `assign` проверки принадлежности к отделу. Правила в репозитории прямо требуют общий инвариант назначения. ## Отключение, удаление и даты

- **Каскад Client и User.** Для клиента проверены реальные переходы в `AT_WORK` и `READY_FOR_REVIEW`. В обоих случаях `PATCH /admin/clients/{id}/disable` вернул 500, и клиент остался включён. У пользователя при согласованной паре `ready_for_review/waiting_for_confirmation` HTTP 500 оставил сотрудника включённым и обе записи прежними. Для клиента отдельно воспроизведён успешный перевод пары в `suspended/suspended` с закрытой внутренней и открытой пользовательской карточками. После включения клиента следующее отключение дало HTTP 500 на самопереходе `SUSPENDED → SUSPENDED` пользовательской карточки. Приоритет высокий ввиду невозможности выполнить штатное отключение. Выбор действий при `READY_FOR_REVIEW` должен соответствовать утверждённой политике. Код документирует продолжение для `AT_WORK`, самой смены графа недостаточно для согласования всей пары. Ссылки: `src/application/services/client_service.py:163–222`, `src/domain/services/client_service.py:52–80,198–254`, `src/application/services/user_service.py:462–499`, `src/domain/services/user_service.py:352–392,435–448`, `src/domain/statuses/rules/ticket_status_transition.py:76–119`, `src/domain/statuses/ticket_user_status_transitions.py:34–42,69–74`. Регрессия — рабочие состояния и смешанный набор заявок, повтор отключения после включения, проверка обеих историй после повторного чтения.
- **Дополнительный дефект в успешной ветви отключения User.** При согласованной новой паре `PATCH /admin/users/{id}/disable` вернул 200, пользователь был отключён, внутренняя заявка стала `suspended`, пользовательская сохранила `created` и прежнюю версию. Доменный `UserService.disable` меняет пользовательскую заявку через синхронизацию, но сразу возвращает пустой `changed_ticket_users`; приложение сохраняет только элементы этого результата. Это отдельный дефект от запрещённого перехода в предыдущем пункте. Ссылки: `src/domain/services/user_service.py:373–398`, `src/application/services/user_service.py:480–499`. Исправление — включать действительно изменённую пользовательскую заявку в результат. Регрессия — успешное отключение пользователя с открытой согласованной парой, проверка `suspended/suspended`, обеих новых записей истории и отката при отказе записи второй части.
- **DELETE различается по наличию связи.** Для созданной через HTTP самостоятельной заявки с правом `TICKET_CANCELLED` удаление дало 500 с `AttributeError`, а строка и история сохранились. Для связанной заявки тот же маршрут дал 204 и обе строки были удалены. Физическое удаление и выбор разрешений остаются отдельными вопросами контракта. Регрессия — обе ветви и отсутствие частичного удаления при искусственном отказе второго репозитория.
- **Ретроспективные даты и финализация.** В обычном HTTP-потоке для `ASSIGNED` вызов `/complete-work-retroactively` с интервалом, записанным в `+03:00`, дал 500 и не добавил историю; тот же момент в `Z` дал 200 и новые `at_work, ready_for_review`. ## Транзакции, SQLite и списки

- **Коммит перед построением ответа.** Подтвердил на границе HTTP с инъекцией сбоя в `TicketAssembler.to_dto`: корректное административное создание вернуло 500, отдельное соединение обнаружило новую строку. Конкретный естественный вход, нарушающий сборку DTO, не установлен. В пользовательском POST DTO собирается внутри контекста до автоматического коммита; другие пользовательские записи используют два помощника с обратным порядком. Перенос сборки DTO до коммита закрывает эту инъекцию, однако HTTP-модель и сериализация происходят позже, и повтор при потере ответа требует самостоятельного решения. Ссылки: `src/application/services/ticket_service.py:1176–1202`, `src/application/services/ticket_user_service.py:200–206,893–929`, `src/web/routers/admin/tickets.py:86–93`, `src/adapters/uow/sqlite_unit_of_work.py:106–120`. Регрессии — инъекция отказа до коммита и независимый тест повторной подачи при потере ответа.
- **Конкуренция и ошибка автоматического COMMIT.** Согласен с двумя механизмами из Python-отчёта. После ошибки `commit()` в `__exit__` состояние флагов UoW расходится с состоянием соединения; при явном `commit()` внутри `with` обычный путь проходит через ветвь отката. Обычные запросы получают новый UoW и закрывают соединение, поэтому повторная фиксация старой записи через другой HTTP-запрос не установлена. Нагрузочный отказ HTTP и повторное использование UoW в Python — отдельные последствия. Ссылки: `src/adapters/uow/sqlite_unit_of_work.py:76–151`, `utils/db/connect.py:46–109`, `src/web/dependencies/services.py:22–32`. Регрессия — два соединения с детерминированной блокировкой, отдельно обычный HTTP-контракт для busy и автоматический COMMIT с последующим reuse того же объекта; проверить состояние SQL и независимый снимок базы.
- **Схема, старые строки и пакетное чтение.** Провал DDL из-за `sqlite_sequence` независимо подтверждён в первом QA-раунде. NULL в duration воспроизводим на допустимой по DDL строке, которую текущий штатный писатель обычно не создаёт. Для NULL-версии нулевой fallback маппера действительно расходится с SQL-предикатом равенства. Дефект пакетного чтения доказан на адаптере; поиск вызовов штатных прикладных сервисов показал только объявления, а HTTP `/admin/tickets/closed` вызывает `get_finished()` без ID клиента. Поэтому не заявляю поражение списка через пакетную ветвь. Ссылки: `db/schema.sql:1–9,111–166`, `src/adapters/repositories/mappers/ticket_mapper.py:64–79,100–124`, `src/adapters/repositories/gateways/ticket_gateway.py:58–120,162–176`, `src/application/services/ticket_service.py:1106–1134`. До миграции проверить распространённость NULL и исторические значения полей на разрешённой копии, а регрессии строить на синтетическом старом формате.
- **Чтение всех клиентских заявок.** Согласен с установленной стоимостью в коде: один запрос корней и две дочерние выборки на каждый корень до фильтрации. Замера задержки нет. Ошибка гидратации чужой строки может прервать легитимный запрос текущего клиента до фильтра, что можно проверить синтетической повреждённой историей. В ответе обычные фильтры всё ещё ограничивают владельца и клиента. Ссылки: `src/application/services/ticket_user_service.py:465–658`, `src/adapters/repositories/ticket_user_repository.py:50–102,161–171`, `src/adapters/repositories/gateways/ticket_user_gateway.py:25–37`. Регрессия — измерить число SQL-запросов при росте объёма только у второй организации, отдельно проверяя состав ответа и фильтр закрытых записей.
