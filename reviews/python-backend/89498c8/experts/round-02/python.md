### Переключение состояния учётной записи пользователя — QA-01

**Согласен. Дефект с высокой достоверностью, отсутствовавший в моём первом отчёте.** В обоих методах контекст завершается сразу после чтения. Последующий `save` меняет сотрудника, связи ролей и аккаунт вне UoW. Встроенный драйвер SQLite начинает свою транзакцию по первому UPDATE, но обёртка помечает её неактивной. Закрытие соединения отменяет незафиксированные изменения. Через новое временное соединение подтвердил единство симптомов: сервис вернул `enabled_login=False`, его собственное соединение видело `(accounts.enabled, employees.version) = (0, 1)`, внешнее соединение до и после закрытия читало `(1, 0)`. Сходные методы администратора держат мутацию в области UoW.

**Решение и регрессия.** Перенести обе записи в существующий контекст и проверять оба перехода через новое соединение. Проверять одновременно флаг аккаунта, увеличение версии ровно один раз и откат обеих записей при сбое. Отдельная проверка закрытия соединения закрепит границу транзакции.

**Согласен с двумя самостоятельными ошибками.** У POST различаются значения на записи, у PATCH выполняется запись без применения входного ID. **Дополнительное расхождение контракта.** В административной смене контакта ID 0 допускается внешней схемой, но домен отвергает пустого пользователя и для отдельной внутренней заявки. Проверять эти ветви по отдельности, а для пользовательского PATCH проверять ещё отсутствие изменения версий при отклонённой команде.

### Каскад отключения и повтор — аналитик 3

**Согласен, включая повтор команды.** Первый Python-раунд подтвердил отказ клиента при `AT_WORK` и отдельно пользователя при `READY_FOR_REVIEW`. Аналитик прав, что расхождение признаков закрытости становится наблюдаемым дефектом повторной команды, даже если сами признаки отражают принятый продуктовый контракт. На синтетической согласованной паре первый вызов отключил клиента, закрыл внутренний Ticket и оставил внешний TicketUser открытым в `SUSPENDED`. Немедленный повтор и повтор после включения клиента дали `DomainOperationError` на переходе `SUSPENDED → SUSPENDED`. Во второй ветви клиент остался включённым. Случай `READY_FOR_REVIEW` должен отдельно пройти через доменный граф и обычный каскад отключения обоих типов.

**Решение и регрессия.** Выбор заявок для приостановки следует связать с решением по паре. Для повторного отключения демонстрационная последовательность уже различает неидемпотентность команды и вопрос о восстановлении открытых работ. Зафиксировать требование к повтору явно, поскольку граф сам по себе не определяет, должен ли повтор вернуть прежний успешный результат. Для `AT_WORK` есть документированное правило сохранения работы, для `READY_FOR_REVIEW` требуется решение о дальнейшей проверке и о её исполнителях при отключённом заявителе.

Код — `src/application/services/client_service.py:114–143,163–222`, `src/domain/services/client_service.py:52–80,198–254`, `src/domain/services/user_service.py:352–397,435–448`, `src/domain/statuses/rules/ticket_status_transition.py:76–96,113–147`, `src/domain/statuses/ticket_user_status_transitions.py:34–42,69–75`, `src/adapters/repositories/gateways/ticket_user_gateway.py:31–32`.

### Обработка ошибок, срочность и согласование UTC — аналитик 6–7, QA-04–05

**Согласен с ошибками HTTP, разделяю две причины.** QA динамически подтвердил 500 для неверных учётных данных, отсутствующих ресурсов и невалидного ID. Общий обработчик действительно отправляет `str(exc)` и имя класса. Для части путей ожидаемая ошибка уже теряет исходный тип раньше HTTP, например голый `except` вокруг `users.save` превращает `OptimisticLockError` в `ApplicationValidateError`. Одной регистрации нового обработчика 409 недостаточно для этих сервисов. Наличие Pydantic-валидации и стандартного 401 без Bearer изолирует ошибку в прикладных исключениях, а не в общей работе FastAPI. Настройку невалидного пароля и Bearer следует различать как два пути формирования ответа.

**Время и enum.** Неизвестная срочность на административном POST достижима, поскольку входная модель принимает произвольную строку, а значение превращается в enum внутри UoW. Общая обработка HTTP исправит код ответа, но не явность схемы запроса. Пропуск нормализации в расписании подтверждён повторно с Pydantic-моделью и реальным прикладным сервисом. Отдельно проверил ретроспективный путь. Модель приняла интервал с `+03:00`, сервис вернул `ItemValidationError`, последним сохранённым статусом остался `assigned`. Те же моменты в UTC затем успешно зарегистрировали переход в `ready_for_review`. Утверждение об отклонении нормального смещения зависит от календарного ограничения только для планирования. Интервал ретроспективной записи должен завершиться до момента её регистрации.

**Различающие проверки.** На HTTP зафиксировать отдельно неверные данные, отсутствующий ресурс, штатный конфликт версии, неожиданное исключение и классификацию блокировки SQLite. На временной SQLite сравнить сохранённые даты после двух представлений одного момента, включая переход календарного дня вокруг полуночи UTC. Для неизвестной срочности и неправильной даты проверять отсутствие любых новых строк и изменения версий ссылочных объектов.

### Схема, запуск и актуальность тестов — QA-06

**Согласен с отказами конкретных точек входа.** Сбой буквального DDL воспроизводится независимо от команд тестов. Корневой `main.py` вызывает pytest при импорте и не возвращает его код. Встроенная ветка Uvicorn указывает именно на этот модуль. Попытка запуска полноимённого ASGI-импорта, проверенная QA, подтверждает достижимость приложения отдельным путём. Сочетание `reload=True` с `workers=4` не подтверждает, что встроенная команда реально использует четыре процесса. Дерево Git подтверждает отсутствие директорий, на которые указывают обычные команды. Архивные сценарии QA показывают ценность намерений, но их результат нельзя считать текущей зелёной проверкой.

**Регрессия.** Зафиксировать один способ старта ASGI и один тест CI с кодом возврата для пустого сбора. Проверять полноценную временную SQLite от буквальной схемы, импорт, health и прикладные запросы. Для восстановления отдельно определить, используется ли `schema.sql` как операторская точка восстановления и какая миграция отвечает за исторические NULL.

## Статическая проверка границ авторизации

- **QA-07. Подтверждаю отзыв по непроверенному имени и общность storage.** Реализация строит два экземпляра одного singleton, а выборка при отзыве учитывает только логин. У отзыва по токену нет той проверки типа субъекта, которая есть у обновления. Важно ограничить формулировку о совпадении идентификаторов между типами. Текущий DDL даёт глобальный уникальный индекс на `accounts.login`, поэтому одновременное наличие двух текущих аккаунтов с одинаковым логином невозможно в БД этой схемы. Для сквозного эффекта через обе роли нужна дополнительная предпосылка, например сохранённые сессии после переиспользования имени. Эффект простого отзыва чужих refresh-сессий не зависит от этой предпосылки. Защитные регрессии должны закрепить проверенный контекст для общего отзыва и разделение субъектов по типу и стабильному ID. `src/web/routers/auth.py:92–102,126–133`, `src/web/dependencies/auth.py:35–36,95–117`, `src/web/auth/services/services.py:223–272`, `src/web/auth/storage.py:65–85,153–170`, `db/schema.sql:180–181`.
- **QA-08. Подтверждаю различие между входом, обновлением и использованием access-токена.** Для защищённых операций RBAC обычно перепроверяется по актуальным ролям, но загрузка актора проверяет флаг сотрудника и пропускает флаг аккаунта. QA-01 объясняет независимый отказ сохранять пользовательский флаг. Исправление QA-01 само по себе не изменит защиту операций после успешного отключения или отвязки. Эндпоинты перечисления статических разрешений используют проверку типа токена и выдают константы enum, поэтому это отдельный узкий пример проверки principal, а не расширение полномочий. Для исправления нужна централизованная проверка статуса либо политика с явно принятым остаточным сроком ранее выданного токена. `src/web/dependencies/auth.py:129–162`, `src/application/helper/actor_helper.py:239–277`, `src/domain/employee.py:148–160`, `src/domain/policies/admin.py:9–20`, `src/domain/policies/user.py:9–23`, `src/web/routers/admin/roles.py:24–28,57–74`.
- **QA-09. Согласен по двум независимым рискам конфигурации и хранения паролей.** Встроенное значение ключа действует при отсутствии внешней настройки. Какой источник реально используется в развёртывании, не устанавливал. Для паролей применён быстрый хеш без соли, что следует как из функции, так и из пути создания `Password`. Размер риска зависит от доступа к копии БД. Случайные opaque refresh-токены имеют иной способ генерации, поэтому их хранение хешем не нужно смешивать с рекомендацией для низкоэнтропийных паролей. Регрессии должны покрывать обязательность внешнего ключа и совместимость безопасной миграции паролей. `src/web/config.py:8–23`, `src/domain/value_objects.py:342–368,438–465`, `src/web/auth/storage.py:87–103`.
- **QA-10. Согласен с потерей refresh-сессий при перезапуске и несогласованностью между процессами.** Хранилище — дикт в памяти одного процесса. Очистка определена, но активного вызова в `src` нет. Ротация последовательно валидирует, удаляет и создаёт токен, поэтому отказ после удаления может оборвать сессию. При гонке второе удаление отсутствующего ключа бросает ошибку. Из этого кода не следует, что два конкурентных обновления обязательно оба выдадут новый токен. Дополнительно refresh проверяет существование по имени, но использует прежний ID при выпуске. Привязка к стабильному субъекту и атомарная ротация устранят зависимость от сменяемого имени и промежуточного отказа. `src/web/auth/services/services.py:42–93,223–248`, `src/web/auth/storage.py:79–83,110–140`, `src/web/auth/services/auth_service.py:92–107,163–179`.
- **Принадлежность клиента и контакта, замечание аналитика.** Статически согласен, что активные фабрики и административное изменение контакта проверяют доступность объектов, а индивидуальные внешние ключи не выражают их принадлежность одному клиенту. Основные пользовательские списки проверяют клиента перед выдачей, поэтому из этой находки нельзя вывести раскрытие данных. Важно валидировать принадлежность и владельца, и контакта общим правилом в каждом пути записи. Пользовательский PATCH в текущем виде игнорирует значение, поэтому его вклад в проблему проявится, если исправить загрузку и направление без валидации принадлежности. `src/application/services/ticket_user_service.py:141–195,745–844`, `src/application/services/ticket_service.py:133–187,323–363`, `src/domain/services/ticket_service.py:162–174,389–397`, `db/schema.sql:111–151`.
