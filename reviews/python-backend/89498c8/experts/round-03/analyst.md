# Раунд 3. Пересмотр выводов системного аналитика

Снимок `main` `89498c8318d587f197b0ae584d95899d5939c8d8`. Прочитал все три отчёта второго раунда и сверил их с первичными выводами. Оценки ниже опираются на наблюдения QA на штатном ASGI с синтетической SQLite, прикладные проверки Python-ревью и мою доменную и прикладную синтетику из первых двух раундов. Авторизационные выводы имеют статическое основание.

## Пересмотр семи первичных находок

| Первичная находка | Решение и граница доказательства | Следующая проверка или решение |
| --- | --- | --- |
| **1. Разные контакты сразу после создания пары** | **Сохраняю высокий приоритет.** Достижимость подтверждена через оба POST для активного контакта-коллеги, у администратора без автопринятия. Ранняя пользовательская отмена дала HTTP 500 и оставила оба статуса и версии прежними. QA и Python-ревью расширили доказательство положительной ветвью. Обычное `/accept` и автопринятие выравнивают контакт, пока TicketUser редактируем. Возможный сбой подтверждения требует отдельного рассогласования уже на стадии проверки. | Проверить оба POST с владельцем и явным контактом, ветви с автопринятием и без него, затем оба сохранённых значения и раннюю отмену. При исправлении старых пар сначала утвердить авторитетное значение. |
| **2. Пользовательское изменение контакта игнорирует ID** | **Сохраняю высокий приоритет.** QA подтвердил HTTP 200 и рост обеих версий при прежнем контакте в согласованной паре. Для ранее рассогласованной пары PATCH способен выбрать сохранённый контакт Ticket независимо от входа. Установлено дополнительное расхождение. Административный `0` проходит схему, но для отдельного Ticket операция отклоняется, хотя агрегат допускает очистку. | В общей команде разрешить новое значение до мутации, проверить редактируемость и принадлежность, изменить Ticket как источник проекции. Проверить смену, сброс, отказ при запрещённом статусе и атомарность. Для связанного административного PATCH утвердить значение `0`. |
| **3. Client с активной или проверяемой заявкой не отключается** | **Сохраняю высокий приоритет и расширяю.** QA воспроизвёл оба состояния клиента и `READY_FOR_REVIEW` пользователя. `UserService` явно пропускает `AT_WORK`, у Client эта политика пока только в docstring. На синтетической SQLite независимо подтверждена отдельная успешная ветвь User: после отключения внутренний Ticket становится `SUSPENDED`, а TicketUser остаётся `CREATED`, поскольку домен пропустил его в результате для сохранения. Дополнительно и QA, и прикладные проверки подтвердили срыв отключения Client после включения из-за уже приостановленного TicketUser. | Сначала закрепить продолжение работы в `AT_WORK` либо утвердить изменение действующей политики. Для `READY_FOR_REVIEW` решить, кто продолжает проверку после отключения. По одному решению на связанную пару проверить смешанные состояния, обе истории, атомарный откат и последовательность `disable → enable → disable`. Поведение немедленного повтора требует собственного контракта. |
| **4. Удалённое самоназначение пропускает проверку отдела** | **Сохраняю подтверждённое нарушение целостности по статике.** При `ACCEPTED` и `TICKET_AT_WORK_REMOTE` путь добавляет реальную запись `ASSIGNED`, обходя валидацию, которой подчинён обычный `assign`. QA и Python-ревью подтвердили цепочку. Отдельное разрешение задаёт допуск к команде. Инвариант совпадения отделов описан общим правилом в `Department` и в `rules.md`. Для пересмотра нужна утверждённая бизнес-политика исключения, которой в доступных правилах нет. Высокую предметную серьёзность обосновывает активное недопустимое назначение, частота и конфигурация прав неизвестны. | Закрепить общую проверку в ветви, создающей назначение. Положительный тест должен сохранить атомарность `ASSIGNED → AT_WORK`. Защитная регрессия после исправления должна утверждать отказ с сохранением истории при отсутствующем или другом отделе. Ветвь из `ASSIGNED` сохраняет правило текущего исполнителя. |
| **5. Физическое удаление отдельной заявки** | **Сохраняю средний приоритет для точечного дефекта.** QA повысил доказательность до HTTP и повторного чтения. Самостоятельный Ticket при 500 остаётся с историей. У связанной заявки наблюдался 204 и удаление обеих строк. | Условно удалять связанную сущность. Проверить два положительных сценария и откат при отказе второй операции. Отдельно утвердить допустимые статусы и разрешение на физическое удаление. |
| **6. Ожидаемые ошибки возвращаются как 500** | **Сохраняю предметный вывод и принимаю высокий приоритет общего дефекта.** QA установил аналогичный эффект для входа, отсутствующей заявки и отрицательного ID. Стандартный отказ без Bearer и Pydantic-валидация используют собственные ответы. Корректировка требует также сохранить тип ошибки на прикладной границе. Например, `users.save` может потерять `OptimisticLockError` внутри общего `except`. | Проверить отдельно неверный пароль, отсутствие или недействительность токена, RBAC, отсутствие ресурса, отклонённый переход, конфликт версии и SQLite busy. Для неожиданного сбоя зафиксировать безопасный ответ без внутреннего текста. |
| **7. Нет нормализации часового смещения при планировании и ретроспективной работе** | **Сохраняю средний приоритет, уточняю формулировку.** Смещение проходит входную модель и передаётся без нормализации. QA подтвердил HTTP 500 для `+03:00` и 200 для тех же моментов в UTC, с появлением двух записей истории лишь при успехе. Python-ревью подтвердило прикладной результат. Неизвестная срочность административного создания — другой дефект входной модели с тем же симптомом 500. | Переиспользовать нормализацию aware-datetime при создании, планировании и ретроспективном вводе. Проверить одну и ту же дату в разных представлениях, календарную границу UTC для планирования, положительный интервал до момента регистрации, отказ для naive datetime и неизвестной срочности. |

## Решения по дополнительным замечаниям

- **Состояние аккаунта пользователя.** Принимаю QA-01 как самостоятельную высокую находку. Оба перехода сохраняются вне UoW, и HTTP 200 не отражает изменение в БД. QA доказал оба направления. Python-ревью показало, что собственное соединение временно видит обновление версии и аккаунта, а новое соединение видит старые значения. После правки проверять на новом соединении флаг и ровно одно увеличение версии. Политика отзыва access-токена остаётся второй задачей после реального сохранения отключения. `src/application/services/user_service.py:242–282,624–636`, `src/adapters/repositories/user_repository.py:130–153`, `src/web/dependencies/services.py:22–32`.
- **Принадлежность Client.** Поднимаю пробел из гипотезы до статически подтверждённой ошибки валидации: активные фабрики и административный PATCH подтверждают доступность кандидата, а правило принадлежности находится в невызываемом методе. Внешние ключи проверяют отдельные ID. Масштаб текущих данных и влияние на доступ остаются неизвестны. В пользовательском PATCH переданный ID сейчас вообще не применяется. Исправление этой команды должно сразу использовать тот же инвариант, что и действующие записи, с отдельной проверкой владельца и контакта. Если межклиентский контакт нужен, потребуется явная политика, которая определит последствия для карточек и каскадов. `src/application/services/ticket_user_service.py:141–195,265–307,745–844`, `src/application/services/ticket_service.py:133–187,323–363`, `src/domain/services/ticket_service.py:162–174,389–397`, `db/schema.sql:111–151`.
- **Завершение и комментарии.** Принимаю подтверждение QA, что `finish-work` с `TICKET_EXECUTED` сохраняет `READY_FOR_REVIEW`, а отдельный `/execute` выполняется дальше. Считаю это расхождением docstring и реализации, требующим выбора продукта. Отдельные вопросы — публичность комментария ретроспективной работы, форма `{value: ...}` в административном JSON и строка у пользователя, отображение `SUSPENDED` как открытого статуса и восстановление после включения. Исправление каскадных ошибок не требует объявлять внешнюю приостановку закрытием. Существующие ограничения смены отдела при активном назначении последовательно действуют в коде. Формулировка `AT_WORK` в рабочих заметках не устанавливает требование ослабить ограничения остальных состояний. `src/application/services/ticket_service.py:787–834,891–926`, `src/application/assemblers/assembler.py:44–70,111–140`, `src/domain/ticket.py:668–693`, `src/domain/statuses/rules/ticket_state_rule.py:24–73`, `rules.md:35–51`.
- **Стоимость списков.** Принимаю `1 + 2N` как установленную форму чтения до фильтрации. Замер задержки остаётся открытым. Следующий измеримый тест — вырастить данные второго клиента при неизменных данных первого, считая SQL и проверяя состав результата. При оптимизации заранее исправить клиентские предикаты закрытых заявок и привязку `client_id` в репозитории Ticket. Ошибки пакетного чтения и nullable-данных оставляю в группе адаптеров и исторических данных. `src/application/services/ticket_user_service.py:465–658`, `src/adapters/repositories/ticket_user_repository.py:50–102,161–171,230–238`, `src/adapters/repositories/ticket_repository.py:265–273`, `src/adapters/repositories/gateways/ticket_gateway.py:58–69`.
- **Транзакции, DDL и эксплуатация.** Принимаю разграничение коллег. Инъекция отказа DTO доказывает запись при ошибке HTTP, обычный вход для этого эффекта не установлен. Ошибка автоматического COMMIT подтверждает риск повторного использования UoW, а HTTP закрывает штатное соединение. Конкурирующий `BUSY` отделён от конфликта версии. Буквальная инициализация DDL и два скриптовых способа запуска требуют своих smoke-проверок. Предположение о единственной связи Ticket–TicketUser следует из обычного workflow, а дубликат через штатное создание не показан. `src/adapters/uow/sqlite_unit_of_work.py:76–151`, `src/web/dependencies/services.py:22–32`, `src/application/services/ticket_service.py:1176–1202`, `db/schema.sql:1–9,124–155`, `src/web/main.py:80–96`, `main.py:1–5`.
- **Границы авторизации.** Принимаю уточнение Python-ревью к QA-07 и к собственной формулировке. Индекс `accounts.login` глобально уникален в текущем DDL, поэтому сценарий двух одновременно существующих аккаунтов с равным логином не служит доказательством межролевого эффекта. В общем процессном хранилище потребовались бы дополнительные условия, такие как сохранившаяся сессия после переиспользования имени. Необходимость привязать отзыв refresh к удостоверенному субъекту остаётся. Для QA-08 подтверждено статическое расхождение проверок аккаунта между login/refresh и access, со сроком действия выданного access. Встроенное значение подписи, политика хеширования пароля и процессный storage остаются отдельными статическими выводами. Реальные настройки и количество workers требуют данных развёртывания. `db/schema.sql:180–181`, `src/web/routers/auth.py:92–102,126–133`, `src/web/auth/storage.py:65–85,153–170`, `src/web/auth/services/services.py:209–272`, `src/web/dependencies/auth.py:129–162`, `src/application/helper/actor_helper.py:239–277`.
