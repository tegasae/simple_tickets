## Уточнения по рабочим маршрутам и дополнительные дефекты

- **Каскады отключения.** В итоговый приоритет включаю три самостоятельных сбоя. Client с `AT_WORK` или `READY_FOR_REVIEW` и User с `READY_FOR_REVIEW` остаются включёнными после 500. При нормальном `CREATED` отключение User даёт 200, но внешняя история теряет `SUSPENDED`, потому что синхронизированная запись не добавляется в `changed_ticket_users`. Успешно отключённый Client с внешним `SUSPENDED` после включения не может отключиться снова из-за попытки самоперехода. Утверждённая судьба работы в `READY_FOR_REVIEW` и открытость внешнего `SUSPENDED` нужны для изменения графа. Потеря сохранения и повторное отключение уже доказаны независимо от этих решений. `src/domain/services/user_service.py:352–398,435–448`, `src/application/services/user_service.py:480–499`, `src/domain/services/client_service.py:52–80,198–254`, `src/domain/statuses/ticket_user_status_transitions.py:34–42,69–74`.
- **DELETE.** Сохраняю доказанный дефект отдельной заявки: 500 с `AttributeError`, строка и история остались. В той же проверке связанная заявка удаляется с 204 и исчезают обе строки. Политика права и допустимых состояний для физического удаления остаётся отдельным продуктовым вопросом. Добавить позитивные проверки двух ветвей и отказ записи второго удаления. `src/application/services/ticket_service.py:964–981,1153–1170`, `src/adapters/repositories/ticket_user_repository.py:324–352`.
- **Инварианты отдела и клиента.** С аналитиком согласен по механизму. Самоназначение из `ACCEPTED` не применяет обычное правило соответствия отдела, а ветвь `ASSIGNED` проверяет текущего исполнителя. Формулирую как расхождение ограничения целостности, для приоритета и фиксации нужно подтвердить, есть ли утверждённое специальное исключение для удалённой работы. Правила репозитория такого исключения не устанавливают. По клиенту статическая цепочка показывает проверку индивидуальной доступности вместо принадлежности во всех активных фабриках и в административной смене контакта. Из этого нельзя вывести выдачу данных другой организации. Защитные тесты принадлежности нужны и для исправленного пользовательского PATCH. `rules.md:45–64`, `src/application/services/ticket_service.py:133–187,323–363,580–629,693–718`, `src/application/services/ticket_user_service.py:141–196,803–844`, `src/domain/services/ticket_service.py:162–174,236–264,349–361,389–397`.

Вложенный административный комментарий передаётся как объект, пользовательский как строка; оба поля схематически открыты, вызывающий клиент не проверен. `finish-work` оставляет заявку в `READY_FOR_REVIEW` даже с `TICKET_EXECUTED`, штатный отдельный `execute` работает.
