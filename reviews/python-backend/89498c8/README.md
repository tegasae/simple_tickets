## Находки по приоритету

### P1. Конфигурация допускает встроенный ключ подписи JWT

При отсутствии внешнего значения приложение запускается с ключом из исходника, который используется для выпуска и проверки JWT. Если развёртывание пользуется этим значением, доверие к подписанным токенам нарушается. Код подтверждает значение по умолчанию. Тест конфигурации на исходном снимке показал, что отсутствие внешнего ключа допустимо.

Патч требует новый внешний ключ и исключает принятие старого значения. Строка с прежним значением остаётся в исходном файле, чтобы unified diff не содержал ключ. Для внедрения нужен новый секрет в конфигурации среды, ротация действующих ключей и отдельное удаление прежнего литерала из исходника. Проверки `test_signing_config_has_no_implicit_key` и `test_typical_signing_configuration_loads_explicit_key`. [Настройки](https://github.com/tegasae/simple_tickets_copy/blob/89498c8318d587f197b0ae584d95899d5939c8d8/src/web/config.py#L8-L23) · [Подпись и проверка](https://github.com/tegasae/simple_tickets_copy/blob/89498c8318d587f197b0ae584d95899d5939c8d8/src/web/auth/tokens.py#L109-L134) · [Патч 07](patches/07-require-jwt-signing-key.patch)

### P1. Отзыв сессий по имени не привязан к аутентифицированному субъекту

Оба logout-маршрута передают запрос менеджеру без проверки личности. Ветка отзыва всех refresh-сессий использует имя из запроса. Хранилище выбирает записи по имени, а обе зависимости получают один объект из-за singleton. Подтверждено по цепочке вызовов. Последствие касается возможности обновлять сессии. Глобальный уникальный индекс на логин ограничивает одновременное совпадение имён среди записей, но совпадение имён в сессиях после переиспользования логина отдельно не установлено.

Патч сохраняет завершение одной сессии предъявлением её refresh-токена с проверкой типа субъекта, а для завершения всех сессий требует действующий Bearer и фильтрует по ID и типу субъекта. Проверены штатный logout обоими способами и применимость diff. Обход на исходном приложении не разыгрывался. ### P1. Создание и изменение контакта расходятся между карточками одной заявки

### P1. Отключение клиента или пользователя нарушает жизненный цикл заявок

Отключение клиента пытается перевести каждую открытую внутреннюю заявку в `SUSPENDED`. Граф запрещает этот переход из `AT_WORK` и `READY_FOR_REVIEW`, поэтому откатывается всё отключение. Повтор также может сорваться на пользовательской заявке в `SUSPENDED`, которая осталась открытой. Отключение пользователя пытается приостановить заявку на проверке и при допустимом переходе забывает передать изменённую пользовательскую карточку на сохранение.

Патч использует действующие таблицы переходов, сохраняет обе карточки и оставляет активную работу и проверку в текущих состояниях. Это выбранное поведение до решения о допустимости новых переходов. Регрессии проверяют активную работу, проверку, приостановку пары, непосредственный повтор и отключение после включения. ### P1. Обычный комментарий пользовательской заявки ломает запись и повторное чтение

### P1. Ожидаемые ошибки возвращают 500, а неожиданные раскрывают детали

Фабрика регистрирует общий `Exception`, который возвращает строку исключения и тип. На исходнике отсутствующая заявка дала 500, QA также подтвердил 500 для неверных синтетических учётных данных. Общий обработчик способен вернуть внутреннюю причину отказа SQLite. Патч добавляет обработчики известных предметных, авторизационных и версионных ошибок с кодами 4xx, а общий 500 возвращает стабильное сообщение. Сохранение Admin и User передаёт исходные ошибки вместо преобразования любого исключения в ApplicationValidateError. Проверки покрывают 400 для отрицательного ID, 404 для отсутствующей заявки, 401 для недействительной собственной сессии, 409 при инъекции конфликта версии и общий 500 при искусственном сбое. Значения 400 для предметных ошибок и 409 для конфликта версии выбраны согласно семантике команд, контракт кодов для всех потребителей нужно утвердить. ### P2. Защищённые маршруты не учитывают актуальное состояние аккаунта

Зависимости API проверяют подпись и тип JWT. Основные сервисы затем проверяют активность сотрудника и права, а два маршрута метаданных разрешений ограничиваются зависимостью. Активный сотрудник с отдельно отключённым или отвязанным аккаунтом может сохранять доступ до истечения уже выданного JWT. Логин и refresh проверяют состояние аккаунта, а для пользователя также состояние клиента. Это подтверждено по коду при условии, что изменение состояния сохранено. 

Патч повторно применяет политики актуальности аккаунта в используемых зависимостях API. Проверены штатный вход и чтение своих заявок с Bearer. Поведение старых JWT при отзыве доступа оценено статически. ### P2. Сбой коммита оставляет транзакцию, а сборка DTO после коммита маскирует успешную запись

При блокировке на автоматическом COMMIT UoW сбрасывает внутренние флаги, оставляя SQL-транзакцию активной. HTTP-зависимость закрывает соединение и обычно откатывает её. При повторном использовании экземпляра UoW следующая операция может зафиксировать запись из предыдущего неуспешного контекста. Тест с двумя соединениями проверяет откат и повторный вход. Вторая регрессия проверяет, что другой UoW на том же соединении не присваивает себе уже начатую транзакцию. Отдельная ошибка в сервисах заявок возникает, когда DTO собирается после явного коммита. Инъекция сбоя сборщика воспроизводит HTTP 500 с уже сохранённой заявкой или переходом. Патч перемещает сборку DTO перед коммитом. Сериализация HTTP и доставка ответа остаются за границей транзакции.

Конкурирующие обновления также способны получить `SQLITE_BUSY` до сравнения версий. Это подтверждено отдельным опытом Python-эксперта. Патч отката исправляет жизненный цикл соединения. Для классификации `BUSY` и политики повторов нужен отдельный контракт с повтором полной команды на свежем снимке. for variant in base patched; do
  (cd "$scratch/$variant" &&
   PYTHONPATH=. PYTHONDONTWRITEBYTECODE=1 "$scratch/venv/bin/python" \
     -m pytest -o addopts='' -p no:cacheprovider -q --tb=short review_tests)
