# Реализация и проверка слоя хранения

## Патч 10 — отсутствие режима работы

SQL хранит nullable `ticket_status_records.work_is_remote`. Mapper записи передаёт `record.work_is_remote` напрямую. Новый статус без режима получает SQL `NULL`, а административный ответ команды содержит JSON `null`. Раньше повторный GET превращал это значение в `false` при чтении mapper. Доменный контракт выделяет обязательный булев режим рабочего эпизода. SQLite-код полагался на прежнее преобразование `NULL → false` для старых рабочих записей, которые остаются допустимыми по DDL. `db/schema.sql:164` · `src/adapters/repositories/mappers/ticket_mapper.py:103`, `:185` · `src/domain/statuses/rules/ticket_status_rule.py:42`, `:93` · `src/domain/statuses/ticket_status_record.py:128` · `src/application/assemblers/assembler.py:44`.

Патч читает статус до преобразования поля. Реально записанные ноль и единица преобразуются в соответствующие булевы значения. Для SQL `NULL` lookup `TICKET_STATUS_RULES[status].requires_work_mode` сохраняет исторический fallback `False` у `AT_WORK`. У прочих статусов с отсутствующим значением результат остаётся `None`. Правка действует в маппере чтения. API возвращает `null`, когда у статуса без режима поле в SQLite имеет значение `NULL`. [Патч 10](../patches/10-preserve-work-mode-null.patch)

В независимой копии оригинала на Python 3.12.14 и SQLite 3.53.1 два параметризованных случая завершились на первом GET, который показал `false` для `CREATED/ACCEPTED`. Чтение синтетической legacy-строки прошло и до изменения. После применения 10 все три случая прошли на исходнике и на 05+06. Тесты создают заявку через HTTP, читают её после создания и старта работы с каждым булевым значением, затем сверяют SQL. Отдельная фикстура задаёт SQL `NULL` в записи `AT_WORK` у заявки, дошедшей до `READY_FOR_REVIEW`, и проверяет сохранение `false` в истории. [Тест режима работы](../tests/test_ticket_work_mode_roundtrip.py)

## Покрытие границ UoW

Два самостоятельных теста проверяют сбой фиксации из-за SQLite-читателя и назначение полного окна старому результату при последующем успешном создании другим ключом. Трасса собирает только маркеры `COMMIT` и `ROLLBACK`. Фикстуры используют общую конфигурацию тестов и отдельные временные SQLite. Оба теста прошли вместе с тремя проверками патча 10. [Тесты COMMIT и срока](../tests/test_idempotency_commit_boundary.py)

На исходных черновиках 05+06 прошли 20 выбранных тестов общей миграции и транзакций. Четыре обычных повтора эквивалентных тел вернули ложные 409. Синтетическая проверка DDL также выявила пропуск строки с телом и отсутствующим кодом. Временная проверка двух кандидатов на исправление, включая патч 10, дала 31 passed и 2 deselected. Правку нормализации координатор интегрирует из собственного согласованного варианта QA. Условие CHECK передано отдельной строкой. Состав рабочей SQLite, production Python 3.14 и PostgreSQL здесь не проверялись. [Раунд 2](round-02/python.md)
