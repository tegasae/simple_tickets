Основной последовательный цикл двух карточек соответствует решениям владельца. Сквозные проверки подтвердили телефонный сценарий, текст и авторство комментариев, положительный общий контакт, ограничения назначения, проекцию подтверждения и отмены и отдельную административную финализацию работы отключённого клиента. ## Существенные отклонения

### N01. Отзыв refresh отсутствует в бизнес-командах

Ожидается постоянное прекращение всех затронутых refresh при смене пароля, удалении Account или сотрудника и отключении Account, сотрудника или Client. Запись бизнес-изменения и отзыв должны быть одной транзакцией. Факт: `create_app` выбирает память процесса или отдельный `TokenStorageSQLite`. Этот SQLite-адаптер сам открывает своё соединение. `AuthManager.login` и `refresh` сначала читают и проверяют бизнес-сущности через auth service с UoW, затем отдельно выполняют запись или ротацию. Защита отдельного хранилища при замене одного токена не согласует эту запись с состоянием Account или Client. В записи есть тип и ID сотрудника, а постоянный ID Account отсутствует. В бизнес-командах отключение, смена пароля и удаление завершаются сохранением своих агрегатов. Реестр refresh в этих транзакциях не меняется. Это нарушает постоянство отзыва, в том числе при повторном включении. `OWNER-SCOPE.md:6`, `reviews/answers.md:12–17`, `src/web/main.py:39–52`, `src/web/auth/storage_sqlite.py:23–40,73–96`, `src/web/auth/tokens.py:186–215`, `src/web/auth/services/services.py:197–263`, `src/web/auth/services/auth_service.py:94–113,140–186`, `src/application/services/admin_service.py:211–299,420–447,544–580`, `src/application/services/user_service.py:217–322,446–538`, `src/application/services/client_service.py:163–221`.

Проверенный штатный вход и ротация сохранили первоначальные `created_at` и `expires_at`, разница ровно семь суток. Срок нового access оказался в пределах пяти минут. Условия ближе к окончанию сессии проверены чтением кода, где установлен минимум обычного `exp` и абсолютного срока. После штатного отключения Account в тесте флаг Account стал 0, а запись refresh осталась в хранилище с `revoked=False`. Попытки обновления после отключения и межпроцессные гонки не выполнялись. Текущая проверка активности User, его Account и Client в штатном HTTP входе и access сохраняет самостоятельный смысл. `src/web/config.py:18–24`, `src/web/auth/tokens.py:63–83,217–240`, `src/web/auth/services/services.py:86–106`, `src/web/dependencies/auth.py:125–165`, `src/web/routers/admin/admins.py:244–265`.

Критерий исправления: один реестр и UoW для обычных FastAPI процессов, стабильные идентификаторы Account и субъекта, согласованная транзакционная сериализация выпуска/ротации и отзыва, сохранение первоначального дедлайна и границы `exp`. Для каждой команды отзыва проверить, что после успешного изменения и после повторного включения затронутый refresh остаётся отозванным, незатронутые сессии работают, а откат команды откатывает её отзыв. Удаление и новое создание Account проверять с тем же логином. Проверить два независимых экземпляра приложения и обе очередности конкурирующих выдачи/ротации и отзыва с управляемым барьером. Переход завершает старые сессии, требует новый вход и исключает приём refresh из прежнего файла и памяти. Дополнительная обязательная проверка `sid` для каждого access решением владельца не предусмотрена. `OWNER-SCOPE.md:6`, `reviews/answers.md:1–2,12–17`.

### N06. Повторная команда исполняется ещё раз

Ожидается один зафиксированный результат по совпавшему ключу, субъекту, команде и нормализованному входу с целью, включая созданный Account и историю. Во всех десяти командах отправлены одинаковые авторизованные запросы последовательно с одним тестовым `Idempotency-Key`. Ни один повтор не воспроизвёл сохранённый результат. Команды во входе принимают бизнес-тело и актора и вызывают сервис непосредственно, в схеме отсутствует реестр результатов. `OWNER-SCOPE.md:8`, `reviews/answers.md:18`, `db/schema.sql:1–186`.

Конфликты уникальности имени и логина не реализуют воспроизведение результата. Для Ticket/TicketUser имеющийся UoW пары и истории даёт границу для совместной записи результата команды. Сервисы создания и комментариев используют разные точки commit, поэтому реестр, записанный после возврата из сервиса, не даст требуемой атомарности. `src/application/services/ticket_service.py:124–231,1183–1204`, `src/application/services/ticket_user_service.py:111–206,846–875`, `src/adapters/uow/sqlite_unit_of_work.py:92–121,133–145`.

Критерии исправления: все десять команд проходят с необязательным ключом. Совпадение возвращает исходный результат и HTTP-статус после текущей проверки доступа, без повторных бизнес-записей. Несовпадение текста, смыслового поля или целевого ID даёт 409. Представления с одинаковым нормализованным смыслом совпадают. Повтор после конкурирующего успеха проходит через штатный механизм занятости и клиентский повтор. Проверить откат после промежуточных записей, остановку после COMMIT до отметки срока, следующее успешное обращение, восстановление срока и поведение после 24 часов. Если отметка не успела записаться, совпавший разрешённый запрос возвращает уже сохранённый результат и начинает окно хранения заново. ### Версии старых Employee, Department и Client

Ожидается миграция `NULL → 0`, сохранение прежних числовых версий, `NOT NULL DEFAULT 0` для новых данных. В DDL всех трёх таблиц по-прежнему только `DEFAULT 0`. На синтетических NULL GET Admin и GET Department дали 500 при приведении `None` к int. PUT обычного User с NULL Employee и числовой версией Client дал 409 на CAS Employee. PUT Client с NULL дал 409 на CAS Client. Сами строки в реальной БД неизвестны. Критерий миграции: фикстуры с NULL и ненулевыми версиями проходят преобразование, вставка без версии получает 0, явный NULL запрещён, чтение и обычная мутация после миграции работают, устаревшая ненулевая версия по-прежнему даёт конфликт. `OWNER-SCOPE.md:7`, `reviews/answers.md:3–8`, `db/schema.sql:1–18,41–50`, `src/adapters/repositories/mappers/admin_mapper.py:31–43`, `src/adapters/repositories/mappers/department_mapper.py:15–25`, `src/adapters/repositories/mappers/user_mapper.py:27–38`, `src/adapters/repositories/mappers/client_mapper.py:19–38`, `src/adapters/repositories/gateways/employee_gateway.py:10–22`, `src/adapters/repositories/gateways/client_gateway.py:15–24`, `src/adapters/repositories/gateways/department_gateway.py:15–23`.

### Обычное редактирование Admin может снять отдел

Маршрут `PUT /admin/admins/{id}` описан как обновление личных и контактных данных. Входное поле `department_id` по умолчанию 0 и попадает в DTO даже при его отсутствии. `update_admin` создаёт пустой Department, затем `AdminService.update` воспринимает его как запрос смены отдела. HTTP PUT только с новым именем сотрудника без текущей заявки вернул 200, и повторный GET подтвердил сохранённый `department_id=0` вместо 2. Для назначенного сотрудника аналогичный контактный PUT получил 400. При передаче его прежнего отдела PUT прошёл. ## Границы и решения по изменениям

- Критика из раздела о PostgreSQL READ COMMITTED в документе решения относится к предыдущему срезу. В текущем снимке оба ранее пропущенных `touch` существуют. Они проверяют версию той же строки Employee, что меняют disable и смена Department. Оправдано сохранить их и проверить обе очередности на двух PostgreSQL-соединениях после появления или подключения соответствующего адаптера. Повторное добавление тех же guard не требуется. Последовательная SQLite-проверка подтвердила эффекты обеих веток, конкурентная PostgreSQL-проверка не выполнена. Для отдельного вызова application-сервиса User с явно указанным `department_id` чтение отдела в ветке создания не сопровождается `departments.touch`. Текущая модель HTTP User такого поля не принимает.
