## N01, N06 и взаимодействие патчей

- **05. Сессии и прежний access.** Уточнение В об объёме доказательств принимаю. Первый проход лично подтвердил одну неизменённую refresh-запись и обычную ротацию. Кандидат подтверждает полный перечень штатных событий отдельной матрицей. Вход и ротация используют тот же `SQLiteUnitOfWork`, что и мутации, сохраняют абсолютный срок семь суток и ограничивают `exp` access. Сохранена штатная проверка JWT и активности. Старый access с прежней подписью, пока он действителен и субъект допущен, работает через новый экземпляр. Старый refresh из отдельного файла или старой таблицы отвергается. Результат обычного logout одной сессии и всех собственных сессий подтверждён. Смена пароля удаляет refresh, оставляя прежний access до его `exp`, если проверки допуска продолжают проходить. Прямая замена Account через POST attach дополнительно покрыта для Admin и User: 200, две прежние записи удалены в том же UoW, соседний субъект сохраняет сессию, вход с новыми реквизитами работает. `src/web/auth/services/shared_sessions.py:25–107`, `src/web/dependencies/auth.py:119–159`, `src/application/services/admin_service.py:196–222`, `src/application/services/user_service.py:183–218`. [Проверки срока](../../tests/test_lifetime.py) · [Проверки общих сессий](../../tests/test_shared_sessions.py) · [Регрессия attach](../../tests/test_refresh_attach_replacement.py)

- **05. Порядок каскада и выдачи.** Согласен, что наличие CAS само по себе не доказывает конкурентный результат. Дополнительно проверил четыре комбинации `Client.disable` против login/refresh через два HTTP-запроса с независимыми SQLite-соединениями в WAL и барьером перед записью User. Когда первым фиксировался disable, вход или ротация получили 503, пара закрылась и refresh User отсутствовали. Когда первым фиксировался вход или ротация, начальный disable получил 503 и оставил пару в состоянии проверки. Повтор отключения со свежим чтением закрыл пару и удалил свежий refresh. Во всех четырёх SQLite-опытах сессия Admin сохранилась. `src/web/auth/services/auth_service.py:171–214`, `src/application/services/client_service.py:197–229`.

- **06. Транзакция, адресат и срок.** Согласен с Б о границе UoW и с В об объёме десяти команд. Резерв ключа, команда с историей и публичный ответ фиксируются вместе. Ранние внутренние COMMIT отключены в присоединённом вызове. Финальный CHECK таблицы допускает либо резерв без ответа, либо завершённый результат с успешным статусом и телом. Тесты включают необязательный ключ, оба родительских создания с Account, конфликт изменённого тела, тот же текст на другой цели комментария, пересчёт актуальных прав, ошибку COMMIT и сохранение ответа при потере доставки. Для цели, закрытой после исходного комментария, можно вернуть прежний снимок после проверки доступа, удалённая цель даёт 404. Сужение отметки срока до того же ключа из формулировки моего первого отчёта снимаю: владелец подтвердил следующее успешное сохранение с ключом либо совпавший replay без отметки. `src/web/idempotency.py:79–151`, `db/schema.sql:206–219`. [Матрица](../../tests/test_idempotent_creations.py) · [Тест границы COMMIT](../../tests/test_idempotency_commit_boundary.py) · [Требования](../../docs/requirements.md#идемпотентность-созданий)

- **06 и 09. Два эффекта нормализации.** Проверка В о ложных 409 из черновика 06 была верной для того кода. В финальном 06 поля проходят нормализацию теми же доменными типами, массивы ролей и прав сравниваются по множеству, значимые поля и цель остаются в отпечатке. 09 отдельно нормализует логин перед проверкой занятости. В собственном сквозном опыте первое создание User с пробелами вокруг логина вернуло 201 и канонический логин, повтор канонической формы с тем же ключом вернул тот же 201 и JSON. Обычная команда без ключа с тем же логином и краевыми пробелами получила 400. В SQLite осталась одна строка Account. Аналогичные проверки дубликата для Admin и User выполнены штатным набором. `src/web/idempotency.py:46–76`, `src/application/helper/employee_helper.py:23–34`. - **10. Представление истории.** Подтверждаю предложение Б и уточнение В о разнице между replay и свежим GET. Причина исходного дефекта — `bool(NULL)` при чтении сохранённой записи. Исправление ограничено представлением истории. На финальном кандидате начальные события и пауза сохранили `work_is_remote:null` после GET. В одном цикле после удалённой работы и очного возобновления события `AT_WORK` сохранили порядок `true, false`. Старый синтетический `AT_WORK` с SQL NULL допустимо прочитался как `false`. Внешнее авторство карточки и каскады от этой правки не зависят. `src/adapters/repositories/mappers/ticket_mapper.py:113–125`. ## Границы и открытые решения

- По подтверждённым владельцем состояниям Department, профилю Admin, начальной правке контакта, каскаду отдельного контакта и автору `CREATED` разногласий нет. Для нулевого контакта пути сохраняют различие: User возвращает контакт к владельцу, Admin отклоняет его для пользовательского происхождения. В N06 пропуск контакта и явный 0 воспроизводят один 201, а явный ID самого владельца при том же ключе даёт 409 без второй пары. Это различные значения публичного входа с той же текущей контактной записью. Унификацию или признание их одним входом стоит считать отдельным решением. `src/web/models/tikcets_user.py:20–35`, `src/web/idempotency.py:46–76`.

- Будущая 1:N остаётся открытым проектным решением по проекции статусов, отмене и удалению. Приёмка сейчас подтверждает одну пару на создание и одну пару на снимок результата N06. Для существующего рабочего адаптера PostgreSQL доказательств нет: штатная точка входа создаёт SQLite, четырёхчастный опыт WAL и результаты COMMIT/503 относятся к этой СУБД. На PostgreSQL отдельно проверить конкуренцию назначения/отключения/смены отдела и согласование отзыва и keyed COMMIT. `src/web/dependencies/services.py:22–32`. [Принятый объём](../../docs/owner-scope.md)

- Семантика прежних данных остаётся явной границей. 10 сохраняет явные исторические SQL-значения `0` и `1`. Переписывание истории выходит за проверенный контракт. Правила создания и проекции в новом документе актуальны, старые формулировки README и диаграмм из первого заключения остаются задачей синхронизации документации. Для N06 общий подписывающий ключ необходим всем экземплярам, его ротация внутри окна имеет описанное последствие для старых отпечатков. [Контракт](../../docs/requirements.md)
