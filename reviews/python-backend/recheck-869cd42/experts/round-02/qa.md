Для приёмки сохранить проверку обеих веток, фактического автора обычного комментария и ровно одной пары. Внутренний `created_from_request_user` и внешний `created` должны оставаться разными событиями истории. Пропуск `department_id` сохраняет текущий отдел и допускает обновление личных полей даже при назначении. Явный `0` означает снятие с проверкой текущего назначения. Успешное редактирование проверять повторным GET, а отказ проверять вместе с состоянием отдела и неизменностью личных данных. Независимый QA проверил сохранённые строки после пяти событий у каждого типа и после каскада Client, а также динамически проверил ограничение `exp` на последних секундах. Для кандидата нужны отдельные подтверждения пройденных гонок, обеих очередностей и незатронутых сессий. Статическое наличие транзакционного guard определяет, что именно проверять. Сравнение нормализованных форм должно доходить до доменной семантики. Нормализованные логины и контактные поля сотрудников дают полезные контрпримеры для исходного 06. ## Заключение инженера Python

- Область пропуска `departments.touch` в User create следует указать прямо рядом с выводом. Прикладной DTO допускает `department_id`, но опубликованный `UserTicketCreateRequest` этого поля не описывает и запрещает дополнительные поля. Поэтому предполагаемая гонка относится к прямому вызову сервиса или будущему HTTP-входу. Оба варианта назначения Admin уже обновляют версию исполнителя в штатном маршруте. Их порядок фиксации требует испытания на целевом адаптере отдельно от этой гипотезы. [Вывод инженера](/workspace/simple_tickets/reviews/python-backend/recheck-869cd42/experts/round-01/python.md:31) · [Модель HTTP User](/workspace/simple_tickets/src/web/models/tikcets_user.py:14) · [Граница назначения](/workspace/simple_tickets/src/application/services/ticket_service.py:587).
- Замечание о версии составного создания точно разделяет INSERT и следующий UPDATE. Проверка DDL должна ожидать `0` при вставке без версии и сохранение числовых версий миграцией. Создание Employee с ролями сейчас содержит второй `save` в том же COMMIT. Для него конечная версия `1` является эффектом этого UPDATE. При обязательной проверке неошибочного CAS сравнивать с фактической сохранённой версией. [Вывод инженера](/workspace/simple_tickets/reviews/python-backend/recheck-869cd42/experts/round-01/python.md:21).
- Пример объекта со старой версией после rollback подтверждает требование использования свежего запроса и свежих агрегатов. В кандидате 06 ветка конфликта claim заканчивает прежнюю транзакцию до нового чтения, а штатная занятость возвращается клиенту. Доказательство корректности будущего повторного использования экземпляра прикладного сервиса из этого не следует. [Эксперимент инженера](/workspace/simple_tickets/reviews/python-backend/recheck-869cd42/experts/round-01/python.md:25).
- Различие `work_is_remote=null` при создании и `false` при повторном GET относится к HTTP-форме истории. Это значимо отдельно от N06. Успешный keyed POST и совпавший повтор должны возвращать снимок исходного ответа, а свежий GET формирует представление из сохранённого статуса. Для согласования GET с исходным ответом нужен отдельный контракт nullable поля и регрессия для статуса без режима, удалённой и очной работы.
