## По отчёту аналитика

- Данные об авторах телефонной пары согласуются с SQL. `TicketUser.CREATED` хранит автора подачи User, внутренняя запись регистрации и обычные комментарии хранят Admin. SQL-отказ при записи внутренней истории и доменный отказ из-за прошедшей даты дают взаимодополняющие доказательства одного отката. Для самостоятельного создания внутренний `actor_id=0` восстанавливается из SQL `NULL`. Изменение первого внешнего статуса или истории по патчу 01 исключено действующим решением. - Уточнение про Department в User create верное. Поле существует в прикладном `TicketUserDTO`, у штатного HTTP `UserTicketCreateRequest` его нет. Сценарий одновременно создать заявку сразу в отделе и отключить пустой отдел остаётся условием проверки лишь для прямого вызова сервиса или будущего HTTP-поля. Прежнюю формулировку моего отчёта следует читать с этой границей. Для `assign(self)` и удалённого старта из `ACCEPTED` актуальные `admins.touch` есть. Явный `0` остаётся запросом снятия отдела с проверкой текущего назначения. При сохранении сотрудника применяется существующий CAS Employee. Наблюдения о разрешении смены контакта в `CREATED` и каскаде по отдельному контакту фиксируют действующий объём поведения. Для их сужения требуется отдельное решение владельца. ## Ревью 05 и 06

### Общая транзакция и миграция 05

- `SQLiteUnitOfWork` создаёт репозиторий сессий на том же `Connection`, что и бизнес-репозитории. Стандартные login и refresh владеют внешней транзакцией. Auth проверяет актуальные данные и выполняет CAS Employee, выдача и ротация сохраняют состояние в том же UoW. Бизнес-команды отключения и смены пароля сначала сохраняют объект на CAS Employee, затем удаляют сессии. Удаление Account выполняется в транзакции и использует FK `ON DELETE CASCADE`. При отключении Client обновляются Employee из списка реально отключённых активных User и их сессии. Эта схема опирается на инвариант штатного потока, при котором уже отключённый User не имеет действующей новой refresh-записи. Критерий QA следует сохранить на двух PostgreSQL-соединениях с реальным адаптером, включая порядок выдачи и отключения Client. Здесь вывод о сериализации основан на коде. `src/adapters/uow/sqlite_unit_of_work.py:46` · `src/web/auth/services/shared_sessions.py:25`, `:46` · `src/web/auth/services/auth_service.py:94`, `:180`, `:213` · `src/application/services/client_service.py:197` · `src/application/services/admin_service.py:655` · `src/application/services/user_service.py:628` · `db/schema.sql:188`.
- Миграция известного старого DDL открывает одну `BEGIN IMMEDIATE`, пересобирает три таблицы с `COALESCE(version, 0)`, переносит столбцы и зависимые индексы и восстанавливает исходный `sqlite_sequence`. `foreign_key_check` выполняется до фиксации, исходный режим FK восстанавливается в `finally`. Повтор на перенесённой схеме даёт ноль изменений. Независимо повторены два существующих приёмочных теста. Подтверждены прежние ненулевые версии, строгие новые столбцы, FK, индекс Department, продолжение ID после удалённого максимума и CAS после миграции. При ошибке FK откатились DDL и данные. Текстовая проверка известной схемы ограничивает поддержку этим DDL. Успех миграции рабочего файла требует проверки его фактической формы владельцем в среде развёртывания. `scripts/migrate_backend_storage.py:32`, `:54`, `:81` · [Приёмочные проверки миграции](../../tests/test_migration.py).

### Claim, фиксация и восстановление 06

- Ключ с областью `(subject_type, subject_id, command, key)` имеет составной PRIMARY KEY. Claim выполняется до бизнес-INSERT. Внешний UoW объединяет резерв, вызов сервиса с `join_transaction`, подготовку публичного ответа и `complete`. В затронутых путях внутренний commit отключается. Только DB unique в операции reserve переходит в `CreationAlreadyReserved`, повторное чтение происходит после отката. Повторный прямой reserve на реальном SQLite подтвердил этот перевод и сохранение существующего результата. При обычном конкурентном HTTP SQLite воспроизведён `BUSY → 503` с последующим клиентским повтором. HTTP-ветку unique следует проверить отдельно на PostgreSQL. Прошли 18 текущих тестов атомарности и времени из общего набора, включая все согласованные создания и составные Account. `src/web/idempotency.py:83`, `:117` · `src/adapters/repositories/creation_result_repository.py:26`, `:37` · `src/domain/uow/unit_of_work.py:83` · `utils/db/sqlite_errors.py:11` · [Регрессии транзакций](../../tests/test_idempotency_transactions.py).
- Согласованное окно допускает отметку старого результата после успешного создания с другим ключом. После синтетической остановки обслуживания в точке после бизнес-COMMIT результат оставался с `expires_at=NULL`. Через три дня другая ключевая команда запустила прежнему результату 86400 секунд. На последней секунде вернулся исходный ID, срок не изменился, на границе следующий запрос создал записанный заново результат. Ограничение обслуживания тем же ключом не требуется. [Требование к сроку](../../docs/requirements.md) · [Синтетический тест](../../tests/test_idempotency_commit_boundary.py)

Воспроизведены ложные 409 для Department с пробелами имени, Client с эквивалентными email и описанием, Admin с эквивалентными именем и логином и User с эквивалентными телефоном и фамилией.
