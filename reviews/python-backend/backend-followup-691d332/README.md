# Регрессии заявок и начальное состояние отдела

Базовый коммит `691d332415ef7226c57799e0e5766f4cf021b722`, ветка `api-new-client-scheme` репозитория `tegasae/simple_tickets`. Патчи независимы. [Базовый коммит](https://github.com/tegasae/simple_tickets/commit/691d332415ef7226c57799e0e5766f4cf021b722)

## Отмена и физическое удаление

Отмена через `PATCH /admin/tickets/{id}/cancel` требует `ticket.canceled` и комментарий. Домен проверяет текущий статус. При допустимом переходе добавляет `CANCELLED` в историю внутренней заявки и синхронизирует связанную пользовательскую заявку в `CANCELLED_BY_ADMIN`. В обеих историях сохраняются ранее записанные события и комментарии. [Команда отмены](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/src/application/services/ticket_service.py#L988-L1020) · [Синхронизация](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/src/domain/services/ticket_sync_service.py#L43-L70)

Физическое удаление через `DELETE /admin/tickets/{id}` требует того же `ticket.canceled`. Команда загружает карточки и удаляет их в одной транзакции. Отдельной проверки перехода или причины нет. Статусы и комментарии внутренней заявки удаляет SQLite по внешним ключам. Для пользовательской заявки их удаляет репозиторий. На синтетической завершённой паре сотрудник с одним `ticket.canceled` получил `400` на отмену и `204` на удаление. Повторное чтение SQLite подтвердило потерю обеих заявок и обеих историй. [Команда удаления](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/src/application/services/ticket_service.py#L1023-L1041) · [Удаление истории TicketUser](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/src/adapters/repositories/ticket_user_repository.py#L324-L354) · [Внешние ключи](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/db/schema.sql#L93-L105)

Результат идемпотентного создания хранится отдельно. В проверке создали заявку с ключом, удалили её и получили `404` при чтении. Повтор исходного POST с тем же ещё действующим ключом вернул прежний `201` с тем же ID. Для будущей политики удаления стоит явно выбрать поведение такого повтора. [Таблица результатов](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/db/schema.sql#L206-L217) · [Повтор сохранённого ответа](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/src/web/idempotency.py#L94-L102)

Если задача состоит в том, чтобы убрать заявку из рабочих списков, подходит архивирование с сохранением карточек и истории. Если физическая очистка нужна, выделить отдельное полномочие, например `ticket.delete`, согласовать допустимые состояния и сохранять независимую запись об удалении с указанными ID, временем, автором и причиной. Право на отмену не должно автоматически давать это полномочие. Политика удаления в этих патчах не меняется.

## Что входит в патчи

- [01-default-ticket-role-regressions.patch](patches/01-default-ticket-role-regressions.patch) добавляет проверяемые сценарии ролей, назначения и двух связанных историй в обычный `tests/`.
- [02-preserve-department-enabled.patch](patches/02-preserve-department-enabled.patch) передаёт в доменный сервис `department_dto.enabled`. Входной контракт и значение по умолчанию `true` сохраняются. Тесты проверяют `false`, `true`, пропущенное поле, запись в SQLite и повтор с тем же ключом. Сохранённый до исправления ответ с тем же действующим ключом продолжает воспроизводиться из таблицы результатов. [Исправляемое место](https://github.com/tegasae/simple_tickets/blob/691d332415ef7226c57799e0e5766f4cf021b722/src/application/services/department_service.py#L59-L76)

```bash

git apply --check "$patch_dir/"*.patch
git apply "$patch_dir/"*.patch

```
