# simple_tickets: согласованные правила и подготовка к production

Дата: **24 ноября 2026 года**, Europe/Moscow.

Документ объединяет обсуждение после повторного аудита Python-бэкенда и последние уточнения владельца. Он предназначен для скачивания и дальнейшей постановки задач. Решения ниже не означают, что соответствующий код уже реализован или прошёл production-проверки.

Основание аудита — снимок `bbf7a392dafe0fede2d5d017af36281b6f4f40a2` репозитория `tegasae/simple_tickets`, ветка `api-new-client-scheme`. Последующие ответы владельца уточняют требования и имеют приоритет над открытыми вопросами прежних отчётов.

## 2. Бизнес-правила, которые теперь определены

| Тема | Согласованное правило |
|---|---|
| Контакт заявки пользовательского происхождения | Если Ticket создан из пользовательской заявки — `CREATED_FROM_TICKET_USER` или `CREATED_FROM_USER_REQUEST` — положительный `contact_user_id` обязателен и сохраняется на всём жизненном цикле. Очистка контакта до отсутствующего значения запрещена |
| Изменение контакта | Через обе карточки разрешено менять контакт при внутреннем `ACCEPTED/DEFERRED`. Внешний `IN_WORK` представляет несколько внутренних состояний, поэтому проверка внутреннего Ticket сохраняется |
| Начальный `CREATED.actor` | Фактический инициатор: Admin при регистрации заявки за пользователя, User при самостоятельном создании. Владелец заявки хранится отдельно |
| Обычный комментарий | Автором является тот, кто ввёл текст; комментарий Admin не приписывается владельцу User |
| Смена отдела Admin | Пока у сотрудника есть текущее назначение исполнителем, менять отдел нельзя. Документацию, упоминающую только `AT_WORK`, нужно привести к этому правилу |
| Включение Admin | Нельзя включить сотрудника в отключённом назначенном Department. Сначала включить отдел либо снять назначение в отдел |
| JSON комментария | В административном ответе текст должен быть строкой, как в пользовательском API. Доменный value object может сохраняться внутри приложения |
| Отключение владельца или клиента | Заявки, уже находящиеся на проверке, закрываются как финальный `SUSPENDED` в обеих карточках; активная работа продолжается |
| Завершение сохранённой активной работы отключённого клиента | Сотрудник завершает работу, заявка остаётся в `READY_FOR_REVIEW`. Проверку и дальнейшую административную финализацию выполняет Admin отдельной командой. Это допустимый редкий сценарий |
| Автоматический `EXECUTED` | После `finish-work` не требуется: сохраняется отдельный этап проверки |

Требование о фактическом инициаторе начального статуса уточнено после аудита. Ранее предложенный патч автора обычного комментария сам по себе это поле не исправлял. Формат административного JSON следует изменять на границе ответа, сохраняя корректную доменную модель.

## 3. Контроль конкурентного назначения исполнителя

### Проблема

На PostgreSQL READ COMMITTED возможен следующий порядок:

1. T1 читает включённого Admin из отдела А и проверяет возможность назначения.
2. T2 не видит ещё не сохранённого назначения, отключает Admin либо переводит его в другой отдел и фиксирует изменения.
3. T1 сохраняет Ticket на основании старого состояния сотрудника.

Версия Ticket не обнаруживает изменение другого объекта — Admin. В проверенном коде общий guard исполнителя пропущен для `assign(self)` и ветки удалённого самоназначения из `ACCEPTED`. Успешное нарушение такого инварианта на SQLite не показано; реальная PostgreSQL-проверка ещё нужна.

### Предлагаемое исправление

Для этой гонки достаточно общего `touch` исполнителя при выполнении всех условий:

- touch условно изменяет версию строки Admin при совпадении с прочитанной версией; несовпадение даёт конфликт;
- отключение и смена отдела сохраняют Admin с проверкой той же версии;
- проверка условий, touch, сохранение Ticket и истории выполняются одной транзакцией;
- конфликт откатывает всю команду;
- новая попытка использует свежие объекты и повторяет проверки.

Общий guard нужен и при назначении себя, и при назначении другого сотрудника. Простое повторное чтение перед записью не заменяет его: между чтением и записью остаётся окно изменения.

Проверка: два PostgreSQL-соединения, управляемый барьер после чтения, назначение против отключения/смены отдела. Обе команды не должны успешно фиксировать запрещённое сочетание. Это направление исправления конкретной гонки, а не утверждение о проверенной безопасности всех конкурентных операций приложения.

## 4. Одна или несколько внутренних заявок

Владелец допускает, что в будущем из одного TicketUser будет формироваться несколько Ticket. Сейчас обычный сценарий создаёт одну внутреннюю карточку.

Поэтому UNIQUE на `tickets.user_ticket_id` не предлагается как постоянное правило модели. Внешний ключ продолжает проверять существование указанной пользовательской карточки. Отсутствие уникальности с учётом выбранного направления не считается самостоятельным дефектом.

До включения сценария «один TicketUser — несколько Ticket» нужно доработать методы, возвращающие одну внутреннюю карточку, и определить агрегирование общего статуса, завершения, отмены и истории. Существующий API не объявляется уже поддерживающим этот сценарий.

## 5. Токены и отзыв сессий

### 5.1. Утверждённые сроки

| Параметр | Значение |
|---|---|
| Access JWT | **5 минут** |
| Refresh-сессия | **7 суток от первоначального входа** |
| Абсолютный срок сессии | **Те же 7 суток**, без бесконечного продления |

При refresh меняется токен, но конечная дата сессии сохраняется. Ротация на шестые сутки не даёт ещё семь суток. После абсолютного срока нужен новый вход. Access-токен, выдаваемый в конце сессии, не должен продлевать доступ за согласованный абсолютный срок.

Сроки задаются именованными параметрами в одном месте. Числовые значения не распределяются по методам. В дальнейшем источник параметров переносится в конфигурацию без изменения логики авторизации.

### 5.2. Что означает отзыв

Смена пароля, удаление аккаунта и отключение сотрудника отзывают его refresh-сессии. Повторное включение не восстанавливает отозванные refresh. Аккаунт и субъект проверяются по постоянным идентификаторам и типу, а не только по логину.

Владелец допускает задержку прекращения действия ранее выданного access на несколько минут. Поэтому рабочая схема не требует отдельной проверки серверного `sid` при каждом запросе: access ограничен своим сроком, а обновить его через отозванный refresh нельзя. Существующие проверки активности сотрудника/аккаунта/клиента и прав сохраняются и могут отказать раньше истечения JWT.

Это уточняет раннее предложение немедленно проверять серверную сессию на каждом запросе. Ранний вариант остаётся технической возможностью, но больше не является обязательным требованием. Подпись и срок JWT проверяются всегда; кеш не должен продлевать истёкший access.

Важно различать гарантии: refresh после повторного включения не оживает; ранее выданный access оценивается обычными проверками до своей исходной даты окончания. Если сотрудника быстро отключить и включить до этой даты, немедленная неизменяемая инвалидизация старого access этим вариантом не обещается.
