## 2. Резюме для владельца проекта

Frontend v3 создаётся как рабочее место сотрудников контура **Admin**. Отдельный кабинет User в первый релиз не входит.

Backend предоставляет достаточные операции для основных сценариев Admin, включая полный жизненный цикл заявки, назначение сотрудников, самостоятельное начало работы на горячей линии, комментарии, управление справочниками и назначение ролей Admin и User. Редактирование определения существующей роли через HTTP API отсутствует.

Frontend v2 уже содержит значительную часть прикладных форм и API-вызовов, но его правила отображения действий расходятся с текущими правами и переходами backend. Простое копирование экрана заявок, таблицы, модального окна, системы прав и кэша справочников перенесёт известные ошибки. React, Vite, `fetch`, чистые функции форматирования, часть форм и визуальные токены пригодны для повторного использования после проверки и адаптации.

Основные решения для v3:

- рабочие вкладки заявок с независимыми черновиками;
- сохранение контекста при переходе к клиенту, заявителю или контакту;
- компактный поиск и раскрываемые расширенные фильтры;
- клиентская фильтрация, сортировка и пагинация над разрешённой серверной выборкой;
- предложенная консилиумом очередь Admin `READY_FOR_REVIEW` под названием «На проверку», ожидающая отдельного согласования;
- действие «Взять в работу на горячей линии» одним вызовом `start-remote-work`, результатом которого становится `AT_WORK`;
- назначение ролей отдельно от сохранения профиля сотрудника;
- восстановление входа после обновления страницы в пределах действующей серверной сессии;
- WCAG 2.2 AA как целевой уровень доступности.

## 4. Заключение Senior FastAPI Expert

### 4.1. Архитектура и стек

Backend запускается как `uvicorn src.web.main:app`. `create_app()` подключает восемь роутеров и реестр обработчиков исключений. Поток запроса проходит через Pydantic-модели, DTO, прикладные сервисы, доменные агрегаты, SQLite Unit of Work, репозитории и SQL gateways. ORM не используется.

Зафиксированные основные зависимости:

- FastAPI `0.143.0`;
- Pydantic `2.14.1`;
- pydantic-settings `2.15.0`;
- PyJWT `2.15.1`;
- Starlette `1.8.0`;
- Uvicorn `0.54.0`.

Dockerfile backend использует `python:3.14-slim`. Для производственного запуска требуется явно заданный `SECRET_KEY`, отличный от значения по умолчанию. Источники — `requirements.txt`, `dockerfiles/backend/Dockerfile:1`, `src/web/main.py:37`, `src/web/config.py:27`, `src/adapters/uow/sqlite_unit_of_work.py:38`.

### 4.3. Аутентификация и ошибки

Вход принимает `application/x-www-form-urlencoded` с логином и паролем. Login и refresh возвращают access и refresh token в JSON. Срок access token по умолчанию пять минут, refresh-сессии — семь дней. Refresh-токен ротируется. Logout отзывает refresh-сессию, а уже выданный access token действует до истечения срока при действующей учётной записи.

Admin получает актуальные права через `GET /admin/admins/permissions`. У User отсутствуют endpoint собственного профиля, endpoint прав и разрешённый справочник контактов. Источники — `src/web/auth/services/shared_sessions.py:25`, `src/web/dependencies/auth.py:119`, `src/web/routers/admin/admins.py:117`.

Frontend должен различать:

- `400` — доменное ограничение или бизнес-валидация;
- `401` — недействительная или истёкшая сессия;
- `403` — недостаточно прав;
- `404` — сущность отсутствует;
- `409` — конфликт или optimistic lock;
- `422` — структурная валидация FastAPI;
- `503` — временная недоступность хранилища.

Создания и комментарии поддерживают необязательный `Idempotency-Key`. Повтор того же запроса может вернуть сохранённый снимок ответа, поэтому после повтора нельзя затирать им более новое состояние карточки. Источники — `src/web/main.py:60`, `src/web/idempotency.py:42`, `src/web/idempotency.py:123`.

### 4.4. Жизненный цикл заявки

Начальные статусы внутренней заявки:

| Нормализованный код frontend | Значение API | Утверждённая подпись |
|---|---|---|
| `CREATED` | `created` | Создана |
| `CREATED_FROM_REQUEST_USER` | `created_from_request_user` | Создана по запросу клиента |
| `CREATED_FROM_TICKET_USER` | `created_from_ticket_user` | Создана из заявки клиента |

После создания доступны принятие или отказ, назначение, работа, пауза, продолжение, передача на проверку, административное завершение или подтверждение связанной заявки пользователем. `READY_FOR_REVIEW` внутренней заявки отображается как `WAITING_FOR_CONFIRMATION` связанной заявки User. User-контур в первый релиз frontend v3 не входит. Источники — `src/domain/statuses/rules/ticket_status_transition.py:21`, `src/domain/statuses/mapping_statuses.py:29`.

В `TicketResponse` нет верхнеуровневого поля `current_status`. Frontend должен получать текущий статус из последнего элемента `statuses` после нормализации истории, а не ожидать отдельное поле ответа.

## 5. Заключение Senior React Expert

Frontend v2 использует JavaScript/JSX, React `19.2.8`, React DOM `19.2.8`, Vite `8.1.5`, npm и `fetch`. Библиотек маршрутизации, форм, серверного состояния и прикладных frontend-тестов в манифесте нет. `node_modules` отслеживается в v2 и не должен переноситься в v3. Источник — `simple_tickets_frontend_v2/package.json`.

Подтверждённые рабочие области v2:

- вход Admin и оболочка;
- заявки;
- клиенты;
- пользователи;
- сотрудники;
- отделы;
- роли.

Ключевые технические проблемы v2:

- навигация хранится в `activePage` и не поддерживает URL, Back/Forward и восстановление карточки;
- карточка заявки хранится в одном `selected`;
- переход к связанной сущности закрывает карточку;
- общий `Modal` закрывается кликом по фону и не управляет фокусом;
- правила доступности workflow-кнопок расходятся с backend;
- кэш справочников не защищён от устаревших асинхронных ответов;
- токены хранятся в `localStorage`;
- `DataTable` ориентирован на mouse click и не имеет полного доступного управления сортировкой и открытием строки;
- статус в одном фильтре сравнивается как код API, хотя пользователю показывается русская подпись;
- назначение ролей сотрудника связано с сохранением профиля и может скрыться после ошибки загрузки каталога.

Источники — `simple_tickets_frontend_v2/src/App.jsx:83`, `simple_tickets_frontend_v2/src/components/Modal.jsx:1`, `simple_tickets_frontend_v2/src/components/DataTable.jsx:53`, `simple_tickets_frontend_v2/src/components/TicketsPage.jsx:49`, `simple_tickets_frontend_v2/src/referenceData.jsx:59`, `simple_tickets_frontend_v2/src/storage.js:28`.

Рекомендуемое повторное использование:

| Решение | Состав |
|---|---|
| Перенести после проверки | Чистые функции дат, длительности, текста и имени, подходящие CSS-токены |
| Адаптировать | Login, Shell, RolePicker, простые формы справочников, история, комментарии, уведомления |

## 6. Заключение Senior UX / Usability Expert

Предполагаемые рабочие категории Admin — оператор приёмки, диспетчер, исполнитель, сотрудник горячей линии и администратор справочников. Это экспертная модель. Фактическое распределение обязанностей и частота операций требуют проверки с владельцем и реальными пользователями.

| Проблема | Критичность 0–4 | Рекомендация |
|---|---:|---|
| Строка таблицы и сортировка недоступны полноценному клавиатурному сценарию | 4 | Кнопки или ссылки открытия, кнопки сортировки, `aria-sort`, видимый фокус |
| Клик по фону закрывает форму, Escape и возврат фокуса не определены | 3 | Фон не закрывает форму, Escape действует на верхний слой, черновик защищён |
| Нельзя вести несколько заявок без потери контекста | 3 | Рабочие вкладки с отдельными черновиками и дочерним контекстом связанных сущностей |
| Поиск и два слоя фильтров могут скрывать результат | 3 | Одна строка поиска, сворачиваемые фильтры, видимые активные условия, единый сброс |
| Новая заявка может оказаться на последней странице | 3 | Сортировка новых сверху и ссылка на созданную заявку из сообщения об успехе |
| Отключённые отделы и неподходящие исполнители доступны для нового назначения | 3 | Только активные допустимые варианты, архивные связи показывать с меткой |
| Длинные select клиента, заявителя и контакта | 3 на больших справочниках | Доступный combobox с поиском, клавиатурой и ограничением по клиенту |
| Карточка перегружена, комментарий открывается отдельным диалогом | 3 | Статус и следующее действие сверху, комментарии первой вкладкой, inline composer |
| Ошибка загрузки и пустой результат различаются недостаточно явно | 3 | Разные состояния с понятным следующим действием |

Целевой стандарт доступности — WCAG 2.2 AA. Автоматические проверки должны дополняться ручными сценариями клавиатуры, экранного считывателя, масштабирования, reflow и контраста.

## 7. Заключение Senior QA Engineer

Штатный pytest в `frontend_new` использует `tests/`. В целевой ветке обнаружены шесть файлов и 20 функций `test_*` с дополнительной параметризацией. Покрыты отдельные сценарии создания и идемпотентности, refresh и транзакций, отделов, ролей, удаления заявки, рабочего процесса и горячей линии. `tests_pyramid/` в целевом коммите отсутствует, а проверки в `reviews/` являются историческими и не входят в штатный запуск. Источники — `pytest.ini`, `tests/`.

Приоритетные проверки v3:

1. Два независимых черновика заявок, переход к связанной сущности и возврат.
2. Клик по фону, Escape только верхнего слоя, блокировка фона и возврат фокуса.
3. Поиск по русской подписи статуса, сортировка до пагинации, новая заявка под активным фильтром.
4. Отключённые отделы, другой отдел исполнителя и устаревший справочник.
5. Минимальные комбинации прав, включая `ticket.at_work_remote`, `ticket.assign_executor`, `role.assign` и `role_user.assign`.
6. Две сессии, одновременно выполняющие `start-remote-work` для одной заявки.
7. Частичное применение последовательных grant/revoke ролей.
8. Ошибки `400`, `401`, `403`, `404`, `409`, `422`, `503` и ответы `204`.
9. Запоздалый refresh или GET предыдущей сессии после logout или нового login.
10. Доступность основных сценариев в браузере.

| Принятые и требующие подтверждения смешаны | `ACCEPTED`, `READY_FOR_REVIEW` и User `WAITING_FOR_CONFIRMATION` имеют разные смыслы | Для Admin консилиум предлагает отдельный список «На проверку» по `READY_FOR_REVIEW`; User-контур исключён. Очередь Admin ожидает согласования |

## 9. Матрица прав Admin

| Возможность | Право backend и условия |
|---|---|
| Читать заявки | `ticket.view` |
| Создать заявку | `ticket.created` или `ticket.operation`; рекомендация дополнительно требует `ticket.set_remote_recommendation` |
| Изменить основные данные и добавить комментарий | `ticket.operation` и допустимое состояние; изменение рекомендации отдельно требует `ticket.set_remote_recommendation` |
| Принять | `ticket.accepted` |
| Отклонить или отменить | `ticket.canceled` |
| Назначить другого исполнителя | `ticket.assign_executor`; для безопасного выбора из каталога нужен `admin.view` |
| Взять рекомендованную заявку на горячей линии | `ticket.at_work_remote`; из `ACCEPTED` сервер требует рекомендацию, активного подходящего Admin, положительный `department_id` заявки и совпадение отдела, затем назначает исполнителя и переводит заявку в `AT_WORK`; из `ASSIGNED` сервер требует рекомендацию и совпадение текущего исполнителя |
| Начать обычную работу | `ticket.at_work` и текущий исполнитель |
| Приостановить или завершить текущий эпизод работы | `ticket.at_work` или `ticket.at_work_remote`; пауза обычной работы доступна текущему исполнителю и не применяется к ретроспективному эпизоду; обычное завершение требует текущего исполнителя, ретроспективное допускает другого Admin с общим правом; Admin только с remote-правом должен быть текущим исполнителем удалённого эпизода |
| Продолжить работу | Из `PAUSED` — только текущий исполнитель; локальный эпизод требует `ticket.at_work`; удалённый допускает `ticket.at_work` либо `ticket.at_work_remote`, причём рекомендация обязательна для Admin, у которого есть только remote-право |
| Зарегистрировать работу ретроспективно | `ticket.at_work_retrospective` |
| Завершить проверку | `ticket.executed` |
| Физически удалить | `ticket.delete` |
| Читать и менять клиентов | `client.view`; изменения распределены между `client.operation`, `client.create`, `client.decision` |

| Читать и менять пользователей | `user.view`, `user.operation` |
| Читать и менять отделы | `department.view`, `department.operation` |
| Управлять ролями и назначениями Admin | `role.assign` |
| Управлять ролями и назначениями User | `role_user.assign` |

### 9.1. Операционные связи frontend и API

| Сценарий frontend | Метод и URL | Успешный результат | Право и критические условия |
|---|---|---|---|
| Загрузить очередь заявок | `GET /admin/tickets/`, `GET /admin/tickets/open`, `GET /admin/tickets/closed` или специализированная выборка | `200`, список `TicketResponse` | `ticket.view`; клиентские фильтры применяются ко всей полученной выборке |
| Создать заявку | `POST /admin/tickets/` | `201`, `TicketResponse` | `ticket.created` или `ticket.operation`; при рекомендации также `ticket.set_remote_recommendation`; допустим `Idempotency-Key` |
| Добавить комментарий | `POST /admin/tickets/{id}/comments` | `200`, `TicketResponse` | `ticket.operation`, допустимое состояние; допустим `Idempotency-Key` |
| Назначить другого исполнителя | `PATCH /admin/tickets/{id}/executor` | `200`, `TicketResponse` | `ticket.assign_executor`; backend проверяет сотрудника и отдел |
| Начать работу на горячей линии | `PATCH /admin/tickets/{id}/start-remote-work` | `200`, `TicketResponse` со статусом `AT_WORK` | `ticket.at_work_remote`, рекомендация и условия состояния из матрицы выше |
| Передать результат работы на проверку | `PATCH /admin/tickets/{id}/finish-work` | `200`, `TicketResponse` со статусом `READY_FOR_REVIEW` | `ticket.at_work` или `ticket.at_work_remote` и условия текущего эпизода работы |
| Административно завершить проверку | `PATCH /admin/tickets/{id}/execute` | `200`, `TicketResponse` со статусом `EXECUTED` | `ticket.executed` и допустимое состояние |
| Загрузить роли Admin | `GET /admin/roles/admin` | `200`, список ролей | `role.assign` |
| Назначить или снять роль Admin | `POST` или `DELETE /admin/admins/{id}/roles` | `200`, `AdminResponse` | `role.assign`; после частичного результата перечитать профиль |
| Загрузить отделы | `GET /admin/departments/` | `200`, список отделов | `department.view`; для новой связи показывать только активные |
| Загрузить сотрудников для назначения | `GET /admin/admins/` | `200`, список Admin | `admin.view`; frontend ограничивает выбор активными сотрудниками отдела заявки |
| Загрузить заявителей и контакты клиента | `GET /admin/users/client/{client_id}` | `200`, список User | `user.view`; не использовать неподдерживаемый query `GET /admin/users/?client_id=...` из v2 |

Во всех сценариях заявок текущий статус берётся из последнего элемента `TicketResponse.statuses`; поля `current_status` в ответе нет.

## 10. Предлагаемая архитектура frontend v3

Базовый стек — React, Vite, npm и `fetch`. Новые зависимости добавляются после отдельного обоснования через проверяемую потребность.

Предлагаемая структура:

```text
simple_tickets_frontend_v3/
├── docs/
└── src/
    ├── app/          # оболочка, сессия, маршрутизация, layout
    ├── api/          # transport, resource clients, adapters, errors
    ├── features/
    │   ├── tickets/
    │   ├── clients/
    │   ├── users/
    │   ├── admins/
    │   ├── departments/
    │   └── roles/
    └── shared/
        ├── ui/
        ├── lib/
        └── styles/
```

Архитектурные правила:

- транспортный слой не знает о компонентах;
- ответы API преобразуются на границе;
- доступность действия вычисляется по праву, состоянию заявки и отношению актёра к заявке;
- сервер остаётся окончательным источником авторизации;
- каждая открытая заявка имеет собственный черновик и состояние дочернего контекста;
- фильтрация и сортировка выполняются над всем полученным разрешённым набором до пагинации;
- запоздалые ответы старой сессии или старого запроса не обновляют интерфейс;
- произвольные PATCH не повторяются автоматически после неизвестного результата;
- после конфликта или частичного результата карточка перечитывается, а локальный ввод сохраняется;
- Bearer отправляется только на настроенный адрес API;
- конфиденциальные поисковые термины и черновики не сохраняются без отдельного решения.

## 12. Решения владельца и предложения консилиума

1. Frontend v3 обслуживает только контур Admin.
2. User-контур и `WAITING_FOR_CONFIRMATION` вне первого релиза.
3. **Предложение консилиума, ожидает согласования:** для Admin создать отдельный список «На проверку» по `READY_FOR_REVIEW`.
4. «Взять в работу» означает переход в `AT_WORK`.
5. Метка `remote_work_recommended` — «Рекомендовано для горячей линии».
6. Владелец подтвердил вызов `PATCH /admin/tickets/{id}/start-remote-work` и переход в `AT_WORK`; текст кнопки «Взять в работу на горячей линии» является предложением консилиума.
7. Несколько открытых заявок нужны для работы, чтения и внесения данных.
8. Подписи начальных статусов установлены в разделе 4.4.
9. «Дата создания» берётся из `statuses[0].date_created` в карточке и списках.
10. Обычное обновление страницы должно восстанавливать вход, пока серверная сессия действительна.

Предложение по сессии для реализации — access token в памяти и refresh token в `sessionStorage` текущей вкладки. Это обеспечивает восстановление после обновления страницы, но refresh остаётся доступен JavaScript. Альтернативная HttpOnly-сессия не поддерживается текущим API и потребовала бы отдельного серверного решения.

- Модульный уровень с mock API: adapters ответов, вычисление действий по правам и состояниям, фильтрация, сортировка, пагинация, независимые черновики и защита от устаревших ответов.

- Контрактный уровень с реальным изолированным backend и отдельной временной SQLite: схемы запросов и ответов, коды ошибок, permission, workflow, refresh и идемпотентность.
- Сквозной уровень в браузере против изолированного backend: основные сценарии Admin, несколько вкладок заявок, переход к связанным сущностям, горячая линия, конкурентные операции и восстановление сессии.

- Регрессия и контроль области изменений: штатные backend-тесты, frontend-тесты, сборка, независимый review и проверка Git diff только в разрешённой области v3.

Mock используется для быстрых и исчерпывающих frontend-состояний, но не считается доказательством соответствия backend. Контрактные и E2E-проверки выполняются на реальном API в изолированной тестовой среде, не на рабочей базе.

Оно перечисляет все подключённые группы маршрутов и подробно связывает критические Admin-сценарии с методами, ответами и правами, но не содержит построчный контракт всех 107 сочетаний метода и пути.

До начала реализации отдельно должны быть подготовлены и согласованы:

- `API_CONTRACT.md` с каждой используемой операцией, полями request/response, кодами ответа, permission и бизнес-условиями;
- полная таблица workflow для каждого действия Admin;
- маршруты и пользовательские сценарии Admin;
- детальная схема frontend-модулей, состояния, сессии и восстановления ошибок;
- проверяемые критерии приёмки и трассировка требований к тестам.

Такая граница не отменяет выводы отчёта, но не позволяет считать ещё не созданные документы завершёнными.

## 21. Контроль ограничений исследовательского этапа

В ходе исследования backend и frontend v2 не изменялись. Зависимости не устанавливались. Приложение, тесты и миграции не запускались. Frontend v3 не создавался как приложение, код не переносился. Коммиты с программной реализацией, merge и Pull Request не создавались.

До явного разрешения владельца проект остаётся на этапе исследования и согласования. Настоящий документ и `DECISIONS.md` являются документацией результатов обсуждения.
