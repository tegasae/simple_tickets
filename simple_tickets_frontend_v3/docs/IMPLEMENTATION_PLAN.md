# План реализации и backlog

План этапов 3–6 для отдельного разрешения. Роли в backlog — ответственные за техническую работу и рецензирование. Задачи остаются в статусе Planned или Blocked. Все указанные пути внутри `simple_tickets_frontend_v3/`, структура приведена в [ARCHITECTURE.md](ARCHITECTURE.md). Тесты выполняются на изолированных данных. Критерии AC и TC указаны в [требованиях](FUNCTIONAL_REQUIREMENTS.md) и [стратегии](TESTING_STRATEGY.md).

## I1. Первое рабочее приложение

Цель — Admin в тестовом окружении входит, открывает разрешённый список и карточку, обновляет страницу без потери действующей сессии и видит доступные причины отказа. Обязательная очередь позволяет найти запись, сортировать и просмотреть её дату. Дополнительные области по подтверждённым GET вводятся в пределах согласованного read-only объёма. Первая вертикаль включает клиентскую фильтрацию/пагинацию основного списка, прямой URL и Back к исходной выборке. Редакторы и связанный контекст запланированы в I2.

1. Lead фиксирует ветку, исходный commit, состояние staged/unstaged/untracked, согласованный план I1 (DEC-010/011/016) и синтетический стенд. Для стенда использовать тестового Admin с `ticket.view` и без него, пустые и непустые выборки, разные статусы, отдельную test SQLite и согласованный API origin. `/health` — только liveness, авторизованные GET — обязательный smoke.
2. React адаптирует `index.html`, `src/main.jsx`, кнопки/стили и форму из `LoginPage.jsx`, пригодные фрагменты `Shell.jsx`, `Toast.jsx`, чистые части `ticketUtils.js`, CSS-токены `base.css`/`themes.css` по [плану повторного использования](CODE_REUSE_PLAN.md). Карточка отделяется от монолитного `TicketsPage.jsx`. `api.js`, `storage.js` и permissions используются как справочник, транспорт и session state создаются для v3.
3. Создать v3-only `package.json`, `package-lock.json`, `vite.config.js`, `index.html`, публичный образец env, `.gitignore` для локальных зависимостей и сборки. Согласовать Node/npm, закрепить React/React DOM `19.2.8`, Vite `8.1.5` и plugin-react `6.0.4` по кандидату DEC-011, проверить полный lockfile и воспроизводимые install/build. Разработка через Vite dev proxy. Ограничить runtime-зависимости указанным стеком; тестовые инструменты выбирать по нужной проверке.
4. Реализовать shell, login/restore/logout, permissions, GET списка/детали, чтение истории и комментариев, подписи и дату, состояния загрузки, пустоты, 401/403/404/5xx/сети. Разрешить один одновременно выполняющийся refresh на поколение и один повтор конкретного чтения после успешного refresh. Поддержать последующие ротации. Защищённый view открывается после bootstrap. Закрытая сессия очищает кэш. Карточка доступна по URL и с клавиатуры.
5. Проверить install/build, unit нормализации и сессии, UI-состояния, живой контракт и E2E входа, reload и отказа без права. На временном same-origin стенде прямой `/tickets/{id}` открывает SPA, `/api/admin/…` обращается к API, Bearer привязан к origin. Проверить два поздних ответа после выхода, пустую историю, выбор даты и статуса. QA рецензирует, UX проверяет клавиатуру и фокус, FastAPI сверяет запросы и статусы.
6. Перед handoff сверить `git status --short`, `git diff --name-only`, `git diff --cached --name-only`, новые и игнорируемые пути, обе стороны rename и `git diff <исходный commit> -- src simple_tickets_frontend_v2`. Все изменённые и созданные проектные пути лежат в v3; проверить неизменность backend, v2 и инфраструктуры. Владельцу показать работающий срез на тестовых данных, результаты проверок по TC, точное дерево изменений и оставшиеся условия для I2.

## Definition of Ready

Задача готова, если определены цель, FR/NFR, критерии AC и TC, согласованы сценарий и решения DEC, подтверждены API и права, известны зависимости, допустимые пути и риски, нет блокирующего вопроса и не требуется изменение backend. Контракты, которые невозможно проверить на тестовом стенде до начала, фиксируются как условие в задаче. Переход к коду требует явного разрешения.

## Definition of Done

Реализованы согласованные критерии, API и бизнес-правила проверены, права и ошибки обработаны, ввод и доступность проверены в согласованном объёме. Нужные тесты и сборка прошли, независимое ревью проведено, критические замечания устранены, документация синхронизирована. Область diff ограничена v3, backend и v2 совпадают с исходным commit. Для каждой непроведённой проверки указывается причина, влияние и условие закрытия. [Приёмочные проверки](TESTING_STRATEGY.md).
