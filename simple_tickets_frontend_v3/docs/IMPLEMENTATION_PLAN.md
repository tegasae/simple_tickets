## I1. Первое рабочее приложение

Цель — Admin в тестовом окружении входит, открывает разрешённый список и карточку, обновляет страницу без потери действующей сессии и видит доступные причины отказа. Обязательная очередь позволяет найти запись, сортировать и просмотреть её дату. Дополнительные области по подтверждённым GET вводятся в пределах согласованного read-only объёма. Первая вертикаль включает клиентскую фильтрацию/пагинацию основного списка, прямой URL и Back к исходной выборке. Редакторы и связанный контекст запланированы в I2.

В I1 заложить стабильные ключи для текстов всех создаваемых экранов и встроенный русский словарь. Подключение обновляемых файлов и приёмка публикации относятся к BK-014.

1. Lead фиксирует ветку, исходный commit, состояние staged/unstaged/untracked, согласованный план I1 (DEC-010/011/016) и синтетический стенд. Для стенда использовать тестового Admin с `ticket.view` и без него, пустые и непустые выборки, разные статусы, отдельную test SQLite и согласованный API origin. `/health` — только liveness, авторизованные GET — обязательный smoke.
2. React адаптирует `index.html`, `src/main.jsx`, кнопки/стили и форму из `LoginPage.jsx`, пригодные фрагменты `Shell.jsx`, `Toast.jsx`, чистые части `ticketUtils.js`, CSS-токены `base.css`/`themes.css` по [плану повторного использования](CODE_REUSE_PLAN.md). Карточка отделяется от монолитного `TicketsPage.jsx`. `api.js`, `storage.js` и permissions используются как справочник, транспорт и session state создаются для v3.

4. Реализовать shell, login/restore/logout, permissions, GET списка/детали, чтение истории и комментариев, подписи и дату, состояния загрузки, пустоты, 401/403/404/5xx/сети. Разрешить один одновременно выполняющийся refresh на поколение и один повтор конкретного чтения после успешного refresh. Поддержать последующие ротации. Защищённый view открывается после bootstrap. Закрытая сессия очищает кэш. Карточка доступна по URL и с клавиатуры.

## I2. Рабочая карточка

Владелец утвердил объём BK-002–BK-004. Сначала реализуются вкладки и чтение связей, затем создание и правка полей, затем отправка комментариев.

- Одна вкладка на заявку. Повторное открытие активирует её. Клиент, заявитель и контакт открываются с соответствующим правом и возвратом к прежним данным и фокусу. Черновик живёт в памяти страницы до её обновления или выхода.
- Для создания обязательны клиент и тема. Для существующей заявки редактируются описание, контакт, отдел, срочность и плановая дата. Рекомендация для горячей линии требует отдельного права. Комментарий добавляется в карточке. При обнаруженном расхождении с актуальным снимком интерфейс показывает изменённые поля и сохраняет черновик. Ограничения записи определяются существующим API.
- На отдельной SQLite подготовить три профиля. Читатель проверяет доступ на просмотр и отказ в записи. Автор с `ticket.created` и `client.view` создаёт заявку без `ticket.view`. Оператор с `ticket.view`, `ticket.operation` и нужными правами справочников проверяет рабочие правки, связи и комментарии. Рекомендация проверяется с правом `ticket.set_remote_recommendation` и при его отсутствии.
- Основной приёмочный сценарий начинается с двух заявок и двух отдельных черновиков. После перехода к клиенту и обратно первая правка сохраняется, а второй черновик остаётся доступным. Дополнительно проверить закрытие изменённой вкладки, 403/422, расхождение серверного снимка и неизвестный результат отправки. [Критерии AC-005–AC-008](FUNCTIONAL_REQUIREMENTS.md) · [Сценарии](USER_JOURNEYS.md).

## I3. Обработка заявки

- Карточка рассчитывает действия по правам Admin, серверному статусу, текущему исполнителю и рабочему эпизоду. Работа завершается статусом `READY_FOR_REVIEW`. Отдельное действие с `ticket.executed` переводит заявку в `EXECUTED`.
- «Горячая линия» использует открытые заявки, для которых выполнены доступные frontend проверки. В карточке «Взято в работу на горячей линии» отправляет один `/start-remote-work` и подтверждается новым `AT_WORK` в удалённом режиме.
- Перед PATCH перечитывается карточка. Найденное расхождение оставляет черновик и требует проверки актуального состояния. Если ответ потерян, повтор блокируется до сверки новой истории. [Отчёт I3](ITERATION_3_REPORT.md).

## I4. Администрирование

Владелец разрешил продолжить по сохранённому плану I4. Все сценарии выполняются в рабочем месте Admin по разрешениям действующего API.

1. **BK-008. Справочники и аккаунты.** Подготовить списки и карточки клиентов, пользователей клиентов, сотрудников Admin и отделов. Для каждой области сверить права чтения и записи, доступные поля и ограничения связанных записей.
2. **BK-009. Управление ролями.** Добавить просмотр и создание ролей, назначение и отзыв ролей у сотрудников Admin и пользователей клиентов в пределах полномочий. По DEC-015 сверять состояние после частичного применения и перечитывать собственные права.
3. **BK-010. Отмена и удаление.** Добавить отмену заявки с причиной и подтверждение удаления там, где его допускает backend. Проверить состояние заявки, ограничения связанных записей и результат команды.

Завершённые BK-013 и BK-014 входят в релизную приёмку I5. [Публикация тем, языков и подписей](RUNTIME_CONFIGURATION.md) · [Проверки TC-018 и TC-019](TESTING_STRATEGY.md).

## Definition of Ready

Задача готова, если определены цель, FR/NFR, критерии AC и TC, согласованы сценарий и решения DEC, подтверждены API и права, известны зависимости, допустимые пути и риски, нет блокирующего вопроса и не требуется изменение backend. Контракты, которые невозможно проверить на тестовом стенде до начала, фиксируются как условие в задаче. Переход к коду требует явного разрешения.

## Definition of Done

Реализованы согласованные критерии, API и бизнес-правила проверены, права и ошибки обработаны, ввод и доступность проверены в согласованном объёме. Нужные тесты и сборка прошли, независимое ревью проведено, критические замечания устранены, документация синхронизирована. Область diff ограничена v3, backend и v2 совпадают с исходным commit. Для каждой непроведённой проверки указывается причина, влияние и условие закрытия. [Приёмочные проверки](TESTING_STRATEGY.md).
