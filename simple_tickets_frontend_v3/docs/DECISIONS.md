# Решения Simple Tickets Frontend v3

Источники — ответы владельца после первого консилиума и задание этапа 2. [Отчёт этапа 1](INITIAL_RESEARCH_REPORT.md) · [Протокол](CONSILIUM_LOG.md). Approved отмечает явно определённый владельцем результат. Способ реализации описан отдельно.

|---|---|---|---|
| DEC-001 | Approved | Первый релиз — рабочее место Admin. В пределах прав Admin ведёт справочники клиентов, сотрудников, пользователей и контактов. | FR-001, FR-002, FR-012, FR-013, FR-017 |
| DEC-002 | Approved | User UI и очередь `WAITING_FOR_CONFIRMATION` исключены из первого релиза. | FR-011, FR-017 |
| DEC-003 | Approved | Метка «Рекомендовано для горячей линии». Admin запускает `start_remote_work`; результат `AT_WORK`. | FR-010 |
| DEC-004 | Approved | Параллельно открытые заявки нужны для чтения и внесения данных. | FR-005, FR-006 |
| DEC-005 | Approved | `created` — «Создана», `created_from_request_user` — «Создана по запросу клиента», `created_from_ticket_user` — «Создана из заявки клиента». | FR-003, FR-004 |
| DEC-006 | Approved | «Дата создания» в карточке и списках из первой записи истории статусов. | FR-003, FR-004 |
| DEC-007 | Approved | Автоматически восстанавливать вход после обычного reload, пока серверная сессия действительна. | FR-001 |
| DEC-008 | Proposed | Очередь Admin «На проверку» по `ready_for_review`. Альтернатива — фильтр и карточка без отдельной очереди. При регулярной проверке отдельный пункт может ускорить выборку. | FR-011 |
| DEC-009 | Proposed | Текст «Взять в работу на горячей линии» для кнопки и «Взято в работу на горячей линии» для результата. Альтернатива — сохранить формулировку владельца на кнопке. Полный текст ясен вне контекста очереди. | FR-010 |
| DEC-010 | Proposed | Access в памяти, refresh в `sessionStorage` при rotation. Выполняет reload в текущей вкладке, требует принятия JS-доступного refresh. Варианты — в [AUTHENTICATION.md](AUTHENTICATION.md). | FR-001, NFR-003 |
| DEC-011 | Proposed | Сохранить JS/JSX, React/Vite/npm, fetch/CSS. Дополнительные зависимости только при проверенной потребности. | NFR-001, NFR-007, NFR-008 |
| DEC-012 | Proposed | Вкладка на ID, черновик в памяти, связанные страницы с возвратом. Одна карточка теряет контекст, постоянное хранение расширяет риск PII. | FR-005, FR-006 |
| DEC-013 | Proposed | Серверные scoped-выборки и локальные поиск/фильтры/сортировка до пагинации. По умолчанию новые сверху, tie-breaker по ID. Измерить объём до усложнения. | FR-003, FR-004, FR-016, NFR-004 |
| DEC-014 | Proposed | WCAG 2.2 AA, семантические компоненты, ручная проверка ключевых потоков. | NFR-005, NFR-006 |
| DEC-015 | Proposed | Grant и revoke отдельны от сохранения профиля, обработка частичного результата и сверка чтением. | FR-013 |
| DEC-016 | Proposed | Первая вертикаль охватывает вход, восстановление, права, очередь и карточку на чтение. | FR-001–FR-004, FR-014 |
| DEC-017 | Proposed | Same-origin API, изоляция сессии, safe retry, адаптеры и pre-read для расхождений. Схема доставки подлежит отдельной проверке. | FR-001, FR-002, FR-007, FR-014, NFR-002, NFR-003 |
| DEC-018 | Rejected | Режим сравнения заявок. Владелец определил иной сценарий для нескольких карточек. | FR-005 |
| DEC-019 | Approved | Этап 2 ограничен документацией v3 в `frontend_new`. Разработка требует отдельного разрешения. | [Готовность](PROJECT_STATUS.md) |
| DEC-020 | Blocked | Update определения роли, вложения и bulk операции не имеют команд в текущем HTTP API. | FR-013, FR-017 |
| DEC-021 | Superseded | Повторить v2 localStorage и общий кэш. Этот вариант заменён предложением DEC-010 и DEC-017. | FR-001, NFR-003 |
| DEC-022 | Rejected | Оставить `ASSIGNED` после старта hotline или запускать два PATCH. Владелец требует `AT_WORK`, API поддерживает атомарную команду. | FR-010 |
| DEC-023 | Approved | В Frontend v3 новые темы в пределах поддерживаемых параметров оформления добавляются после развёртывания без изменения компонентов и пересборки frontend. Опубликованная тема появляется в переключателе при следующей загрузке каталога. | [FR-018](FUNCTIONAL_REQUIREMENTS.md#fr-018) |

## Гипотезы и вопросы

Профили оператора, диспетчера, исполнителя, горячей линии и администратора — рабочие гипотезы. Реальные наборы прав, объём очереди и устройства нужны для приёмки. Производственные числовые цели утверждаются после замера. [UX-анализ](USABILITY_ANALYSIS.md) · [NFR](NON_FUNCTIONAL_REQUIREMENTS.md).

До реализации первой вертикали нужны разрешение владельца и согласование плана I1 (DEC-010/011/016). DEC-008 и замену подписи по DEC-009 можно решить до соответствующей итерации. Схема публикации v3 под рабочим origin обсуждается до эксплуатации. [План](IMPLEMENTATION_PLAN.md).
