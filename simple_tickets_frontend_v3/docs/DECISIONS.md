# Simple Tickets Frontend v3 — ответы владельца проекта

Целевая ветка — `frontend_new`. Контракты ниже сверены при исследовании коммита `88e8bfb573541774ca51eead8ca4d11b5475cd38`.

## 1. Очередь подтверждения

Очередь `WAITING_FOR_CONFIRMATION` относится к кабинету User и в текущий релиз не входит. Для Admin отдельно предложен список **«На проверку»** по статусу `READY_FOR_REVIEW`. Завершение из него доступно с правом `ticket.executed`. Список Admin пока остаётся предложением на согласование.

## 2. Горячая линия

- Метка для `remote_work_recommended` — **«Рекомендовано для горячей линии»**.
- «Взять в работу» означает сразу перейти в `AT_WORK`. Для этого frontend вызывает `PATCH /admin/tickets/{id}/start-remote-work`.
- Из `ACCEPTED` сервер назначает вошедшего Admin исполнителем и запускает работу. Из `ASSIGNED` запустить работу может текущий исполнитель. Сервер проверяет рекомендацию, права и условия назначения.
- Предложенная подпись кнопки — **«Взять в работу на горячей линии»**. Сообщение об успехе — **«Взято в работу на горячей линии»**.

## 3. Работа с несколькими заявками

Параллельно открытые заявки нужны для чтения и внесения данных. Рабочие вкладки позволяют переключаться между заявками и сохранять отдельный черновик каждой. Переход к клиенту, заявителю или контакту сохраняет возможность вернуться в исходную заявку.

## 4. Статусы создания и дата

| Статус API | Подпись |
|---|---|
| `CREATED` | Создана |
| `CREATED_FROM_REQUEST_USER` | Создана по запросу клиента |
| `CREATED_FROM_TICKET_USER` | Создана из заявки клиента |

В карточке и в списках **«Дата создания»** берётся из `statuses[0].date_created`, даты первой записи истории статусов. Предложенный порядок списка по умолчанию — новые заявки сверху.

## 5. Объём первого релиза

Frontend v3 — рабочее место **Admin**. Отдельный вход и кабинет User вне текущего релиза. Admin работает с пользователями и контактами через административные справочники в пределах своих прав.

## 6. Восстановление входа

Повторный вход после обычного обновления страницы неудобен. Требование — восстанавливать вход автоматически, пока серверная сессия действительна. Предложение по реализации — refresh-токен в `sessionStorage` текущей вкладки, access-токен в памяти. При выходе очищаются токены и данные сессии.
