Проектное предложение по `frontend_new@5e2a8e6`. Архитектурные решения и их согласование ведутся в [DECISIONS.md](DECISIONS.md), контракты в [API_CONTRACT.md](API_CONTRACT.md), требования в [FUNCTIONAL_REQUIREMENTS.md](FUNCTIONAL_REQUIREMENTS.md).

## 2. Стек и развёртывание

| Часть | Предложение и обоснование |
|---|---|
| Язык и UI | JavaScript/JSX и ESM, React и React DOM `19.2.8`. Это исходная база v2 для выборочного повторного использования. Отдельную миграцию на TypeScript рассматриваем при подтверждённой стоимости сопровождения JS-контрактов |
| Сборка | Vite `8.1.5`, `@vitejs/plugin-react` `6.0.4`, npm, отдельный lockfile v3. Версии берём из v2 как исходную точку |
| Node/npm | В исследуемой среде Node `24.22.3`, npm `11.19.1`. Предложение для первой итерации — линия Node 24 LTS и совместимая версия npm. Точные версии инструментов закрепляются после проверки полного графа lockfile, `npm ci` и `npm run build` |
| HTTP, формы, стили | Браузерный `fetch`, управляемые поля React, нативные HTML-ограничения с локальными проверками, CSS-переменные и CSS-модули или локальные селекторы там, где они упрощают изоляцию |
| Тесты | `node:test` для чистой логики. Тестовый runner для JSX и браузерная автоматизация выбираются по сценариям из [TESTING_STRATEGY.md](TESTING_STRATEGY.md). Наличие этих инструментов в v2 не предполагается |

Версии React, Vite и плагина зафиксированы в [package.json v2](../../simple_tickets_frontend_v2/package.json#L11). Источник ограничений Node для полного графа — [package-lock.json v2](../../simple_tickets_frontend_v2/package-lock.json). Результаты установки и сборки v3 ещё предстоит получить.

**Новые зависимости.** Первая вертикаль не требует дополнительных runtime-библиотек. Библиотеку маршрутизации оцениваем вместе с альтернативой на History API по прямым ссылкам, вложенному маршруту, Back/Forward, управлению фокусом и объёму кода. Библиотеку серверного состояния оцениваем вместе с небольшим кэшем по стоимости дедупликации, отмены, инвалидации и защиты от поздних ответов. UI-библиотеку или отдельный headless-компонент рассматриваем, если приёмка собственных диалога, вкладок и combobox покажет существенную стоимость доступности и сопровождения. Любая новая зависимость требует зафиксированного обоснования и отдельной проверки лицензии, версии, размера и тестируемости.

**Подключение к API.** Предлагается относительный префикс `/api` на том же origin. Vite dev proxy снимает префикс и передаёт запрос в настроенный backend. Сборку обслуживает существующий или отдельно согласованный HTTP-маршрут к API с SPA fallback для маршрутов приложения. Proxy Vite относится к разработке. Первая итерация должна подтвердить production-подобную доставку статических ресурсов, прямой URL карточки и отсутствие попадания путей API в SPA fallback. `VITE_*` попадает в браузерный bundle, поэтому там допустимы только публичные настройки. [Конфигурация v2](../../simple_tickets_frontend_v2/vite.config.js#L4)

## 4. Маршрутизация, вкладки и состояние

- Предлагаемые маршруты frontend включают `/login`, `/tickets`, `/tickets/new`, `/tickets/:ticketId`, `/tickets/:ticketId/client/:clientId`, `/tickets/:ticketId/user/:userId`, `/clients`, `/users`, `/admins`, `/departments` и `/roles`. Это URL интерфейса. Маршрут детали проверяет ID и полномочие независимо от способа входа. Маршрут создания отдельно проверяет `ticket.created` или `ticket.operation`. Ссылка на результат требует `ticket.view`.
- Активная вкладка определяется маршрутом. Ключи открытых вкладок, связанная панель и черновики по ID хранятся в памяти страницы. При смене вкладки черновик сохраняется. Закрытие изменённой вкладки требует явного решения. Выход и обновление страницы сбрасывают черновики. При уходе с незаписанными данными показывается поддерживаемое браузером предупреждение. После обычной перезагрузки URL восстанавливает активную карточку по её ID.
- Связанная сущность открывается в контексте исходной заявки с явным действием возврата. Back/Forward восстанавливает маршрут и параметры списка. Прямая ссылка работает без прежней истории вкладок. Без права на связанную сущность действия перехода заменяются доступной информацией или состоянием 403.
- В URL допустимы ID и значения из разрешённых наборов очереди (`queue=all|open|mine|hotline|closed|review`), сортировки, статуса и страницы. `review` доступна после DEC-008. Тексты поиска и черновики, которые могут содержать персональные данные, остаются в памяти. Для безопасных предпочтений интерфейса допустимо отдельное хранилище с ограниченной схемой.
- Типичные состояния страницы — восстановление сессии, загрузка, успех, пустая разрешённая выборка, отсутствие доступа, сущность не найдена, временная ошибка. Пустая очередь не запускает автоматическую загрузку другой выборки. Сохранение формы и переход workflow имеют собственный статус выполнения.

Связи с FR-003–FR-006, FR-014 и DEC-012–DEC-014. Сценарии и доступность уточняют [USER_JOURNEYS.md](USER_JOURNEYS.md) и [ACCESSIBILITY.md](ACCESSIBILITY.md).

## 5. Серверное состояние и заявки

- Контрактные функции нормализуют идентификаторы, даты и формы ошибок на границе API. В `TicketResponse` текущий статус берётся из последней записи упорядоченного `statuses`, дата создания — из `statuses[0].date_created`. При пустой или неполной истории отображается состояние отсутствующих данных. Поля `current_status`, номер версии и `If-Match` не входят в этот HTTP-контракт. [Модель TicketResponse](../../src/web/models/tickets.py#L243) · [Сборка истории](../../src/application/assemblers/assembler.py#L44) · [Порядок истории в SQL](../../src/adapters/repositories/gateways/ticket_gateway.py#L235)
- Для списков запрашивать фактическую серверную выборку `open`, `closed`, `by-executor` и другие нужные подтверждённые области. Поиск, фильтры, сортировка и страницы применяются в этой области клиентом. Точный статус фильтруется по коду, текстовый поиск принимает видимую подпись. Сортировка по времени создания допускает стабильное разрешение совпадений по ID. Новые сверху — предложение для обсуждения. Очередь `READY_FOR_REVIEW` выводится из доступной выборки открытых заявок после DEC-008.
- Для справочников каталог по клиенту загружается отдельно. Канонический путь v3 предлагается `GET /admin/users/client/{client_id}`. `GET /admin/users/?client_id=…` также поддержан. Доступ к справочникам проверяется независимо от права работать с заявкой. Уже сохранённые неактивные связи остаются читаемыми при наличии прав. Для нового назначения выбираются только допустимые записи. [Роутер пользователей](../../src/web/routers/admin/users.py#L120) · [Выборка по клиенту](../../src/web/routers/admin/users.py#L188)
- Данные разделяются по поколению сессии, ресурсу и области запроса. Запросы одной области дедуплицируются, устаревший GET отменяется или игнорируется. Изменение сущности обновляет актуальный кэш по ID и пересчитывает членство в известных очередях. Если результат не определён, инвалидируется затронутая выборка и перечитывается карточка.
- I3 использует общий для карточки и горячей линии расчёт допустимых переходов по `TicketResponse` и правам. Перед командой сверяются последняя запись истории, исполнитель, отдел и рекомендация. После неопределённого ответа намерение хранится во вкладке. Сверка ищет новые записи с ожидаемым актёром и параметрами. [Отчёт I3](ITERATION_3_REPORT.md).
- Время до первого результата, объём ответа, задержка фильтрации и размер DOM измеряются на согласованных наборах. В первую очередь использовать узкие подтверждённые серверные выборки и ограниченное число строк на странице. Лимиты, производительные цели и необходимость виртуализации определяются после замеров.

## 6. Сессия, авторизация и транспорт

Утверждённая модель DEC-010 и транспортные ограничения I1 выполняют FR-001, FR-002 и FR-014. Полный жизненный цикл описан в [AUTHENTICATION.md](AUTHENTICATION.md).

1. Приложение стартует в состоянии восстановления. Access-токен находится в памяти, вращаемый refresh — в `sessionStorage` текущей вкладки по предлагаемой модели. Успешный refresh заменяет сохранённый refresh, затем приложение получает разрешения Admin. При отсутствии действительного refresh открывается вход. Временный сетевой сбой оставляет пользователю действие повторить.
2. Одновременные запросы делят один выполняющийся refresh. Поколение сессии привязывает его результат, права и данные к тому входу, при котором запрос стартовал. Logout или новый login меняют поколение, отменяют запросы, очищают токены, черновики и кэши. Запоздалый ответ прошлой сессии отбрасывается. Дублирование вкладки может скопировать исходный refresh. Отдельный тест должен подтвердить безопасное поведение при ротации и предсказуемое восстановление через вход.
3. Ограничение маршрута и видимость действия вычисляются по фактическим правам и данным сущности. `sub` access-токена при `subject_type=admin` — подсказка для интерфейса. Окончательная авторизация, актёр и допустимость перехода определяются сервером. Для действия горячей линии каталог Admin и получение профиля не обязательны.
4. Bearer отправляется только на разрешённый API origin и префикс. URL берутся из зарегистрированных клиентских вызовов, а параметры кодируются. Переход на другой origin не переносит авторизацию. Токены, авторизационные заголовки, пароли и чувствительные тексты исключаются из URL, логов и уведомлений. Refresh, доступный JavaScript, сохраняет остаточный риск XSS. Нужны безопасный текстовый рендеринг и проверка CSP в согласованном способе развёртывания.
5. Запрос чтения после 401 допускает один повтор по успешному refresh. 403 обновляет состояние доступа и сохраняет валидную сессию. 404 отображает отсутствие сущности. Доменная ошибка 400 и конфликт 409 сохраняют ввод, при изменении серверного состояния перечитывается карточка. Ошибка 422 связывается с полями по `detail[].loc`. 503 и сбой сети допускают явный повтор чтения. Для 500 и неожиданного формата ответа отображается нейтральное сообщение об ошибке. Пустой 204 обрабатывается отдельно.
6. Запись имеет состояние pending на уровне операции и защищена от повторной отправки. После неизвестного результата у произвольного PATCH сначала перечитать карточку. Для операций с подтверждённой серверной идемпотентностью допустим повтор той же попытки с тем же `Idempotency-Key` и телом. Ответ такого повтора может содержать прежний снимок. Он не должен перезаписывать уже полученные свежие данные. [Refresh и logout](../../src/web/auth/services/shared_sessions.py#L46) · [Ключ идемпотентности](../../src/web/idempotency.py#L42)

## 7. Формы, рабочие действия и доступность

- Форма отделяет отправляемые данные от отображаемых значений. API-адаптер проверяет представление дат, числовые ID, длину текста и поля схемы. Доменная валидация остаётся серверной. Ошибки поля видимы и связаны с контролом, введённые данные сохраняются после отказа и конфликта.
- Горячая линия вызывает один `PATCH /admin/tickets/{ticket_id}/start-remote-work` с JSON `{}` или `{"comment":"…"}`. В ветке `ACCEPTED` сервер проверяет право `ticket.at_work_remote`, рекомендацию и пригодность актёра для отдела и назначает его до старта. Из `ASSIGNED` требуется текущий исполнитель. Известное несовпадение отдела ограничивает действие в UI. При отсутствии права загрузить профиль решение принимает endpoint. [Router](../../src/web/routers/admin/tickets.py#L852) · [Сервис](../../src/application/services/ticket_service.py#L710)
- Роли назначаются через отдельные операции grant/revoke. При частичном результате интерфейс показывает, что уже подтверждено, перечитывает доступный серверный набор и сохраняет оставшуюся цель. Автоматической компенсации не выполняется. Определение существующей роли не редактируется через псевдооперацию удаления и создания. Связи DEC-015 и FR-013.
- Модальный слой используется для действия, требующего удержания внимания. Клик по фону сохраняет диалог, Escape действует на верхний слой, после закрытия восстанавливается фокус. Рабочая вкладка сохраняет отдельный черновик. Сортировка и открытие строки доступны клавиатурой. Combobox различает введённый текст и выбранный ID. Токены стилей задают типографику, отступы, цвет, фокус и состояния. Цель WCAG 2.2 AA обсуждается по DEC-014. [UI_GUIDELINES.md](UI_GUIDELINES.md) · [ACCESSIBILITY.md](ACCESSIBILITY.md)

## 8. Проверяемая первая итерация

DEC-016 утверждает вертикаль «Вход → разрешённый список заявок → карточка для чтения». В область входят сессия, право `ticket.view`, API списка и детали, восстановление после reload, корректное Back/Forward, сортировка и дата в согласованном представлении, состояния ошибки. Редактирование, операции горячей линии и очередь «На проверку» следуют отдельными задачами.

Критерии проверки — проход сборки после установки по lockfile, модульные проверки статуса и даты, проверка 401/403/404/503 и отмены, сквозной вход и чтение против изолированного API, восстановление после reload и клавиатурное открытие карточки. Защищённые пути контролируются сравнением Git до и после. Моки проверяют клиентские состояния, совместимость подтверждается отдельным прогоном на реальном тестовом API. [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) · [TESTING_STRATEGY.md](TESTING_STRATEGY.md)

## 9. Каталог тем после развёртывания

DEC-023 утверждает возможность добавлять темы без пересборки. Предлагаемый механизм — внешний JSON-каталог, который браузер читает по постоянному same-origin URL, например `/config/themes.json`. Файл обслуживается как отдельно обновляемая статическая конфигурация. При публикации темы заменяется каталог, уже развёрнутые JS и CSS остаются прежними. В конфигурации доставки маршрут каталога обслуживается отдельно от SPA fallback. Проверка актуальности HTTP-кэша при загрузке страницы позволяет увидеть обновление после обычного reload.

- Запись каталога содержит стабильный ID, отображаемое имя и значения поддерживаемых дизайн-токенов. Переключатель строит список по каталогу, а общие компоненты используют CSS-переменные. Базовый набор для переноса из v2 включает «1С 8.3», «Классика», «Футуризм» и «Barbie».
- Версия схемы, уникальность ID и строгие типы значений проверяются до применения. Каталог принимает только предусмотренные токены оформления. Имена отображаются текстом. Ссылки на внешние ресурсы, произвольные правила CSS и скрипты через каталог не поддерживаются.
- Браузер хранит ID выбранной темы как локальное предпочтение. При недоступном или некорректном каталоге, а также при отсутствующем ID используется встроенная резервная тема. Загрузка каталога не блокирует вход и работу с заявками. API Simple Tickets для публикации тем не меняется.

## 10. Локализация и редактируемые тексты интерфейса

**Важно.** DEC-024 требует обновлять переводы и любые предусмотренные тексты интерфейса без пересборки. Компоненты с первой итерации получают подписи по стабильным ключам сообщений. Один и тот же ключ используется в разных языках. Подписи для разных действий и контекстов имеют отдельные ключи, даже если их исходные тексты совпадают. Согласованные русские подписи статусов из DEC-005 входят в исходный словарь.

Предлагаемый механизм — отдельный статический JSON-каталог языков и словари по языку на том же origin. Они публикуются отдельно от JS/CSS и читаются браузером во время работы. При добавлении языка публикуется словарь и обновляется каталог, при изменении подписи достаточно обновить значение ключа действующего словаря. После обычного обновления страницы браузер проверяет актуальность файлов и отображает опубликованные тексты. Выбранный язык хранится локально.

- Словарь содержит текст и предусмотренные именованные параметры. Клиент проверяет схему и допустимые параметры и отображает значения как текст. Публикация выполняется сопровождающим с доступом к конфигурации.
- Встроенный русский словарь поддерживает работу при недоступном или некорректном файле и при отсутствии отдельных ключей. По выбранному языку задаётся атрибут `lang` документа и форматируются даты и числа.
- Права, действия и статусы определяются их кодами. Подписи из словаря используются для отображения и поиска, а ошибки API сопоставляются с сообщениями интерфейса по кодам и данным контракта. Тексты заявок, комментариев и других пользовательских данных сохраняются как введены.
