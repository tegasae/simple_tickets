## Архитектура и стек

`uvicorn src.web.main:app` создаёт FastAPI и подключает восемь роутеров. Маршруты принимают Pydantic-модели, преобразуют вход в DTO и вызывают прикладные сервисы. Прикладной сервис проверяет контекст актёра, открывает SQLite Unit of Work и вызывает доменный агрегат и репозитории. Gateway выполняет SQL. Assembler формирует response DTO, web-модель сериализует результат. SQLite Unit of Work задаёт транзакционные границы, включая связанные Ticket и TicketUser при переходах. [Точка входа](../../src/web/main.py#L37) · [Unit of Work](../../src/adapters/uow/sqlite_unit_of_work.py) · [Сервис заявок](../../src/application/services/ticket_service.py) · [Assembler](../../src/application/assemblers/assembler.py).

В requirements закреплены FastAPI 0.143.0, Pydantic 2.14.1, pydantic-settings 2.15.0, PyJWT 2.15.1, Starlette 1.8.0 и Uvicorn 0.54.0. Backend Dockerfile основан на `python:3.14-slim`. SQLite используется через репозитории и SQL без ORM. При production-start проверяется наличие заданного случайного ключа подписи длиной от 32 байт. `/health` возвращает статический ответ, поэтому проверка сквозного подключения дополнительно включает вход, получение прав и чтение заявки. [Зависимости](../../requirements.txt) · [Dockerfile](../../dockerfiles/backend/Dockerfile) · [Settings](../../src/web/config.py) · [Health](../../src/web/main.py#L95).

## Бизнес-логика

- Начальные статусы соответствуют источнику заявки (DEC-005). Tenant/source и актёр для создания выводятся из команды и ссылки, а состояние определяется доменом. `POST /admin/tickets/` принимает клиента, тему и необязательные поля. Связанные User должны относиться к этому клиенту. Опциональные параметры могут налагать дополнительные права и требования к ссылкам. [Создание Ticket](../../src/application/services/ticket_service.py#L79).
- Сервер разводит назначение, текущую работу, сдачу результата и закрытие. При старте принятой заявки на горячей линии сервер выполняет самоназначение и переход в одной команде. `finish-work` завершает эпизод и переводит в `ready_for_review`, `execute` выполняется только из `ready_for_review`, а `suspended` терминален. `GET /closed` включает терминальные состояния, в том числе отмену и отклонение. [Таблица переходов](../../src/domain/statuses/rules/ticket_status_transition.py#L21) · [Рабочие права](PERMISSIONS_MATRIX.md).
- Permission, статус, текущий актёр и свойства эпизода проверяются совместно. Ветка hotline из `accepted` проверяет активного Admin и положительный совпадающий ID отдела, без отдельного чтения `Department.enabled`. Из `assigned` критично совпадение текущего исполнителя. Изменение отдела, включённость клиента или связанного пользователя проверяются собственными командами. [Use case hotline](../../src/application/services/ticket_service.py#L710) · [Назначение](../../src/domain/services/ticket_service.py#L255).
- Структурные/доменные ограничения раздельны. Время планирования приводится к UTC и проверяется по дате UTC. Ретроспективная запись принимает положительную длительность либо пару времён `начало < конец ≤ запись`. [Планирование](../../src/domain/ticket.py#L922) · [Эпизоды](../../src/domain/statuses/ticket_status_record.py#L216).
- Физическое удаление Ticket может удалить и связанный TicketUser вместе с историей и комментариями. Доступ определяется `ticket.delete`. Команды удаления справочников защищают ссылки и системные роли. Ни UI-подтверждение, ни наличие права чтения не заменяют серверную проверку. [Удаление](../../src/application/services/ticket_service.py#L1023) · [Тест удаления](../../tests/test_ticket_deletion_permission.py).

## Ограничения и адаптация

| Ограничение | Адаптация v3 |
|---|---|
| Нет произвольного поиска, сортировки и пагинации Ticket на сервере | Использовать существующую область выдачи и применить локальный фильтр, сортировку и страницы. Отдельная выдача по отделу, клиенту, контакту и исполнителю поддержана. |
| Нет API update определения роли и атомарного grant+revoke | Просмотр, создание, разрешённое удаление, явные отдельные операции выдачи и отзыва. Отобразить подтверждённый шаг и перечитать профиль. |
| Нет revision/ETag/If-Match на Ticket | Сравнить актуальный снимок с основой черновика, при расхождении спросить пользователя. При сетевой или доменной ошибке перечитать. Гонки между чтением и записью всё ещё возможны. |
| Refresh — JSON-токен, абсолютный срок, ротация | Использовать поддерживаемый сценарий той же вкладки после согласования хранения. Случаи потерянного ответа и конкурирующего refresh обрабатывать отдельно. |
| Нет WebSocket/SSE, массовых операций и вложений | Обновление списка по запросу и после команд, одиночные действия. |
| Текущий Dockerfile frontend собирает v2 | Dev proxy v3 и изолированная интеграция для первой вертикали. Схема доставки v3 с same-origin API согласуется до эксплуатации. |

Контракты, операции и ошибки — [API_CONTRACT.md](API_CONTRACT.md). Логин и доступ — [AUTHENTICATION.md](AUTHENTICATION.md). Изменение backend для предложенного объёма не требуется.
