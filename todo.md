### Department
Необходима новая сущность, отдел. Каждый Admin может принадлежать к тому или иному отделу. Каждая заявка может 
принадлежать к тому или иному отделу или не приндалежать никакому. Исполнителем может быть назначен только тот Admin, 
который принадлежит тому же отделу, что и заявка

#### Department
##### Department — отдельная сущность.
- Department может быть активным или отключённым, если ты решишь добавить enabled.
- Нельзя назначать Admin или Ticket в несуществующий отдел.
- Нельзя назначать Admin или Ticket в отключённый отдел, если отделы будут иметь статус enabled/disabled.
- Нельзя перевести Department в disable, если там есть хотя бы один Admin в enabled.
- 
##### Admin и Department
- Admin может не принадлежать ни одному отделу.
- Admin может принадлежать одному отделу.
- Admin без отдела не может быть назначен исполнителем заявки.
- Admin может менять отдел.
- Admin не может менять отдел, если он является текущим исполнителем хотя бы одной заявки в статусе AT_WORK.
- При проверке предыдущего пункта учитывается именно текущий исполнитель, то есть последняя запись назначения исполнителя по заявке.
- Если Admin когда-то был исполнителем заявки, но сейчас уже не является текущим исполнителем, это не мешает менять его отдел.
- Отключённый Admin не может быть назначен исполнителем.

##### Ticket и Department
- Ticket может не принадлежать ни одному отделу.
- Ticket может принадлежать одному отделу.
- Ticket без отдела не может получить исполнителя.
- Ticket может менять отдел, если заявка не находится в статусе AT_WORK.
- Ticket не может менять отдел, если заявка находится в статусе AT_WORK.
- Ticket не может менять отдел, если заявка закрыта.
- Если у Ticket уже есть текущий исполнитель, но заявка ещё не в AT_WORK, отдел менять можно только если после смены отдела исполнитель остаётся валидным, либо исполнителя надо снять. Для простоты лучше выбрать правило: если есть текущий исполнитель, отдел менять нельзя. Но это отдельное решение.

##### Назначение исполнителя
- Исполнителем Ticket может быть только Admin.
- Исполнитель должен быть активным Admin.
- Исполнитель должен принадлежать отделу.
- Ticket должен принадлежать отделу.
- Admin.department_id должен быть равен Ticket.department_id.
- Если Admin.department_id != Ticket.department_id, назначение запрещено.
- Если Admin.department_id is None, назначение запрещено.
- Если Ticket.department_id is None, назначение запрещено.
- Нельзя назначать исполнителя на закрытую заявку.
- Нельзя назначать исполнителя на выполненную заявку.
- Нельзя назначать исполнителя на отменённую заявку.

##### Статус AT_WORK
- Статус AT_WORK означает, что заявка уже находится в работе.
- Если Ticket в AT_WORK, его отдел менять нельзя.
- Если Admin является текущим исполнителем заявки в AT_WORK, отдел этого Admin менять нельзя.
- Если Admin связан с заявкой в AT_WORK только как автор комментария или actor статуса, это не должно блокировать смену отдела. Блокирует только роль текущего исполнителя.

##### Где проверять правила
- Правила про состояние самого Ticket лучше проверять в Ticket или TicketWorkflowService.
- Правило Ticket.department_id == Admin.department_id лучше вынести в TicketAssignmentPolicy.
- Проверку “есть ли у Admin заявки в AT_WORK как у текущего исполнителя” надо делать через TicketRepository.
- ApplicationService должен оркестрировать: загрузить Ticket, загрузить Admin, загрузить Department, вызвать policy/workflow, сохранить изменения.

Я бы пока зафиксировал главный минимальный набор так:

1. Admin может быть без отдела.
2. Ticket может быть без отдела.
3. Admin без отдела не может быть исполнителем.
4. Ticket без отдела не может иметь исполнителя.
5. Исполнитель Ticket должен быть Admin из того же отдела.
6. Ticket в AT_WORK не может менять отдел.
7. Admin не может менять отдел, если он текущий исполнитель Ticket в AT_WORK.
8. Закрытая, выполненная или отменённая заявка не может получать нового исполнителя.
